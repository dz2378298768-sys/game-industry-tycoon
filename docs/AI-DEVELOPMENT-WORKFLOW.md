## 0. 一轮循环总览

```
① 设计            ② 设计审核          ③ 编码            ④ 编码审核         ⑤ 阶段验收
主 AI 派任务  →  设计审核代理出结论 →  主 AI 派任务  →  编码审核代理出结论 →  主 AI 整体判断
    ↓ 设计代理产出      ↓ 不过 → 退回设计      ↓ 编码代理交付      ↓ 不过 → 退回编码      ↓ 不全 → 回到①
    └────────────── 设计闭环 ──────────────┘   └────────── 编码闭环 ──────────┘
```

**两个闸门，缺一不可**：

| 闸门 | 位置 | 判据 | 失败后果 |
|---|---|---|---|
| 设计闸门 | ② 之后 | 设计审核 PASS / PASS_WITH_NOTES | 不得派发编码；退回设计代理修改 |
| 编码闸门 | ④ 之后 | 编码审核 PASS / PASS_WITH_NOTES | 不得 CLOSED；退回编码代理整改 |

**一个总闸**：⑤ 阶段验收。单个任务通过 ≠ 阶段完成。

## 1. 阶段一：设计

### 1.1 输入（主 AI 必须提供）

| 项 | 要求 |
|---|---|
| 任务编号与目标 | 一句话说清要解决什么玩家/系统问题 |
| 背景 | 为什么现在做、与哪些既有系统相邻 |
| 相关既有规格 | **给路径**，不要只说"参考一下" |
| 范围 / 非范围 | 明确不做什么，防止范围蔓延 |
| 约束 | 冻结规格限制、性能/存档/兼容要求、不可动的接口 |
| 交付要求 | 文件命名、版本号、必须包含的章节 |
| 期限与粒度 | 一次交付还是分段 |

### 1.2 设计代理的产出（缺一不可）

1. 设计目标与玩家价值（这个设计让玩家多得到什么决策/反馈）
2. 规则与公式（含单位、取整、边界值）
3. 数据与接口（字段、类型、来源、幂等键）
4. 状态与转换（允许的状态、非法转换的处理）
5. UI/交互（文案、空态、异常态、文案单一来源）
6. 异常与边界（数据缺失、并发、超限、读档残留）
7. 设计假设与待确认项（**必须显式列出**，不得埋在正文里）
8. 验收口径（怎么判断"做对了"，可被测试表达）
9. 变更说明（相对上一版改了什么、为什么）

### 1.3 主 AI 的检查（送审前）

- [ ] 九个交付项是否齐全
- [ ] 是否引用了正确的规格版本
- [ ] 是否越出任务范围
- [ ] 是否与既有冻结规格冲突（冲突则先裁定，不得送审）
- [ ] 假设与待确认项是否会影响实现（会影响则先澄清，不要交给编码代理猜）

> **不合格就退回设计代理**，不要"先送审看看审核怎么说"。主 AI 不做质量过滤 = 浪费一轮审核。

## 2. 阶段二：设计审核

### 2.1 审核代理的检查维度（八维，源自 `DESIGN-ROLE-GDR-001.md`）

| 维度 | 问什么 |
|---|---|
| 可行性 | 现有架构能否实现；有无技术死结 |
| 游戏性与经营决策 | 是否产生真实取舍；是否为"点下一步"式空转 |
| 完整性 | 规则/字段/边界是否够编码代理直接落地 |
| 一致性 | 与既有系统是否冲突（尤其成本、状态、幂等键） |
| 数值合理性 | 公式量级是否成立；是否有可校准的参数与默认值 |
| 体验闭环 | 玩家能否感知因果；反馈是否及时可读 |
| 异常边界 | 失败路径是否定义（空数据、超限、并发、读档） |
| 可验收性 | 每条要求能否被测试或实测验证 |

**外加体验四问**（不可跳过）：玩家目标是否明确？循环是否有趣？不同选择是否产生不同结果？是否避免沦为数据展示模拟器？

### 2.2 结论状态

| 状态 | 含义 | 下一步 |
|---|---|---|
| **PASS** | 全部强制项通过 | → 阶段三 |
| **PASS_WITH_NOTES** | 强制项通过，有非阻塞项 | → 阶段三，备注登记待办 |
| **REVISE_REQUIRED** | 存在必须修改的问题 | → 回设计代理，改后**重新审核** |
| **REJECTED** | 根本性缺陷，需重新设计 | → 回设计代理重做方案 |
| *BLOCKED*（旁路） | 缺输入/依赖未定，无法判定 | → 主 AI 补输入或调整计划 |
| *NOT_VERIFIED*（旁路） | 无法验证（如需真人试玩） | → **不得当作通过**，登记未验证项 |

### 2.3 审核报告必含

- 审核对象（规格文件名 + 版本）
- 逐维判定（八维 + 体验四问）
- 问题清单：编号 / 维度 / 等级 P0–P3 / 描述 / 证据（引用章节或行）/ 修改要求
- 结论 + 一句话理由
- 未验证项（如实列）

### 2.4 返工路径

```
审核出 REVISE_REQUIRED
  → 主 AI 判断：问题属设计缺陷（B 类）还是任务范围问题
  → 派回设计代理，附问题清单（原样转，不改写、不弱化）
  → 设计代理出 v1.x 修订版 + 变更说明
  → 设计审核代理**重新审核**（可只审改动处 + 关联处，但须说明范围）
  → 直到 PASS / PASS_WITH_NOTES
```

**次数上限**：同一设计连续 3 次 REVISE_REQUIRED，主 AI 必须重新评估设计方向（换方案或缩范围），不得无限打补丁。

## 3. 阶段三：编码

### 3.1 任务书必填（16 项，缺一不得进入 READY）

编号 / 名称 / 目标 / 背景 / 规格及版本 / 范围 / 非范围 / 依赖 / 功能要求 / 数据接口 / UI / 异常 / 测试 / 验收 / 交付物 / 禁止事项

> 本项目已有 14 份任务书可作模板，见 `docs/TASK-M1.1-*.md`。

### 3.2 编码代理的交付（9 项）

1. 提交 SHA
2. 修改文件清单（增/删/改）
3. 实现说明（为什么这么做，与规格的对应关系）
4. 对应规格版本
5. 自动化测试结果（文件数/用例数/skip 数）
6. 手动测试步骤与结果（UI 类必附截图）
7. 已知问题与未完成项
8. 运行/复现方式
9. 存档与兼容说明

> **超出任务书的补充必须主动申报**。本项目有先例：`TERMINAL-RELEASE-001` 主动申报"超时路径也清空分配"，审核据此判定为合理补全而非越界。

### 3.3 编码代理的停止条件

遇到以下情况**停止实现并反馈主 AI**，不得自行决定：

- 规格未覆盖的关键业务规则
- 两条规格互相矛盾
- 规格要求与现有架构冲突（需要改核心实体/状态机）
- 需要改任务书"禁改范围"内的文件

## 4. 阶段四：编码审核

### 4.1 审核代理必做

| 项 | 要求 |
|---|---|
| 自跑命令 | 测试 / typecheck / lint / build **自己跑**，贴原始输出；不引用交付说明的数字 |
| **反证测试** | 至少一项：删掉关键实现 → 对应测试必须变红 → 恢复。全绿说明测试无效 |
| 功能回归 | 按规格的验收条件逐条实测，尤其是"用户能否走通流程" |
| 一致性 | `git show --numstat` 确认既有断言未被删改（防"改测试凑通过"） |
| 边界 | 读档兼容、schema 版本、空数据、超限 |
| 副作用 | 新增日志、i18n 双语言同步、共享对象被就地修改 |

### 4.2 结论状态

同 §2.2 四态 + 两旁路。`REVISE_REQUIRED` 时：

```
审核出 REVISE_REQUIRED
  → 主 AI 判断整改范围（只改缺陷 or 需要重发任务）
  → 派回编码代理，附问题清单
  → 编码代理出整改提交（新 commit，不 amend 已审提交）
  → 编码审核代理**复审**（须明确原问题是否关闭，不能只改报告文字）
```

### 4.3 问题分类（沿用规范 §4）

| 类别 | 含义 | 处理 |
|---|---|---|
| A 编码实现 | 逻辑/接口/计算/状态/UI/异常/测试错误 | 整改任务 → 编码代理 |
| B 设计规格 | 规则冲突/字段不全/公式缺失/边界未定义 | 主 AI 裁定并更新规格 → 再整改 |
| C 测试证据 | 缺测试/不可复现/覆盖不足 | 编码代理补测或审核代理复验 |
| D 外部阻塞 | 依赖未完成/环境不可用/资料缺失 | 主 AI 协调或调整计划 |

## 5. 阶段五：阶段验收（最容易被跳过的一步）

**单个任务 PASS 不等于阶段完成。** 主 AI 必须做跨任务、跨系统的整体检查：

### 5.1 跨系统检查（本项目真实教训）

| 检查 | 为什么必须做 | 本项目实例 |
|---|---|---|
| 核心循环是否完整 | 玩家能否从零走到目标 | 建公司→招人→立项→组队→推进→QA→上市 |
| 多系统组合是否正常 | 单项通过、组合失败 | **S-1**：001-B 定"暂停仍分摊"、001-C 以"终态不产生成本"排除、CLEANUP 只清标记 → 三个单任务 PASS，合起来终态项目仍占人，第二款游戏组不了队 |
| 是否存在"每个都对、合起来不对" | 跨任务缝隙只能用跨任务视角发现 | 同上 |
| 玩家能否真正完成预期流程 | 默认配置能否走通 | OI-20：默认预算/资金走不到上市 |
| UI/UX 是否达标 | 文案、空态、焦点、窄屏 | UI 线四轮修复 10 项 |
| 是否有未关闭阻塞 | P0/P1 归零 | S-1 关闭后 P1=0 |
| 体验验证是否完成 | 真人试玩 | M1.1 当前唯一缺口 |
| 文档/代码/测试/版本是否一致 | 台账数字与实测一致 | 曾出现"21 提交"实为"21 测试文件" |

### 5.2 九项核查（规范 §5）

强制任务完成 / 关键任务审核通过 / 无未关闭阻塞 / 无影响目标的未验证项 / 集成正常 / 体验目标满足 / 回归完成 / 文档版本交付完整 / 无重大风险

### 5.3 结论只能是四种

**阶段完成** / **阶段有条件完成**（须写明批准范围与风险） / **阶段未完成** / **阶段暂停**

> 不得为推进进度降低验收标准；改变阶段目标须先形成设计变更记录；M1.1 等阶段的最终关闭仍须 Owner 确认。

## 6. 任务生命周期与关闭条件

```
PLANNED → READY → IN_PROGRESS → IMPLEMENTED → IN_REVIEW → ACCEPTED → CLOSED
             ↑                                    │
             └──────── REVISION_REQUIRED ←────────┘
                        DESIGN_BLOCKED（设计裁定）/ RE_REVIEW（整改复审）
```

| 状态 | 谁能置 | 条件 |
|---|---|---|
| READY | 主 AI | 任务书 16 项齐全 + 设计已过审 |
| IN_PROGRESS | 主 AI | 已派发编码代理 |
| IMPLEMENTED | 编码代理申报，主 AI 确认 | 9 项交付齐全 |
| IN_REVIEW | 主 AI | 已派发编码审核代理 |
| ACCEPTED | 审核代理出结论 + 主 AI 确认 | PASS / PASS_WITH_NOTES |
| **CLOSED** | **主 AI 独占** | ACCEPTED + 整改项关闭 + 台账更新 |
| REVISION_REQUIRED | 主 AI | 审核出 REVISE_REQUIRED |
| DESIGN_BLOCKED | 主 AI | 需设计裁定 |

> **子代理在任何情况下都不能把任务标为 CLOSED。** 它只能"申报完成"或"给出审核结论"。

## 7. 审核状态口径映射（新旧并存时的写法）

历史报告用旧五态，新流程用新四态。**留档时同时标注两套口径**，例如：

```
结论：REVISE_REQUIRED（旧口径：FAIL）
```

| 新四态 | 旧口径 | 说明 |
|---|---|---|
| PASS | PASS | 等价 |
| PASS_WITH_NOTES | PASS_WITH_NOTES | 等价 |
| REVISE_REQUIRED | FAIL（可整改） | 问题明确、路径清楚 |
| REJECTED | FAIL（根本性） | 需重做方案/实现 |
| BLOCKED（旁路） | BLOCKED | 无法判定 |
| NOT_VERIFIED（旁路） | NOT_VERIFIED | 未验证，不算通过 |

**历史文件不改写**。映射表只用于新报告与读旧报告时的对照。

## 8. 证据与留档规范

| 类型 | 命名 | 存放 |
|---|---|---|
| 任务书 | `TASK-<阶段>-<编号>.md` | `docs/` |
| 设计规格 | `DESIGN-<主题>-<版本>.md` | `docs/` |
| 设计审核报告 | `REVIEW-DESIGN-<任务编号>.md` | `docs/` |
| 编码交付说明 | `DELIVERY-<任务编号>.md` | `docs/` |
| 编码审核报告 | `REVIEW-TASK-<任务编号>.md` | `docs/` |
| 处置单 | `DISPOSITION-<任务编号>.md` | `docs/` |
| 走查记录 | `UI-WALKTHROUGH-<阶段>.md` | `docs/` |
| 机器可读结果 | `result-*.json` | `docs/evidence/` |
| 截图 | `<任务>-<场景>.png` | `docs/evidence/` |
| 可复跑脚本 | `*.cjs` / `*.js` | `docs/evidence/scripts/` |

**硬要求**：报告里出现的每个数字（用例数、断言数、提交数）必须来自命令输出，能被人一条命令复现。本项目已因"估算数字"出过两次错。
