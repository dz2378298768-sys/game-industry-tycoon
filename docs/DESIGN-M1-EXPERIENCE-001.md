## 0. 验收哲学与效力

1. **本规格是 M1.1 是否可关闭的核心判据之一**。编译成功、单测通过 ≠ 体验完整。
2. **体验验收 ≠ 工程验收**：工程验收看命令退出码，体验验收看"玩家能否走通闭环并感受到决策后果"。
3. M1.1 定位（D-02）：研发经营垂直切片，不是完整商业经营游戏。完整销售/定价/营销/退款属后续阶段，**不得宣称 M1.1 已实现完整商业化经营**。
4. 本规格每条流程标注当前代码能力（基于本人实测，见 00_接任状态核对报告），并明确"可玩 / 数据模拟 / 依赖后续 / 体验断点"四档结论。

---

## 1. M1.1 目标体验闭环（D-02 原文）

```
创办公司 → 创建研发项目 → 组建团队 → 分配资源 → 推进研发
        → 处理进度和质量问题 → QA → 产品上市 → 观察经营决策影响
```

验收要求：玩家能以真实操作走通上述 9 环节，并在关键节点感受到"我的选择改变了结果"。

## 2. 玩家流程逐条规格

### 2.1 创办公司

| 项 | 内容 | 数值来源 |
|---|---|---|
| 操作 | 玩家输入公司名、选择城市 → 创建 → 进入经营主界面 | 现有 `create-company.tsx` |
| 初始资金 | $50,000（5,000,000 分），唯一 `advance` 交易入账 | D12 + DESIGN_DECISIONS 补充裁定 |
| 初始公司状态 | active；brand/technologyCapacity/managementCapacity 取规格默认；growthStage='startup' | 03 领域实体 §2.1；数值以 TUNING 为准 |
| 初始团队 | **0 人**（需玩家招聘）；管理容量上限 15 人 | 实施报告集成流程"招聘4人"；TUNING.managementCapacity |
| 初始游戏日期 | 以内容数据/规格定义的起始 DayIndex 为准（不自行编造） | 08/06 内容最小集 |
| 可操作功能 | 查看总览、招聘、立项、财务、设置/存档 | 04 UI 标准 P0 页面 |
| 初始目标 | 无明显强制教程目标（渐进复杂度 3.4）；总览提示"下一步：招聘核心团队" | 03.4 设计原则 |

**验收点**：玩家创建后现金恰为 $50,000 且流水仅 1 笔 advance；总览显示日期/速度/现金（04 UI §4.1）。

### 2.2 创建研发项目

| 项 | 内容 |
|---|---|
| 页面 | 立项向导 `new-project.tsx` |
| 步骤（04 UI §4.3） | 产品定位 → 范围/功能 → 平台/市场 → 团队/预算 → 上市计划 → 确认 |
| 表单字段 | 项目名、genreId、audienceSegmentIds、targetPlatformIds、scope/规模预设、预算 totalCap、qualityTargets、plannedLaunchDay |
| 默认值 | 规模为新手预设（规模等级仅预设，不替代具体范围）；质量目标默认 60（代码实测 project-service.ts 默认 60） |
| 输入校验 | 平台 `earliestAvailabilityYear` 与受众 `availableYearStart` 双端年代校验（F19）；预算正整数；核心岗位≥1 人（状态机守卫） |
| 预算提示 | 显示预算→工作量预估影响；预算不足时**明确阻止创建或提示追加预算**（GDR D-EXP-01 裁定 2026-11-19：原"要求高风险模式"属 M2 TUNING、M1.1 无落点，已删除），**不得静默接受**（04 UI §4.3） |
| 创建结果 | phase='CONCEPT', subPhase='DRAFT', isPaused=false；进入项目详情 |

**验收点**：年代不合法的平台/受众不可选或选中被拒；创建后状态符合状态机；预算→工作量联动可见。

### 2.3 组建团队

| 项 | 内容 |
|---|---|
| 页面 | 招聘 `hire.tsx` + 员工 `employees.tsx` |
| 招聘 | 选择角色（designer/programmer/artist/qa/producer/manager）、技能 1-5、城市系数后月薪；成本=月薪×15%（D12） |
| 分配 | 在项目详情设置 TeamAssignment.allocationRatio（0-1）与 roleOnProject；同一员工 Σratio ≤ 1.0 |
| 能力匹配 | 学科能力、roleFit 影响 effectiveWork（03 工作量模型 §3）；角色错配产出低 |
| 工资成本 | 月薪在月末结算；分摊归属按 DESIGN-G05-1.0 §3（一笔工资多项目分摊） |
| 跨项目限制 | ΣallocationRatio ≤ 1.0 强制（08/03 §1.6） |

**验收点**：非法比例（>1 或 ≤0 或 NaN）被拒（input-guards 已覆盖）；分配后立即影响预计产能展示；管理中显示容量 15 人上限。

### 2.4 研发推进

| 项 | 内容 |
|---|---|
| 时间推进 | 按天推进，玩家可调速度（slow/normal/fast/faster，game-shell.tsx 实测四档） |
| 阶段门控 | CONCEPT/PRE_PRODUCTION 不累计；PRODUCTION 累计设计/程序/美术；QA 仅累计 QA（A4） |
| 玩家可观察 | 研发进度、各学科工作量、团队效率、预算消耗（DESIGN-G05 落地后含真实归属）、项目风险标志、预计完成时间（A5 estimateDaysToFinish） |
| 日/月分离 | 日推进工作量；月末结算工资+租金（D13）；避免重复扣款（NEXT_HANDOFF 唯一调度） |

**验收点**：项目详情页能回答 03 规格 §8 的 7 个问题（当前阶段/瓶颈学科/预计完成区间/预算已花-承诺-剩余/质量差距/加人延期砍范围后果/主要风险）；日期推进不重复结算。

### 2.5 风险处理（真实决策，非看进度条）

M1.1 现有能力可支撑的**真实决策点**（基于已落地规则，不虚构事件）：

| 风险情境 | 玩家可选决策 | 系统反馈（已有能力） |
|---|---|---|
| 预算不足/耗尽（G-05 落地后） | 追加预算 / 砍范围 / 暂停 | 耗尽横幅、暂停、需手动恢复（DESIGN-G05 §6） |
| 项目延期 | 维持计划 / 接受延期 | 预计完成日"晚 N 天"提示；**超期不自动失败**（A5） |
| 质量问题 | 提前进 QA 承担惩罚 / 做满 90% | B7 提前惩罚公式、缺陷等级可见 |
| 人员分配不合理 | 调整投入比例 / 招聘 | roleFit/skillFactor 影响产能；跨项目 Σratio 约束 |
| 研发瓶颈学科 | 加人 / 转岗 | 瓶颈学科高亮；单学科超额不自动补其他学科（03 §3） |
| 财务困难（负现金） | 暂停招聘/立项 | 负现金横幅、禁止招聘与立项（D14） |

**明确排除**：随机历史事件、AI 竞争冲击、市场窗口关闭等不属 M1.1（D-02 / 已知问题清单），**不得**作为验收项。

**验收点**：至少 3 个风险情境下，玩家的不同选择导致可观测的不同结果（进度/质量/现金/状态之一变化）。

### 2.6 QA 与上市

| 项 | 内容 |
|---|---|
| 进入 QA | 设计/程序/美术三学科完成度 ≥90%，或玩家主动提前（承担 B7 惩罚） |
| QA 推进 | QA 学科工作量推进；缺陷等级随 QA 进度下降（B8：×（1-0.7×QA完成度）） |
| 上市闸门 | QA 100% 才能进 READY_TO_LAUNCH（B6）；玩家手动确认上市（C9）；到计划日不自动上市 |
| 上市检查 | 8 项前置全满足（C11）；`launchPriceCents=null`（无真实定价）；`actualLaunchDay` 记真实日 |
| 结果观察 | 生成 Product（含 finalQualityScore/defectLevel）；前期选择（提前 QA、加班、范围）通过 finalQualityScore 体现 |

**验收点**：QA<100% 时上市按钮禁用且返回 PRJ_QA_INCOMPLETE；上市后生成唯一 Product；前期质量决策在 finalQualityScore 上体现差异。

### 2.7 决策影响的可见性（体验核心）

玩家必须能"看到前期选择的后果"：

| 前期选择 | 后期可见后果 | 数据字段 |
|---|---|---|
| 提前进 QA | 初始缺陷更高、最终质量更低 | initialDefectLevel / finalQualityScore（B7/B8） |
| 招聘高技能/角色匹配员工 | 研发更快完成 | effectiveWork / 预计完成日（A2） |
| 超预算/不加预算 | 预算耗尽暂停（G-05 落地后） | budgetExhausted / 耗尽横幅 |
| 过度分配疲劳 | 疲劳累积影响产能 | fatigue（E17） |

**验收点**：同一初始条件、两种不同策略推进，至少在 finalQualityScore 与完成日期两个维度出现可解释差异。

## 3. 四档体验结论（M1.1 真实判定）

> 以下结论基于本人实测代码能力与规格比对，**不是**宣称 M1.1 已通过。最终验收由独立审核 AI + Owner 完成。

| 流程 | 可玩（已实现） | 数据模拟（有数值无反馈） | 依赖后续阶段 | 体验断点 |
|---|---|---|---|---|
| 创办公司 | ✅ 创建、现金、城市 | 品牌/技术容量初始值无玩法后果 | — | 无强制目标，新玩家可能迷茫 |
| 创建项目 | ✅ 向导、年代校验、难度预设 | 市场规模/吸引力预期 | 真实市场潜力（M2） | 预算→工作量联动较弱 |
| 组建团队 | ✅ 招聘、分配、工资、容量 | 士气/疲劳数值 | 自动离职（E18 明确不做） | 能力匹配反馈不够直观 |
| 研发推进 | ✅ 日推进、阶段门控、预计完成 | 预算消耗（G-05 落地前只展示） | — | G-05 落地后补真实归属 |
| 风险处理 | ⚠️ 延期/质量/财务困难可感知 | 预算耗尽（G-05 落地后补齐） | 随机事件/AI 竞争 | 事件驱动决策缺失（符合 D-02） |
| QA 与上市 | ✅ QA 闸门、B7/B8、手动上市 | 定价（null）、评价/销量 | 销售/退款/评价（M2） | 上市后无经营反馈（垂直切片边界） |
| 决策影响可见 | ✅ 质量/日期/现金可追溯 | 品牌长期影响 | 市场反馈闭环（M2） | 上市后决策链断在 Product 生成 |

## 4. 总体验收结论（待审核方确认）

**M1.1 是否满足垂直切片目标（D-02）**：

- 目标闭环 9 环节中，**8 个环节已实现流程**（创办→立项→组队→研发→风险→QA→上市→决策可见)，1 个（预算耗尽风险）在 G-05 落地后补齐。
  - 【GDR D-EXP-02 裁定 2026-11-19】"已可玩"措辞改为"已实现流程"以与 §3 四档表对齐：其中"风险处理"环节标注为 ⚠️（部分）、"上市后反馈"断在 Product 生成（D-02 边界），这两处尚非完整可玩体验；是否达到"可玩"须以 GDR 审查 + 独立审核实测为准，设计负责人不在此宣称通过。
- 上市后"观察经营决策影响"仅到 Product 生成为止，销售/营销/退款/评价反馈依赖 M2——**符合 D-02 边界**，不构成体验断点。
- 结论：**M1.1 在 G-05（P1）与 pause_timeout UI（P3）落地后，具备垂直切片体验验收条件**。当前（G-05 未落地）预算消耗仍是数据模拟，不满足完整体验闭环。

**关闭前置**（M1.1 关闭五项条件，交接文件 §11）：
1. 功能范围符合冻结规格 —— 需确认 G-05 落地。
2. 设计缺口有正式裁定 —— 本轮 DESIGN-G05/EXPERIENCE/PAUSE-UI 三份规格。
3. 体验验收通过 —— 本规格 + 独立审核实测。
4. 独立审核完成 —— 待审核方。
5. Owner 确认阶段关闭 —— 待 Owner。

**本设计负责人不宣布 M1.1 通过**，仅提供验收基准与判定材料。
