## 1. 目标与玩家价值

### 玩家当前目标是否明确？
**明确**：玩家的终极目标是把第一款游戏做出来并上市，中间目标包括"招齐团队""分配人员""立项""推进研发""顺利上市"。但当前数值配置让这一路径上出现了**不可控的资源耗尽**——玩家在 Day 120 左右就会撞上预算耗尽暂停（实测已花 $32,000），被迫手动追加预算 $10,000 才能继续。这不是"选择困难"，而是"默认路径走不通"。

### 这个设计让他多做哪个决策？不做会损失什么？
调参后，默认配置下玩家**可以不追加预算走到上市**。追加预算从"被迫补救"变成**策略杠杆**——玩家可以选择追加预算换更充裕的 runway，也可以选择精简团队/调整节奏省着花。损失：数值平衡回归之前"走不通"，玩家被迫操作与体验割裂。

### 不同选择是否产生不同结果（而不是不同数字）？
是。默认薪资 $1,300/人 vs 玩家主动招高薪员工（$2,000+），不只是数字差——后者预算耗尽更快，**倒逼玩家在更早的时间点做出"追加预算还是砍掉范围"的决策**。这引入了节奏差异。

### 玩家能否感知因果（做了 A 所以 B 发生）？
**能**。`startingCashCents` 和 `defaultStartingSalaryCents` 都是 tuning 入口，调参后数值变化直接体现在 UI 的"建议薪资"和"初始资金"展示上。玩家知道"我付的薪水越低，预算撑得越久"。

### 是否有成长感与长期目标？
本次调参**不直接引入**成长系统，但它是玩家后续做选择的基础条件——只有默认路径走得通，玩家才有空间去体验 M1.2 新增的决策杠杆（砍范围 C-01、延期 C-02）。调参是"地基工作"。

### 与既有系统是否有有意义的互动（而非并列堆放）？
**有**：
- 与 DESIGN-G05 的预算分摊公式（`remainingCap = totalCap - committed - spent`）直接联动——新数值要走通的核心依赖这个公式的正确性。
- 与工作系统（`workPerMillionBudget`）联动——工作量降低 = 研发天数减少 = 工资分摊次数减少。
- 与每日调度的月末结算联动——预算耗尽触发时点直接由新数值决定。

### 是否形成持续挑战与反馈，而非一次性操作？
是。预算是持续压力源，不是"过了就好"。即使调参后，预算在第二个项目上依然可能不够（因为第二个项目可能有更高质量目标或更多团队成员）。玩家需要持续管理预算节奏。

### 是否避免沦为数据展示模拟器？
**避免**。调参前玩家只能看数字崩掉；调参后数字的变化对应真实的游戏节奏变化。

### 这个设计如何被验证"好玩"，而不只是"完整"？
三条验证路径：① 走查 A 链路重跑——不追加预算能否上市；② 走查 B 链路（玩家主动追加预算 + 高薪员工）——压力场景是否仍能触发有意义的决策；③ 平衡区间探测脚本——穷举"预算 × 薪资 × 团队规模 × 上市日"的组合，确认玩家选择的自由度区间≥30%。

## 2. 规则与公式

### 2.1 调参方案（一次性落地 tuning.ts）

| 参数 | 当前值 | 目标值 | 单位 | 调幅 | 依据 |
|---|---|---|---|---|---|
| `TUNING.company.startingCashCents` | 5_000_000 ($50,000) | **6_500_000 ($65,000)** | 美分 | +30% | 覆盖 $30,000 项目预算 + $8,400 租金(4月×$2,100 SF) + $780 雇佣成本 + 留 $25,820 余量 |
| `TUNING.employee.defaultStartingSalaryCents` | 200_000 ($2,000) | **130_000 ($1,300)** | 美分/月 | −35% | 4人月薪合计 $5,200，4 次工资分摊（上市 Day 150 前）= $20,800 ≤ $30,000 × 70% |
| `TUNING.project.workPerMillionBudget.design` | 100 | **65** | 工作点/百万美分 | −35% | 整体等比例下调，保持学科比例不变（design:programming:art = 1:1.5:1.2） |
| `TUNING.project.workPerMillionBudget.programming` | 150 | **97.5 → 98**（取整） | 工作点/百万美分 | −35% | 同上；workPerMillionBudget 的值应为整数（design 期望），97.5 四舍五入为 98，比例略有偏差但可接受 |
| `TUNING.project.workPerMillionBudget.art` | 120 | **78** | 工作点/百万美分 | −35% | 同上；整数 |
| `TUNING.project.qaWorkRatio` | 0.2 | **0.15** | 比例 | −25% | QA 工作量从 20% 降到 15%，减少 QA 阶段天数，进一步压缩总工资支出 |
| `TUNING.project.budgetFactorMin` | 0.5 | **0.5**（不变） | — | — | 保持 |
| `TUNING.project.budgetFactorMax` | 4 | **4**（不变） | — | — | 保持 |

> **关于 plannedLaunchDay 引导值**：当前立项页无默认上市日引导（走查 A 脚本手动传 180）。M1.2 在 `new-project.tsx` 增加**默认上市日建议** = 立项日 + 150 天（约 5 个月）。此为 UI 层行为，不改 tuning，玩家可自由调整。

### 2.2 手算验证

**走查 A 链路（默认配置重跑预期结果）**：

| 项目 | 当前值（OI-20 实测） | 调参后预期 | 计算过程 |
|---|---|---|---|
| 月薪合计 | $8,000（4 × $2,000） | $5,200（4 × $1,300） | 4人 × defaultStartingSalary |
| 4个月工资分摊 | $32,000（Day 31/59/90/120） | $20,800 | 4 × $5,200 |
| $30,000 预算耗尽日 | Day 120（第4次结算后 remainingCap = -$2,000） | Day **200+**（预期上市后才可能耗尽） | $30,000 / $5,200 ≈ 5.77 个月 → 约 Day 170 后才耗尽 |
| 上市日 | Day 180 | Day 150（默认引导值） | 立项日 + 150 天 |
| 上市时已花 | $48,000（含追加） | **$20,800**（无追加） | 4 次工资分摊 |
| 上市时剩余预算 | −$18,000（耗尽后无） | **$9,200** | $30,000 − $20,800 |
| 剩余预算比例 | 0% | **30.7%** | $9,200 / $30,000 ✓ 达标 ≥30% |
| 上市时公司现金 | −$7,600 | **≥$25,000** | $65,000 − $780 雇佣 − $8,400 租金 − $20,800 工资 |

**研发工期验证**：
- $30,000 → budgetFactor = 3
- design = 65 × 3 = 195，programming = 98 × 3 = 294，art = 78 × 3 = 234
- PRODUCTION 总量 = 723
- 达到 90% 门槛 = 650.7
- 日产能 PRODUCTION = 16.5（3 个学科 × 5.5 work points/day）
- PRODUCTION 天数 = ceil(650.7 / 16.5) = **40 天**
- QA 工作量 = 723 × 0.15 = 108.45
- QA 天数 = ceil(108.45 / 5.5) = **20 天**
- 总研发天数 = **60 天**（与 Day 0→Day 60 完成研发、Day 60→Day 150 等待上市一致）

### 2.3 边界值与约束

| 场景 | 预期行为 |
|---|---|
| 玩家主动调高薪资到 $2,000/人 | 月薪回到 $8,000 → 预算 Day 120 耗尽（与旧配置一致）→ 倒逼玩家追加或砍范围（新杠杆 C-01 此时才有意义） |
| 玩家降低预算到 $20,000 | budgetFactor = 2 → 工作量减少 → 研发天数更少 → 工资分摊次数 ≤3 次 → $15,600 ≤ $20,000，余量 $4,400（22%）。略低于 30% 但仍走得通 |
| 玩家提高预算到 $50,000 | budgetFactor = 4 → 工作量翻倍 → 研发天数 ≈ 80+ 天 → 工资分摊 5 次 = $26,000 → 余量 $24,000（48%） |
| 玩家招 5 人（含 producer） | 月薪 $1,300×5 = $6,500/月 → 4 个月 $26,000 → 预算 $30,000 余量 $4,000（13%）。略紧但走得通 |

## 3. 数据与接口

### 3.1 tuning.ts 变更

```ts

  dataStatus: 'TUNING' as const,
  version: 2,  // 从 1 → 2，表示参数值有变更

  company: {
    startingCashCents: 6_500_000,  // 原 5_000_000
    // ...其他不变
  },

  employee: {
    defaultStartingSalaryCents: 130_000,  // 原 200_000
    // ...其他不变
  },

  project: {
    qaWorkRatio: 0.15,  // 原 0.2
    workPerMillionBudget: {
      design: 65,      // 原 100
      programming: 98, // 原 150
      art: 78,         // 原 120
    },
    // ...其他不变
  },
}
```

### 3.2 数据来源与状态归属

| 字段 | 归属 | 说明 |
|---|---|---|
| 新数值 | `src/content/tuning.ts` | 唯一调参入口，非存档字段（新游戏启动时读） |
| 存档 `remainingCapCents` | `Project` 实体 | 不新增字段，旧存档保持不变（见 §6 存档兼容） |
| 存档 `totalCapCents` | `Project` 实体 | 立项时由玩家指定，不受 tuning 变更影响 |
| 新游戏创建时的现金 | `TUNING.company.startingCashCents` | 每次 createCompany 读 tuning 值入账 |

### 3.3 接口契约（不改动）

- `FinanceService.registerCompany / postTransaction` — 无变更，新现金值通过初始化交易自动入账
- `ProjectService.create → defaultWorkTotalByDiscipline` — 工作量系数从 tuning 读取，自动生效
- 月末结算 `DailyScheduler.applyMonthlySettlement` — 月薪来自员工实体，玩家手动招人的薪资由 UI 传入，默认薪资来自 tuning

## 4. 状态与转换

本设计**不引入新状态**，仅调整状态转换的触发时点（预算耗尽日延后）。

| 状态 | 允许转换 | 非法转换处理 |
|---|---|---|
| 预算充足 → 预算耗尽 | `remainingCapCents <= 0` | 不新增路径；时点从 Day 120 延后到 Day 170+ |
| 公司现金 ≥ 0 → < 0 | 无阻断（M1.2 后续 OI-21 处理） | 无变更 |
| 项目 LAUNCHED → 继续研发 | 不允许 | 无变更 |

## 6. 异常与边界

### 6.1 存档兼容性（关键）

| 场景 | 行为 |
|---|---|
| **加载旧存档（旧 tuning 下运行的存档）** | **不做任何迁移**。存档里的 `project.budgetTotalCapCents`、`project.budgetSpentCents`、`company.cashBalanceCents` 保持原样。tuning 只在游戏启动时读一次，**不影响已存在的存档数据**。旧存档可能已经是"预算耗尽暂停"状态，加载后维持原样，玩家可选择追加预算继续或放弃 |
| **在旧存档基础上建新游戏/新项目** | 新游戏会用新 tuning 的 startingCash ($65,000) 和默认薪资 ($1,300)。旧存档里的项目保持旧数值，但如果玩家在旧存档里追加预算，追加额由玩家手动输入，不受 tuning 影响 |
| **旧存档里的 `remainingCapCents` 快照** | 校验公式不变（`remainingCap = totalCap - committed - spent`），与 tuning 无关。旧存档能通过校验继续加载 |
| **旧存档里的 `workTotalByDiscipline`** | 这是立项时快照固化在项目里的，不受 tuning 变更影响。已存在的项目工作量不变 |

> **核心裁定**：tuning.ts 变更只影响**新创建的游戏和新项目**。已存在的存档是不可变数据快照，不做向后迁移。这避免了"迁移把玩家积累的状态搞乱"的风险。

### 6.2 数值漂移防护

| 风险 | 防护 |
|---|---|
| 不同 tuning 版本下工作量计算不同 | 立项时工作量快照写入 `workTotalByDiscipline` / `workRemainingByDiscipline`，与 tuning 解耦 |
| 测试断言硬编码旧数值 | 走查脚本 `v2-A.js` 里的预算/时间断言需同步更新；测试文件 `company-init.test.ts` 断言 $50,000 需改为 $65,000 |
| 玩家感知"变便宜了" | i18n 文案统一为"建议值"，不承诺"够用" |
