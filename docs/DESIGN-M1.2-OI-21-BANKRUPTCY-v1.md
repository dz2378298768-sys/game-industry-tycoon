## 1. 目标与玩家价值

### 玩家当前目标是否明确？
**明确**：上市第一款游戏。但 OI-24 指出 M1.1 无收入系统，现金必然只出不进。这意味着即使 OI-20 调参让默认路径走通，玩家如果主动选择高薪/扩招/多项目并行，最终还是会走向现金负数。"无限透支"让这个过程没有紧张感。

### 这个设计让他多做哪个决策？不做会损失什么？
现金下限 + 破产机制让玩家在**日常操作中感受到持续压力**：要不要接受这个高薪候选人？要不要同时开两个项目？要不要推迟发薪？这些决策之前在无限透支下毫无意义——反正欠钱也没人管。加了下限后，每个决策都有了成本。

### 不同选择是否产生不同结果（而不是不同数字）？
**是**。保守经营（低薪/少人/单项目）→ 公司稳定，顺利撑到上市。激进扩张（高薪/多人/多项目）→ 现金触及警告线 → 进入破产保护 → 只能裁员缩规模。这是**定性不同**的结果，不是数字差异。

### 玩家能否感知因果（做了 A 所以 B 发生）？
**能**。每次发薪/租金结算都会刷新现金余额；余额触及警告线（< $4,000）时弹警告横幅；触及下限（< 0）时触发破产，公司状态从 `active` 变 `bankrupt`。UI 全程可视化，因果链清晰。

### 是否有成长感与长期目标？
**有**。破产不是终点——M2 收入系统上线后，玩家可以通过上市产品获得销售收入，把公司从 `bankrupt` 救回 `active`。这形成了"冒险 → 危机 → 自救 → 成长"的弧线。

### 与既有系统是否有有意义的互动？
**强互动**：
- 与 OI-20 调参联动：调参让默认薪资 $1,300 下 4 人月薪 $5,200/月，初始现金 $65,000 ≈ 12.5 个月的安全 runway
- 与 C-01 砍范围联动：现金紧张时玩家可以砍范围减少工资支出
- 与 C-02 延期上市**冲突但有意义**：延期增加现金消耗，可能触发下限——玩家需要权衡
- 与 finance-service 的 `allowNegativeBalance` 参数联动：当前固定结算（工资、租金、解雇补偿）用 `true`，自主支出（招人、立项）用 `false`。本设计新增的是**固定结算后的公司级余额检查**，不是在每笔交易时拦截

### 是否形成持续挑战与反馈，而非一次性操作？
**是**。现金余额是持续变量，每天变化（虽主要在月末）。玩家需要持续监控并调整策略，而不是"过了这个坎就没事了"。

### 是否避免沦为数据展示模拟器？
**避免**。现金数字变化直接触发 UI 横幅、命令可用性限制，不是单纯的数字展示。

### 这个设计如何被验证"好玩"，而不只是"完整"？
两条线：① 极端扩张场景（高薪 + 5 人 + 2 项目）能否触发破产 → 玩家能否通过裁员自救；② 试玩反馈——玩家是否感受到"我在管一家要倒闭的公司"的压力，而不是"钱只是数字"。

## 2. 规则与公式

### 2.1 现金下限设置（三层阈值）

| 层级 | 阈值 | 触发事件 | 效果 |
|---|---|---|---|
| **L0 安全** | `cashBalance >= 400_000`（$4,000+） | — | 正常，无提示 |
| **L1 警告** | `0 <= cashBalance < 400_000`（$0 ~ $4,000） | 任何结算后余额落入此区间 | UI 顶部横幅警告「现金低于 $4,000，下次发薪可能触发破产」 |
| **L2 破产** | `cashBalance < 0`（现金为负） | 任何结算后余额为负 | 公司 status 从 `active` → `bankrupt`（不立即 dissoved）；见 §2.2 |

> **为什么 L2 不设在 $0 以上？** 如果设成 $1,000 或 $500 就破产，玩家需要精确计算"本月发薪后还剩多少"，但由于游戏是按天推进、月末才结算，玩家在发薪日之前很难精确预测（不知道当天的日推进会不会触发额外成本）。$0 作为下限最清晰：**欠钱了就是破产**，因果无歧义。

### 2.2 破产后效果（Bankrupt Mode）

公司进入 `bankrupt` 状态后，**模拟继续运行**但限制玩家部分命令：

| 命令 | 破产前可用 | 破产后可用 | 原因 |
|---|---|---|---|
| 招员工 `hireEmployee` | ✅ | ❌ 拒绝 | 破产公司不能扩大支出 |
| 解雇员工 `fireEmployee` | ✅ | ✅ 保留 | 唯一自救手段（裁员降低未来工资支出） |
| 立项 `createProject` | ✅ | ❌ 拒绝 | 不能启动新项目烧钱 |
| 推进项目阶段 | ✅ | ✅ 保留 | 继续已有项目研发 |
| 暂停/恢复/取消项目 | ✅ | ✅ 保留 | 包括取消项目释放团队 |
| 追加预算 `topUpBudget` | ✅ | ❌ 拒绝 | 破产状态下追加预算无意义（公司没钱）；**特例**：如果玩家有"投资人注资"命令（M2 候选），届时可放开 |
| 上市 `launchProject` | ✅ | ✅ 保留 | M1.2 无收入系统（OI-24），破产下上市**不产生收入**，仅让玩家看到"已上市"状态；收入自救接口预留 M2 |
| 调整团队分配 `assign/unassignEmployee` | ✅ | ✅ 保留 | 可优化现有人员利用率、降 burn rate |
| 取消项目 | ✅ | ✅ 保留 | 释放团队减少工资 |
| 砍范围 `descopeProject` | ✅ | ✅ 保留 | **关键自救手段**：减少工作量 = 减少未来工资分摊 |
| 延期上市 `delayLaunch` | ✅ | ✅ 保留 | 绝望操作：延期增加现金消耗，但玩家可自行权衡 |

**破产状态的命令守卫位置**：`game-store.ts` 或 `game-world.ts` 的命令入口层，在执行前检查 `company.status !== 'active'`。领域层（`ProjectService`、`FinanceService`）保持不变。

### 2.3 破产触发时点与条件

**唯一检查时点**：每日调度末尾，在 `syncCompanyCash` 之后统一执行一次：

```
applyBankruptcyCheck(world, dayIndex):
  for each company where status === 'active':
    balance = finance.getCashBalance(company.id)
    if balance < 0:
      → company.status = 'bankrupt'
      → 记录领域事件 CompanyBankrupted { companyId, dayIndex, balanceAtBankruptcy }
      → 记录 changeLog
      → UI 横幅触发
```

**为什么不在每笔交易时拦截？** 因为：
1. `finance-service.ts` 已有 `allowNegativeBalance` 参数，固定结算（工资、租金）固定传 `true`。在交易层拦截需要改所有调用方，风险高。
2. 每日统一检查是 G-05 预算耗尽的模式（也是每日末尾统一判定），复用一致的设计模式。
3. 避免"同日多次结算多次触发破产"的幂等问题。

### 2.4 破产后收入系统联动（M2 接口预留）

公司 `bankrupt` 状态下，M2 收入系统上线后的行为：
- 产品上市后产生的销售收入**正常入账**（不被冻结）
- 当 `cashBalance` 回到 ≥ $5,000（L0/L1 边界）时，**自动**将 company.status 从 `bankrupt` → `active`（"自救成功"）
- 无需玩家手动"宣布破产"或"申请重组"

这个"自动恢复"机制在 M2 实现，M1.2 仅预留 status 字段。

### 2.5 与现有 `allowNegativeBalance` 的关系

当前 `finance-service.ts` 的 `allowNegativeBalance: true` 用于：
- 月末工资
- 办公室租金
- 解雇补偿

`allowNegativeBalance: false` 用于：
- 招员工（雇佣成本）
- 立项（未来扩展）
- 追加预算（未来扩展）

**M1.2 本设计不改变这个区分**——破产检查是**事后检查**，不是在每笔交易前拦截。`allowNegativeBalance` 继续保留其"自主支出 vs 固定结算"的语义。

## 4. 状态与转换

### 4.1 Company.status 状态机

```
              收入回流 ≥ $5,000（M2）
    [active] ──────────────────────► [active]（自动恢复）
       │                              ▲
       │ cashBalance < 0              │ 收入回流 ≥ $5,000（M2）
       ▼                              │
    [bankrupt] ──────────────────────┘
       │
       │ 玩家手动"关闭公司"命令（M2+ 候选）
       ▼
    [dissolved]（不可逆）
```

### 4.2 允许的转换与非法处理

| 当前状态 | 触发条件 | 目标状态 | 处理 |
|---|---|---|---|
| `active` | `cashBalance < 0` | `bankrupt` | 每日调度末尾检查、原子转换、记录事件 |
| `bankrupt`（M2 预留） | `cashBalance >= 5_000_000` | `active` | 每日调度末尾检查、自动恢复 |
| `dissolved` | — | 不可转换 | 终态 |

**非法转换**：
- `bankrupt → dissolved`（玩家手动关闭）属 M2+ 范围，M1.2 不开放
- 领域层（`ProjectService`、`FinanceService`）不检查 company status，命令守卫在应用层/UI 层

## 6. 异常与边界

### 6.1 数据缺失

| 场景 | 处理 |
|---|---|
| 旧存档里 company.status 非 'active' | 维持原值（bankrupt 或 dissolved），读档后破产横幅立即显示 |
| tuning 未设置 `cashBankruptThresholdCents` | 默认 0（现金为负） |
| 存档里 cashBalanceCents 与流水不一致 | 现有 save-schema 校验已覆盖（`SAVE_CASH_MISMATCH`） |

### 6.2 并发（同日多次结算）

破产检查在每日调度末尾**统一执行一次**，不存在同日多次触发的问题。

### 6.3 超限

| 场景 | 处理 |
|---|---|
| 现金极大负数（−$500,000+） | 正常进入破产状态，无额外处罚。玩家可以继续裁员自救（每次解雇降低未来月薪支出） |
| 破产后继续产生新的支出 | 固定结算（工资、租金）不受破产状态影响——破产是公司级标记，不是停止模拟。玩家需要**主动**解雇员工来降低未来支出 |

> **关键裁定**：破产状态不停止模拟运行。已签订的劳动合同继续执行（G05-R6：暂停项目不自动解除工资义务；破产同理）。玩家必须**主动**执行解雇/取消项目来降低未来现金流出。

### 6.4 读档残留

旧存档（M1.1 创建）里如果公司 status 是 'active'，破产检查会基于当前现金余额重新判定。如果存档加载后现金已为负（例如玩家之前把钱都花光了没管），则加载后立即进入破产状态。

### 6.5 与 C-02 延期上市的冲突

延期上市增加研发时间 → 增加工资分摊次数 → 增加现金消耗。如果玩家在现金接近警告线时选择延期，可能直接触发破产。这是**有意义的交互**：C-02 的"延期"选择此时变成了"拿公司性命换时间"的艰难决策。

## 9. 变更说明

| 项目 | M1.1 现状 | M1.2 变更 | 为什么 |
|---|---|---|---|
| 现金无限透支 | `allowNegativeBalance` 对工资/租金恒 true；无公司级余额检查 | 每日末尾检查 `cashBalance < 0` → 触发 bankrupt | 给玩家压力、倒逼决策 |
| `Company.status` | save-schema 已定义 `'active' \| 'bankrupt' \| 'dissolved'` 但只有 `'active'` 被写入 | 破产时写入 `'bankrupt'` | 复用已有枚举值，不新增存档字段 |
| 命令守卫 | 无公司级状态检查 | 应用层增加 `company.status !== 'active'` 守卫 | 在领域层保持纯净的前提下实现功能限制 |
| L1 警告 | 无 | 现金 < $4,000 时顶部横幅 | 在破产前给玩家预警，而非突然死亡 |
| 破产模拟 | 不存在 | 破产后继续运行、限制部分命令 | 让玩家有自救路径，而不是直接 Game Over |
| M2 恢复接口 | 无 | 破产公司收入 ≥ $5,000 自动回 active | 与收入系统联动，形成"破产→自救→重生"弧线 |
