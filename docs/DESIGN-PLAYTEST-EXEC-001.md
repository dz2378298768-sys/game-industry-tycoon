## 0. 为什么需要这份规格

`GAME_DESIGN_PHILOSOPHY.md` 核心信条：**"先证明玩法有趣，再保证系统完整，最后追求模拟深度"**，其 §14 明确：

> 设计文档写得完整，不代表游戏一定好玩。自动化测试通过，也不代表玩法有趣。每个重要玩法都应该经过实际试玩。设计师必须允许设计被实际试玩结果推翻。

当前 M1.1 处于"保证系统完整"阶段，编码闭环后 **109 用例全绿 ≠ 体验有趣**。本规格把"好玩"从主观感觉变成**可执行、可观察、可记录、可判定**的试玩活动，是 M1.1 体验验收不可替代的一环。

**效力声明**：本规格是试玩执行的**方法论与记录模板**。真实试玩须由真人参与者操作（设计负责人可主持/观察，但不得用自己的操作代替玩家行为），试玩结论作为 M1.1 阶段判断的输入之一，不由设计负责人单方面宣布"好玩"。

---

## 1. 试玩目标（要回答的问题）

对应 GAME_DESIGN_PHILOSOPHY §1 的三问：玩家为什么玩？为什么继续玩？为什么再玩一局？M1.1 具体化为：

1. 玩家能否在**无口述提示**下理解当前目标与下一步操作？
2. 玩家能否走通 M1 闭环（创办→立项→组队→研发→QA→上市）？
3. 玩家是否**主动做出选择**（而非机械点击）？是否在决策点停顿、权衡？
4. 玩家是否**在意结果**，能否解释"为什么质量低/为什么延期/为什么现金变负"？
5. 玩家是否体现出**策略差异**（不同人走不同路线）？
6. 玩家在结束时是否表达"想再试一次/换个策略"的意愿？

## 2. 试玩准备

| 项 | 要求 |
|---|---|
| 参与者 | 3–5 名，至少 2 名从未接触本项目；覆盖"熟悉经营游戏"与"不熟悉"两类 |
| 环境 | 可运行的开发版本（待 001-B~E、UI-001 编码闭环后）；记录构建 SHA |
| 主持人 | 设计负责人或指定人员；**只观察与计时，不指导、不替玩家操作** |
| 记录工具 | 本规格 §5 记录表 + 屏幕录制（可选）+ 出声思考（think-aloud）引导 |
| 初始条件 | 统一初始存档（$50,000、Day 起始、0 人团队），确保跨玩家可比 |
| 时长 | 单场 30–45 分钟，或推进到上市为止 |

## 3. 分场景试玩脚本（对应 DESIGN-M1-EXPERIENCE-001 七流程）

每个场景记录：是否完成 / 耗时 / 是否主动决策 / 是否理解反馈 / 卡点描述。

### S1 创办公司
- 任务："创办一家游戏公司，看看接下来能做什么。"
- 观察：是否找到创建入口？是否理解初始现金 $50,000？创建后是否知道下一步（招聘）？
- 判据：无需提示完成创建；能说出"接下来要招人/立项"。

### S2 创建研发项目
- 任务："做一款游戏，自己定方向。"
- 观察：是否理解定位/平台/预算各项含义？预算与工作量的联动是否被注意到？年代校验被拒时是否理解原因？
- 判据：独立完成立项；被拒时能理解并改正，而非反复乱试。

### S3 组建团队
- 任务："招人并分配到项目。"
- 观察：是否理解技能/角色匹配影响产出？是否注意到 Σ分配≤1 约束？是否意识到工资成本？
- 判据：合理分配（非随意）；能说出"为什么招这个岗位"。

### S4 研发推进
- 任务："推进研发，观察项目状态。"
- 观察：是否理解阶段门控（CONCEPT/PRE_PRODUCTION 不累计）？是否关注进度/瓶颈学科/预计完成日/预算消耗？是否会调速度？
- 判据：能指出当前瓶颈；能解释预算数字变化（G-05 落地后含真实归属）。

### S5 风险处理（关键：验证"有意义决策"）
- 任务（视进程注入情境）：预算耗尽 / 项目延期 / 质量问题 三选一，观察玩家反应。
- **M1.1 可用杠杆清单（v1.1 补充，经代码核实 `game-store.ts`）**：玩家真正能做的只有三类——① 预算（追加/不追加/放弃项目）；② 人力（招聘/解雇/调整分配比例）；③ 时间（推进速度、暂停/恢复、何时进入 QA 与上市）。**不存在**"砍范围""延期上市""调整上市日"命令（已登记为 M1.2 候选 C-01/C-02）。
- **因此 S5 的判定口径（v1.1 修订）**：
  - **必测情境 = 预算耗尽**（唯一有直接杠杆的情境）：观察玩家选"追加""放弃""摆着不动"中的哪一种，是否比较过工资仍在发生这一代价；
  - **观察情境 = 延期风险 / 质量问题**（只有间接杠杆）：观察玩家是否想到"加人/调比例/给足 QA 时间"，还是只会调速度等数字；
  - **不要求**玩家做"砍范围/延期上市"（能力不存在，要求即为设计缺陷，不是玩家缺陷）。
- 判据：≥2 名玩家在**预算耗尽**情境做出不同选择并能说出理由；若所有玩家都只会"追加"或都"摆着不动"，且说不出代价，判"有意义决策不足"→ 体验需修。

### S6 QA 与上市
- 任务："把游戏做完并上市。"
- 观察：是否理解 QA 闸门（<100% 不能上市）？面对"提前上市惩罚"是否犹豫？是否理解前期质量决策的影响？
- 判据：能走通 QA→上市；被闸门拦下时理解原因。

### S7 决策影响复盘
- 任务："回想你做过的决定，哪些影响了结果？"
- 观察：能否举出具体例子（提前 QA 导致质量低、招错人导致慢、超预算导致暂停）？
- 判据：至少能说出 2 条可追溯的因果链（对应 GAME_DESIGN_PHILOSOPHY §9 反馈系统）。

## 4. 收尾访谈（体验闭环三问）

试玩后统一提问，记录原话：
1. 这游戏现在在让你做什么决定？（检验"理解自己正在做什么"）
2. 有没有哪个时刻你觉得"这个选择挺纠结"？（检验"有意义的选择"）
3. 再来一次你会换什么策略？为什么？（检验"愿意再玩一局"+"策略多样性"）

## 6. 判定与处理

| 判定 | 条件 | 处理 |
|---|---|---|
| **体验达标** | 7 场景多数完成 + 多数玩家主动决策/理解结果 + 出现策略差异 + 有再玩意愿 | 作为 M1.1 体验验收通过的证据之一，交独立审核与 Owner |
| **体验需修** | 存在明确卡点或"机械操作、无主动思考" | 设计负责人据试玩结果裁定修正（B 类），允许**推翻既有设计**——不因投入大量设计工作就坚持保留（§14） |
| **无法判定** | 样本不足或环境未就绪 | 补做试玩，不得凭编译/单测通过推断"好玩" |

**重要**：试玩可能推翻设计。若 S5 显示所有玩家都选同一方案（唯一最优解），或 S4 显示玩家只是在等数字变化（时间推进成为核心玩法），设计负责人须记录并修正，而非粉饰通过。
