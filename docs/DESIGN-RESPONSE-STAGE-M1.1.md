## 2. S-1 的定级分歧：我把它从 P2 升为 P1

审核判 **P2**，理由表述为"影响账目可信度，不阻塞五场景"。我复核后**改判 P1**，理由如下：

审核测到的是"`spent` 在终态后继续增长"（账目问题）。但我按同一条线索继续测了一步，发现更严重的后果：

> 项目取消/上市后，`teamAssignments` 仍保留 → 该员工 `Σ allocationRatio` 被终态项目永久占用 → `assignEmployeeToProject` 返回「该员工在多个项目上的投入比例合计超过 100%」→ **玩家做完第一款游戏后，无法为第二款游戏组队**。

实测记录（`b98c9af`，`T-A` 取消后建 `T-B`）：

```
asg1: {"success": true}          // 分配到 T-A 成功
（取消 T-A，推进 30 天）
asg2: {"success": false, "message": "该员工在多个项目上的投入比例合计超过 100%，请降低分配比例。"}
p1.spentGrowth: 240000           // 终态项目 30 天内又花了 $2,400
p2assignments: 0                 // 新项目一个人都进不去
```

**P1 的理由**：这不是"账目不准"，是"核心循环在第二次迭代就断"。M1.1 的出口条件写的是"一款游戏从立项到上市的完整流程可玩"——单款确实跑通了；但玩家上市后第一件想做的事就是"再做一个"，此时直接卡死。对即将进行的真人试玩而言，这会污染整个体验数据（试玩者会卡在一个与"好不好玩"无关的实现缺陷上）。

审核判 P2 没有错——它的取证范围是五场景与账目，没有测"第二款能否组队"。**这正是双轨的价值：审核发现线索，设计侧顺着线索走了一步。** 我不认为这是审核疏漏，而是职责边界使然。

**处置**：先改规格（`DESIGN-G05-1.0` v1.7 §3.3、§10.1a-4、§10.2；`DESIGN-M1-PAUSE-TIMEOUT-UI-001` v1.9 §3.2），再派 `TASK-M1.1-TERMINAL-RELEASE-001`（P1）。顺序不能反——编码者只以指定版本规格为依据。

## 5. 对试玩时点的裁定（重要）

**试玩必须等 `TERMINAL-RELEASE-001` 修复并复审通过后再开始。**

理由：试玩的核心问题是"这个经营循环好不好玩、玩家会不会做出不同决策"。若带着"做完第一款就无法做第二款"的缺陷去试玩：

- 玩家的时间会消耗在与设计无关的实现障碍上；
- 观察到的"挫败感"无法归因（是设计不好玩，还是 bug 卡住？）；
- 数据作废，等于白做一次真人试玩——而真人试玩是本阶段最稀缺的资源（需 Owner 组织 3-5 人）。

已在 `PLAYTEST-KICKOFF-M1.1.md` **v1.2 §0** 写明"必须用 S-1 整改后的提交"，并给出"若在修复前试玩需口头告知"的兜底说明。
