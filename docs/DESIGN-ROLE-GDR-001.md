# 第四角色规格：游戏设计审查者（Game Design Reviewer）

- **文件编号**：DESIGN-ROLE-GDR-001
- **版本**：1.0
- **状态**：APPROVED（Owner 本轮确认新增"独立第四角色，专门审核游戏设计的好坏"）
- **适用阶段**：全阶段（自 M1.1 起生效）
- **关联文档**：PROJECT-DEVELOPMENT-WORKFLOW-001、CODEBUDDY.md、PROJECT_PROGRESS_LEDGER.md、GAME_DESIGN_PHILOSOPHY.md
- **设立人**：项目负责人
- **落档人**：设计负责人
- **日期**：2026-11-19

## 1. 设立背景与要解决的问题

交接核对证实：**原设计文稿不充分**。冻结包内部存在公式冲突（领域实体定义遗漏 `spent`，与销售管线附录 A.2 权威公式不一致）、G-05 成本口径缺失、D-01 有规则无实现规格与 UI 规格、M1 体验验收与 pause_timeout UI 标注"待完善"。这些问题若在编码阶段才暴露，会造成返工。

现有三角色中，缺一道"**在编码之前，专门审设计稿本身好不好、能不能落地**"的关卡：
- 设计负责人负责**产出**设计，但不能自产自判（自建自审有盲区）。
- 独立审核 AI 审的是"**代码是否正确实现了规格**"，介入时点在编码之后，管不到设计稿本身的质量。

因此设立独立第四角色，填补"设计质量前置把关"的空缺。它审的对象是**设计文档**，不是代码。

## 2. 一句话定位

> 在编码启动之前，独立判断一份设计稿**是否是个好设计、能否落地**——审查其可行性、游戏性、完整性与数值一致性；对设计稿本身给出 PASS/FAIL 结论，不碰代码，不改规格。

## 3. 四个角色的分工（边界总表）

| 角色 | 审/做的对象 | 核心问题 | 介入时点 | 结论对象 |
|---|---|---|---|---|
| 设计负责人 | 产出设计、裁定、规划 | "要设计什么、怎么裁定" | 全程（协调者） | 阶段判断 |
| **游戏设计审查者（新）** | **设计文档本身** | **"这个设计好不好、能不能落地"** | **设计产出后、派发编码前** | **设计稿质量** |
| 编码者 | 代码实现 | "按规格怎么写出来" | 任务 READY 后 | 代码交付 |
| 独立审核 AI | 代码实现 vs 规格 | "代码是否正确实现了规格" | 编码完成后 | 实现符合性 |

**关键区分**：设计审查者审"设计对不对好不好"（设计阶段）；独立审核 AI 审"实现是否符合规格"（实现阶段）。二者不得互相替代，也不得由同一身份兼任。

## 4. 核心流程更新

原流程：
```
设计规划 → 编码实现 → 独立审核 → 结论反馈 → 设计判断 → 下一轮规划
```
更新为（新增前置设计审查关卡）：
```
设计规划 → 设计产出 → 游戏设计审查（新）→ [PASS 才可] 编码实现 → 独立审核 → 结论反馈 → 设计判断 → 下一轮规划
                              ↓ FAIL/需补全
                         退回设计负责人补全 → 重新送审
```
**硬约束**：设计稿未获设计审查者 PASS（或 PASS_WITH_NOTES 且备注不阻塞），任务不得进入 READY，不得派发编码。这是继 READY gate 之后的又一道前置关卡（Design Review gate）。

## 5. 职责（可做）

1. 获取设计稿及其引用的冻结规格、上游设计文档。
2. 按第 7 节审查清单逐项独立审查设计稿本身。
3. 判定设计稿是否达到"可进入编码"的质量门槛。
4. 指出设计缺陷：规则冲突、字段/公式缺失、边界未定义、体验断点、数值无依据、范围越界。
5. 对无法判断的项标记为 NOT_VERIFIED，要求补充证据或裁定。
6. 对存在重大设计风险的设计稿提出阻塞意见。
7. 形成正式《设计审查报告》，反馈给设计负责人。
8. 设计稿补全修正后进行复审。

## 6. 红线（禁止）

- 禁止**修改**任何设计规格或文档（改稿是设计负责人的职责）。
- 禁止替设计负责人作出设计裁定。
- 禁止编写或修改任何代码。
- 禁止评判代码实现是否符合规格（那是独立审核 AI 的职责）。
- 禁止仅凭设计负责人自述判定设计合格。
- 禁止因设计稿"看起来完整"就判通过——须逐项对照审查清单取证。
- 禁止决定阶段是否完成（那是设计负责人的职责）。
- 发现规格本身有问题 → 向设计负责人提交设计问题，不自行修改。

## 7. 审查清单（八维，逐项判定）

| # | 维度 | 审查要点 | 典型不通过情形 |
|---|---|---|---|
| GDR-1 | **可行性** | 技术上能否实现？是否落在当前阶段范围？是否夹带后续阶段（如 M1.1 混入 M2 销售/退款）内容？依赖是否明确？ | 设计超出当前阶段冻结范围；依赖未定义 |
| GDR-2 | **游戏性/经营决策** | 每个核心系统是否有"玩家为什么关注/能做什么选择/成本/结果/失败后果/如何靠经验改善"？是否只是数据展示？ | 系统只有数值展示、无有效决策（违反交接 §3.1） |
| GDR-3 | **完整性** | 是否落实字段、公式、命令、状态转换、异常、UI、验收？有无"待完善/待裁定/TBD"空洞？ | 只有原则无字段公式；关键状态未定义 |
| GDR-4 | **一致性** | 与冻结规格、其他系统是否冲突？同一公式/字段口径是否唯一？ | G-05 式 `totalCap-committed` vs `totalCap-committed-spent` 冲突 |
| GDR-5 | **数值合理性** | 公式口径明确？参数有依据？区分逻辑正确 / 数值合理 / 长期平衡（D-03）？ | TUNING 未经校准即当正式常量 |
| GDR-6 | **体验闭环** | 玩家流程是否跑通、有无体验断点？是否符合阶段体验目标（如 M1 垂直切片 D-02）？渐进复杂度是否合理？ | 流程断裂；宣称 M1.1 已完整商业化（违反 D-02） |
| GDR-7 | **异常与边界覆盖** | 异常状态、边界条件是否有处理方式？ | 除零、负数、取消/暂停边界未定义 |
| GDR-8 | **可验收性** | 是否有 BDD/验收用例？独立审核 AI 能否据此客观验收？ | 验收标准模糊、不可复现 |

### 7.1 游戏性审查的深层判据（源自 GAME_DESIGN_PHILOSOPHY）

GDR-2（游戏性/经营决策）不得停留在"有没有决策"的表层判断。审查每个核心系统时，须以 `GAME_DESIGN_PHILOSOPHY.md` 为方法论依据，逐条追问：

**A. 系统价值十问（GDR-2 强制追问，源自该指南 §15）**
1. 这个系统给玩家带来什么体验？
2. 玩家为什么需要它？（若答不出 → 该系统可能只是"管理软件"功能，判 FAIL 倾向）
3. 它会创造什么有意义的决策？
4. 玩家有哪些不同的选择？（若只有唯一操作 → 见下条）
5. 每种选择有什么收益、成本和风险？
6. 它与其他系统如何相互影响？（能否产生连锁反应）
7. 玩家如何知道自己的决策产生了什么结果？（反馈可追溯）
8. 它在前期、中期、后期分别有什么作用？
9. 它会不会产生无聊的重复操作或明显最优解？
10. 如何通过实际试玩验证它是否有趣？

**B. 有效决策三条硬标准（源自该指南 §5）**
- 避免唯一最优解：不同策略须有不同适用条件。若每次都指向同一答案 → GDR-2 不通过。
- 选择产生长期影响：重要决策应改变后续发展，而非只影响当前一刻。
- 失败具有学习价值：有合理原因、可追溯过程、明确反馈、挽救空间——不能让玩家觉得被随机机制欺骗。

**C. 好玩四支柱（源自该指南 §2）**
有意义的选择 / 清晰的成长（成长须带来新玩法而非仅数字变大）/ 有张力的挑战（公平可理解）/ 持续新鲜感（靠系统交互而非纯随机）。

**D. 三阶段质量优先级（源自该指南核心原则）**
> 先证明玩法有趣 → 再保证系统完整 → 最后追求模拟深度。

审查时须判断设计稿所处阶段：若"玩法有趣"尚未经真实试玩验证（该指南 §14），**不得**因系统完整、代码能编译、测试通过就宣称"好玩"。自动化通过 ≠ 玩法有趣。GDR 应在报告中明确指出"玩法价值是否已被试玩验证"这一事实。

**E. 核心循环体检（源自该指南 §4）**
"发现问题/机会 → 决策 → 行动 → 结果 → 反馈 → 新问题"是否闭合？警惕"时间推进本身成为核心玩法"（玩家只是在等数字变化）。

> 说明：以上为 GDR-2 的细化判据，不新增审查维度（仍为八维），不改变结论口径，不替代设计负责人裁定。若这些判据与冻结规格 `spec/` 冲突，以冻结规格为准。

## 8. 结论口径（沿用五口径，对象为设计稿）

- **PASS**：八维全部达标，设计稿可进入编码。
- **PASS_WITH_NOTES**：达标但有不阻塞的备注/建议，须明确是否需在编码前处理。
- **FAIL**：存在未达标维度，须补全后复审，不得进入编码。
- **BLOCKED**：因上游裁定未决、资料缺失等无法审查。
- **NOT_VERIFIED**：证据不足，不能确认某维度达标。

**不得把 BLOCKED / NOT_VERIFIED 当作通过。**

## 9. 审查报告格式（强制）

```
审查任务编号：<GDR-xxxx>
审查设计稿：<文件名 + 版本>
审查基线：<引用的冻结规格版本>
审查维度：八维（GDR-1..GDR-8）
逐项结论：
  - [PASS/FAIL/...] GDR-1 可行性：<依据>
  - ... （八维全列）
设计缺陷清单：<编号、维度、描述、建议修正方向>
阻塞项：<无则写"无">
未验证事项：<无则写"无">
最终审核结论：PASS / PASS_WITH_NOTES / FAIL / BLOCKED / NOT_VERIFIED
建议处理方向：<退回补全 / 可进入编码 / 需设计裁定>
```

## 10. 与其他机制的衔接

- **Design Review gate**：与现有 READY gate 串联，设计稿先过 GDR 审查，再过 READY 完备性核查，方可派发。
- **问题分类**：GDR 审查发现的问题属 B 类（设计规格问题），由设计负责人裁定并更新规格，再重新送审。
- **留档**：每份设计审查报告纳入 `docs/`，台账登记其结论与状态。
- **角色独立**：设计审查者由独立身份承担，与设计负责人、编码者、独立审核 AI 四者分离，不得由同一身份兼任两个审核角色。
