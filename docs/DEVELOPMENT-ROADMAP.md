## 0. 先分清两套"阶段"（最易混淆点）

本项目同时存在两套阶段，含义完全不同，不得混用：

| 维度 | 开发里程碑（M0–M5 + 正式版） | 玩家成长阶段 |
|---|---|---|
| 是什么 | **工程交付顺序**，本项目路线图的主体 | **玩家在游戏内的体验进程** |
| 内容 | M0 规则冻结 → M1 研发切片 → M2 商业化 → M3 AI与发行 → M4 内容与历史 → M5 UI与平衡 → 正式版 | 创业期 → 小型工作室 → 成长型厂商 → 中型发行研发商 → 成熟厂商 |

| 本文档范围 | **是** | 否（仅在此说明区别，详见 spec/02/02） |

用户所问"到完成正式版游戏的大阶段"指**开发里程碑**，下文详述。

任何系统从 DESIGN 转为"可交付实现"前必须具备：完整状态机 + 输入输出字段与类型 + 规则/公式与单位 + 边界与失败行为 + 命令/领域事件/幂等规则 + UI行为与反馈 + 单元测试及至少一个集成场景。

## 5. 正式版总验收（spec/06 §3–§6）

- **核心游戏性**：精品研发、类型专精、IP系列、发行协作四条路线均可行；比较 1/5/10 年存活率与收益分布。
- **经济校准**：破产率与破产时间分布、首款产品成败率、研发/销量收入比、营销边际回报、策略胜率、AI存活与市场集中度、极端值与参数敏感性、玩家可理解性。不得只用平均利润判断平衡。
- **UI验收**：每页覆盖正常/空/加载/错误/无权限/禁用/重复提交/超长名称/窗口缩小/键盘导航/大数据量；无真实测试记录不得标 PASS。
- **长期模拟**：多随机种子运行 1970–2026，检查公司数量、平台演进、市场集中、经济通胀、AI破产、玩家成长、事件频率；异常须定位原因，不得用全局倍率掩盖。

## 6. 首发范围边界（已 DECIDED，设计负责人不得擅自扩张）

首发主线：**游戏研发商 + 轻量发行经营**。明确 DEFERRED：玩家运营游戏平台、经营游戏引擎、硬件设计与制造、IPO/股票/复杂股权、并购与多事业部、多人联机/创意工坊、复杂国家税制劳动法（简化为地区成本与税率参数）、数百历史公司事件（精选）、深度授权/订阅/云服务生态。任何范围扩张必须说明新增玩家决策、与核心循环的因果联系、开发与测试成本及替代删减项，并由 Owner 决策。
