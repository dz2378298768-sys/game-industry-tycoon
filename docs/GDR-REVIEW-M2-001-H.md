# GDR-REVIEW-M2-001-H：输入端口修复规格 R1

| 属性 | 内容 |
|---|---|
| 对象 | `DESIGN-M2-001-H-MARKET-INPUTS.md` v1.0 |
| 结论 | **REVISE_REQUIRED** —— P1×3、P2×2 |
| 日期 | 2026-11-20 |

## 1. P1

**P1-1 “内容表”其实没有内容来源（架构一致性）**
`market_regions.json` 只有 id/名称/币种，`consumer_segments.json` 只有起始年。把人口、份额、兴趣写进 `market-inputs.ts` 的常量表，等于把内容伪装成代码常量：版本无法追溯、与 content 目录的单一权威冲突、以后调平衡会改代码。
**改法**：明确它属于 content 层且**就是权威表**（新增文件并在 content 索引导出），字段必须带单位与来源假设；同时写死“调平衡只改此表，不改公式/服务”。给出数值来源标注（本项目无第三方数据，标注为“设计初值，待 M5 校准”）。

**P1-2 旧档只回填一次会留下“僵尸产品”（兼容性）**
§4.3 只在 `restore` 回填。问题：回填后若玩家不保存就退出，下次读档又回填（幂等没问题），但 **`save` 前 UI 展示仍是 0**；更严重的是产品若在旧档里 `status='active'` 但已处 long_tail，回填会让它突然开始卖，现金与流水在“恢复瞬间”变化，玩家无法解释。
**改法**：回填只写认知度、不补历史销售；并在回填时记录 `ProductLifecycleChanged` 事件（reason=`awareness_backfill`），让“从哪天开始有销量”可追溯；规格写明“不回补读档前的销量与现金”。

**P1-3 校准协议没有“反例门槛”（可验收性）**
只写“目标 30%–45%”，没写不达标怎么办、也没写用哪套 provider 值判定。编码者可以把分享与兴趣调到 60% 就宣布通过，也可能调到 20% 后改夹具掩盖。
**改法**：写死“校准必须用生产 provider，不得改夹具；两轮内未达 25% 则回到设计调表并登记，不得改测量协议”；并加一条负向验收：把 `SEGMENT_PROFILE` 两段改成相同值，H07 必须变红（证明测试真的在测差异）。

## 2. P2

| 编号 | 问题 | 改法 |
|---|---|---|
| P2-1 | `store.init()` 注入 provider，但 `new GameWorld(seed)` 仍是 NULL，两个入口行为不同，容易误用 | 规格明确“生产仅允许 `createGameWorld()` 工厂”，`init/restore` 都走它；测试可显式用 NULL |
| P2-2 | `stableProductKey` 用 name，玩家改名会不会变 | 产品名上市后不可变，写死“name 上市后只读”；若未来开放改名，key 改用 `sourceProjectId` 的稳定哈希 |

## 3. 八维

可行性 通过｜游戏性 待验（需看真实销量曲线）｜完整性 **不通过**（P1-1/2）｜一致性 **不通过**（P1-1/P2-1）｜数值 **不通过**（P1-3）｜体验闭环 待补（回填事件）｜异常 通过｜可验收 **不通过**（P1-3）

## 4. 结论

P1×3 + P2×2 → v1.1 后进 R2。
