## 3. 产品目标与首版边界

### 3.1 产品目标

《游戏产业大亨》是一款围绕“经营一家游戏公司并持续做出产品决策”的模拟经营游戏。玩家应当通过有限资金、团队能力、产品创意、开发质量、市场定位和上市结果形成可理解的经营故事。

核心体验循环为：

`观察公司状态 → 选择产品方向 → 组建与分配团队 → 推进开发 → 处理质量/时间/现金风险 → 交付与上市 → 读取市场反馈 → 调整下一款产品`

每个循环必须满足四个顶层原则：

- 玩家真实完成过关键操作，而不是只通过测试函数证明存在。
- 每次关键点击都有可理解的反馈、状态变化或失败原因。
- 结果来自真实内核计算，UI 不以显示层数值掩盖规则缺陷。
- 非法状态 fail-closed；不能把错误状态长期留在可继续经营的路径中。

### 3.2 首版承诺

首版范围被定义为：**一轮完整产品闭环 + 第二款产品的决策入口**。这意味着首版必须能让玩家完成第一款产品从立项到上市，并在结果反馈后看到下一款产品的经营选择入口。

首版应保留：

- 单工作室经营与基础现金流。
- 产品创建的最小表达（模块、内容包、受众映射和派生反馈）。
- 团队/人才、项目推进、质量与交付、上市与销售的可验证接线。
- 统一账本、存档恢复、失败原因和关键决策反馈。
- 第二款产品的决策入口，不要求在首版完成全部产业生态。

### 3.3 首版明确不承诺

以下内容保留在 P2 及以后，不能为了“看起来完整”提前塞入 P1：

- 多公司全面竞争、复杂发行网络和全球产业生态。
- VisionDirectory 中尚未被阶段任务吸收的长期主题。
- 不能为首版闭环提供直接决策价值的细分现实产业流程。
- 在核心闭环未通过体验验收前新增的独立大系统。

## 4. 阶段路线与目标

P0–P7 是唯一的正式阶段验收体系；G0–G6 是执行里程碑；REC 是当前恢复阶段的串行任务编号。G 阶段关闭不自动等于对应 P 阶段通过。

| 阶段 | 目标 | 关键出口 | 当前状态 |

| P0 | 设计基线、工程边界和核心规则稳定 | 规则可追溯、依赖清楚、工程可运行 | 已完成 |

| P2 | 产品与市场深度 | 不同产品设计和经营策略产生明显差异 | 未开始 |

### 4.1 P1 的阶段门禁

P1 必须通过五道门：设计验收、工程验收、界面验收、体验验收、模拟/数值验收。以下任一项未闭合，P1 只能保持 `STAGE_FIX` 或 `STAGE_BLOCKED`：

- 真实玩家无法完成第一款产品的完整操作链。
- UI 点击不产生对应的内核变化，或测试通过但真实功能不存在。
- 交付失败没有逐条原因，返工成本不能在确认前看到。
- 现金、薪资、承诺或上市收入的计算不来自统一账本。
- 存档往返后关键状态不一致。
- 规格与实现存在未登记的 OPEN，或使用旧口径覆盖新裁定。

### 5.5 设计确认到任务的追踪规则

每条新增设计要求登记 `DES-<领域>-<序号>`，记录来源章节、玩家可见结果、系统/数据连接、阶段、依赖任务、验收场景、证据位置和状态。状态只允许 `MAPPED → SPEC_READY → IMPLEMENTED → VERIFIED`，存在冲突则为 `BLOCKED` 并关联 ADJ。阶段评审时逐条检查：未映射不得派工；未有验收场景不得标实现完成；测试通过但缺玩家可见证据时不得标体验 VERIFIED。当前三循环追踪表及后续工作包以 REC-05~12 台账为准；新 P2+ 项在对应阶段启动时拆成独立任务卡并估算。

## 6. 统一实现流程

### 6.1 任务生命周期

`IDEA → TRIAGED → SPEC_READY → DESIGN_REVIEW → READY_FOR_CODE → IN_PROGRESS → CODE_REVIEW → INTEGRATION → ACCEPTED / FIX / BLOCKED`

状态变更必须有负责人、证据位置和下一步；只在聊天中说“完成”不能关闭任务。

### 6.2 L1/L2/L3 分级

| 等级 | 适用范围 | 必要流程 |
|---|---|---|
| L1 | 单文件、低风险、无核心规则和公共接口变化 | 主 AI 任务卡→实现→定向测试→主 AI 验收 |
| L2 | 常规功能、跨模块但边界清晰 | 组成批次；一次设计审核→并行实现→批量编码审核→批次集成→主 AI 验收；每个任务保留独立结论 |
| L3 | 跨系统核心规则、存档、长期模拟、重大 UI 闭环或高风险数值 | 专项规划→设计审核→分阶段编码→分阶段审核→体验/模拟评估→阶段验收 |

默认按 L2 处理，但先判断是否适合批次并行；不能为了省流程把 L2/L3 降成 L1，也不能把低风险 L1 强行套入完整串行链。

### 6.3 每个任务的最小交付包

任务卡必须写明：目标、范围、禁止项、依赖、规格版本、适用 ADJ、允许修改文件、验收标准、测试基线和交接对象。交付时必须给出修改文件、实际测试命令与结果、未解决问题、证据路径和后续动作。

### 6.4 V2.3 执行通道

- **FAST**：L1 低风险任务走“任务卡→实现→定向验证→主 AI 验收”；触发核心规则、公共接口、存档或阶段风险时升级。
- **STANDARD**：L2 相关任务组成 `BATCH-<编号>`，共用一次设计审核，按文件所有权并行实现，批量编码审核后统一集成；每个任务保留独立结论。
- **STRICT**：L3、财务、存档、核心规则、跨系统闭环和阶段出口继续走完整双闸门和专项评估。

主要编码工作流默认最多两条并行流。同一核心状态机、公共服务、账本入口或存档结构一次只允许一个写入流。批次说明卡落档于 `docs/tasks/BATCH-<编号>_<名称>.md`，记录依赖、接口、文件所有权、合并顺序和集成退出条件。

### 7.1 角色与权限

| 角色 | 责任 | 不得做的事 |
|---|---|---|
| 主 AI / 项目统筹 | 拆分任务、裁定冲突、维护基线、阶段验收 | 不能把独立审核结果冒充自己验证 |
| 设计 Agent | 编写规格、数据、状态、边界和验收场景 | 不得自审自关，不得擅改 Owner 裁定 |
| 设计审核 Agent | 独立检查完整性、一致性、可实现性 | 不得先看其他审核结论再迎合 |
| 编码 Agent | 按批准规格实现并补测试 | 不得扩大范围或改变未授权规则 |
| 编码审核 Agent | 检查实现、反证、测试真实性和回归 | 不得以全绿测试替代规格审核 |
| 体验/模拟评估 Agent | 在有运行版本时进行真实试玩或模拟 | 没有运行版本不得声称已试玩 |
| Owner | 批准范围、重大裁定、发布和外部权限 | 不把临时讨论当正式规格 |

### 7.2 派发与交接

主 AI 派发任务时必须附带“当前有效版本、禁止修改范围、证据要求、停止条件”。Agent 发现规格冲突、范围升级、环境异常或风险超出等级时，应立即停在当前边界并报告，不自行猜测关键规则。

交接报告至少包含：任务/批次 ID、当前状态、已完成项、修改文件、测试基线、审核结论、遗留问题、下一步、禁止重复执行的事项和证据路径。稳定信息只引用权威位置，不在多个报告中全文复制。

### 7.3 双闸门

设计审核和编码审核是独立闸门。`PASS_WITH_CONDITIONS` 只能在条件、责任人和复验方式明确时进入下一步；条件未复验不得标记 `ACCEPTED`。主 AI 负责综合裁定，但不得取消必要的独立审核。

## 8. 项目管理标准

### 8.1 单一台账

所有任务只在一个总台账中维护，字段包括：ID、阶段、等级、负责人、状态、依赖、规格版本、代码提交、测试证据、审核结论、风险、下一步。网页是台账的可视化入口，Markdown 是可审计记录。

### 8.2 变更与风险

- 新需求先进入 `IDEA`，不得直接插入当前编码批次。
- 改变核心规则、公共接口、存档或数值单位必须生成 ADJ，并回填受影响任务。
- 风险分为 blocker、critical、major、minor、observation；只要影响 P1 闭环或证据真实性，至少按 major 管理。
- 推迟事项必须写明原因、责任人、触发条件和回收阶段。

### 8.3 报告节奏

- 任务状态变化时更新项目快照和台账。
- 每个阶段结束时生成综合验收报告。
- 自动化播报只读取最新快照，不以旧网页或聊天摘要覆盖仓库事实。
- 每次恢复工作前先检查工作区、HEAD、测试基线和最近交接文档。
