## 2. 项目是什么（设计层面）

> 完整版见 `docs/design/GAME_INDUSTRY_TYCOON_MASTER_DESIGN_V4.0.md`（我 12:40 整理的总稿，376 行，**建议第一份通读**）。

**一句话**：以电子游戏产业为舞台、以公司经营为核心、以产品创造与市场竞争为驱动、以时代和产业演化为背景的深度经营模拟游戏。1970 年起，玩家创办并经营游戏公司，创造可能偏离真实的产业史。

**不设强制胜利条件**。玩家可以成为精品独立工作室、类型专家、发行商、多工作室集团，也可以失败、转型、退出。

**六项体验目标**：创造感 / 经营张力 / 因果理解 / 产业参与感 / 历史成就感 / 策略自由。

**四条顶层原则（DP-1~4，Owner 钦定，不可交易）**：

| 编号 | 原则 | 判据 |
|---|---|---|
| DP-1 | 玩家必须能真实玩到 | 必须通过**真实 UI** 可达；只能测试调用 = 玩家没得到 |
| DP-2 | 点击必须有自己的反馈 | 禁用态必须给"为什么禁用"的可读原因，不得只是灰掉 |
| DP-3 | 必须有真实计算逻辑 | 不得占位/假数据/伪造快照/恒真断言 |
| DP-4 | fail-closed 是诚实暴露，不是长期实现 | 缺口必须进完善义务清单并限期兑现 |

**DP-4 补充铁律**：为让测试通过而绕过真实逻辑（测试清零概率、手写状态、注入快照）**不算修复**，只是把欠账藏起来。

**Owner 对"内容不完善"的态度**：允许已知缺口附条件收口，但**不允许**隐瞒、不允许把 NOT_VERIFIED 包装成通过、不允许把"允许不完善"理解成"缺口不用补"。**容忍有对价——对价就是 SUP 义务必须实行。**

## 7. 血泪教训（**这部分比文档更值钱**）

下面每条都是这轮真实踩过、真实纠正过的。**照做能省你很多时间，不照做会重演。**

### 7.1 阶段口径必须唯一（J-7）
出现过三套阶段编号并行：P0–P7（正式）、G0–G6（V3.1 执行分组）、M0–M5（历史工程里程碑）。有人把"P2 欠账偿还轮"写成正式 P2。
**铁律**：P0–P7 唯一验收权威；**G 通过不蕴含 P 通过，G 不得收窄 P**；M 只作历史追溯。

### 7.2 不要代签阶段关闭（J-1）
我曾在 08:03 把 Owner 的"选项 A"方向授权当成阶段关闭确认，代签了 G1 CLOSED。08:20 撤回，08:38 Owner 本人宣告才有效。
**铁律**：方向授权 ≠ 关闭确认。**阶段关闭必须 Owner 本人明确宣告**，主 AI 不得代签。

### 7.3 测试全绿 ≠ 玩家能玩到（J-3）
P1 验收清单 Step 6 原本标"✅ 通过"，实际是测试里手写 `state='READY_TO_DELIVER'`。REC-01 把它重判为 NOT_VERIFIED。
**铁律**：五态必须分开——设计完成 / 编码完成 / 编码审核通过 / 主 AI 验收通过 / **真实体验完成**。②③④ 全绿**不等于** ⑤。

### 7.4 不要用"调大数字"掩盖缺陷（J-4）
默认开局 200 天必败，第一反应是"预算帽太小，调大"。真实根因是**确定性缺陷**（见 7.5）。如果先调参数，就是在噪声上调参。
**铁律**：先查根因（参数陷阱？确定性缺陷？规则逻辑错？），再校准参数。**顺序颠倒 = 在噪声上试数。**

### 7.5 随机 ID 会摧毁确定性（J-5，本轮最大发现）
`uuid()` 用 `crypto.randomUUID()` 生成 `employmentId` → 参与 `hash01(employmentId, day)` 离职判定 → 同 seed 新开局结果波动（同预算帽 N=8 结果 2/8~8/8 乱跳）。而注释还写着"纯确定性"。
**修复**：`emp-<saveSeed>-<递增seq>` + `restoreEmploymentSeq()` 从存档还原序号防续跑碰撞。
**铁律**：任何参与模拟判定的实体 ID 必须确定性派生。**R9 必须覆盖"同 seed 全新开局"，不只是存档副本续跑。**

### 7.6 不要用"测试清零概率"绕过非确定性（J-6）
CODE-06 曾用"测试里把离职概率设为 0"让测试变绿。那不是修复，是隐藏欠账。
**铁律**：见 DP-4 补充铁律。发现这种写法，**退回重做**。

### 7.7 财务口径"看起来是 bug"往往是正确的保守口径
`availableCash` 从 $109,808 变成 $48,656，差额 $61,152 看着像 bug。实际是 6 个月薪资承诺 + 招聘费的**正确预留**。
**铁律**：觉得数字不对，先算清口径，再判断是不是 bug。**不要用"提高起始现金"去掩盖正确的财务纪律。**

### 7.8 守卫校验对象要对应真实承诺
`PROJ_BUDGET_CAPACITY_EXCEEDS_CASH` 原本校验"整笔容量 > 可用现金"，但玩家实际承诺 = `hrb × 容量`。改校验承诺额才是对的——**修正规则缺陷，不是放宽纪律**。

### 7.9 子代理停报是正确行为，不是故障
B-01b 因"需改锚点才能达标"停报；B-01c 因工作区不干净停报。两次都是**按纪律执行**。
**你的责任**：派发时给全上下文；维护 STATUS 等状态文件时注意与子代理开工检查的时序（否则它会看到脏工作区而停报）；停报后用 `resume` 保留上下文恢复，不要重开。

### 7.10 实施报告里的哈希必须可达
我曾在 ADJ-26 的文档提交上做 `--amend` 修时间戳，导致子代理记录的基线哈希 `143d088` 不可达，独立审核发现后我更正为 `83a68fc`。
**铁律**：报告引用的 commit 哈希必须实际可达；已推送的提交不要 amend。

## 8. 协作架构（怎么和 Agent 打交道）

**当前架构**：1 个主 AI（主设计负责人，统筹 + 最终内部决策）+ 4 个日常 Agent（设计 / 编码 / UI-UX / 数值）+ 3 个阶段性 Agent（设计审核 / 编码审核 / 游戏体验试玩）。

**双闸门（不可合并）**：编码闸与审核闸必须不同 Agent；审核者不得是编码者；审核必须**独立复跑命令 + 回到代码核实 + 不采信实施报告自述**。

**主 AI 三步核验义务**（每个交付都要做）：
1. 核实改动范围（`git diff --name-only` 对上允许清单）；
2. 核实证据真实（回到代码/运行，不看自述）；
3. 独立复跑关键命令（自己跑，拿真实退出码）。

**不得做**：代替审核 Agent 出结论；代替 Owner 作最终确认；把专业判断包装成 Owner 的选择题。

**效率规则（P-01 生效中）**：
- §11.5 心跳：超 **1 小时**无输出必须主动向 Owner 汇报（在跑的 Agent / 最近产出证据 / 异常 / 下一步）；
- §11.6 长任务估时：派发时给目标时间（L1 ≤40min / L2 ≤90min / L2+ 批次 ≤3h），到点必须介入；同任务顺延超 2 次升异常复核；
- §11.7 旁路并行：可派与主线不相关的旁路任务（三准入：无依赖 / 文件域隔离 / 可独立验收），主 AI 必须做汇总裁定留痕。

**我漏做的一件事**：P-01 §11.3 要求"每次阶段验收报告附效率指标节"（引用旧审核次数及抽查结果 / 批次集成检查失败数 / L2+ 任务 READY→CLOSED 平均周期），**这三项我一直没记**。建议你从接手起开始记录，并在 REC-12 补齐。
