## 2. DEF-001：NaN 预算校验

### 2.1 问题与整改

原实现仅在 `budgetTotalCapCents <= 0` 处拒绝，`NaN <= 0` 为 `false`，因此 NaN 预算可以通过；随后 `budgetTotalCapCents / 1_000_000` 会污染工作量计算。

整改后预算入口规则（双入口，不只靠 UI）：

- 必须是 `number`；
- 必须 `Number.isFinite`（拒绝 `NaN`、`Infinity`、`-Infinity`）；
- 必须 `Number.isInteger`（拒绝小数）；
- 必须 `> 0`（拒绝 0 与负数）。

非法输入返回明确错误码 `PRJ_INVALID_BUDGET`，**不创建项目、不写入世界状态**。

### 2.2 修改文件

| 文件 | 改动 |
| --- | --- |
| `src/simulation/services/project-service.ts` | `create()` 预算校验改为有限正整数；`defaultWorkTotalByDiscipline()` 对非有限预算兜底，避免 NaN 工作量向上游渗漏 |
| `src/application/mediators/game-world.ts` | `createProject()` 在应用层入口先做同样校验，非法预算返回 `PRJ_INVALID_BUDGET` |
| `src/application/__tests__/input-guards.test.ts` | 新增 6 类非法预算参数化用例 + 1 条 `ProjectService` 直调用例 |

### 2.3 测试证据

`npx vitest run src/application/__tests__/input-guards.test.ts`（28 用例全过），新增：

- `拒绝非法预算 NaN / Infinity / -Infinity / 0 / -1 / 1500000.5，且不创建项目`
- `ProjectService 直接调用时同样拒绝 NaN 预算，且工作量不会变成 NaN`

断言：`result.success === false`、`errorCode === 'PRJ_INVALID_BUDGET'`、项目数量前后不变。

## 3. DEF-002：取消项目后的暂停状态

### 3.1 问题与整改

原 `cancel()` 直接改 `phase` 并写 `isPaused: true`，与规格冲突。规格 `08_设计补齐/01_项目状态机统一方案.md` 明确：`CANCELLED` 时 `isPaused` 必须为 `false`，且取消必须记录 `cancellationReason`。

整改后：

- `VALID_PROJECT_TRANSITIONS` 允许所有非终态 → `CANCELLED`（`LAUNCHED`、`CANCELLED` 仍不可取消）；
- `transitionProject()` 增加 `TransitionOptions.cancellationReason`，进入 `CANCELLED` 时强制 `isPaused = false` 并写入原因；进入 `LAUNCHED` 时也强制 `isPaused = false`；
- `ProjectService.cancel()` 不再手改字段，统一调用状态机；`GameWorld.cancelProject()` 传入当前 `dayIndex`，保证 `updatedAt` 正确；
- 取消后 `DailyScheduler.applyProjectWork()` 对 `CANCELLED` 直接跳过，不产生研发进度；日调度只处理在职员工，取消项目不再产生项目产出。

### 3.2 修改文件

| 文件 | 改动 |
| --- | --- |
| `src/simulation/systems/phase-rules.ts` | 转换表放开非终态→CANCELLED；`transitionProject` 处理取消/上市时的 `isPaused` 与原因 |
| `src/simulation/services/project-service.ts` | `cancel()` 改走状态机并接收 `dayIndex` |
| `src/application/mediators/game-world.ts` | `cancelProject()` 传 `dayIndex` |
| `src/simulation/__tests__/pause-auto-cancel.test.ts` | 新增 2 条取消一致性用例 |

### 3.3 测试证据

- `玩家主动取消：phase=CANCELLED、isPaused=false、原因写入`
- `已取消项目不能再次取消，也不能暂停/恢复`
- `自动取消后不再产生研发进度，团队分配保留但产出为 0`（同时覆盖 D-01 第 8 条）

## 4. D-01：连续暂停 60 天自动取消

### 4.1 规则映射

| 设计裁定要求 | 实现 | 证据 |
| --- | --- | --- |
| 进入暂停后开始累计 | `pause()` 将 `consecutivePauseDays = 0`；`applyPauseTimers` 每个完整日 +1 | 恢复/重暂停用例 |
| 每经过一个完整游戏日、当日保持暂停则 +1 | `DailyScheduler.executeDay` 在日推进时调用 `applyPauseTimers`（早于研发推进） | 59 天用例 |
| 第 59 天结束仍暂停 | 第 59 天计数 59，`phase=CONCEPT`、`isPaused=true` | 59 天用例 |
| 第 60 天当日调度触发取消 | 计数达 `TUNING.project.autoCancelAfterPausedDays=60` 当日转 `CANCELLED` | 60 天用例 |
| 必须经统一状态机 | 调用 `transitionProject(..., 'CANCELLED', ..., { cancellationReason: 'pause_timeout' })` | 60 天用例断言 `isPaused=false` |
| 60 天前恢复立即清零 | `resume()` 将计数重置为 0 | 第 59 天恢复用例 |
| 再次暂停从 0 累计 | `pause()` 重置 | 重暂停 10 天用例 |
| 取消后无研发进度/人员投入/项目结算 | 状态机终态 + `applyProjectWork` 跳过 | 取消后工作量不变用例 |

## 6. TR-01：幂等键生命周期

### 6.1 规则（整改后）

| 阶段 | 规则 |
| --- | --- |
| 创建 | `postTransaction` / `reverseTransaction` 成功入账时写入 `idempotencyKey → transactionId` |
| 保留 | **整个存档生命周期保留，不做过期清理** |
| 过期 | 无过期（此前“30 天 + ≥1024 键才触发”的清理已删除） |
| 清理 | 仅随存档重放重建；`replay()` 从交易流水重建索引 |
| 重放 | 同键再次提交返回 `success=true, idempotent=true`，不新增交易、不改余额 |

### 6.2 修改文件

- `src/simulation/services/finance-service.ts`：删除 `idempotencyDay`、`IDEMPOTENCY_RETENTION_DAYS`、`pruneIdempotency()` 及全部调用；`replay()` 重建索引保留。
- `src/simulation/__tests__/finance-service.test.ts`：新增 2 条用例。

### 6.3 重复交易风险分析

原逻辑仅在索引 ≥1024 且键龄 >30 天时清理。月度薪资等键每 30 天复用一次，一旦被清理，下一次重放会再次扣款；跨读档时索引由 `replay()` 重建，不会丢失，但运行期清理仍可能造成重复入账。改为永久保留后：索引规模与交易流水同阶（一交易一键），不构成额外内存风险；重复提交与异常重试均被拦截。

### 6.4 测试证据

- `幂等键不因时间窗口过期而失效（TR-01）`：day 0 入账后，day 1100 同键重放 → `idempotent=true`，交易数仍为 2，余额不变。
- `读档重放后幂等键仍然有效（TR-01 跨存档）`：`replay()` 后同键提交仍被拦截。
