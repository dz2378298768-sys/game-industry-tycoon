## 1. 为什么需要阶段审核（而不是逐任务审核相加）

逐任务 PASS 只证明"每个任务按各自规格完成"，不证明：

- 任务之间的**集成**真的通了（例如 001-C 的耗尽判定 + 001-E 的横幅 + D-01 的 60 天计数是否互相干扰）；
- **规格漂移**不存在（多轮整改后，代码与 DESIGN-G05 v1.5 是否仍然一致）；
- **文档与实现**没有分叉（台账声称的状态是否与 git 历史一致）。

阶段审核就是回答这三个问题。

## 3. 审核维度（六项）

### A. 规格一致性（代码 vs v1.5）
逐条抽查 DESIGN-G05 §3.1 公式、§3.2 分摊取整、§6 耗尽/恢复/终态、§7 幂等（含 `topupSeq` 分配、`resumeSeq` 换轮）、§10.1a 显示口径。**重点抓多轮整改后的漂移**：001-C 的 `resumeSeq`、001-D 的 seq、001-E 的 seq 初值与 runwayDays 是否都落在规格文本上。

### B. 集成正确性（跨任务）
必须实测（不得只看单测）：

1. 预算耗尽 → 追加 → 恢复 → 再次耗尽：事件是否每次产生（幂等键换轮）、横幅是否重现、`resumeSeq` 是否正确 +1；
2. 手动暂停 → 60 天超时取消：`cancellationReason='pause_timeout'`、`isPaused=false`、过程态字段是否清空；
3. 预算耗尽暂停 → 60 天超时：`cancellationReason` 仍为 `pause_timeout`（**不得**是 `budget_exhausted`）；
4. 工资分摊跨项目：一笔现金交易、多条分摊、Σ = 工资额（最大余数法）；
5. 存档读回：`remainingCap = totalCap - committed - spent` 校验生效；公式不符拒绝加载且不覆盖当前运行态。

### C. 测试证据质量
- 用例总数与台账是否一致（当前预期 ≥ 145）；
- 是否存在"把缺口锁为期望值"的用例（001-E N-5 已出现过）；
- 是否有 skip/todo；
- 关键路径是否有非全 mock 的集成断言。

### D. 文档与实现一致性
- 台账任务状态与 `git log` 是否对应；
- 是否有"声称已实现但代码不存在"的项（历史 Δ-01~Δ-07 教训）；
- 截图/走查记录是否真实（可复跑同一构建）。

### E. 范围合规
- `spec/` 零改动（`git diff <base>..HEAD -- spec/` 为空）；
- 无 M2 功能夹带（无销售/退款/营销页面与服务）；
- `tuning.ts` 未被擅自修改。

### F. 体验证据（不作技术判定，但须核验真实性）
- 试玩报告是否为真人样本（参与者数量、场景完成率、策略差异记录）；
- 走查是否覆盖 UI-WALKTHROUGH 的 5 条主链路；
- 若体验证据缺失或明显造假，判 `NOT_VERIFIED` 并说明。

## 4. 取证纪律

1. 在**干净工作区**取证：`git status` 必须无未提交改动；必要时用 `git worktree add /tmp/audit-m11 <SHA>` 隔离，避免并行污染（本项目已发生过一次）。
2. 亲自跑四命令：`npm run typecheck`、`npm run lint:check`（无 `lint` 脚本）、`npx vitest run`、`npm run build`，记录真实输出。
3. 集成场景尽量用脚本/真实浏览器复现，不依赖他人截图。
4. 不改代码、不改规格、不替编码者修复。发现问题只记录并要求整改。

---

## 5. 结论口径

只用：`PASS` / `PASS_WITH_NOTES` / `FAIL` / `BLOCKED` / `NOT_VERIFIED`。

- `BLOCKED`：取证条件不满足（如工作区污染、构建不可复现）；
- `NOT_VERIFIED`：某维度无法验证（如体验证据缺失）；
- **不得**因"单任务都 PASS"直接给阶段 PASS。
