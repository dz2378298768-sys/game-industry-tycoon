## 0. 本规格的立场与阅读方式

### 0.1 一句话主张

产品设计系统的唯一职责，是**把玩家做出的若干个离散设计选择，转换成一组可被研发、市场与档案三个下游系统消费的结构化事实**；它不做销售计算，不做团队排产，也不做完整度裁判。

### 0.2 一条核心原则

> **设计选择必须同时产生"成本侧后果"和"市场侧后果"，且两条后果不能互相抵消。**

若某个设计选项只增加成本而不改变市场匹配（或反之），它就是无效参数，不得进入设计项。这条原则是对基线 §7.2「高级深度设计必须改变工作量、技术要求、受众匹配或产品表现」的可执行化。

### 0.3 已做的六项主动取舍（阅读本文档时请先看这里）

| # | 取舍 | 放弃的方案 | 理由 |
|---|---|---|---|
| T1 | **模块实例即单位**：同一模板可多次装配为不同实例（如"战斗"与"驾驶"都是战斗域但不同数值档） | 每个模块模板只能装一次 | 一次性排除会强迫玩家在"多类型混搭"上失去表达力，与 P2「相同类型不同玩法组合可形成不同受众」冲突 |
| T2 | **影响力分四通道独立输出**（工作量/技能负载/技术门槛/市场匹配），不合成"设计价值分" | 合成一个设计综合评分 | 基线红线 §14「不用单一综合分数掩盖产品质量、完整度和市场匹配的差异」 |
| T3 | **废弃无返工**：设计项在锁定后不可删除，只能"停用"（Deactivating） | 允许研发中删模块并全额返还 | 删除会伪造"没做过的工作"，破坏因果可追溯性；停用保留沉没成本 |
| T4 | **新增即返工且不可自动批准**：执行中变更必产生返工，费用"分档可估"但**实际值在任务推进时才确定** | 返工费用精确预估并锁死 | 精确预估会诱导玩家寻找"最优点击顺序"，把设计决策退化为数值优化 |
| T5 | **首版新类型生成只做"命名 + 标签 + 识别"**，不做新机制生成、不做新品类核心循环 | 动态生成全新机制的玩法概念 | 基线与阶段规划均要求逐步开放；过早承诺会拖垮 P1/P2 |
| T6 | **估算一律给区间**，显示为"低/中/高"带宽而非单值 | 显示精确工期/成本 | 与系统地图 §6「预测必须显示区间、更新时间和关键假设」一致 |

## 1. 系统目标与玩家体验目标

### 1.1 系统目标（可判定）

| 编号 | 目标 | 判定方式 |
|---|---|---|
| G1 | 让玩家设计的每一个产品在结构上可区分 | 任意两份成功的 `ProductBlueprint` 至少在 1 个 `differentiating` 维度上不同（判定见 §5.5） |
| G2 | 让设计决策产生可解释的生产后果 | 任一代价变化，均可回溯到具体的 `SlotBinding` / `ModuleInstance` / `OptionSelection` |
| G3 | 让设计决策产生可解释的市场侧后果 | 系统输出 `MarketAppealProfile`，D-04 可直接消费，无需二次解释 |
| G4 | 替代 V2.1.7 的"规模参数 + 复杂度分" | 不存在的字段：`scale`、`complexityScore`；规模仅作为预设（`BlueprintPreset`） |
| G5 | 让研发中改设计有代价且可追溯 | 所有变更产生 `DesignChangeRecord`，关联 `ReworkTask` 与成本 |
| G6 | 让产品设计成为长期资产 | 蓝图锁定后进入产品档案，可被续作/更新引用（D-07 接口） |

### 1.2 玩家体验目标

| 编号 | 体验 | 对应的机制抓手 | 反例（必须避免） |
|---|---|---|---|
| X1 | **创造感**：我造的是"一款有性格的游戏" | 定位层 6 个差异化维度 + 玩法槽 + 标志性卖点（最多 3 个） | 玩家只调预算和工期 |
| X2 | **取舍感**：加了就得减 | 人力资源预算 `HRB`（§6.2）、依赖代价、范围上限 | 无成本地堆模块 |
| X3 | **可预期又不可预测**：大方向可估，细节靠团队 | 设计意图（玩家定）× 实现质量（团队定）分离 | 玩家直接看到"最终评分 87" |
| X4 | **品味责任**：市场不接受不是 bug | 市场匹配来自"玩家宣称受众"与"实际模块构成"的差距 | 系统自动选最优受众 |
| X5 | **局部失手的痛感**：一个错误决策拖住整个项目 | 关键路径与技能瓶颈（§6.3） | 全模块平均拉平，无局部失败 |

### 1.3 与基线核心体验的对应

- 创造感（基线 §2.3）→ X1，落在 §4.2 定位层与 §4.4 玩法层。
- 经营张力（§2.3）→ X2，落在 §6.2 人力资源预算与 §6.3 瓶颈。
- 因果理解（§2.3）→ G2/G3，落在 §6 全节与 §9.3 解释面板。

## 3. 系统在整体架构中的位置

### 3.1 数据流方向（单向）

```
市场洞察 + 技术可用性 + 创意种子
        ↓（玩家）
   ProductBlueprint（设计权威）
        ↓ DesignVersionSnapshot（锁定快照）
   Project（执行权威）——引用快照，不反向改蓝图
        ↓ WorkloadEstimate / SkillDemand / TechRequirement
   WorkPackage / 团队执行 → Build → Product
        ↓ Product.attributeProfile
   D-04 市场与消费者
```

### 3.2 权威归属（对齐系统地图 §2.2）

- **设计权威**：`ProductBlueprint` 拥有定位与玩法构成本身。
- **执行权威**：`Project` 只引用某个 `DesignVersionSnapshot`，执行期间的"实现现状"由 Project 记录，不得回写蓝图。
- **估算权威**：所有 `Estimate` 都是**派生只读对象**，由蓝图 + 外部输入（技术/人才/市场）在当前时刻重算；不得作为蓝图字段持久化为"事实"。
- **档案权威**：产品上市后的档案由 D-07 持有；蓝图在锁定后进入只读冻结态供其引用。

## 4. 核心实体与数据结构

> 约定：所有实体字段以表列出；`类型` 为逻辑类型（int / decimal / enum / ref / list / map）；`约束` 为可程序化校验的规则编号（规则定义见 §5）。ID 均为稳定不可变标识。

### 4.1 实体总览

| 实体 | 职责 | 生命周期 |
|---|---|---|
| `ProductBlueprint` | 产品设计方案根对象（身份 + 当前设计版本指针） | 创建 → 迭代 → 锁定 → 归档 |
| `BlueprintVersion` | 设计版本（可编辑单元） | 草稿 → 评审 → 锁定 → 执行中 → 返工 → 完成/废弃 |
| `PositioningProfile` | 定位层字段集合 | 随版本 |
| `GameplaySlot` | 玩法层槽位（结构位） | 随版本 |
| `ModuleInstance` | 装配到槽位的模块实例 | 随版本，可停用 |
| `ModuleTemplate` | 模块库模板（策划数据） | 静态 |
| `ContentPack` | 内容包（关卡/剧情的量级档） | 静态 + 选择 |
| `CombineRule` / `RequireRule` / `ConflictRule` | 组合规则（数据驱动） | 静态 |
| `DesignVersionSnapshot` | 锁定快照（不可变） | 生成后不可变 |
| `DesignChangeRecord` | 设计变更记录 | 追加 |
| `ReworkTask` | 返工任务 | 生成 → 完成 |
| `EstimateBundle` | 派生估算集合 | 临时/缓存 |
| `MarketAppealProfile` | 市场吸引力画像（输出） | 派生 |
| `ModuleArchetype` | 新子类型/类型识别结果 | 派生 + 可提升为数据 |
| `BlueprintPreset` | 预设（替代旧"规模参数"） | 静态 |

### 4.2 `ProductBlueprint`

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `blueprintId` | id | 蓝图唯一标识，产品一生不变 | 不可变 |
| `ownerCompanyId` | ref Company | 归属企业 | R-ORG-1 |
| `workingTitle` | string(1–40) | 工作名称（可改） | 空则显示"未命名项目"，不得阻止保存草稿 |
| `finalTitle` | string(1–40) / null | 上市名称 | 锁定前可空；上市前必须非空 |
| `franchiseId` | ref Franchise / null | 所属系列 | 由产品运营/D-07 提供，本文档只存引用 |
| `currentVersionId` | ref BlueprintVersion | 当前编辑版本指针 | 指向最新草稿或执行中版本 |
| `lockedVersions` | list<ref BlueprintVersion> | 已锁定版本（按序） | 至少 0 个；追加式 |
| `originTemplateId` | ref ModuleTemplate / null | 创意来源（见 §4.6 构想来源） | 可为空 |
| `seedIdea` | string | 系统生成的"产品构想"文本（只读） | 创建时生成，不参与计算 |

### 4.3 `PositioningProfile`（定位层）

| 字段 | 类型 | 含义 | 是否差异化维度 | 约束 |
|---|---|---|---|---|
| `primaryTypeId` | ref GameplayArchetype(数据) | 主类型（如 RPG / 策略 / 模拟经营） | ✔ `differentiating` | 必须非空才能锁定版本 |
| `secondaryTypeIds` | list<ref>, ≤2 | 次类型 | ✔ | 不得与主类型重复；组合规则 §5.3 |
| `settingIds` | list<ref SettingTag>, 1–3 | 题材 | ✔ | 时代可用性检查（D-06/P4） |
| `perspectiveId` | enum{side_scroll, top_down, isometric, first_person, third_person, text} | 视角 | ✔ | 与技术门槛挂钩（§6.4） |
| `structureId` | enum{linear, open_zone, sandbox, level_based, roguelike, persistent_online_scope_out} | 结构 | ✔ | `persistent_online` 标 `REJECTED`（联机不进入当前规划） |
| `targetSegmentClaims` | list<ref SegmentTag>, 1–3 | **玩家宣称**的目标受众标签 | ✔ | D-04 提供标签词表；玩家只能宣称，不能直接选群体 |
| `sellingPoints` | list<ref USPId>, 1–3 条 | 卖点 | ✔ | 每条卖点须由蓝图内某个模块/选项支持（§5.4 规则 R-COM-7） |
| `platformTargets` | list<ref Platform>, ≥1 | 目标平台 | ✘（非差异化，但影响成本） | 平台存在性由平台系统校验 |
| `commercialPositioning` | enum{premium, budget, free_to_play_later, subscription_later} | 商业定位 | ✘ | 当前只允许 `premium`（早期）；其余标 `DEFERRED`，枚举保留占位 |
| `presetId` | ref BlueprintPreset / null | 起点预设 | ✘ | 创建后即失效，不再参与计算 |

**关键裁定（DESIGN_BASELINE）**：定位层只有 7 个 `differentiating` 维度参与"可区分性判定"（§5.5）。平台与商业定位不计入区分维度——他们影响**成本与可及性**，不影响"这是什么游戏"。

**已撤除的旧字段（REWORK）**：`scale`（规模 1–5）、`complexityScore`。规模由"槽位数量 + 模块档位 + 内容包档位"自然导出；复杂度由四个估算通道分别表达。**禁止**在实现中重新引入单一规模或复杂度字段。

### 4.4 `GameplaySlot`（玩法层结构位）

槽位是玩家**看得见的"骨架"**，模块填进去。

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `slotId` | id | 槽位实例 ID | |
| `slotKind` | ref SlotKind(数据) | 槽位种类（核心循环/支撑系统/内容承载/呈现/成长/社交单机向） | 由模板或类型定义 |
| `requiredForType` | bool | 对当前主类型是否必选 | 由类型定义（D-02 会补充完整度语义，本文档只标"必选槽"） |
| `domainAcceptance` | list<ref GameplayDomain> | 此槽接受的玩法域 | 类型定义 |
| `maxInstances` | int | 若多实例槽，允许的实例数上限 | 默认 1 |
| `bindings` | list<ref ModuleInstance> | 装配实例 | ≤ `maxInstances` |
| `isContentSlot` | bool | 是否内容承载槽（挂 ContentPack） | |
| `outsourcingEligible` | bool | 是否可作为外包单元（D-05 用） | 只标记，不实现 |

**槽位的开放难度（DESIGN_BASELINE）**：P1 仅开放 `core_loop ×1`、`support ×2`、`content ×1`；P2 扩展到 5–7 槽；P3+ 依内容库扩展。**槽位数量本身是范围控制手段**，不对玩家开放"增加槽位"能力（防止无成本加宽）。

### 4.5 `ModuleInstance`（模块实例）

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `instanceId` | id | 实例 ID | |
| `templateId` | ref ModuleTemplate | 所用模板 | 模板须属槽位接受域 |
| `slotId` | ref GameplaySlot | 所属槽 | R-MOD-1 |
| `displayLabel` | string(1–24) | 玩家命名的模块名（实例级） | 默认取模板名；**同名同域不同参数视为不同实例** |
| `domain` | ref GameplayDomain | 玩法域（战斗/探索/成长/叙事/经营/建造/社交/解谜/节奏/模拟） | 由模板决定，实例不可改 |

## 5. 业务规则

### 5.1 玩法域分类（分类体系）

两级：**玩法域（GameplayDomain）→ 模块模板（ModuleTemplate）**。

玩法域（10 个，DESIGN_BASELINE）：

| 域 | 定义边界 | 典型标签 | 不负责 |
|---|---|---|---|
| `combat` | 直接对抗冲突的规则 | real_time / turn_based | 难度曲线（属选项） |
| `exploration` | 空间/信息的发现与移动 | open / linear / procedural | 叙事（`narrative`） |
| `progression` | 能力/资源/阵营的成长 | leveling / gear / skill_tree | 数值平衡 |
| `narrative` | 剧情/角色/分支呈现 | branching / linear / environmental | 对话量（属 content） |
| `management` | 资源调度与效率优化 | economy_loop / scheduling | — |
| `building` | 空间/设施构造 | free_build / grid | — |
| `social_sp` | 单机内的角色/关系系统（非联机） | companion / faction | 联机（`REJECTED`） |
| `puzzle` | 规则约束下的求解 | logic / physics | — |
| `rhythm` | 时序输入 | music / action | — |
| `simulation` | 系统状态推演 | economy_sim / life_sim | — |

**约束 R-DOM-1**：一个 `ModuleInstance` 的域由模板决定，不可在实例上改域。跨域混搭通过"多个实例"实现，而不是"混合模块"。

### 5.2 定位字段之间的关系（类型/题材/视角/结构）

| 关系 | 规则 | 级别 |
|---|---|---|
| 类型 ↔ 槽位 | 主类型决定必选槽与槽位接受域 | 硬 |
| 类型 ↔ 模块 | 主类型的 `typeAffinity` 给出对某些域的"推荐强度"，影响 `MarketAppealProfile` 的 `genreFit`，**不阻止**装配 | 软 |
| 题材 ↔ 时代 | 题材标签带 `eraRange`；越界仅提示（历史可能不存在该题材） | 软 |
| 视角 ↔ 技术 | 视角带 `baseTechGate`（如 first_person 需更高技术） | 硬（技术门） |
| 结构 ↔ 内容 | `open_zone` / `sandbox` 要求 content 槽为 `sandbox_seed`，`roguelike` 要求 `procedural` 标签 | 硬 |
| 受众宣称 ↔ 模块 | 亲和差距 → `positioningFit` 指标（§6.5），影响市场匹配 | 软但高影响 |
| 卖点 ↔ 模块 | 卖点须有支撑（R-COM-7） | 硬 |
| 平台 ↔ 输入方式 | 视角+结构与平台输入能力（手柄/键鼠/触屏）兼容检查 | 硬（技术门） |

### 5.3 组合限制（CombineRule）

1. **槽位容量**：`len(slot.bindings) ≤ slot.maxInstances`（硬）。
2. **域接受**：`instance.domain ∈ slot.domainAcceptance`（硬）。
3. **时代可用**：`template.era.fromYear ≤ year ≤ template.era.toYear`（硬，P4 起强制）。
4. **互斥标签**：同一栈内出现互斥标签对时，`ConflictRule.severity=hard` 禁止（例：同一产品的"实时"与"回合"核心战斗不得同时为主核心，除非有 `hybrid` 标签切换项）。
5. **结构约束**：见 §5.2 结构行。
6. **内容包约束**：content 槽必须绑定 `ContentPack`，且 `compatibleDomains` 覆盖内容槽语义（硬）。
7. **卖点支撑**：每条 USP 至少被一个 active 模块或其选项支撑（硬，锁定校验）。
8. **区分度下限**（软）：若不满足 §5.5 的"可区分性"，给出"与其他近期产品高度相似"警告，不阻止锁定。

### 5.4 依赖与冲突判定（算法）

**输入**：`active` 的 `ModuleInstance` 集合 `M`、其 `optionSelections`、`positioning`。

**求解顺序**（确定性，顺序固定）：

1. `HardConflict` 检测：对每对 `(a,b) ∈ M`，若满足 `ConflictRule` 且 `severity=hard` → 违规 `E-CONFLICT`。
2. `SoftConflict` 检测：同上，`severity=soft` → 违规 `W-CONFLICT`，并写入 `RiskProfile.synergyPenalty`。
3. `RequireRule` 解析（见算法 R1）：
   - 按 `severity` 降序处理（hard 先）；
   - 对每个 `subject`（模板或选项或卖点），检查 `requires` 是否满足；
   - 若未满足且 `hard` → `E-DEP`；`soft` → `W-DEP` 并计入 `penalty`。
4. 依赖链闭包：`RequireRule` 的 `requires` 可能再引依赖（如 A 需 B，B 需 C）。**判定为传递闭包**，若闭包内出现环 → 违规 `E-CYCLE`（§10.2）。
5. 输出：`ViolationSet`（含每个违规的 `ruleId`、涉及实例、建议修复方向）。

**算法 R1（RequireRule 求值）**

```
for rule in rules sorted by severity(hard first):
    for subject in active_subjects_matching(rule.subject):
        satisfied = all(req in requires : exists_active_support(req))
        if not satisfied:
            emit violation(rule, subject)
```
`exists_active_support(req)` 定义：`req` 为模板 → 存在 active 实例且 `templateId == req`；为标签 → 存在 active 实例带该 `combineTag`；为选项 → 存在实例选择该 option。

**重要裁定（DESIGN_BASELINE）**：依赖只做**检查**，不做**自动补全**。系统不得自动替玩家添加模块——自动补全会掩盖设计决策。

### 5.5 可区分性判定（G1 的落地）

两个蓝图 `A`、`B` 在 `differentiating` 维度集合 D = {primaryType, secondaryTypes(集合), settingIds(集合), perspective, structure, targetSegmentClaims(集合), sellingPoints(集合)} 上比较。

- 若 `∀d ∈ D : A.d == B.d` → 判定 A、B 为同一设计（生成 `W-SIMILAR`）。
- 只要一个维度不同即视为不同设计，但**同类相似度高**（≥ 5/7 维度相同）时给出"与《X》结构高度相似"提示，供玩家判断差异化。

### 5.6 版本提升规则

- 新锁定版本若与上一锁定版本（`supersedesVersionId` 链上）无任何设计项差异 → 不产生新版本，只更新说明（避免版本膨胀）。
- 版本号在**每次锁定**递增；内部草稿迭代不递增 `versionNo`。

## 6. 计算公式

> 约定：所有常量以 `k_*` 表记，全部 `TUNING`。所有公式输出**区间**：给定 `Δ`（相对不确定度，默认 ±25%，TUNING），输出 `[v·(1-Δ), v·(1+Δ)]`。

### 6.1 计算总览

```
蓝图 ──► ①工作量(W)  ──► 项目排期/成本
      ├─► ②技能负载(S) ──► 团队需求/瓶颈
      ├─► ③技术门槛(T)  ──► 可行性/技术风险
      └─► ④市场匹配(A)  ──► D-04 需求换算
```

四个通道**互不合成单一分数**（T2）。

### 6.2 ① 工作量 `WorkloadEstimate`

对每个学科 `d ∈ {design, code, art, audio, qa}`：

```
W_d(instance i) = baseWorkUnits[i][d]
                × intensityCurve[i.intensity]
                × depthMultiplier(i.depthSelection)
                + Σ_{o ∈ optionSelections(i)} costDelta[o][d]

W_d(content c)   = workUnitsPerTier[c.compatibleDomain][d] × c.tier^α   (α≈0.85, TUNING)
```

产品级：

```
W_d^raw = Σ_{i} W_d(i) + Σ_{c} W_d(c)
```

**协同增益（避免全加法的"模块越多越线性"感）**：

```
W_d = W_d^raw × (1 − synergy(i 之间共享 tag 的比例) × k_syn) × HRB_scale
```

其中：
- `synergy` = `1 − |distinct tags across modules| / |total tag occurrences|`，取值 [0,1)；
- `k_syn` ∈ [0, 0.25]（TUNING）—— 表示共享技术/资产的复用收益；
- `HRB_scale` = f(人力资源预算 §6.2.1)。

**各学科不同步（关键）**：`synergy` 按学科不同：`code` 与 `art` 复用收益更大，`design` 与 `narrative` 复用收益接近 0（好故事不能复用代码）。**实现时 `k_syn` 为按学科向量**：`{design:0.05, code:0.22, art:0.18, audio:0.12, qa:0.15}`（TUNING）。

#### 6.2.1 人力资源预算 `HRB`（范围内生成本）

替代旧的"规模参数"。玩家在蓝图层设置 0–1 的 `HRB`（默认 0.5）：

```
HRB_scale = k_hrb_min + (k_hrb_max − k_hrb_min) × HRB^γ    (γ≈0.9, TUNING)
```

- `HRB → 0`：`HRB_scale ≈ 0.75`，代价是 `qualityCeiling` 下降（由 D-02/Project 消费，本文档只输出 `qualityCeilingBand`）；
- `HRB → 1`：`HRB_scale ≈ 1.6`，`qualityCeiling` 上升；
- **必须存在拐点收益递减**（`γ < 1`），否则玩家会被推向"永远拉满"。

> 此处 `HRB` 是**本项目的人力预算**，不是公司总预算；公司预算由企业经营系统管。二者不得混同（R-ORG-2）。

### 6.3 ② 技能负载 `SkillDemandProfile`

```
S_d = W_d / k_peakEfficiency[d]           # 该学科"需要多少人手同时在场"的峰值量
```

输出：
- `peakFraction[d] = S_d / ΣS` —— 学科占比；
- `peakWindow` —— 由 Project 依据 `Rule` 决定，本文档只要求 Project 在"关键路径"上参考 `peakFraction`。

**玩家可见表述**：「程序需求高」「美术需求极高」「叙事需求低」，不显示具体人数（人数是 Project 的事）。

### 6.4 ③ 技术门槛 `TechRequirement` 与 `RiskProfile`

**门槛集合**：

```
T = { template.techGates for active modules }
  ∪ { perspective.baseTechGate }
  ∪ { platform.techStandard gates }
  ∪ { structure.extraGates }
  ∪ { ⋃ option.techGates }
```

**不满足项**：`T_unsat = { g ∈ T : capability(g) < g.minCapabilityLevel }`（`capability` 由 D-06 提供）。

**技术风险**（不满足项的加权）：

```
R_tech = 1 − exp(− Σ_{g∈T_unsat} k_tech · (1 − capability/min) )
```

取值 ∈ [0,1)；显著 → Project 显示"高风险技术，预计测试期缺陷率上升"（缺陷率公式归 Project/QA，本文档不定义）。

**协同风险（软冲突）**：

```
R_synergy = Σ softConflict.penalty  (归一化到 [0,1])
```

**范围风险**（超规模预警）：

```
R_scope = clamp( (W_total / W_baseline_type) / k_scope_max , 0, 1 )
```

`W_baseline_type` 为该主类型在当前时代的典型单产品工作量中位数（TUNING，按类型表）。`R_scope ≥ 0.8` 触发 `W-SCOPE`：系统提示"范围远超同类典型规模，预计交付周期显著延长"，**但不阻止**（玩家可自行承担风险）。

### 6.5 ④ 市场吸引力 `MarketAppealProfile`

本文档**只产出画像**，D-04 负责把画像换算成需求。输出字段：

| 字段 | 公式/来源 | 说明 |
|---|---|---|
| `affinity[SegmentTag]` | `Σ_i audienceAffinity[i.template][tag] × intensityWeight(i) + Σ option.affinityDelta` | 原始亲和 |
| `positioningFit` | `cosine(targetSegmentClaims 的亲和, 实际拓扑的亲和)` 的简化版：`1 − Jaccard 距离 × k_fit` | 宣称受众与真实构成本是否一致 |
| `uspCredibility[uspId]` | `支撑强度 / 宣称强度`，支撑强度来自支撑模块的 `intensity` 与选项 | 卖点是否"吹得动" |
| `noveltyNote` | 与近 N 个同类型产品的相似度（来自 `ModuleArchetype` 判定） | 只做提示，不进入数值 |
| `contentVolumeBand` | 由 `Σ c.tier` 映射到 低/中/高（**供 D-02 完整度用**，本文档不做判断） | |

**红线**：`MarketAppealProfile` **不得**包含任何"预计销量/预计评分"字段。销量属于 D-04 + 产品运营。

### 6.6 公式的确定性要求

- 所有公式**纯函数**：同输入（含 `RandomService` 派生子流种子）必得同输出。
- 任何公式变更需版本化（`formulaVersion`），存档记录版本以支持回溯重放。
- 区间来源必须可分离：`Δ_base`（模型不确定度）+ `Δ_team`（团队能力不确定度，来自 Project）——两者分别显示，不得合并成一个"误差"。

### 7.1 设计版本状态机

状态：
`DRAFT`（草稿）、`IN_REVIEW`（评审/校验中）、`LOCKED`（已锁定，待立项或待执行）、`EXECUTING`（执行中）、`REWORK`（返工中）、`COMPLETED`（对应项目已交付）、`ABANDONED`（废弃）。

```
                 ┌─────────────(玩家放弃)──────────────┐
                 ▼                                     │
   [DRAFT] ──fix──► [DRAFT]                            │
      │                                                │
      │ request_lock                                    │
      ▼                                                │
  [IN_REVIEW] ──校验通过 & 玩家确认──► [LOCKED]         │
      │                                    │           │
      │ 校验失败/玩家取消                    │ 立项Project│
      └────────────► [DRAFT]                ▼           │
                                        [EXECUTING]     │
                                            │           │
                       ┌──设计变更──┐        │ 交付        │
                       ▼           │        ▼           │
                    [REWORK] ──完成──┘   [COMPLETED]    │
                                            │           │
                       任一状态 ──项目取消──► [ABANDONED]◄┘
```

### 7.2 转换表

| From | To | 触发 | 前置条件 | 副作用/事件 |
|---|---|---|---|---|
| DRAFT | DRAFT | 任一设计修改 | 玩家有编辑权 | 追加 `DesignChangeRecord`（草稿级，不产生返工） |
| DRAFT | IN_REVIEW | `request_lock` | 必填项齐备（§5.3 硬规则） | 生成 `EvaluationSummary`；冻结编辑 |
| IN_REVIEW | LOCKED | 玩家确认（审核项全部为 W 级） | 无 `E-*` 违规 | 生成 `DesignVersionSnapshot`；`versionNo++` |
| IN_REVIEW | DRAFT | 校验失败/取消 | — | 保留草稿 |
| LOCKED | EXECUTING | Project 立项成功且绑定 `snapshotId` | 同企业 | 快照冻结；编辑入口关闭 |
| LOCKED | ABANDONED | 放弃 | — | 版本灰显 |
| EXECUTING | REWORK | 玩家在研发中提交设计变更并确认返工 | 见 §15 | 生成新 `DesignChangeRecord` + `ReworkTask`；`EXECUTING` 保持不变，另存“返工会话” |
| REWORK | EXECUTING（恢复设计一致性）| 返工完成 | `ReworkTask` 全完成 | 追加新 `BlueprintVersion`（`supersedes` 指向旧）并重新绑定 |
| EXECUTING | COMPLETED | 项目交付 | — | 锁定版本进入产品档案 |
| 任意 | ABANDONED | 项目取消/产品放弃 | — | 保留全部历史（不允许删除） |

**裁定（DESIGN_BASELINE）**：`REWORK` 不是独立的状态机分支，而是"EXECUTING + 返工会话"的呈现式标签。目的是避免出现"版本一半在旧快照一半在新快照"的权威歧义——**快照始终只有一份被 Project 引用**，新快照在返工完成时才切换（§15.3）。

### 7.3 蓝图层状态

`ProductBlueprint.state ∈ {active, archived}`。
- `active`：可创建新版本；
- `archived`：产品退役或公司放弃，只能查看。

## 9. 玩家操作方式与自动化行为

### 9.1 玩家定（有决策意义）

| 决策 | 层级 | 代价 |
|---|---|---|
| 主类型 + 次类型 | 战略级 | 决定必选槽与受众 |
| 题材、视角、结构 | 战略级 | 技术门槛、内容结构 |
| 宣称受众 | 战略级 | 影响 `positioningFit` |
| 卖点（≤3） | 战术级 | 必须被支撑，否则可信度低 |
| 槽位内模块选择与命名 | 战术级 | 工作量、技能负载、亲和 |
| 强度档 1–5 | 战术级 | 成本非线性 |
| 深度档 + 选项 | 执行级 | 成本与风险微调 |
| `HRB` | 战术级 | 成本与质量上限 |
| 是否锁定、是否返工 | 闸门级 | 沉没成本 |

### 9.2 系统算（自动化）

- 工作量、技能负载、门槛、风险、画像；
- 违规检测与修复建议；
- `ModuleArchetype` 判定（命名 + 标签）；
- 与近期产品的相似度提示；
- 估算区间与置信度。

### 9.3 不自动化（红线）

- 不自动补依赖模块；
- 不自动替换冲突模块；
- 不自动选择受众或卖点；
- 不自动判定"应该锁定"。

### 9.4 玩家可见的解释（对齐系统地图 §6）

- 结果：估算区间（低/中/高）；
- 原因：前三个驱动因素（哪个模块、哪个选项、哪条协同）；
- 置信度：区分"模型不确定"和"团队不确定"；
- 影响：工期、成本、风险等级；
- 后续选择：可削减哪一项、代价是什么。

### 10.3 P-MODULE-LIB：模块浏览面板

- 筛选：玩法域、时代可用、技术可用性、槽位兼容、标签；
- 列表项：名称、域、强度曲线预览、技能负载标签、技术门槛标签、可用性状态；
- 不可用项**仍显示**但灰化 + 原因（"时代不可用""技术不足"），**允许**点击查看详情但不能装配（除非配置允许草案先行，见 §11.6）；
- 空状态：筛选无结果时提示"放宽筛选"。

### 10.4 P-ESTIMATE：影响估算

四个分区（工作量/技能/技术/市场），每区：
- 主值（低/中/高）；
- "较上次修改"的增量（+/-）；
- 主驱动因素前三（可点击定位到具体模块）；
- 置信度标签（"模型不确定±25%"、"团队不确定待定"）；
- 提示：不显示"销量预估"（红线）。

### 10.5 P-VALIDATION：校验结果

- 分两类：**阻断（E，红）**、**警告（W，黄）**；
- 每条：规则 ID、涉及模块、原因说明、建议操作（按钮直达对应槽位/选项）；
- 阻断项 > 0 时"D-LOCK 确认按钮"禁用；
- 空状态："无问题，可锁定"。

### 10.6 D-LOCK：锁定确认

- 摘要：定位 7 维、槽位数量、active 模块数、估算区间、风险等级；
- 阻断项列表（应为 0）；
- 警告项列表；
- 新类型识别结果（若有）："该组合接近全新子类型「X」"（见 §14）；
- 按钮：取消 / 锁定并生成快照；
- 锁定后跳转：立项页 / 返回工作台（只读）。

### 10.7 D-REWORK：返工确认（执行中变更）

- 变更摘要：新增/停用/改档/改选项；
- 沉没成本：受影响模块的已投入工作量（来自 Project）；
- 返工估算：低/中/高（分档，§15.2）；
- 风险提示：预计工期延长、质量影响区间；
- 按钮：取消 / 确认并开始返工 / 仅保存为"下一版草案"（不影响当前项目）；
- **"确认并开始返工"不可逆**，需二次确认。

### 10.8 N-ARCHETYPE：新类型提示（P3+ 起生效，见 §14）

- 只在使用 `ModuleArchetype` 提升为数据时显示；
- 内容：识别名、组成标签、判定依据（"现有类型库无匹配"）；
- 按钮：查看 / 暂不提升；
- **不得**显示"你创造了一个新品类"的文案（避免过度承诺）。

### 10.9 P-VERSION-HISTORY

- 时间线：版本号、锁定时间、变更摘要、关联 Project；
- 点击 → 只读快照；
- 空状态：仅 v1 时显示"尚无历史版本"。

### 10.10 导航与权限

## 11. 异常与边界处理

| 编号 | 情形 | 处理 |
|---|---|---|
| E-1 | 空组合（无任何 active 模块） | 草稿可保存；`request_lock` 时阻断 `E-EMPTY`（必选槽为空）。 |
| E-2 | 循环依赖 | 求值前先检测 `RequireRule` 的传递闭包；出现环 → `E-CYCLE` 并列出环路径。**不自动打破环**。 |
| E-3 | 硬冲突组合 | `E-CONFLICT`，阻断锁定；UI 高亮两个模块并提供"去替换"按钮。 |
| E-4 | 超规模 | `R_scope ≥ 0.8` → `W-SCOPE` 警告，不阻断；D-LOCK 必须显示"预计交付风险：高"。 |
| E-5 | 研发中改设计 | 走 §15 返工流程；不允许"无痕修改"。 |
| E-6 | 技术前提不满足但玩家仍要设计 | 草稿允许；锁定允许但强制生成"高风险"标记与 Project 侧风险提示（技术可能被开发出来也可能失败，符合"科技动态突破"）。**若 D-06 判定该技术在本时代不可能**（硬不可用），则阻断 `E-TECH`。 |
| E-7 | 时代不可用的模块 | 面板灰显；若玩家强行通过 API/旧存档带入 → 打开时校验并标记 `E-ERA`。 |
| E-8 | 同一槽位多实例超上限 | 阻断添加，按钮禁用 + 原因。 |
| E-9 | 卖点无支撑 | 锁定校验 `E-USP`；草稿警告。 |
| E-10 | 断言空值（必填未填） | `IN_REVIEW` 前必填校验，阻断。 |
| E-11 | 平台缺失 | 至少 1 个平台，否则阻断。 |
| E-12 | 版本冲突（两玩家/AI 同时编辑同一蓝图） | 单机可忽略；**若未来联机（DEFERRED）** 采用乐观锁 `payloadHash`，冲突时要求人工合并，不自动合并。 |
| E-13 | 蓝图被删除前已有锁定版本 | 禁止删除，只允许 `ABANDONED`/`archived`。 |
| E-14 | 数值溢出/超长文本 | 名称长度上限校验；`intensity` 越界拒绝。 |
| E-15 | 空内容包 | content 槽必须绑定，否则 `E-EMPTY-CONTENT`。 |
| E-16 | 选项组全空 | 允许（表示默认）；若选项组 `required=true` 则阻断 `E-OPT`。 |
| E-17 | 蓝图层级 `HRB=0` | 允许，但 `HRB_scale` 下限保护（§6.2.1），并提示质量上限降低。 |

**通用错误输出格式**（UI 与日志共用）：
`{ code, severity(E|W), ruleId, subjectIds[], message, suggestedAction }`

## 12. 存档要求

| 编号 | 要求 |
|---|---|
| S1 | `ProductBlueprint` / `BlueprintVersion` / `ModuleInstance` / `DesignVersionSnapshot` 全部持久化，含 `state`、`changeHistory`。 |

## 14. 模块组合产生新子类型/新类型的阶段边界

### 14.1 三级能力定义

| 级别 | 名称 | 能力 | 阶段 |
|---|---|---|---|
| L1 | **组合即类型** | 玩家自由组合已有模块；类型仅作为“定位标签”使用 | P1 |
| L2 | **子类型识别** | 系统从组合中**识别**出近似新子类型，给出名称与标签，允许作为**产品档案标签**（不影响核心机制生成） | P2 |
| L3 | **类型库扩展** | 识别结果可提升为**数据条目**（进入类型库，供 AI/后续玩家作为 `primaryTypeId` 选择），仍不生成新机制 | P3+ 且内容库 ≥ N 模板（OPEN-O2） |
| — | **机制生成** | 从零生成新玩法机制并自动定价 | **DEFERRED**（不在本文档承诺） |

### 14.2 判定算法（L2/L3 共用）

```
输入：active 模块集合 M 的 (domain, combineTags)、定位 7 维
1. 构造特征向量 V = [domain 分布, tag 计数, structure, perspective]
2. 对类型库中每个已有 GameplayArchetype 计算相似度 sim(A, V)
3. best = argmax sim
4. if best.sim ≥ τ_match (TUNING, 约 0.75): 归入 best（子类型，若存在该类的子类型表则继续匹配）
   elif best.sim ∈ [τ_novel_low, τ_match): 判定为"近似 new sub-type" → 生成 ModuleArchetype(provisional)
   else: 判定为"new archetype" → 生成 ModuleArchetype(provisional)
5. provisional 命名 = 规则模板："{主域词} + {结构词} + {核心标签词}"，需玩家确认命名
6. L2 只写档案标签；L3 才写入类型库
```

### 14.3 阶段边界判定规则（何时允许）

| 条件 | 允许的级别 |
|---|---|
| 内容库模板数 < N_min（OPEN） | 仅 L1 |
| N_min ≤ 模板数 < N_full | L1+L2 |
| 模板数 ≥ N_full 且 L2 连续 M 次识别稳定（相同或高度相似） | L3 |
| 任何阶段 | 不生成新机制 |

### 14.4 新类型提升的约束

- 提升后的类型必须至少有一个**核心槽接受域集合**与既有类型不冲突；否则拒绝提升并记录原因。
- 提升的类型最初状态为 `provisional`，只能作为次类型使用；累计 K 次成功产品（TUNING）后升级为可作主类型。
- **AI 与玩家共享类型库**；AI 创造的类型对玩家可见。

## 15. 设计版本与项目执行版本关联、返工规则

### 15.1 关联模型

```
Blueprint (1) ── (n) BlueprintVersion ── (0..1) DesignVersionSnapshot ── (1) Project
                                        └── (0..1) 为返工生成的新快照
```

- **Project 只能引用一个快照**；引用在返工完成时才切换到新快照（§15.3）。
- Project 记录其引用的 `snapshotId` 与 `formulaVersion`，以便重放。
- 蓝图版本与 Project 是 1:1（一个设计版本对应最多一个项目）；同一蓝图不同版本可对应不同项目（续作/复刻）。

### 15.2 返工触发与成本规则

**触发**：在 `EXECUTING` 状态下玩家修改设计项并确认返工。修改分五类：

| 类别 | 例子 | 是否返工 | 成本估算分档 |
|---|---|---|---|
| A 元数据 | 改显示名、改描述 | 否 | 0 |
| B 停用 | active → deactivated | 是（沉没不返还） | 已投入工作量全额沉没 + 少量“清理” |
| C 参数调整 | 改 intensity、改选项 | 是 | 按受影响模块 `ΔW_d × progress_d` 分档 |
| D 新增 | 新模块、新槽位绑定 | 是（且必为返工，T4） | 完整 `W_d(新)` + 集成成本 `k_integ × W_d(新)` |
| E 定位变更 | 改主类型/视角/结构/受众 | 是（且可能强制重估全局） | 全部受影响模块 `ΔW × progress` + `k_reposition` 全局惩罚 |

**成本公式（分档）**：

```
ReworkCost_mode ∈ {minimal, partial, full}  # 以区间呈现，实际值在返工推进时由 Project 落实
```

| 档 | 判定 | 有效工作量返还比例 | 附加 |
|---|---|---|---|
| `minimal` | 新增/停用小模块，`W_d(变更) < 10% W_total` | 已投入的 70% 可复用 | — |
| `partial` | 变更 10–40% | 已投入 50% 可复用 | 工期延长 5–15% |
| `full` | 变更 > 40% 或修改定位 | 已投入 20% 可复用 | 建议"新项目"并保留旧项目产物的存档 |

**返工计数**：每个 Project 记录 `reworkCount`；≥ `k_rework_limit`（TUNING，初始 3）后，UI 提示"项目返工次数过多，风险显著上升"，并在 Project 侧计入额外风险（Project 定）。

### 15.3 快照切换时机

- 返工开始：**保留旧快照为 `Project` 的权威**，生成 `ReworkTask` 指向"目标快照（草稿版）"；
- 返工完成：新快照生成，`Project.snapshotId` 切换；旧快照保留为历史；
- 返工中若玩家取消 → 丢弃目标快照，旧快照继续生效（不损失当前项目进度）。

> 该规则避免第 15 节和第 7.2 节产生歧义：**执行中始终有且仅有一个“生效快照”**。

### 15.4 研发中改设计的不可逆性

- 已停用的模块不可重新启用，只能通过“新增同类模块”替代（记录为不同 `instanceId`）。
- 已锁定的版本不可编辑，只可派生新版本。

### 15.5 变更与历史

每次变更生成 `DesignChangeRecord`：`changeId, versionId, category(A–E), diff(结构差异), requestedBy, requestedAt, reworkRequired(bool), reworkTaskIds[], sunkCostEstimate`。

## 18. 设计任务报告（TASK-P0-D01）

| 项 | 内容 |
|---|---|
| Task ID | TASK-P0-D01 |
| 设计规格版本 | V0.1（DESIGN_DRAFT，待设计审核） |
| 提交文件 | `/workspace/GameIndustryTycoon/docs/archive/design-specs-old/01_产品蓝图与玩法模块体系设计规格_V0.1.md` |
| 上游基线 | V3.0 总纲、系统地图、阶段规划、决策基线、迁移裁定 |
| 覆盖要求 | 2.3B 18 项全覆盖（§17.3） |

**各节要点**

1. **目标**：把“玩家设计选择”转成研发/市场/档案可消费的结构化事实；六个可判定目标 G1–G6。
2. **范围**：IN 9 项、OUT 10 项，与 D-02/D-04 的边界以判定表固化（§2.3），红线上禁止出现评价/销量/完整度作为本系统输出。
3. **实体**：12 类实体字段级定义；彻底移除 `scale` 与 `complexityScore`（REWORK）；新增 `BlueprintVersion` 版本化、`DesignVersionSnapshot` 不可变快照、`DesignChangeRecord` 变更记录。
4. **状态**：7 状态机；`REWORK` 定义为“执行中 + 返工会话”的呈现标签，保证任意时刻仅一个生效快照。
5. **规则**：10 个玩法域、槽位化装配、hard/soft 双层冲突与依赖、求值顺序固定、不自动补全；可区分性判定落为 7 维比较。
6. **公式**：四通道独立（工作量/技能/技术+风险/市场画像），工作量含学科差异化协同增益与 `HRB` 内生成本，风险 = 技术 + 协同 + 范围，全部给区间。
7. **接口**：单向数据流，权威归属明确（设计权威/执行权威/派生只读）。
8. **操作**：玩家定 9 类决策，系统算 6 类，红线 4 条不自动化。
9. **UI**：9 个页面/对话框结构级规格，含默认值、空/错/只读状态与跳转。
10. **异常**：17 条边界情形，统一错误格式。
11. **存档**：7 项要求，快照自包含、模板版本化、旧字段丢弃并记录迁移。
12. **性能**：编辑增量 <16ms、打开 <100ms、锁定 <250ms；不进每日 tick。
13. **测试**：18 个可验证场景 + 验收映射。
14. **新类型**：L1/L2/L3 三级，机制生成 DEFERRED；判定算法与阈值可调。
15. **返工**：五类变更、三档成本、快照切换时机、不可逆性、`reworkCount` 上限。

**关键取舍**：T1 模块实例作为单位；T2 四通道不合成综合分；T3 锁定后不可删除只可停用；T4 执行中新增必返工且不自动批准；T5 新类型首版只做识别；T6 估算一律给区间。

**未解决问题**：9 项 OPEN/TUNING（§16），集中在卖点量化、新类型阈值、模板派生流程、`HRB` 校准、与 D-02/D-04/D-05/D-06 的接口口径。

**建议审核关注点**

1. §6.2 的学科差异化 `k_syn` 是否会造成“程序/美术廉价化”的失衡（需模拟验证）；
2. §15.2 的返工档位判定阈值是否需要随项目规模动态化；
3. §10.2 的“已装模块不兼容时不自动删除”在类型切换场景下是否会造成过多手动操作；
4. §14 的 L3 阶段条件是否过于保守，是否会在 P3 阻碍 AI 企业创造新类型。
