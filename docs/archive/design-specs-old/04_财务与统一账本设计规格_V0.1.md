## 0. 一句话立场（最高原则）

**唯一现金入口**：企业现金只能在统一账本（`FinanceService.postTransaction`）因一笔 `Transaction` 入账/出账而变动；任何业务系统、UI、脚本都不得直接读写 `Company.cash`。现金余额是账本的**派生快照**，不是可写字段。

**破产是经营失败的因果结果，不是随机惩罚。** 玩家每一次失败都可追溯到一条链：承诺支出（招聘/租金/项目预算/合同）→ 跑道缩短 → 现金逼近预警线 → 有限补救窗口 → 未在窗口内改善 → 危机升级 → 破产。预警必须"可理解"（显示原因与倒计时），补救必须"可执行"（列出动作、代价、风险）。任何"凭空扣钱""随机破产""隐藏费用"均违反本规格（对齐基线 §12、§14 红线）。

## 1. 系统目标与玩家体验目标

### 1.1 系统目标

1. **权威账本**：为全游戏提供唯一、不可变、可审计、可重放的现金事实来源，封堵 V2.1.7 迁移分析 §2.3 所指"现金流无经营/投资/融资三分、无应收账款实体"缺口。
2. **因果可视化**：把"现金、利润、承诺支出、应收应付、项目投入、产品收入、合同义务、未来跑道"之间的关系建模为可解释数据（基线 §12）。
3. **危机可玩**：提供分级预警 + 有限补救窗口 + 有后果的重整，让失败成为可读的经营叙事而非黑箱（基线 §12/§13）。
4. **同源规则**：AI 企业与玩家共用账本与危机规则，AI 不得获得隐性现金、免费资金或更宽补救窗口（系统地图 §4.4、基线 §14）。

### 1.2 玩家体验目标（对齐基线 §13 四问）

| 界面四问 | 本系统回答 |
|---|---|
| 当前发生了什么？ | 现金余额、现金警告横幅、当前危机等级 |
| 为什么发生？ | 每笔交易带来源 `referenceId` 与原因码；跑道变化显示"招聘/追加预算/返工"等驱动 |
| 有哪些有意义的选择？ | 危机面板列出可用补救动作（缩减范围/暂停项目/裁员/转租/终止合同/出售资产/寻求预付款/重整） |
| 代价与风险？ | 每个补救动作显示对现金、跑道、债务、声誉、人才、控制权的影响预览 |

### 1.3 关键玩家价值（任务卡）

- 玩家能理解跑道，理解"追加预算/缩减范围"的代价（场景 A 步 6、场景 B 步 6）。
- 失败前有可识别预警（L1 现金警告 + L0 跑道预警）与可执行补救窗口。

### 3.7 CrisisLevel 枚举（危机等级）

`healthy` → `watch`（关注）→ `warning`（预警）→ `critical`（危急，开补救窗口）→ `restructuring`（重整中）→ `bankrupt`（破产）→ `sandbox_observe`（沙盒观察）。

- `watch`/`warning` 为"预警"；`critical` 为"补救窗口"；`restructuring`/`bankrupt` 对应破产流程；`sandbox_observe` 为失败后继续观察（基线 §12，玩家选择）。
- 与企业状态映射：`watch/warning/critical` 保持 `active`；`bankrupt` 对应 `status='bankrupt'`（现有实现）；`sandbox_observe` 为玩家可见的观察态，不改变世界继续运行。

### 3.8 原因码（reasonCodes，因果可追溯）

`LOW_RUNWAY`（跑道低于预警月数）、`LOW_CASH`（现金低于警告线）、`COMMITTED_EXCEEDS_CASH`（承诺支出超过可用现金）、`PAYABLE_OVERDUE`（应付逾期）、`NEGATIVE_CASH`（出现负现金）、`BUDGET_OVERRUN`（项目超支，消费 D-01 ratio）、`REWORK_SUNK`（返工沉没成本）。每个非健康态至少带一个原因码，供 UI"为什么发生"与档案下钻。

### 3.9 TransactionCategory（12 类，复用现有枚举）与现金流三分映射

现有 12 类（`enums/index.ts:L30-L42`）：`salary`、`office_rent`、`project_expense`、`marketing`、`sales_revenue`、`customer_refund`、`platform_fee`、`contract_payment`、`tax`、`advance`、`severance`、`asset_sale`。

| 类别 | `cashFlowType`（TUNING 映射，待校准） | 方向 |
|---|---|---|
| `salary` / `office_rent` / `marketing` / `project_expense` / `tax` / `platform_fee` / `customer_refund` | `operating` | 流出（refund 为收入冲减） |
| `sales_revenue` / `contract_payment`（收入侧） | `operating` | 流入 |
| `advance` | `financing`（P1 唯一融资流入） | 流入 |
| `asset_sale` | `investing` | 流入 |
| `severance` | `operating`（裁员一次性） | 流出 |
| `contract_payment`（付款侧） | `operating` | 流出 |

## 4. 状态与转换

### 4.1 承诺 → 实际交易 → 结算

```
BudgetCommitment(committed)
   │ 兑现事件（月薪计提 / 租金到期 / 项目里程碑 / 合同义务到期）
   ▼
postTransaction(...)  → 现金变动（唯一入口），link referenceId
   │ linkedTxIds += tx；realizedCents += |amountCents|
   ├─ realizedCents < amountCents → partially_realized
   └─ realizedCents = amountCents → realized
撤销（无兑现） → cancelled（不产生 Transaction，现金不变）
```

- `Payable/Receivable`：`open → partially_settled → settled`；到期未清 → `overdue`；放弃 → `written_off`（Need：`written_off` 不冲回已入账现金，仅停止后续兑现）。
- 所有状态迁移由账本服务在某个 `Transaction` 成功入账后同步更新，保持"单一事实"。

### 4.2 危机状态机与现有 BankruptcyPhase 映射

```
healthy
  ├─ 跑道/现金触发 → watch → warning
  └─ 跌破危急阈值 → critical（开补救窗口 remediationDeadline）
critical
  ├─ 玩家选"重整"且窗口内 → restructuring（phase=restructuring）
  ├─ 窗口内现金恢复到 recovery 线 → watch（带滞后滞回，§6.4）
  └─ 窗口耗尽 / 现金<0 未解 → bankrupt（phase=winddown）
restructuring
  ├─ 按重整方案兑现且满足恢复条件 → watch（带后果）
  └─ 失败 → bankrupt（phase=winddown）
bankrupt
  └─ 玩家选择"继续观察" → sandbox_observe（世界继续，玩家不再授权新支出）
```

**映射**：`restructuring` ↔ `BankruptcyPhase='restructuring'`；`bankrupt` ↔ `BankruptcyPhase='winddown'`。`watch/warning/critical` 不进入 `BankruptcyPhase`（仍 `active`）。`sandbox_observe` 为 P1 新增的玩家可见观察态，现有实现需扩展（标 `NEW`/`OPEN-F2` 与 M1.2 UI 对齐方式）。

### 4.3 状态迁移约束

- **S-FIN-1（动作点同步）**：危机升级、补救兑现、重整判定在触发动作提交点同步执行，不延迟到下一日批量（对齐 P0-B S3 精神）；但 L0 每日"财务检查"（P0-B §3.2 步 6）负责阈值探测与横幅刷新。
- **S-FIN-2（单一生效态）**：每公司至多一个 `active` `CrisisState`；迁移写入 `history`，不覆盖旧态。
- **S-FIN-3（同源）**：AI 企业用同一状态机与同一 `remediationWindowDays`，不得更宽或有豁免。

## 5. 业务规则

### 5.1 BR-1 唯一现金入口（最高红线）

- 只有 `FinanceService.postTransaction / bulkPostTransactions / reverseTransaction / replay` 能改变 `LedgerAccount.cashBalanceCents` 与 `Company.cash`。
- 任何系统只能"提交交易"（`postTransaction` 调用），不得直接赋值现金；`Company.cash` 为只读快照。
- 开局注资必须以一笔固定幂等键的 `advance` 交易入账（现有实现规则：`finance-service.ts:30`），不允许 `registerCompany` 直接塞现金（其初始余额固定为 0）。
- **反证锚点（TC-02）**：必须存在测试证明"移除/绕过 `postTransaction` 后任何业务路径都无法改变现金"。

### 5.2 BR-2 交易分类

- 每笔交易必须有 `category`（12 类）与派生的 `cashFlowType`（三分）；必须带 `referenceId` 与 `source`，否则视为不合规入账（拒绝或标 `OPEN` 待补）。
- 金额符号语义固定：正=流入、负=流出；零额拒绝（`FIN_AMOUNT_ZERO`）。

### 5.3 BR-3 承诺支出不可直接改现金

- `BudgetCommitment`、`Payable/Receivable` 只是计划/义务；创建、修改、取消都不产生现金变动。
- 现金变动的唯一途径是"兑现事件提交 `Transaction`"，且一笔兑现对应一笔交易（幂等键绑定承诺 id + 周期）。
- 场景 A 步 3：招聘 5 人 → 生成 5 条薪酬承诺，跑道**在承诺创建时即可预见地缩短**（预测层反映），但现金直到月末计提才实际流出——两者不同，UI 需区分"预计跑道"与"实际现金"。

### 5.4 BR-4 应收应付与防重复结算

- 应收应付按 `dueDate` 进入预测；到期通过一笔 `Transaction` 结算，`settledCents` 累加。
- 同一 `(sourceRef, period, direction)` 只允许一次成功结算；重复提交由幂等键去重（§5.7）。
- 应收不是现金：预计销售产生的 `Receivable` 不增加现金，直到 `SalesRecord` 结算提交 `sales_revenue`。

### 5.5 BR-5 收入确认

- P1 采用"销售结算确认"：`SalesRecord` 生成时提交 `sales_revenue`（`+revenue`）；平台抽成提交 `platform_fee`（`−fee`）；二者净额构成经营流入。
- **OPEN-F3**：收入确认时点（交付即确认 vs 回款确认）与总额法/净额法，属产品运营/D-04 与 D-05 口径；本文只约定"以 `Transaction` 入账为确认标志"，不锁定具体时点。合同分成按净销售−退款结算（现有 `contract-service.ts` 口径），本文沿用其净额口径，不另建规则。

### 5.6 BR-6 退款

- 退款通过 `reverseTransaction(originalId, reason, newKey)` 生成一笔**符号相反**的 `Transaction`（`customer_refund`），原交易 `status=reversed` 并记 `reversedBy`；反向交易记 `reversalOf`。
- 退款来源 `RefundSource={auto_window,player_request}`（现有枚举）；自动窗口退款由系统发起（`source=system_auto`），玩家请求退款为 `player_authorized`。
- 退款幂等：`newKey` 由调用方固定（如 `refund:<originalId>:<source>`）；跨期仍靠 `transactionByKey` 判定（§11.3）。
- 禁止"删除原交易"来退款——账本不可变（§11.1）。

### 5.7 BR-7 幂等与去重

- 每笔交易带唯一 `idempotencyKey`；重复提交返回原交易并标 `idempotent=true`，**不重复改变现金**。
- `idempotencyIndex` 30 天清理；`transactionByKey` 跨期保留，供退款等跨期幂等（迁移 §2.3 正确性关键，不得破坏）。

### 5.8 BR-8 合同付款与分成走同一框架

- `Contract` 记录义务与分成规则（合同权威），但**不自建第二套付款/分成账**；`Contract.settlementRefs` 指向 `Transaction`。
- 合同付款、平台分成、里程碑结算一律经 `FinanceService` 入账，类别为 `contract_payment` / `platform_fee`，并绑定 `referenceId=contractId`。
- 合作场景不得"私下改现金"或记第二本账（系统地图 §2.2、P0-B §1.2 D）。

### 5.9 BR-9 负现金（区分自主与固定结算）

沿用现有 `allowNegativeBalance` 语义：
- **自主支出**（玩家主动追加预算、新增招聘、自愿营销等）余额不足 → 拒绝，返回 `FIN_INSUFFICIENT_CASH`。
- **固定结算**（薪酬、租金、税、退款兑现、合同到期）允许负现金（`allowNegativeBalance=true`），并触发 `NEGATIVE_CASH` 原因码 → `critical`。
- 负现金本身不是破产判定线（破产线 TUNING=0，见 §6.4），而是危机升级信号；持续为负且窗口耗尽才破产（因果链）。

## 6. 计算公式（参数 TUNING）

> 所有金额先用 cents 计算，展示时换算为美元。公式层禁止直接读取 TUNING，由调用方注入快照。

### 6.1 跑道月数（runwayMonths）

```
CommittedBurn_m   = Σ 承诺支出中 period=monthly 且 startAt≤m≤endAt 的 amountCents
ExpectedIn_m      = Σ 预测月 m 的流入（应收到期 + 预计销售），按 confidence 折减
NetBurn_m         = max(0, CommittedBurn_m − ExpectedIn_m)

runwayMonths = 若存在 m 使 CumAvailable(m) ≤ 0，则首次 crossing 的月序（可为小数插值）
               若全窗口 NetBurn_m ≤ 0，则 +∞
```

- **场景 A 步 3**：开局现金 `$120k = 12_000_000 cents`；5 人月薪承诺后 `runwayMonths` 下降（可观察）。
- 研发期无销售时 `ExpectedIn≈0`，`runway ≈ AvailableCash / CommittedBurn`。

### 6.2 承诺扣除后的可用现金（AvailableCash）

```
AvailableCash = LedgerAccount.cashBalanceCents
              − Σ(未兑现的承诺支出，horizon 内)   // BudgetCommitment.amountCents − realizedCents
              − Σ(未结算应付，horizon 内)          // Payable.amountCents − settledCents
              + Σ(高置信应收，可选)                // TUNING FIN-T2：是否计入应收
```

- 这是玩家"真正能动用的钱"，区别于账面现金；UI 必须同时显示 `cashBalanceCents` 与 `AvailableCash`。
- `AvailableCash < 0` 触发 `COMMITTED_EXCEEDS_CASH` 原因码。

### 6.3 预测区间（netCashByMonth）

对每个预测月 `m`（0..`horizonMonths`）：

```
Cash_m(expected) = Cash_0 + Σ_{i≤m}(ExpectedIn_i − CommittedOut_i − ExpectedPayable_i)
Cash_m(low)      = Cash_0 + Σ_{i≤m}(ExpectedIn_i × p_in_low − CommittedOut_i − ExpectedPayable_i × p_pay_high)
Cash_m(high)     = Cash_0 + Σ_{i≤m}(ExpectedIn_i × p_in_high − CommittedOut_i × p_out_low)
```

`p_in_low/p_in_high/p_pay_high/p_out_low` 为 `TUNING`（FIN-T3）置信折减系数；区间用于 UI 显示"最好/预期/最差"三带，`lowCashDate` 取 `Cash_m(low)` 首次跌破警告线之月。

### 6.4 预警阈值与滞后（TUNING，锚定现有实现）

| 参数 | 现有锚点（cents / 业务值） | 口径 |
|---|---|---|
| `cashWarningThresholdCents` | `400_000` = **$4,000** | L1 现金警告线，低于→ `watch/warning` + 顶部横幅 |
| `cashBankruptThresholdCents` | `0` = **$0** | L2 破产线（现金低于 0 且窗口耗尽→破产） |
| `cashRecoveryThresholdCents` | `400_000` = **$4,000** | 恢复线，与警告线同值形成**滞后区间**（0~$4,000 不反复切换，迁移 §M1.2 决策） |
| `budgetOverrunWarnAt` | `1.0`（比例） | 预算超支警告（消费 D-01 `ratio`） |
| `runwayWarningMonths` | TUNING（初始 3） | 跑道低于此月数→ `watch` |
| `runwayCriticalMonths` | TUNING（初始 1） | 跑道低于此月数→ `critical` |
| `remediationWindowDays` | TUNING（有限，初始 60） | `critical` 起补救窗口，**必须有限** |
| `hrbVerdictWarn` / `hrbVerdictCut` | `1.0` / `1.2`（D-01 §6.2.1） | HRB 可行性结论阈值 |

> 单位纪律：任何新 cents 常量必须同时写业务值与代码单位值，并做量级自检（CODEBUDDY.md §13.1/§13.4）。

## 8. 玩家操作与自动化

### 8.1 玩家授权（生成 `source=player_authorized` 的交易/承诺）

- 创办公司（开局注资 `advance`）、设定 `HRB`/预算承诺。
- 招聘/解雇（薪酬承诺/遣散 `severance`）、追加预算、缩减范围、暂停项目。
- 发起重整、选择补救动作（终止合同、出售资产、裁员、寻求预付款 `advance`）。
- 玩家请求退款、批准合同/分成方案。
- 选择进入/退出沙盒观察态。

### 8.2 系统自动记账（`source=system_auto`）

- 每日销售 `sales_revenue` 与 `platform_fee` 入账、自动窗口退款 `customer_refund`。
- 月末薪酬 `salary`、租金 `office_rent`、税 `tax` 计提。
- 合同里程碑/到期结算、应付到期结算。
- 幂等去重、预测重算、危机阈值探测与预警升级、读档 `replay` 重建。

### 8.3 自动化边界（基线 §13）

默认自动化处理重复记账；玩家只在关键节点（预算承诺、超支应对、危机补救、重整）做有意义决策，不被迫微观管理每笔日常交易。日常交易不打断，重大风险/合同承诺/危机明确提示（通知分级）。

## 9. UI/UX 页面结构级规格

> 结构级（非像素级）：页面、区块、状态、空/错/跳转。每个页面回答基线 §13 四问。

### 9.1 财务概览（Overview）

- **区块**：现金余额（`cashBalanceCents`）+ 可用现金（`AvailableCash`）；跑道月数（含"为什么变了"：招聘/追加预算/返工）；顶部现金警告横幅（现金 < 警告线时）；本月净流；最近 5 笔交易。
- **状态**：`healthy`（无横幅）、`watch/warning`（黄色横幅 + 原因码）、`critical`（红色横幅 + 倒计时）、`bankrupt`（破产态横幅）。
- **空态**：未创办公司→"尚无账本" + 跳转创办流程。
- **错态**：INV-1 校验失败→"账本不一致" + 跳转审计/读档修复入口，禁止继续入账。
- **跳转**：→现金流、→预测、→危机面板。

### 9.2 现金流（Cashflow）

- **区块**：交易流水表（日期/类别/现金流三分/金额/来源/关联实体下钻），按类别与时间段筛选；经营/投资/融资三栏汇总。
- **空态**：无交易→"尚无交易记录"（开局注资后至少 1 笔）。
- **错态**：筛选无结果→"该时间段无交易"；加载失败→重试。
- **跳转**：点交易→关联实体（销售/合同/项目/员工）；→预测。

### 9.3 现金预测（Forecast）

- **区块**：跑道曲线（预期/最好/最差三带）、`lowCashDate`、承诺支出构成（薪酬/租金/项目/合同）、假设参数（TUNING，高级可展开）。
- **空态**：无承诺→"尚无承诺支出，跑道无限"。
- **错态**：预测依赖缺失（如 `BudgetCapacity` 未解析）→标 `OPEN` 提示"数据未就绪"，不显示伪造曲线。
- **跳转**：→概览调整预算；→危机面板。

### 9.4 危机面板（Crisis）

- **区块**：当前等级 + 原因码列表（"为什么"）；补救窗口倒计时（`remediationDeadline`）；可用补救动作卡片，每张显示代价/风险预览（对现金、跑道、债务、声誉、人才、控制权）；重整后果清单；沙盒观察开关。
- **状态**：`warning`（预警说明 + 建议）、`critical`（强制呈现补救动作 + 倒计时）、`restructuring`（方案执行进度 + 后果）、`bankrupt`（终态 + 观察选项）。
- **空态**：`healthy`→"财务状况健康" + 最近一次脱离危机的记录。
- **错态**：补救动作前置条件不满足（如现金不足无法裁员补偿）→置灰并说明原因。
- **跳转**：→现金流查原因、→预测看后果、→项目页执行缩减范围。

## 10. 异常与边界

### 10.1 负现金（NEGATIVE_CASH）

固定结算允许负现金并触发 `critical`（BR-9）；自主支出被拒（`FIN_INSUFFICIENT_CASH`）。负现金不直接等于破产，需窗口耗尽或跌破破产线才破产。

### 10.2 重复记账

幂等键去重（BR-7）；跨期退款靠 `transactionByKey`。重复提交返回原交易且不改变现金；测试必须锁定（TC-03/TC-04）。

### 10.3 跨月承诺

`BudgetCommitment.startAt/endAt` 跨月时，每月按 `period` 生成一笔兑现交易（幂等键含承诺 id + 月份）；`realizedCents` 逐月累加；中途取消只停止未来兑现，已入账不冲回。

### 10.4 破产后继续观察（沙盒）

`sandbox_observe` 态：玩家不再授权新支出（`source=player_authorized` 被命令守卫拒绝，对齐 M1.2 破产命令守卫），但世界/AI 继续运行、既有固定结算按规则继续；玩家可查看世界演化，是否继续由玩家选择（基线 §12）。

### 10.5 读档恢复

`replay` 从持久化 `Transaction[]` 重建所有账户余额与索引，校验 INV-1；不一致则拒绝读档并报 `LEDGER_INCONSISTENT`。重建后 `CrisisState` 与预测按重建账本重算，不持久化预测快照作为事实（对齐 P0-B S2）。

## 11. 存档要求

### 11.1 不可变（append-only）

- `Transaction` 入账后不可编辑、不可删除；冲销以新增反向交易实现（BR-6）。
- `status` 只允许 `posted → reversed` 单向；无 `pending → posted` 中途态在 P1（退款批次 `pending` 属产品运营，未兑现前不是交易）。

### 11.2 可审计

- 每笔交易保存 `idempotencyKey, day, category, cashFlowType, amountCents, balanceAfterCents, referenceId, source, reversalOf`；可重放、可对账、可下钻因果。
- `CrisisState.history` 与原因码一并持久化，支撑"破产非随机"的审计叙事。

### 11.3 版本迁移

- 沿用存档 v3 框架与幂等键跨期保留（`finance-service.ts:L43-L48,L250-L259`）。
- 迁移为旧交易补 `cashFlowType`（按 §3.9 TUNING 映射）、`source`（默认 `system_auto`，开局注资标 `player_authorized`）、`reversalOf`；保留 `idempotencyKey`/`transactionByKey`，不破坏跨期幂等。
- 迁移后跑 `replay` 校验 INV-1；`formulaVersion`/`assumptionsVersion` 随存以保证预测可复现（OPEN-F4：与 `save-schema.ts` 具体字段对齐方式）。

## 12. 性能要求

- `postTransaction`：均摊 O(1)；依赖 `idempotencyIndex`、`transactionById`、`transactionByKey` 索引，禁止按 id/category 全表扫描。
- `bulkPostTransactions`：沿用增量回滚（记录起始长度与余额快照，失败截断），不整表复制（迁移 §2.3 实现约束）。
- `pruneIdempotency`：30 天保留策略，避免每日 O(n)；`transactionByKey` 不随清理删除。
- `CashForecast` 重算：仅 L0 探测 + 条件变更时重算，复杂度 O(`horizonMonths × commitments`)，不进逐日热路径。
- `replay`：仅读档时 O(n)，应为可接受的加载期成本；目标上限 `TUNING`（FIN-T5，如十万级流水加载 < 2s，待编码基准校准）。
- 性能优化不得改变玩家可见的经济因果（系统地图 §4.8/基线约束）。
