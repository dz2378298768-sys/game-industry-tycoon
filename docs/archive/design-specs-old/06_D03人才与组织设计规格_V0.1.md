**红线（全文不可违反）**：
- R-D03-1：**Person / Employment 分离**。`Person` 是人物身份与能力权威；`Employment` 是任职关系。同一 `personId` 在任一 `dayIndex` 最多一条 `status ∈ {probation, active, resigning}` 的 `Employment`（"同一人不可双重雇佣"）。跳槽只新增/结束 `Employment`，**不复制、不重建 `Person`**（系统地图 §2.2/§3.3）。
- R-D03-2：**`Cap_d` 唯一来源**。Project 的 `Cap_d` 只经本文 §7.1 接口读取，公式定义以 Project §6.2 为准，本文**只做映射、不改公式**；任何偏离须升 `projectFormulaVersion` 并经主 AI 裁定。
- R-D03-3：**薪资不改现金**。薪资/招聘费/遣散只经 FIN `BudgetCommitment` + `postTransaction` 兑现（FIN BR-3）；D-03 不读写 `Company.cash`。
- R-D03-4：**不复制技能值**。Project `teamRefs` 只存 `ref(Employment)`；技能/士气以 `SkillProfile` 实时读，禁止把等级快照写进 `WorkPackage`。
- R-D03-5：**不做私生活**。`PersonalityProfile`/`CareerPreference`/`PersonRelationship` 在 P1 只保留结构占位，不建模家庭、恋爱、私人社交（基线 §14 红线、迁移裁定 REJECT）。

## 4. 状态与生命周期

### 4.1 `PersonStatus`（人物状态）
`available` 未任职 · `assigned` 已任职（有至少一个有效项目分配） · `on_leave` 任职但休假 / 待岗 · `departed` 已离开本公司（仍为产业中的人物）。

| 当前 | 事件 | 目标 | 条件 | 可逆 |
|---|---|---|---|---|
| —（新建） | `hire` 确认 | `assigned`（若已分配）或 `on_leave`（未分配） | 生成 occupying `Employment` | 是 |
| `available` | `hire` | `assigned`/`on_leave` | 同上 | — |
| `assigned` | 全部 `Assignment.effectiveTo` 结束 / 撤分配 | `on_leave` | Σ 有效分配 = 0 | 是 |
| `on_leave` | 新增有效 `Assignment` | `assigned` | Σ 有效分配 > 0 | 是 |
| `assigned` / `on_leave` | `Employment`→`resigning` | 保持（不加新分配） | — | — |
| `assigned` / `on_leave` | `Employment`→`terminated`/`contract_ended` | `departed` | `occupiesPerson` 置 false | **否**（再雇需新建 Employment） |
| `departed` | 重新 `hire` | `assigned`/`on_leave` | `currentEmploymentId=null`；`rehireCount+=1` | — |
| 任意 | 退休（年龄 ≥ `retireAge`，TUNING） | `departed`（`terminationKind=contract_end`） | 仅在无 occupying Employment 时可强制 | **否** |

**不可退出状态反证**：`departed` 是终态但**不冻结技能**——重新入职读同一 `SkillProfile`，所以"人换雇主"不影响能力（R-D03-1 反证）。`assigned` 不是"被锁死"：撤分配即可回 `on_leave`，故没有"人永不释放"的异常态。

### 4.2 `EmploymentStatus`（任职状态）

```
probation ──(probationEnd 到期 且 morale ≥ probationFailMorale)──▶ active
    │                                                          │
    ├──(probation 到期 且 morale < probationFailMorale)→ terminated（试用不通过）
    │                                                          │
任意 occupying 态 ──(玩家/系统触发辞职)→ resigning ──(noticeDays 满)──▶ terminated(voluntary)
任意 occupying 态 ──(玩家解雇)→ terminated(terminated)  ← 立即，无需 resigning
active ──(合同自然到期且不续约)→ contract_ended
```

| 当前 | 事件 | 目标 | 是否占人（`occupiesPerson`） | 说明 |
|---|---|---|---|---|
| —（new） | hire | `probation` | true | 试用期 `probationMonths`（TUNING） |
| `probation` | 到期且通过 | `active` | true | `renewalCount+1` |
| `probation` | 到期且失败 | `terminated` | false | `terminationKind=terminated`；触发 FIN 遣散/释放 |
| `probation` | 提前解雇 | `terminated` | false | 试用期遣散按 `severanceMonths`（TUNING） |
| `active` | 申请辞职 / 系统触发 | `resigning` | true | 记 `noticeStartDay`；**仍可继续为项目产出**，但不可再加新分配 |
| `resigning` | `noticeDays` 满 | `terminated` | false | `terminationKind=voluntary` |
| `resigning` | 玩家挽留（调薪/加钱）成功 | `active` | true | 需 §6.3 调薪且 morale 回升 |
| `active` | 玩家解雇 | `terminated` | false | 立即；遣散 = `severancePerMonthCents × severanceMonths` |
| `active` | 合同自然到期不续约 | `contract_ended` | false | P1 少见；如出现同 `terminated` 结算 |
| `terminated` / `contract_ended` | — | — | false | **终态**；不可回退，再雇=新建 Employment |

**不可退出状态反证**：`terminated`/`contract_ended` 均为终态，**禁止改回 `active`**（防止"幽灵在职"重复计薪与重复 `Cap_d`）；`resigning` 的存在保证"人走前有通知窗口"，玩家可在窗口内挽留，避免"今日满血明日离职"的突兀流失（E3 体验目标）。

### 4.3 两状态机一致性
`Employment.status` 是 `Person.status` 的**唯一驱动**（单写者）。派生规则：
- 若 `currentEmploymentId != null` 且 occupying：`Person.status = (Σ活跃分配>0) ? assigned : on_leave`。
- 若 `currentEmploymentId == null`：`Person.status = departed`（但仍在产业中存在，可进候选池）。
禁止直接改 `Person.status` 而不改 `Employment`（否则违反 INV-2，返回错误码 `D03_PERSON_STATUS_DESYNC`）。

## 5. 业务规则

### 5.1 分离与唯一占用（R-D03-1）
- **RULE-01**：`Person` 与 `Employment` 之间是 1:N（多段历史），任一时刻最多一条 `occupiesPerson=true`。
- **RULE-02**：`hire` 时若 `person.currentEmploymentId != null` 且其 Employment 为 occupying → 拒绝 `D03_ALREADY_EMPLOYED`。
- **RULE-03**：跳槽 `transfer(personId, toCompanyId)` 只关闭旧 Employment（写 `endDay`）、新建新 Employment，**`personId` 不变**、`SkillProfile` 不重建。
- **反证锁**：以 `personId` 建唯一索引于 occupying Employment；单测构造"同人两条 hiring 命令"必须只成功一次（TC-03）。

### 5.2 招聘规则
- **RULE-04**：只能从 `Candidate` 池按 `candidateId` 招；不可"凭空造人"（区别于旧 `hire` 直接写入任意字段，迁移 §14）。
- **RULE-05**：候选池规模上限 `candidatePoolSize`（TUNING），每日刷新一次（§12）；若候选已在某公司任职，不得出现（防止"挖角"提前进入 P1，O1）。
- **RULE-06**：招进来自动 `currentEmploymentId` 指向新 Employment；同人不可同时在池中两份。

### 5.3 分摊上限（`burden` 侧）
- **RULE-07**：单人 `Σ_{活跃分配 p} allocationRatio[e,p] ≤ 1.0`，超出拒绝 `D03_OVER_ALLOCATED`（**注意与 Project 侧的"最大日产能"不同：这里是分配比例上限，Project 侧 `Cap_d` 是工作单元上限**）。
- **RULE-08**：同一 `(employmentId, projectId)` 同一时刻仅一条有效 `Assignment`；同学科多项目可分多条，但受 RULE-07 与 §6.8 的跨项目产能约束。
- **RULE-09**：`resigning` 的 Employment **不得新增分配**，已有分配保留到 `effectiveTo` 或离职（§4.2），保障项目中途离职有过渡。

### 5.4 离职 / 解雇规则
- **RULE-10**：**自愿离职**只在每日结算（§6.7）中按 `dailyResignProb` 触发，触发达阈值后进入 `resigning`；**不允许 0 通知**。
- **RULE-11**：**解雇**是玩家显式命令，立即转 `terminated`，同时（a）终止其所有 `Assignment`（`effectiveTo=当日`），（b）释放 FIN 薪资承诺（停止未来周期），（c）一次 `one_off` 遣散承诺兑现。
- **RULE-12**：解雇的**士气外溢**：同项目同学科在职者 `moraleModifier -= k_layoffSpill`（TUNING），可追溯（E3）。不做公司文化分（P1 无文化系统）。
- **RULE-13**：解雇**不得使项目 `team_d=∅` 却静默**——必须立即写 `Cap_d=0` 告警并推 Project（§10 E2）。

### 5.5 士气与离职诱因
- **RULE-14**：`morale` 由 `baseMorale`（人物长期）+ `moraleModifier`（任职修正）构成；任一项变化都重算 `morale = clamp(baseMorale + moraleModifier, 0, 100)`（§6.6）。
- **RULE-15**：离职诱因**仅四类**（可追溯）：① `morale` 低于 `resignMoraleThreshold`；② 薪资低于同职级市场基准 `marketSalary(region, role, seniority)` 的 `underpayRatio`；③ 所在项目失败/取消（`project_failed` 事件）；④ 长期无分配（`idleDays`）。**P1 不引入外部挖角、不引入私人原因**（E3、O1）。
- **RULE-16**：`baseMorale` 长期下降（如被连续失败项目拖累）不回弹到原值——离职后 `baseMorale` 保留，进新公司时按 `startingMoraleFloor` 下限（TUNING）。

## 6. 计算公式

> 所有符号全定义；标 `TUNING` 者结构确定、参数待校准，具体值在 `tuning.ts` 的 `employee`/`d03` 段，**不在此处写死**。除零边界见每个公式的 `ε` 分支。

### 6.1 技能等级到 `Cap_d` 的映射（对齐 Project §6.2）

Project §6.2 已给出权威公式，本文**不重定义，只提供其输入并检查可执行性**：

```
# —— 引自 Project V0.1.1 §6.2（权威，本文不改） ——
team_d     = { e ∈ teamRefs : available(e, day) ∧ skillLevel(e, d) > 0 }
f_skill(ℓ) = TUNING map，ℓ ∈ {0..5}           # 例 {0:0,1:0.6,2:0.8,3:1.0,4:1.2,5:1.4}
Cap_d(day) = k_output × Σ_{e ∈ team_d} f_skill( skillLevel(e, d) )
```

本文**定义**以下映射使上式可执行：

```
# Z1：teamRefs 展开为 D-03 的 Employment 集合
teamRefs      = { Employment : employmentId ∈ 项目.teamRefs }
                ∧ 该条的 Assignment(projectId, discipline=d) 存在且生效窗口覆盖 day

# Z2：available(e, day)（回答 Project C7 "待 D-03 确认"）
available(e, day) ≡ Employment.status ∈ {probation, active}        # resigning 也在 but 仅限无新分配
                   ∧ Employment.occupiesPerson = true
                   ∧ EffectiveFrom ≤ day ≤ (EffectiveTo ?: +∞)
                   ∧ 所属 Person.status ≠ departed
# 注 1（语义收敛）：resigning 期间仍可产出（见 §4.2），故 available 判 true 但不得新增分配；
#      若 day 已超过 Notice 截止（离职日），available 判 false，Project team_d 自动剔除。

# Z3：skillLevel(e, d)（Project 缺键缺省 = 0）
skillLevel(e, d) ≡ Person.skills.level[d] ?? 0       # 0 = 不会该学科，不产出
```

**关于 `burden_d` 的关系（关键）**：`Cap_d` 是**团队总日产能（workUnits/day）**，`burden_d` 是**多项目分摊的"可用比例"（0–1 无量纲）**，两者**量纲不同，不可相减**。Project §6.3 `Cap_d_remaining` 是"当日产能余量"，本规格的 `burden` 是"人在项目间瓜分的份额"，由 §6.2 定义并通过 `eff_share` 下传到 `Cap_d` 的 `k_output` 系数里。

- **符号一致性检查表（vs Project §6.2/§6.6）**：

| Project 符号 | 本文来源 | 一致性 |
|---|---|---|
| `skillLevel(e,d)` | §3.3 `level[d]`，缺键=0 | 一致；P1 `audio` 恒 0（OPEN-D03-2） |
| `available(e,day)` | §6.1 Z2 | **本文正式定义**（Project 标"待 D-03 确认"） |
| `f_skill(ℓ)` | Project TUNING map | 本文只读不覆写 |
| `k_output` | Project TUNING | 本文只读；**D-03 不得把 `eff_share` 直接乘进 `k_output` 常量**（防越权改 Project 口径） |
| `salary_e` | §3.2 `salaryMonthlyCents` | 一致 |
| `w_e[d]` | Project TUNING | 本文不涉及 |

### 6.2 多项目分摊：`eff_share` 与 `burden_d`

```
# 单人一学科的多项目分配比例（对每个 (e, 学科 d)）
allocs(e, d)    = { a ∈ Assignment(e) : a.discipline = d ∧ 生效窗覆盖 day }
share(e, p)     = a.allocationRatio / Σ_{a' ∈ allocs(e,d)} a'.allocationRatio   # ∈ (0,1]，Σ_p share = 1
# 若 allocs(e,d)=∅ ⇒ eff_share=0（人未被该项目卷入该学科）

# 单人实际可用产能系数（跨项目）
eff_share(e, p, day) = share(e, p) × fatigue_or_leave_factor(e, day)
# P1 冻结：fatigue_or_leave_factor = 1（不建模疲劳/请假对产能的衰减，见 OPEN-D03-3）

# 项目学科级"可用比例" —— 这就是 burden_d（无量纲，∈[0,1] 的加权平均）
burden_d(project, day) = ( Σ_{e∈team_d} eff_share(e, project, day) )
                       / max(1, |team_d|)
# ε 分支：team_d=∅ ⇒ burden_d = 0（不是 1，也不是 ∞）
```

**D-03 附加产能模型（若要"分摊到人"的写法，可被 Project 消费但 P1 默认不启用）**：

```
# Project §6.2 的默认写法是 k_output × Σ f_skill(...)，不显式含 eff_share。
# 若 Project 后续要按分摊折算，可升级为（标 OPEN-D03-4，需升 projectFormulaVersion）：
Cap_d^share = k_output × Σ_{e∈team_d} [ f_skill(skillLevel(e,d)) × eff_share(e, project, day) ]
```

**关键说明**：**P1 采用 Project §6.2 原式（不显式乘 `eff_share`）**，理由：① Project 为 `Cap_d` 权威方，D-03 不得单方面改式；② 若玩家把同一人拉到两个项目，`Cap_d` 各自仍按满产能算，但在**成本侧**（Project §6.4 `salaryDaily_d` 用 `w_e[d]`）已计入分摊；③ 乘 `eff_share` 会让"同一人被两家项目均摊分"变成"两家分产能"，是 P2 才需要的能力（OPEN-D03-4）。因此 **D-03 的责任边界 = 保证 `skillLevel`/`available` 准确，`eff_share` 仅在 OPEN-D03-4 启用后进入 `Cap_d`**。

- **`burden_d` 的用途**：仅作 UI 展示（"程序组有 6 人，满负荷 100%，分布到 2 个项目"）+ 供 Project 后续 `costPerUnit_d` 细化；**不参与 P1 `Cap_d` 数值**。
- **单项目单人**：`allocs(e,d)` 只有 1 条 ⇒ `share=1` ⇒ `eff_share=1`。这是 P1 90% 场景。

### 6.3 招聘周期 / 周期成本 / 薪资定价

```
# 招聘周期
recruitLeadDays(candidate) = baseLeadDays + k_lead × (seniority==senior ? 1 : 0)   # TUNING
arrivalDay                 = min(hireConfirmDay + recruitLeadDays, candidate.expiresAtDay)
# 若 arrivalDay > expiresAtDay ⇒ 该候选不可招（拒绝 D03_CANDIDATE_EXPIRED）

# 招聘一次性成本（入职时兑现，走 one_off 承诺 → 交易）
recruitCostCents = round( candidate.askingSalaryCents × hireCostRatio )           # 迁移 KEEP：hireCostRatio 默认 0.15
# 注意：此成本在 hire 动作提交时以 project-independent 的 one_off 承诺兑现（§7.2），进 operating 现金流。

# 薪资定价（报价 → 谈判）
marketSalary(region, role, seniority) = baseSalary[role][region] × seniorityMultiplier[seniority]
                                       × (1 + k_marketDrift × 地区趋势)           # TUNING
askingRange(candidate)  = [ floorPrice, ceilingPrice ]                            # TUNING 区间（如 market × [0.85, 1.10]）
negotiatedSalary        = clamp( playerOffer, floorPrice, ceilingPrice )
# 若 playerOffer < floorPrice ⇒ 拒绝（D03_OFFER_BELOW_FLOOR），候选保留
# 若 playerOffer > ceilingPrice ⇒ 接受但 morale 不加（避免玩家"用钱买士气"）

# 调薪（挽留 resigning 用）
raise(newSalary) : 要求 newSalary > Employment.salaryMonthlyCents
                   ⇒ pendingSalary = newSalary；pendingEffectiveDay = day + k_salaryEffectiveLag
                   ⇒ 同时更新 salaryCommitment（终止旧承诺、新建承诺，§7.2）
```

**周期成本**：月薪按 FIN `workingDaysPerMonth` 摊为日成本，月薪承诺每**自然月**兑现一次（`period=monthly`，§7.2）。薪资在 `Employment.status ∈ {probation, active, resigning}` 时都计薪；`terminated/contract_ended` 当月起停止整个当月还是按日？——P1 采用 **"月末兑现，当月中离职按末日计"**：`realizedCents` 只兑现到 `endDay` 所在月（即整月照付，差额留作 DEF-3 改进）。**此为简化，明确标 OPEN-D03-5**。

### 6.7 离职概率（每日）

```
dailyResignProb(employment, day) =
    p_base
      + w_morale  × max(0, resignMoraleThreshold − morale) / 100
      + w_under   × max(0, 1 − salary/marketSalary)                  # 欠薪诱因
      + w_idle    × max(0, idleDays − idleWarnDays)/idleWarnDays
      + w_rehire  × rehireCount                                      # 回流者更易再次离开（TUNING）
      + projectFailedFlag × w_projectFail
```

### 7.1 Project 查询 `Cap_d` 的接口契约

```
# D-03 侧提供（只读投影，不写 Project）
interface PersonnelProjection {
  employmentId: string
  personId: string
  discipline: Discipline            // 该 Employment 当前承担的学科（Assignment 上）
  skillLevel: number                // 0..5（缺键=0）
  available: boolean                // §6.1 Z2
  effShare: number                  // §6.2；P1 Project 不强制读取（见 §6.2 关键说明）
  salaryMonthlyCents: number
}

queryTeam(projectId: string, day: number): { members: PersonnelProjection[], errors: D03Error[] }
```

**调用时机**：
1. `Project` 日推进 tick 前（每日一次）；
2. 玩家改动分配（加人/减人）后立即调一次（当月余量重置）；
3. 读档恢复时。

**字段**：见上 `PersonnelProjection`。缺键 `skillLevel=0`（对齐 Project B-9）。`available=false` 的人**不出现在 `members` 中**（与 Project §6.2 `team_d` 过滤等价）。

**错误码**：

| 错误码 | 触发 | Project 行为 |
|---|---|---|
| `D03_TEAM_EMPTY` | 项目 `teamRefs=∅` | 对应学科 `Cap_d=0`，`Cost_est=+∞`（Project B-2） |
| `D03_EMPLOYMENT_NOT_ACTIVE` | `teamRefs` 含已 `terminated` 的 Employment | 该成员剔除；Project 若该学科无其余成员 ⇒ `Cap_d=0` |
| `D03_UNKNOWN_SKILL` | `Assignment.discipline` 不在 `Discipline` | 该分配视为 0 贡献；记录错误 |
| `D03_OVER_ALLOCATED` | 玩家提交分配触发 | 拒绝分配（D-03 命令侧，不留到 Project） |
| `D03_PERSON_STATUS_DESYNC` | §4.3 一致性校验失败 | fail-closed，不返回该人 |

**契约要求**：
- 纯函数、只读；同一 `(projectId, day, 存档快照)` 必须产生**完全相同**输出（可重算）。
- D-03 **不缓存** Project 侧的 `Cap_d` 结果（防双写）。

### 7.2 薪资 → 账本（FIN）

```
# hire 提交时：
salaryCommitment = FIN.createCommitment({
  companyId, sourceType: 'employment_salary', sourceRef: employmentId,
  amountCents: salaryMonthlyCents, period: 'monthly',
  startAt: startDay, endAt: null,        // 逐月续，直到终止时显式关闭
})   // 金额>0，不改现金（FIN BR-3）

# 解雇/离职：
FIN.cancelCommitment(salaryCommitment, effectiveDay = endDay)  // 停未来周期；已兑现照旧付

# 招聘费 / 遣散：
FIN.createCommitment({ sourceType: 'contract_obligation', amountCents: recruitCostCents,
                       period: 'one_off', startAt: hireDay })
/then FIN.realizeCommitment(...) 以 'severance' / 'contract_payment' 交易兑现
# 注：招聘费建议走 'project_expense' 或 'contract_payment' — 见 OPEN-D03-6
```

**规则**：D-03 **从不调用 `postTransaction` 改变现金**，只创建/取消承诺；兑现由 FIN 月度结算服务执行（§8.1）。`idempotencyKey` 由 FIN 生成，D-03 只提供 `sourceRef`。

### 7.3 技能成长 ← 项目经历（反向）
Project 日推进（`DailyOutput` 写入时）可向 D-03 提供 `(employmentId, discipline, day, out_wp)`；D-03 用 `out_wp>0` 判定 `effort`（§6.8）。**D-03 只读 Project 产出日志，不回写 Project**（R-D03-2）。

### 7.4 D-01 / D-07 关系
- **D-01 `SkillDemandProfile`**：D-03 只消费 `peakFraction`（`S_d`），用于 UI 提示"程序需求极高"。
- **D-07 档案**：`PersonEvent` 全量写入；`Employment` 历史保留（不删除），支持"这位人才做过什么"。

## 8. 玩家操作与自动化

### 8.1 玩家决策（有代价）
| 决策 | 层级 | 代价/约束 |
|---|---|---|
| 招聘候选 | 战术 | `recruitCostCents` + 新增月薪承诺；`arrivalDay` 延迟；候选过期 |
| 调整报价 | 战术 | 低于 `floorPrice` 被拒；过高浪费钱但不会加士气 |
| 分配/撤分配 | 战术 | 受 `ΣRatio≤1`；`resigning` 不准新增；撤出后项目 `Cap_d` 下降 |
| 调薪挽留 | 战术 | 立即生效于 `pending`；现金跑道缩短 |
| 解雇 | 战术/危机 | 立即 `terminated` + 遣散兑现 + 士气外溢；破产补救（FIN §8.4）中的 `cut_staff` 走 FIN 路径，D-03 提供名单与代价预览 |
| 设置分配优先级（自动） | 战略 | 玩家定"程序组优先 P0 项目"，系统按 §8.2 自动分配 |
| 招多少（headcount） | 战略 | `headcountCap` 上限；组织扩张阈值（DEFERRED） |

### 8.2 系统自动（玩家不逐日操作）
- 每日：`Cap_d` 投影、士气回归、离职判定（§6.6/§6.7）、成长积累（§6.8）。
- 月度：薪资承诺兑现（由 FIN 调度，D-03 不参与）。
- 自动分配：若玩家未显式分配，系统默认将空闲员工加入"最高优先级项目"（§8.2 策略，TUNING）；或留空（玩家可关）。**默认 = 不自动分配**，避免"被系统抓去干活"。

- **状态**：`departed` ⇒ 只读（仍可在候选池里再招）。

### 9.5 跳转
- TeamOverview → PersonDetail；TeamOverview → Recruitment；ProjectAssignment ⇄ TeamOverview；ProjectDetail（团队区块）→ ProjectAssignment。

## 10. 异常与边界

| 编号 | 情形 | 处理 |
|---|---|---|
| E1 | 无人可用（全员 `departed`/无在职） | `D03_TEAM_EMPTY`；Project `Cap_d=0` → `Cost_est=+∞`（Project B-2）；UI 引导招聘 |
| E2 | 项目被分到某学科但全员 level=0 | 仍可分配但 `Cap_d` 贡献 0（`skillLevel=0` 过滤）；UI 标"该学科无人会"（OPEN-D03-1） |
| E3 | 超额分配（Σ>1） | 命令侧拒绝 `D03_OVER_ALLOCATED`；已有超限仅在读档/旧档迁移时出现 → 按 `share` 归一化（不报错） |
| E4 | 同一人双重雇佣 | RULE-02 拒绝 `D03_ALREADY_EMPLOYED`；读档发现重叠 → 保留 `startDay` 最早的一条，其余 `terminated`（记 `PersonEvent`） |
| E5 | `Cap_d` 计算时 `team_d=∅` | 不除零，直接 `Cap_d=0`（Project B-2；本文 `burden_d=0`） |
| E6 | 项目中途离职 | `resigning` 期间仍可产出至 `effectiveTo`；到点后 `available=false` → Project 下次 tick 自动剔除，**该学科 `Cap_d` 立即降**，UI 告警"某学科团队减员"（RULE-13） |
| E7 | `teamRefs` 含已终止 Employment | `D03_EMPLOYMENT_NOT_ACTIVE`；剔除该成员；若该学科无余 ⇒ `Cap_d=0` |
| E8 | 读档恢复 | `dailyResignProb` 用确定性种子（§11），读档后结果一致；`probation` 到期、`noticeStart`、`pendingSalary` 均按 `dayIndex` 恢复；如读档 `day` 已过 `probationEndDay` 则补算转换（§11 S1） |
| E9 | 技能等级 0 出现在 `teamRefs` | 不抛错，按 §6.1 Z3 过滤（`Cap_d` 贡献 0） |
| E10 | 同一人在两个项目同学科 | 允许；`allocs(e,d)` 有 2 条 ⇒ `share=0.5` 各；**P1 Project `Cap_d` 不减半**（见 §6.2 关键说明，OPEN-D03-4），但收益必须靠 `burden` 提醒玩家 |
| E11 | 候选同人重复入池 | 去重；`D03_DUPLICATE_CANDIDATE` |
| E12 | `retireAge` 到但正忙于项目 | 不强制，离职换 `resigning`（走通知窗口）；不可解雇后立刻重招（曾占用 `Person` 视为退休） |
| E13 | 人格/诉求 = null | 所有代码分支必须 `?? default`，P1 不得因 null 崩溃（DEF-1） |

## 11. 存档要求

| 存档段 | 必须持久化 | 读档行为 |
|---|---|---|
| S1 `Person` | `personId/displayName/birthDay/regionId/skills/seniority/status/currentEmploymentId/baseMorale/rehireCount` | 若 `currentEmploymentId` 指向的 Employment 不 `occupiesPerson` ⇒ 修正为 null（fail-safe） |
| S2 `Employment` | 全部字段（含 `pendingSalary`/`startDay`/`endDay`/`moraleModifier`/`salaryCommitmentId`） | `salaryCommitmentId` 必须能在 FIN 找到（外键校验，缺则修复生成） |
| S3 `Assignment` | 全部 | 读档时若 `effectiveTo < day` ⇒ 标为历史、不计入 `Cap_d` |
| S4 `Candidate` | 全部（含 `availableFromDay`/`expiresAtDay`） | 过期自动移除；已入职的从池中移除 |
| S5 `PersonEvent` | append-only 全量 | 不重算、不压缩 |
| S6 随机种子 | 离职判定用 `hash(employmentId, day)`，**不持久化随机状态** | 天然可重放 |
| S7 版本 | `d03SchemaVersion` | 旧档 `Employee` → 迁移到 `Person`+`Employment`（§14） |

- **确定性**：任何随机（离职、候选池刷新）必须用确定性种子（`hash(entityId, day, salt)`），存档不含 `Math.random` 结果。
- **读档一致性**：`Cap_d` 由 D-03 投影重算，与存档不符即重建（不信任旧缓存，D-03 无缓存）。

## 12. 性能要求

| 指标 | 要求 | 说明 |
|---|---|---|
| 单日 tick（D-03） | ≤ 5 ms（P1，员工数 ≤ 200） | 士气→投射→离职判定；无 O(n²) |

| `fatigueGainPerAllocation`/`fatigueRestRecovery`/`fatigueMultiplier`/`moraleMultiplier` | DEFER | DEFER | P1 不用 |

**注（重要，与 Project §6.2 冲突的解释）**：旧 `baseEffectiveWorkPerDay` 用 `base × skillFactor × moraleFactor × fatigueFactor` 计算出**每个员工的日产能**；Project §6.2 定义为 `k_output × Σ f_skill(level)`，**不含 `morale`/`fatigue`**。按权威顺序 **Project > 旧代码**，故 P1 以 Project 为准，旧 `moraleFactor`/`fatigueFactor` 不参与 `Cap_d`。为保留"士气影响产出"的经营意义，P1 只在**离职**（§6.7）上使用士气；士气不影响当日产出。**此点登记为 OPEN-D03-3**（是否在 P2 将 `morale` 以 `k_morale` 系数注入 Project 公式，需升 `projectFormulaVersion`）。
