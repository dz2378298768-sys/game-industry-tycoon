## 2. 对 R-01 的裁定：不改，理由如下

审核建议把规整段移到引用完整性检查之后（或把终态项目的分配排除出该检查）。**我不接受这一整改**，因为：

1. **会直接违反已冻结规格。** `DESIGN-G05 v1.7 §3.3` 写的是"读档时静默置空，**不因此拒绝加载**"。若把规整移到检查之后，"终态项目 + 悬空员工引用"的旧存档会在 `SAVE_BROKEN_REF` 处被拒绝——玩家一个早已结束、本就该被丢弃的项目上的一条垃圾分配，会导致**整份存档打不开**。这比"掩盖损坏信号"严重得多。
2. **审核提的第二方案与现状等价。**"将终态项目的分配排除出该检查"在实现上就是"先丢弃再检查"，与 `9e474de` 的做法同一效果，只是代码组织不同。
3. **完整性检查的价值在于保护存活数据。** 终态项目的分配已被判定为"必须清空的死数据"，为一条马上要被丢弃的记录做悬空引用校验，没有收益。
4. **损坏信号并非完全丢失。** ① `console.info` 已留痕（`[save] 终态项目团队分配已按 DESIGN-G05 §3.3 释放（N 条）`）；② 非终态项目的悬空引用仍会正常报 `SAVE_BROKEN_REF`（审核探针 P3 已实测）；③ 终态项目自身 `companyId` 悬空仍会被拦（规整只动 `teamAssignments`）。

> **归类说明**：R-01 表面是 A 类（代码位置），实质是 B 类（规格对"容错 vs 报错"的取舍）。按 §5 分工，B 类由设计负责人裁定，不返工编码。若未来 M2 引入存档完整性体系（`DESIGN-M2-DATA-001` 已有 v1→v2 迁移规划），再统一评估"可丢弃数据"与"必须报错数据"的分界。
