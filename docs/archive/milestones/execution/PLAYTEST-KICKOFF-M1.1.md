## 0. 用哪个版本试玩（重要）

**必须用 `TASK-M1.1-TERMINAL-RELEASE-001` 修复之后的提交**，不要用 `b98c9af`。

原因：阶段审核（`../reports/REVIEW-STAGE-M1.1.md` S-1，P1）发现 `b98c9af` 及之前所有版本存在一个功能阻断——项目上市或取消后，原来的团队仍被挂在已结束的项目上，**做完第一款游戏就无法再给第二款组队**（会提示"该员工在多个项目上的投入比例合计超过 100%"），同时已结束项目的预算花费还会在月末继续增长。修复提交出来后，本页的"构建 SHA"一栏填该提交号。

若在修复前试玩，请把这一条加入开场告知，否则玩家做第二款时会直接卡死，试玩数据也就废了。

---

## 1. 为什么这件事必须由真人做

自动化测试（139 用例全绿）只能证明"系统没坏"，**不能证明"好玩"**。本项目设计理念的第一条是"先证明玩法有趣"，因此 M1.1 关闭前必须有 3-5 名真人试玩记录。设计负责人可以主持、观察、记录，但不能代替玩家，也不能用自己的熟悉度冒充新手体验。

---

## 1.5 试玩前**必须**告知参与者的三件事（否则数据会被误读）

这三条是当前版本的**已知范围边界**，不是 bug。主持人开场用 30 秒说完即可，不要说成"设计说明"，就当"这个版本还缺什么"。

| # | 告知内容 | 为什么必须说 | 对应 |
|---|---|---|---|
| 1 | **这个版本没有收入**：做出来的游戏上市后不会带来任何钱，公司现金只会往下走 | 否则玩家会以为"游戏坏了/我算错了"，把观察重点从"经营决策"偏到"找 bug" | OI-24（销售收入属 M2） |
| 2 | **钱很可能是负数**，负了也能继续玩、继续发工资 | 否则玩家看到 −$7,600 会认为已经失败而停止尝试 | OI-21（无破产规则） |
| 3 | **第一个项目可能要追加预算**：默认 $30,000 预算大约撑到第 130 天就会自动暂停，需要追加并手动恢复 | 这正是我们要观察的核心决策点（追加多少？恢复还是取消？），不说清楚玩家会以为是数值 bug | OI-20（默认预算需追加约 60%） |

补充说明（可选，视玩家是否卡住再说）：**分配团队后要先点「推进阶段」到生产阶段，进度才会开始增长**；概念阶段和前期制作阶段不消耗团队产能（OI-19）。

## 2. Owner 需要准备的三件事

| # | 事项 | 规格 | 说明 |
|---|---|---|---|
| 1 | **3–5 名参与者** | 至少 2 名从未接触本项目；熟悉经营游戏与不熟悉者各至少 1 名 | 同事/朋友均可，不需要游戏从业背景 |
| 2 | **1 个 90–120 分钟时段** | 单人单场 30–45 分钟，可连场 | 需能共享屏幕或现场围观（供观察） |
| 3 | **可运行版本** | 设计侧提供构建（`npm ci && npm run build && npm run preview`），记录提交 SHA | 统一初始存档：$50,000、Day 起始、0 人团队 |

**不需要**：不需要参与者读任何文档、不需要提前讲解玩法、不需要他们懂代码。

---

## 3. 现场怎么进行（设计负责人主持）

1. **开场 3 分钟**：只说一句"这是一款经营游戏，你随便玩，边玩边说想法"。**不解释规则**——理解成本本身就是观察对象。
2. **按 7 个场景推进**（S1 创办 → S2 立项 → S3 组队 → S4 研发 → S5 风险 → S6 QA 上市 → S7 复盘），每场景只给一句任务话术（见 DESIGN-PLAYTEST-EXEC-001 §3）。
3. **主持人只做三件事**：计时、记录卡点、追问"你现在在想什么"。**不指导、不代操作、不提示答案**。
4. **收尾访谈 3 问**：你现在在做什么决定？哪个选择让你纠结？再来一次你会换什么？
5. **每人一份记录表**（规格 §5），当场填完。

---

## 3.5 主持人如何构造关键情境（不必让玩家等真实时间）

游戏内时间可加速，构造情境只需几步（主持人操作，不要让玩家看到）：

| 情境 | 操作 | 预期 |
|---|---|---|
| 预算耗尽 | 立项时把"预算上限"设为明显低于人力成本（如 2 人 × 2 个月工资）；点顶部 **+30D** 两次 | 月末结算后剩余 ≤ 0，项目自动暂停，出现橙色"⚠ 预算耗尽"横幅，阶段仍为"制作中（暂停）" |
| 追加后仍暂停 | 在耗尽横幅点【追加预算】输入金额确认 | 面板总额增加，但项目**仍然暂停**，提示需手动恢复 |
| 恢复 | 点【恢复项目】 | 项目恢复推进，暂停计数清零 |
| 暂停超时 | 点【暂停】，再点 **+30D** 两次 | 第 60 天自动取消，红色"⛔ 暂停超时"横幅 + 【查看取消原因】 |
| 主动取消 | 点【取消项目】并确认 | 灰色"✕ 玩家已取消"，同样可查看原因 |

> 注意：**不要让玩家提前知道这些按钮的作用**。主持人只负责把状态推到临界点，玩家自己发现"钱不够了会暂停"才算理解反馈。

## 4. 需要重点观察的四件事

| 观察点 | 达标信号 | 危险信号 |
|---|---|---|
| 是否理解目标 | 无人提示下知道下一步 | 反复问"我该干嘛" |
| 是否主动决策 | 在预算/人员/上市时机上停顿权衡 | 一路点"下一步" |
| 是否在意结果 | 能解释"为什么亏钱/为什么延期" | 对结果无反应 |
| 是否出现策略差异 | 不同人走不同路线（≥2 种） | 所有人同一最优解 |

**特别关注 S5（风险处理）**：如果所有玩家在"预算耗尽"情境下都选同一个方案，说明"有意义的选择"没做出来，属设计问题，需要改设计而不是改文案。

## 5. 交回什么

- 3–5 份填好的记录表（纸质/表格均可）
- 每人的收尾访谈原话（能记多少记多少）
- 主持人 1 页汇总：完成率、卡点 Top3、策略差异、是否愿意再玩
- 可选：屏幕录制

设计负责人据此写 `../reports/PLAYTEST-REPORT-M1.1.md`，作为 M1.1 阶段判断输入，并交独立审核与 Owner。

## 6. 判定口径（不许美化）

| 结论 | 条件 |
|---|---|
| 体验达标 | 7 场景多数完成 + 多数人主动决策并理解结果 + 出现策略差异 + 有再玩意愿 |
| 体验需修 | 存在明确卡点，或普遍机械操作、无主动思考 → 设计负责人裁定修正，允许推翻既有设计 |
| 无法判定 | 样本不足/环境未就绪 → 补做，**不得**用测试全绿推断"好玩" |
