## 4. 一轮开发怎么跑（五阶段）

```
① 设计          ② 设计审核        ③ 编码          ④ 编码审核        ⑤ 阶段验收
你派任务    →   审核代理出结论  →  你派任务    →   审核代理出结论  →  你整体判断
设计代理产出     不过→退回改稿     编码代理交付     不过→退回整改     不全→回①
```

**两个闸门 + 一个总闸**：

| 闸门 | 判据 | 不过会怎样 |
|---|---|---|
| 设计闸门 | 设计审核 PASS / PASS_WITH_NOTES | 不得派编码，退回设计代理 |
| 编码闸门 | 编码审核 PASS / PASS_WITH_NOTES | 不得 CLOSED，退回编码代理 |
| 阶段总闸 | 九项核查 + 跨系统验收 | 单个任务通过 ≠ 阶段完成 |

### 4.1 派设计任务的输入（缺一项就别派）

任务编号与目标 · 背景与相邻系统 · **相关规格的文件路径**（不要只说"参考一下"）· 范围 / 非范围 · 约束（冻结项、接口、存档兼容）· 交付要求（文件名、版本、必备章节）· 期限与粒度

### 4.2 设计代理必须交的 9 项

目标与玩家价值 · 规则与公式（含单位/取整/边界值）· 数据与接口 · 状态与转换 · UI/交互（中英双语文案键、空态、异常态）· 异常与边界 · **假设与待确认项（必须显式列表）** · 验收口径 · 变更说明

> 送审前你要自己过一遍这 9 项。不合格就退回，不要"先送审看看审核怎么说"——那是浪费一轮。

### 4.3 审核结论只有四态（另有两旁路）

| 状态 | 含义 | 下一步 |
|---|---|---|
| PASS | 全部强制项通过 | 进入下一阶段 |
| PASS_WITH_NOTES | 强制项通过，有非阻塞项 | 进入下一阶段，备注登记 |
| REVISE_REQUIRED | 必须改（旧口径：FAIL） | 退回生产者，改后**重新审核** |
| REJECTED | 根本性缺陷（旧口径：FAIL） | 退回重做方案/实现 |
| *BLOCKED* | 缺输入/依赖未定 | 你补输入或调计划 |
| *NOT_VERIFIED* | 无法验证（如需真人试玩） | **不得当通过**，登记未验证项 |

留档时两套口径都写：`REVISE_REQUIRED（旧口径：FAIL）`。

### 4.4 派编码任务的 16 项（缺一不得进 READY）

编号 / 名称 / 目标 / 背景 / 规格及版本 / 范围 / 非范围 / 依赖 / 功能要求 / 数据接口 / UI / 异常 / 测试 / 验收 / 交付物 / 禁止事项

### 4.5 编码代理必须交的 9 项

提交 SHA · 修改清单（含增删行数）· 实现说明（对应规格哪条）· 规格版本 · 测试结果（文件/用例/skip + 四命令）· 手测步骤与结果（UI 附截图）· 已知问题 · 复现方式 · 存档兼容说明

### 4.6 编码审核必须做的四件事

1. **自己跑**四条命令，贴原始输出（不引用交付说明的数字）
2. **反证**：注释掉关键实现 → 测试必须变红 → 恢复 → `git status` 干净
3. **功能回归**：按验收条件逐条实测，尤其"用户能否走通流程"
4. **一致性**：`git show --numstat` 确认既有测试删除行数为 0（防改测试凑通过）

### 4.7 返工与上限

```
审核出 REVISE_REQUIRED
  → 你判断整改范围（只改缺陷 or 重发任务）
  → 问题清单原样转给生产者（不改写、不弱化）
  → 生产者出新提交（不 amend 已审提交）+ 变更说明
  → 审核代理复审，须明确"原问题是否关闭"
```

同一设计连续 3 次 `REVISE_REQUIRED` → 你必须重新评估方向（换方案或缩范围），不许无限打补丁。

### 4.8 任务生命周期

```
PLANNED → READY → IN_PROGRESS → IMPLEMENTED → IN_REVIEW → ACCEPTED → CLOSED
                                    ↑                          │
                                    └── REVISION_REQUIRED ←────┘
                     DESIGN_BLOCKED（需设计裁定）/ RE_REVIEW（整改复审）
```

`ACCEPTED`（技术通过）≠ `CLOSED`（目标完成）。**只有你能置 CLOSED**，子代理只能"申报完成"或"给出结论"。

### 4.9 阶段验收（最容易被跳过）

单个任务 PASS 不等于阶段完成。你必须做跨任务、跨系统检查：

| 检查 | 本项目真实教训 |
|---|---|
| 核心循环完整 | 建公司→招人→立项→组队→推进→QA→上市，玩家能否走通 |
| 多系统组合正常 | **S-1**：三个单任务 PASS，合起来第二款游戏组不了队 |
| 是否存在"每个都对、合起来不对" | 只有跨任务视角能发现 |
| 默认配置能否走通 | OI-20：默认预算+资金走不到上市 |
| 未关闭阻塞 | P0/P1 归零 |
| 体验验证完成 | 真人试玩 |
| 文档/代码/测试/版本一致 | 曾把"21 测试文件"写成"21 提交" |

九项核查 → 结论只能四种：**阶段完成 / 阶段有条件完成（写明范围与风险）/ 阶段未完成 / 阶段暂停**。
