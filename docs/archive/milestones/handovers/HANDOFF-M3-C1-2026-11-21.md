## 0. 一分钟看懂

M3 不是「加更多玩法」，而是把 M2 的「单公司经营游戏」升级成「多公司产业生态」：

- 玩家和 AI 在同一批消费者里抢份额；
- AI 要能算清项目全成本、会营销、会定价、会止损、会破产重整；
- 市场份额来自一个统一需求池，而不是每家 AI 各算一份需求；
- 破产不是公司瞬间消失，而是 90 天重整、可延 180 天、360 天解散，期间可以清仓、卖资产、裁项目；
- 所有结果必须能从真实交易追出来，不允许系统给 AI 发钱、锁份额、强制复活。

C1 是这条链路的最小闭环，只做六件事：AI 完整经营、统一需求池、平台生命周期、真实收入驱动重整、合同对等、seed 差异。**不扩 M4**（不做产业观察 UI、IP 授权、融资并购、六套竞争公式）。

## 4. 系统怎么运作

### 4.1 日循环（`DailyScheduler.executeDay`）

顺序固定，不要随意插队：

1. 暂停超时取消；
2. 销售（需求池 → 每日销量 → 收入流水）；
3. 产品生命周期推进；
4. 退款到期兑现；
5. 营销 tick；
6. 合同结算；
7. 项目研发推进；
8. 员工日更新；
9. 月度结算（工资/房租等）；
10. 预算耗尽判定；
11. 公司现金同步；
12. 破产检查；
13. 清仓模式切换；
14. 重整时钟（90/180 天）；
15. 月末解散检查（360 天）。

关键设计：**销售先于研发**，当日研发完成的产品最早 D+1 销售；破产判定必须在当日所有结算之后。

### 4.2 月循环（AI 决策）

`GameWorld.runAiMonthly` 只在每月 1 日跑：

1. 为每个非玩家、非 dissolved 公司构造 `AiCompanyView`；
2. `planAiMonth` 产出候选项、约束失败原因、最终动作；
3. `GameWorld` 执行动作；
4. 决策记录进入 `aiDecisionLog`，保留 24 个月。

动作分两段：

- Phase A（正常经营）：`START_PROJECT / ADVANCE_PHASE / LAUNCH / SET_PRICE / SET_MARKETING / FUND_PROJECT / CANCEL_PROJECT / CUT_STAFF / DO_NOTHING`
- Phase B（破产）：`RESTRUCTURE / SELL_ASSET / CLEARANCE_PRICING`

`RECOVER` 不是动作：恢复由每日现金/现金流判定自动发生，避免 AI 用动作「刷复活」。

### 4.3 需求池数据流

```
内容表（平台装机/市场份额/受众份额/价格参考/类型亲和）
  → buildDemandScopesForDay（按日插值、平台可用性）
  → audienceUnits = installBase × activity × marketShare × segmentShare
  → purchaseIntent = genreAffinity × platformFit
  → poolUnits = audienceUnits × purchaseIntent
  → attraction = awareness^0.35 × quality^0.30 × value^0.15 × fit^0.10 × brand^0.05 × marketingLift × availability
  → share = attraction^1.5 / Σ
  → allocatedUnits = floor(poolUnits × share)，最大余数法补整
  → 销售记录 → 平台费/退款 → 公司现金
```

不变量：

- 同一 scope `Σ allocatedUnits ≤ audienceUnits`；
- 每个产品在每个 platform×segment 池单独进入，不重复拿完整受众；
- 价格只进 `value`，不进 `purchaseIntent`；
- 所有池按 `productId` 稳定排序，保证同 seed 可复现。

### 4.4 认知度

- 新写入只走 `awarenessByScope`，key = `marketId:platformId:segmentId`；
- `awarenessByMarket` 只做只读汇总，不再由销售管线写入；
- 上市前 90 天有 `launchAwarenessFloor`：`(0.05+0.10×storeVisibility×genreMatch)×qualityGate`，quality<40 时为 0；
- 90 天窗口后再线性淡出 90 天，避免断崖。

### 4.5 公司生命周期状态机

```
active
  └─ 现金 < 0（当前实现）→ bankrupt/restructuring（90 天）
       ├─ 恢复条件满足 → active（warning）
       ├─ 第 90 天满足条件 → 延长到 180 天（仅一次）
       ├─ 第 90/180 天不满足 → winddown
       └─ 第 360 天月末 → dissolved
```

设计意图：破产不是「死亡判定」，而是「资产分拆 + 团队处置 + 真实自救窗口」。

### 4.6 资产处置

- 资产不单独持久化，由产品/合同/项目派生；
- 当前实现只覆盖「产品」这一类，合同权利和未完成项目技术资产尚未接入；
- 估值当前为 `max(过去 12 个月收入×0.5, 账面成本×0.2, $1,000)`，是简化版；
- 成交后产品退市并转给买家，卖方现金入账；
- 无买家不入账，不允许系统注资。

## 7. 当前设计债与风险（优化总设计时优先看）

这一节是交接重点。下面不是「代码没写完」，而是「设计上还没闭环或实现有简化」。

### 7.1 破产进入条件只实现了「现金 < 0」

P0-2 v2.2 §2.1 要求三条任一：

1. 现金 <0 连续 3 日；
2. 发薪日现金 < 应付工资；
3. 现金 + 未来 30 天确定应收 < 未来 30 天应付工资 + 应付账款，且无已签处置/授信。

当前 `applyBankruptcyCheck` 只判断 `balance < cashBankruptThresholdCents`（0），没有 3 日连续、没有发薪日、没有 30 天缺口预测。**总设计若要做真实企业生命周期，这是第一个要补的口子。**

### 7.2 「经营现金流」是近似，不是严格定义

当前 `hasPositiveOperatingCashFlow` 把窗口内所有 posted 流水加总，包含 `advance`、`asset_sale` 等非经营项。规格要的是经营现金流。建议在财务层增加 `cashFlowCategory: operating | investing | financing`，或至少排除 `advance/asset_sale`。

### 7.3 `financialState='warning'` 没有落地

P0-2 要求恢复后 `active + warning`，`runway≥6` 才允许新立项。当前 `Company` 没有 `financialState` 字段，恢复只改 `status`。这会导致「刚恢复就扩张」的旧问题回归。

### 7.4 财务服务允许「未来日流水」立即影响余额

`FinanceService.postTransaction` 不校验 `cmd.day <= 当前日`，测试里可以直接 post 未来日销售并立刻改变现金。当前 E05 延长用例就利用了这一点。**这是测试便利，也是设计漏洞**：真实运行时如果任何调用方写未来流水，破产/恢复判定会提前看到不存在的钱。建议加「未来流水只入账、不进可用现金」或严格禁止未来日 post。

### 7.5 资产处置模型是简化版

- 只支持产品，不支持合同权利、未完成项目技术资产、IP；
- 估值没有严格按 `min(12 个月净收入×0.5–1.0, 账面成本×1.2)`；
- 没有多买家报价/最高价，只选现金最多的买家；
- 「贡献 >50% 当前收入的产品保护」只做了「多产品时剔除主导产品」，单产品时仍可卖；
- 出售后产品 `companyId` 改买家但状态 `retired`，合同权利没有转移。

如果总设计要强化「破产是资产分拆」，需要把 `SellableAsset` 提升为正式领域模型，而不是从产品临时派生。

### 7.6 清仓价与正常折扣是两套字段

`clearanceDiscountRatePercent` 与 `discountRatePercent` 并存。市场管线用清仓折扣覆盖有效价，但定价服务/UI 仍只看正常折扣，可能出现「UI 显示原价、成交是清仓价」的认知差。建议统一为「价格修饰链」：挂牌价 → 正常折扣 → 清仓折扣 → 成交价，并在 UI 显示最终价。

### 7.7 重整期认知度加速衰减还没做

P0-2 §3.1 要求清仓期认知度加速衰减。当前只改了价格和 availability，认知度仍按正常生命周期走。需要在 `product-awareness` 增加 `clearanceDecayMultiplier`。

### 7.8 `RESTRUCTURE` 没有一次性约束

AI 每月都可能选 `RESTRUCTURE`，虽然裁员有下限 1 人、取消项目幂等，但没有「本 episode 已重整过」的标记，可能反复产生裁员交易/遣散费。建议加 `restructuredAtDay` 或「每 90 天窗口最多一次」。

### 7.9 T9–T12 未完成

- T9 合同 `rateProfile`：legacy 合同不能改，realistic 新合同要按现实分成/回收；当前 B 系列合同仍按旧逻辑。
- T10 玩家重整面板：玩家破产后看不到 90 天期限、恢复线、可卖资产、清仓状态，体验是断的。
- T11 长跑：还没有 8 seed×10 年 C1 结果，无法回答「恢复次数、破产时点分布、HHI、seed 差异」。
- T12 最终验收：四命令 + E01–E36 语义验收报告未出。

### 7.10 性能与存档

- 需求池按日重算，不做持久化，这是对的；但 10 年长跑的内存/时间还没在 C1 配置下复测。
- `save-schema` 是 `.passthrough()`，新增字段能存但缺少严格校验；旧档迁移测试覆盖了关键字段，不等于所有新字段都有回归。
