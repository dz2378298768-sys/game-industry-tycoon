| 属性 | 内容 |
|---|---|
| 审查对象 | `../../../design/milestone-specs/DESIGN-M2-001-F-MARKETING.md` v1.0 |
| 结论 | **REVISE_REQUIRED** —— P1×3、P2×3 |
| 日期 | 2026-11-19 |

## 1. P1

### P1-1 衰减与投放同日顺序冲突（数值一致性）

§4 写"① 衰减 → ② 扣款 → ③ 提升"，但同时写"衰减仅对有 campaign 记录的产品"。玩家今日刚设预算并当天 tick：衰减先打 3%，再花 50k 提升——等于**新投放第一天必亏 3%**，且与"停止投放"的判定（预算 0 或 ended）语义纠缠。规格没定义"今天有投放是否仍衰减"。

**改法**：衰减只作用于**当日该渠道实际扣款失败或未投放**的情形；当日成功扣款的渠道不衰减。顺序保持"衰减 → 扣款 → 提升"，但衰减判定用"本日扣款结果"回填，明确写成两步：先按上一日有效投放状态衰减，再扣款；扣款成功的渠道在提升前**回补**被误衰减的 3%（等价于不衰减），避免顺序依赖产生不同结果。测试补 F-衰减-01。

### P1-2 分成基数扣退款但已结算部分不追回，口径自相矛盾（财务一致性）

§5 说基数 = 当日净销售 − 当日 posted 退款。但退款可能发生在**销售日之后**（窗口 14 天）：第 100 天销售、第 110 天退款，第 100 天的分成已按毛净额结给发行方，第 110 天基数里却没有这笔冲减。结果是发行方**永久多拿**退款那部分分成，且规格没有任何追回机制。

**改法**：明确"分成按**发生过退款后的最终净额**结算"不可行（无法预知未来），改为：
- 结算日基数 = 当日净销售 − **当日 posted 退款**（保留）；
- 对"退款所属销售日已结算过分成"的批次，在退款当日按同费率**冲减**一笔（负数 `contract_payment`，幂等键 `contract:<id>:refund:<batchId>`），把多付的部分扣回。
- 若合同已 completed/terminated，不再冲减，并在交付中登记为已知边界。

### P1-3 里程碑累计口径与分成不一致（规则一致性）

§5 里程碑"累计基数自 signedDay 起，口径同上"，但"同上"指的是**单日**净额口径；跨日累计时若退款发生在累计期内，按当前写法会重复计算（销售日计一次、退款日再扣一次）或漏算，取决于实现者理解。规格必须给出**累计公式**，不能只写"口径同上"。

**改法**：累计 = Σ(自 signedDay 起每日净销售) − Σ(自 signedDay 起每日 posted 退款)；退款一律落在 `refundDayIndex` 当天扣减，不在原销售日回改历史（与 B 批"历史不可变"一致）。补 F-里程碑-02 验证退款跨日。

## 2. P2

| 编号 | 问题 | 改法 |
|---|---|---|
| P2-1 | 均分余数给"第一个市场"，但市场顺序未定义（对象键序不稳定） | 按 marketId 字典序排序后取第一个 |
| P2-2 | 合同到期"里程碑未达成则 terminated"，但已结算分成合同到期应为 completed | 分成合同到期即 completed；里程碑到期未达成 terminated |
| P2-3 | 现金不足只 warning，但玩家无感知 | 事件 `MARKETING_SPEND_FAILED` 进事件流（第 7 个事件），UI 批展示 |

## 3. 八维

可行性 通过｜游戏性 通过（花钱换销量）｜完整性 **不通过**（P1-2 漏账）｜一致性 **不通过**（P1-1/P1-3）｜数值 待补（P1-1 衰减）｜体验闭环 通过｜异常 通过｜可验收 待补（退款冲减用例）

## 4. 结论

P1×3、P2×3，全部 v1.1 修订后进 R2。
