## 四、C1 专项反证：TC-05 手工验算

### 4.1 Project §6.2 原文（权威，Project V0.1.1 L391–395）

```
team_d   = { e ∈ teamRefs : available(e, day) ∧ skillLevel(e,d) > 0 }
f_skill  = {0:0, 1:0.6, 2:0.8, 3:1.0, 4:1.2, 5:1.4}
Cap_d    = k_output × Σ_{e∈team_d} f_skill(skillLevel(e,d))
```

### 4.2 TC-05 输入（D-03 §13.1 L801–810）

`k_output=10`；`teamRefs={e1,e2,e3,e4}`；`W_code>0`：

| e | level | Assignment(P1) | status / endDay |
|---|---|---|---|
| e1 | design 4, code 3 | art, 0.3 | active / null |
| e2 | design 1, art 2 | art, 0.5 | active / null |
| e3 | code 5 | 无 | active / null |
| e4 | code 2 | code, 0.4 | **resigning / endDay = D** |

### 4.3 逐步验算（本审核独立计算，不取设计稿结论）

**Step 1 `available`**（按 D-03 §6.1 Z2）：

- e1: `occupiesPerson=T ∧ active ∈ {probation,active,resigning} ∧ endDay=null` ⇒ **T**
- e2: 同上 ⇒ **T**
- e3: 同上 ⇒ **T**
- e4: `resigning ∈ 集合 ∧ day=D ≤ endDay=D` ⇒ **T**

`available = (T,T,T,T)`。✅ 与设计稿 L813/L820 一致。

**Step 2 `team_d`**（Project 原文，`skillLevel>0`）：

- `team_code`：e1(code 3)>0、e2(code 0) 排除、e3(code 5)>0、e4(code 2)>0 ⇒ **{e1,e3,e4}**
- `team_design`：e1(4)、e2(1) ⇒ **{e1,e2}**；e3(0)、e4(0) 排除
- `team_art`：e2(2) ⇒ **{e2}**；e1(art 0)、e3(0)、e4(0) 排除

**Step 3 `Cap_d`**：

- `Cap_code = 10 × [f(3)+f(5)+f(2)] = 10 × [1.0+1.4+0.8] = 10 × 3.2 =` **32** ✅
- `Cap_design = 10 × [f(4)+f(1)] = 10 × [1.2+0.6] = 10 × 1.8 =` **18** ✅
- `Cap_art = 10 × [f(2)] = 10 × 0.8 =` **8** ✅

**结论：`Cap_code=32 / Cap_design=18 / Cap_art=8`，与设计稿 §13.1 L815–817 逐值相符，且与 Project §6.2 公式严格一致。** e1（多学科但只分到 art）与 e3（无 Assignment）都被正确计入 `team_code`，这正是 V0.1 Z1 会漏掉的两人。

### 4.4 错误值对照（必须证明 22 才是错的）

若把 V0.1 的 discipline 过滤加回 `team_code`（即 `team_d` 只收"存在 `Assignment(project, d)`"的成员）：

- `team_code' = {e4}`（仅 e4 有 code 分配；e1 分的是 art、e3 无分配）⇒ `Cap_code' = 10 × f(2) = 8`
- 若再加"剔掉 resigning"（V0.1 的 L296 写法）⇒ `team_code'' = ∅` ⇒ `Cap_code'' = 0`

设计稿 L822 给出的对照值是 `10 × [f(5)+f(2)] = 10 × [1.4+0.8] = 22`，对应"**保留 available 与 skillLevel>0 过滤，但仍按 discipline 收窄**"这一种实现（即 e1 被剔、e3 保留、e4 保留）。

- 本审核复核：`10×[1.4+0.8]=22` 算术正确 ✅；
- 其与 32 的差 `32−22=10` 恰等于 `10 × f(3) = 10 × 1.0`，即**被错误剔除的正是 e1 的 code 贡献**——数值上精确对应"多学科员工被 discipline 过滤误杀"这个根因 ✅；
- 因此 22 **确实是错误值**，且设计稿把它标为 FAIL 反证锁是**正确**的（不是"用另一个错值掩盖"）。

**补充复核（设计稿未覆盖，本审核补充）**：设计中还存在第三种错法——"把 `T_d`（有该学科分配者）当 `team_d`"。按 §6.2 L396 `T_code={e4}`、`T_art={e1,e2}`、`T_design=∅`，若误用会得 `Cap_code=8 / Cap_design=0 / Cap_art=10×[1.0+0.8]=18`，**三学科全部不同**。§6.2 L400 已明文警告"二者不得互相替代"，且 TC-05 以 32/18/8 三个值同时锁定，**能覆盖这一错法**。✅

设 `startDay=2026-02-15`、6 个月、月薪 500_000。按 FIN §4.1/§10.3，取消语义是"**停止未来周期**"——即"当前周期（2026-04）及以后"是否仍兑现取决于**周期是否已过**。FIN 全文**没有** `cancelCommitment(effectiveMonth)` 这一参数，也没有"取消所在月仍计一笔"的规则。两种解释给出不同结果：

- **D-03 解释**：cancel 于 2026-04 ⇒ 04 月照付（3 笔，`realizedCents=1_500_000`），05–07 停。
- **FIN 字面**：cancel 生效于 2026-04 ⇒ 从 04 起停止未来周期（04/05/06/07 都不再兑现）⇒ 2 笔，`realizedCents=1_000_000`；04 月若已按周期计提则不受影响（"已入账不冲回"）。

两者相差 1 笔 500_000。**同一"离职当月是否计薪"问题，D-03 §6.3 与 §7.2 给"照付"、FIN §4.1/§10.3 给"停止未来"，且 D-03 自称"按 FIN §3.3 周期口径处理"——引用它并不支持该结论**（FIN §3.3 无此规则，§4.1/§10.3 才是）。这是**确定规则与上游冲突**，属 C4 未关闭的直接证据，也是编码**必然踩坑**点（CODE-06 按 §7.2 写会在 FIN 侧对不上 6 笔/`realizedCents`）。

### 5.3 修改要求

1. **先定语义**：`endDay` 所在月是否计薪。建议**按 FIN §4.1 口径**："`cancelCommitment` 的生效周期 = `endDay` 所在月的**下一周期**起点"，即离职当月已发生时点仍计、未发生时不补——并把"何时算'已入账'"（月末计提 vs 月末结算）写清。
2. 若坚持"离职当月照付"，**必须**给出 FIN 侧依据或标 OPEN，并在 §7.2 算例中改成"3 笔 / `realizedCents=1_500_000`"**且注明与 FIN §4.1 的关系**；同时向主 AI 登记 `cancelCommitment` 的 `effectiveMonth` 参数扩展请求（FIN 现无此参数，`grep` 已确认）。
3. TC-11b 增补"离职当月"分支断言（2 笔 vs 3 笔），避免实现者二选一。
