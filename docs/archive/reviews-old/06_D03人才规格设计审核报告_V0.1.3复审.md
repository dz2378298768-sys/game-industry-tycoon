## 一、最终结论

**PASS WITH CONDITIONS（裁定方向正确、D03-26 作为"金钱规则"已实质闭合；但引入 2 项由裁定派生的新缺陷，其中 1 项**阻塞 CODE-06 交付**）**

### 1.1 判定摘要

1. **D03-26 的"产品规则"层已关闭**。§6.3 L476 给出确定结论（`endDay` = 结算日当天 ⇒ 当月不计），L478–484 五场景表、TC-11b 分支 ③④、§18.5 ORD-01、§18 DEF-3 交叉引用**逐处均在正文**，且五场景数值经本审核独立推算**逐值一致**（§二）。实现者不再需要"顺手选一个方向"。
2. **代码事实成立**。「人事先于薪资结算」两处引用（L101 < L107）**正确**；但 ADJ-07 与正文对这**两条流水线的**具体跳过机制描述**不准确**（§四），并由此漏掉一个真实缺口（新缺陷 **D03-36**）。
3. **新引入 1 个会直接导致 CODE-06 失败的自相矛盾**：§6.3 L476/T7 要求"离职当场置 `status` 非 `active`"，而现基线 `EmployeeStatus` 枚举**没有 `active` 这个值**（`hired/on_leave/resigned/fired`），既有测试 `employee-rules.test.ts:82` 断言**再次解雇返回 `EMP_ALREADY_TERMINATED`**；若按 D-03 的 `terminated` 状态机实现，该测试必失败（**D03-35，MAJOR，阻塞**）。
4. **新引入 1 个契约级缺陷**：ORD-01 把"日循环顺序"写成 D-03 ↔ FIN 的**双方契约**，但日循环顺序的权威属 Project（P0-B §3.2）与仿真编排层；而"薪资先建承诺、月底由 FIN 兑现"的既有链路（`finance-commitment.ts:187` `cancelCommitment(c, effectiveMonth)` 已实现）在当前薪酬结算**完全未被使用**（`daily-scheduler.ts:337` 走的是裸 `postTransaction`）。顺序契约若不注明三条流水线的覆盖范围，D03-26 的裁定在 FIN 承诺链路上**并未真正生效**（**D03-36，MAJOR**）。

6. 上轮遗留 D03-27/28/29（MINOR）与 D03-30~34（SUGGESTION）**均未处置**，不构成回退，继续留档。

## 二、D03-26 关闭验证（自算五场景，未抄 §6.3 表）

### 2.1 独立推算口径

- 输入：`startDay = 2026-02-15`、`initialTermMonths = 6`、`salaryMonthlyCents = 500_000`（与 §7.2 L713 一致）。
- `periodCount`（FIN §3.3 L148/159，`startAt..endAt` 含首尾不同日历月）：`startAt = 2026-02-01`、`endAt = 2026-07-31` ⇒ **6**，`totalPlannedCents = 3_000_000`。
- 结算日：**每月最后一个自然日**（`settle(y,m) = lastDayOfMonth(y,m)`，即 `daily-scheduler.ts:307` 的 `g.day === daysInMonth` 判定）。注意：不是"最后一个工作日"（`workingDaysPerMonth` 只用于成本侧分摊，Project §6.4 L416，与现金不挂钩）。
- 计笔规则：当且仅当 `settle(y,m) < endDay` 时该月已入账（**严格小于**——因为裁定规定"人事先于结算"，`settle == endDay` 当日离职先于当日结算，故不计）。以这一条规则计算，**没有**为"月初/月中"另设分支。

### 2.2 推算结果

| 场景 | `endDay` | 已入账月份 | 笔数 | `realizedCents` |
|---|---|---|---|---|
| 月中离职 | 2026-04-10 | 02、03 | **2** | 1,000,000 |
| 月初离职 | 2026-04-01 | 02、03 | **2** | 1,000,000 |
| **月末结算日当天** | 2026-04-30 | 02、03 | **2** | 1,000,000 |
| **结算日次日** | 2026-05-01 | 02、03、04 | **3** | 1,500,000 |
| 起始月首日 | 2026-02-01 | — | **0** | 0 |

（本审核用独立脚本按上式逐值验证，与 §6.3 L478–484 表**逐格一致**；`04-30` 当日 `settle == endDay` ⇒ 不计；`05-01` 时 `04-30 < 05-01` ⇒ 04 已入账，已入账不冲回。）

### 2.3 与上轮结论的差异

| 场景 | 上轮（V0.1.2）结论 | 本轮结论 | 差异性质 |
|---|---|---|---|
| 月中 04-10 | 2 笔 / 1,000,000 | 2 笔 / 1,000,000 | 无差异 |
| 月初 04-01 | 2 笔 / 1,000,000 | 2 笔 / 1,000,000 | 无差异 |
| **月末 04-30** | **未定**：2a ⇒ 3 笔 / 2b ⇒ 2 笔 | **2 笔 / 1,000,000** | **规格已裁 2b**（即"人事先于结算"） |
| 结算日次日 05-01 | 上轮未单独推（仅隐含） | 3 笔 / 1,500,000 | 新增分支，与"已入账不冲回"同向，无冲突 |
| 起始月首日 02-01 | 0 笔（上轮 §4.2 末段已推，但未入 TC） | 0 笔 | 数值一致；本轮入 TC 未覆盖（见 D03-38） |

- **结论**：五场景全部与裁定同向；**没有**出现"算出不同就是缺陷"的情形。

### 2.4 一个额外的时点事实（不构成缺陷，但影响"起始月"场景的意义）

现基线的**登记录入发生在命令处理时刻**（`game-world.ts:315` `this.world.employees.push(emp)`，`hire` 时 `status: 'hired'` 即写入），而不是 `arrivalDay` 才进入 `world.employees`；这与 D-03 §6.3 L454 的"`arrivalDay`（入职日）由 FIN 兑现"是**两件事**（一个是实体存在，一个是招聘费现金）。本审核核对结论：
- **薪资循环**只看 `status === 'hired'`（`daily-scheduler.ts:333`），招聘当日即可能落到月末 ⇒ **登记录入日恰好是该月结算日时，会当天计 1 笔**。这不是 D03-26 的边界，但与本裁定共享"日循环顺序"，应在 CODE-06 的 TC-11b 分支 ⑤（见 §六 D03-38）同批验证。
- D-03 §6.3 L446–450 未把"登记入 world 的时点"与"`arrivalDay`"的关系写成条款（V0.1.2 即存在），本轮**不算新增**，仅提示编码侧注意。

## 五、新矛盾排查（逐个回答）

### 5.1 Z2 `available` 与"当天不计薪"是否矛盾？——**不矛盾**（本审核独立判定）

**结论：不矛盾，且是本设计的分层本意。**

理由（不引用任务书提出的"可用=产出、薪资=付款"这一先验假设，而是从正文复推）：

1. **§6.3 L350（RULE-11）明确把两件事拆开**：`terminated` 的"出勤"与"薪酬"分别描述——`available` 由 §6.1 Z2 定义，**只回答"此人此刻能否投入"**（L394 原句）；薪酬由 §6.3 + FIN 定义，走"已入账/未入账"的**时点语义**。两句都要求"截止判据是 `endDay`"——一句说**产出的截止**，一句说**付款的截止**。
2. **同一时点的两种不同语义是必要的**：`endDay` 是"最后可工作的一天"，但"这一天的活儿不结算成整月钱"——这正是 DEF-3（P1 不做按日折算）导致的**必然口径**。若强行"当天不计薪 ⇒ 当天不可用"，会导致 `endDay` 当天 `team_d` 少 1 人，与 TC-15 断言"含 `endDay` 当日"相反 ⇒ 反造出一个新的 MAJOR。**因此"可用但无薪"是唯一不破坏 TC-15 的口径**。
3. **边界仍要在文档里说明**（SUGGESTION **D03-39**）：§6.1 Z2 的"≡"式应当有一句"`available` 描述**出勤窗口**，与 §6.3 的**付款窗口**（`settle < endDay`）不是同一判据，二者不一致是 DEF-3 的已知结论，非缺陷"。否则未来的读者会再次提问。

### 5.2 `previewRunwayImpact` / `previewCashAtHire` 是否要按新裁定调整？——**不需要**

- `previewRunwayImpact`（§6.5 L512–518）回答"创建时刻新增在途承诺"：`= salaryMonthlyCents × periodCount + recruitCostCents`，**以未取消的 6 期计**。此式在"离职发生之后"本来就不成立（离职时 `totalPlannedCents` 仍为 3,000,000，但 `realizedCents` 只到 1,000,000），而 §6.5 已写明"两项承诺都在 `hireConfirmDay` 创建 ⇒ 都计入创建时刻"——**口径本身已限定为创建时刻，与离职日的时点无关**。
- `previewCashAtHire`（L519）是"`arrivalDay` 招聘费 + `endDay` 遣散"的**兑现时点**现金，与月薪笔数无耦合（遣散按 `severanceMonths × salary`，固定式）。
- 结论：**两式均无需改**。但建议在 §6.5 加一句"本式不含中途取消后的 `realizedCents` 修正；离职后的实际跑道路径以 FIN `CommittedBurn` 为空"（并入 D03-39）。

### 5.3 §7.2 `cancelCommitment(effectiveMonth = monthOf(endDay))` 与"当月不计"是否一致？——**一致，而且代码天然给出**

- 以 04-30 离职为例：`monthOf(endDay) = 2026-04`。`cancelCommitment` 的 `realizedPeriods = monthOrdinal(2026-04) − monthOrdinal(2026-02) = 2`（`finance-commitment.ts:194`）。这与"02、03 两笔、04 月 0 笔"**逐值吻合**。
- **取消生效月 = 当月，而"当月 0 笔"** 看起来像"取消生效月却没有兑现"——经核对 FIN §4.1 L265 与代码 `set state='cancelled'`，语义是"**自该月起不再兑现**"，不是"该月必须兑现"。`cancelEffectiveMonth` 记录的是边界而非兑现月。**两者一致，无矛盾。**
- 补充确认（正面加固）：`cancelCommitment` 用 `Math.max(c.realizedCents, realizedCents)`（L203）保证"已入账不冲回"——与 05-01 场景的 3 笔口径**同向**。

### 5.4 TC-11b 分支 ③④ 的"结算日"是否可无歧义执行？——**可执行，但"结算日"未入符号表**（MINOR）

- 判据本身可判定：③ `endDay = 2026-04-30` ⇒ 2 笔；④ `endDay = 2026-05-01` ⇒ 3 笔。两者只要实现者在**同一条 6 期承诺**上用同一 `settle()` 定义即可无歧义。
- 但"**结算日**"这个词在本文中**只出现在叙述性的 L475/L476/L482/L483**，**未进 §6.9 符号表**；FIN §3.3 也只有 `periodCount` 与幂等键 `<YYYY-MM>`，**未定义"月末结算发生在哪一天"**。本审核在 §2.1 通过代码（`daily-scheduler.ts:307` `g.day === daysInMonth`）**推断**为"每月最后一个自然日"，而不是"最后一个工作日"。这个推断在现有代码里成立，在规格里是隐含的。
- 判定：**可执行但未闭死**，列为 D03-38（MINOR），要求 §6.9 补 `settlementDay(m) = lastDayOfMonth(m)`。
