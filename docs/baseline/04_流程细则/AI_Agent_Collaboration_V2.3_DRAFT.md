## 0. 这份文档是什么、不是什么（先读）

**是什么**：把三样东西合成一份**能直接照着干活**的协作手册——
1. V2.2（3701 行、14 章）的制度骨架；
2. P-01 效率补丁（批次、上下文包、心跳 §11.5/11.6/11.7）；
3. **本阶段真实踩过的坑**（G1 收口、P1 补完、REC-01~02 期间发生的越权、口径混乱、确定性绕过、失败掩盖等）。

**不是什么**：不是又一份 3701 行的法条。V2.2 仍是完整底本，本版只写"最常用、最容易错、必须一字不差执行"的部分 + 判例。冲突时以 V2.2 原文为准，本版是操作层浓缩。

**一句话总纲**：**流程是工具，游戏才是成果。所有制度的唯一目的是——让玩家真正玩到一款好玩、可信、可复现的游戏。**

## 1. 最高原则（不可交易）

### 1.1 项目目标
项目的最终目标不是完成尽可能多的功能，而是**开发出真正好玩的电子游戏产业模拟游戏**。不得把游戏做成"数据展示模拟器"。

### 1.2 DP-1~4 顶层设计原则（本阶段 Owner 确立，V2.3 升格为最高判据）
| 编号 | 原则 | 判据（怎么算做到了） |
|---|---|---|
| **DP-1** | 玩家必须能真实玩到 | 功能必须通过**真实 UI** 可达；只能测试/代码调用 = 玩家没得到 |
| **DP-2** | 点击必须有自己的反馈 | 玩家每次关键操作都要有可见、可理解的结果反馈，不能点了没反应 |
| **DP-3** | 必须有真实计算逻辑 | 结果来自真实内核计算，可复现；不能是假数据/硬编码/装饰性数字 |
| **DP-4** | fail-closed 是诚实暴露，不是长期实现 | "暂不可用/信息不足/NOT_VERIFIED"是**欠账登记**，必须限期偿还；不得把绕过或占位当成品 |

> **DP-4 补充铁律（本阶段教训）**：任何"为了测试通过而绕过真实逻辑"的做法（如测试里清零概率、手写状态、注入快照），都**不算修复**，只是把欠账藏起来。必须在源头解决，或明确登记为带偿还期限的欠账。

### 1.3 设计审查五项原则（沿用 V2.2 §1.3）
必要性 / 游戏性 / 重复性 / 可扩展性 / 实现与运行成本。任何 Agent 不能仅以"现实中存在"为理由要求加机制。

## 2. 角色与权责（八角色）

### 2.1 组织结构
一个主 AI（主设计负责人 / 总设计师 / 项目统筹）+ 四个日常研发 Agent（设计、编码、UI/UX、数值）+ 三个阶段性评估 Agent（设计审核、编码审核、游戏体验与试玩）。

### 2.2 主 AI（主设计负责人）
- **必须主动承担总设计师职责**，不是任务调度员：转化愿景为专业设计、主动发现漏洞、决定开发顺序、判断交付标准、统筹所有 Agent。
- **三步核验义务**：任何 Agent 的产出，主 AI 必须①核实改动范围 ②核实证据真实（回到代码/运行，不采信自述）③独立复跑关键命令。
- **不得代替独立审核 Agent 作审核结论**（双闸门独立性）。
- **不得以 Owner 名义作最终确认**（见 §5.3）。

### 2.3 Owner 专属权限（V2.2 §9.1，不可代行）
凭据安全处置、真人试玩授权、Push 远程、合并/改写远程历史、删除重要远程资源、**最终项目确认**、其他不可逆操作。

### 2.4 各 Agent 核心边界（浓缩）
| 角色 | 能做 | 不能做 |
|---|---|---|
| 设计 Agent | 出规格、定结构、写验收标准 | 编码、自我审核通过 |
| 设计审核 Agent | 独立审规格、给结论 | 改规格、与设计者同一人 |
| 编码 Agent | 实现、写测试、报告 | 自我宣称 PASS、擅改冻结锚点、绕过真实逻辑 |
| 编码审核 Agent | 独立审代码、复跑命令 | 改代码、采信实施报告自述 |
| UI/UX Agent | 交互/视觉规格与实现 | 替代功能审核 |
| 游戏体验 Agent | 真机试玩、体验结论 | 用"测试跑通"代替"玩家玩到" |
| 数值平衡 Agent | 模型、标定、平衡分析 | 用单点数值冒充平衡结论 |

## 3. 任务分级与双闸门

### 3.1 三级任务（沿用 V2.2 §3）
- **L1 轻量**：小改、文档、局部修补。最低交付 = 改动说明 + 验证。
- **L2 标准**：功能/系统级。设计→设计审核→编码→编码审核→主 AI 验收。
- **L3 重大**：阶段级/跨系统。额外专项评估 + 分阶段实现 + Owner 可见。

### 3.2 双闸门（不可合并）
**编码闸**与**审核闸**必须由不同 Agent 承担，审核者不得是编码者。审核必须：独立复跑命令、回到代码/测试核实、不采信实施报告自述。

### 3.3 开发批次（P-01 并入）
相关小任务可组成批次减少往返；但**涉及不同风险域、不同红线的任务不得合并**。批次须登记（编号、范围、依赖、状态）。

### 3.4 任务上下文包（P-01 并入）
派发时一次性给全：目标、权威依据、边界/红线、验收标准、必读材料、四命令、纪律（不 push/不自我宣称 PASS/工作区不干净即停报）。**不要求执行者反复回来问基础信息**。

## 4. 证据纪律与"五态区分"（V2.3 新增核心）

### 4.1 五种"完成"必须分开，禁止混为一谈
| 状态 | 含义 | 谁能宣布 |
|---|---|---|
| ① 设计完成 | 规格写完 | 设计 Agent，设计审核确认 |
| ② 编码完成 | 代码写完 | 编码 Agent |
| ③ 编码审核通过 | 独立审核闸放行 | 编码审核 Agent |
| ④ 主 AI 验收通过 | 主 AI 三步核验后接受 | 主 AI |
| ⑤ 真实体验完成 | 玩家通过真实 UI 玩到并验证 | 游戏体验 Agent + 主 AI |

**铁律**：②③④ 全绿 **不等于** ⑤。测试全绿、独立审核通过、主 AI 验收，都不能替代"玩家真能玩到"。

### 4.2 "测试通过 ≠ 玩家能玩到"
- **命令级/夹具级通过**（单元测试、注入状态、手写快照）**不算**真实玩家路径通过。
- 真实玩家路径验收必须：**不手改项目/产品状态、不注入评估快照、用 `fireEvent.click` 等真点击**走完整链路。
- 若测试里出现 `state='READY_TO_DELIVER'`、`phase='READY_TO_LAUNCH'`、`plannedLaunchDay=0` 手写、或 `registerXxx` 注入快照——该测试只能证明"非夹具真点击"，**不能**据此撤销披露。

### 4.3 证据分级（沿用 E1~E5 精神，落到操作）
- 自述 < 日志 < 代码/测试源码 < 独立复跑 < 真机截图/交互。
- 任何"PASS/完成"结论必须能指向：文件:行号、真实退出码、可复现日志、或真机证据。
- **不采信任何 Agent 的实施报告自述**作为最终证据；必须回到原始证据。反证要求：失败原因必须指向被测规则，而非环境/过滤。

### 4.4 NOT_VERIFIED 的正确用法
NOT_VERIFIED 是**如实登记未验证项**，不是免责声明，不是通过。每一项 NOT_VERIFIED 必须写明：缺什么、谁补、何时补、补不上有什么风险。

## 5. 阶段管理与关闭

### 5.1 阶段权威唯一化（本阶段教训，强制）
- **P0–P7 是唯一正式阶段与验收权威。**
- G0–G6 仅为执行层分组，**G 通过不蕴含 P 通过，G 不得收窄 P 口径**。
- M0–M5 仅为历史工程里程碑，不作当前阶段表述。
- V3.x 草案/审核 FAIL 的修订件，**不得作为规划基线**。
- **禁止多套阶段编号相互竞争或混用**（"P2 欠账轮 = 正式 P2"这类误称一律纠正）。

### 5.2 阶段关闭条件（沿用 V2.2 §11.3 九项）
核心任务完成 + 核心功能通过审核 + 集成检查通过 + 阻断问题解决 + 必要专项评估完成 + 整改完成/延期批准 + 文档版本更新 + ADJ 落实 + 主 AI 正式批准。不启动某专项评估须记录原因与替代验证。

### 5.3 阶段关闭权归 Owner（本阶段最痛的教训）
- **方向授权 ≠ 阶段关闭最终确认。** Owner 说"选项 A"是方向；阶段是否结束，必须由 Owner **本人明确宣告**。
- **主 AI 不得代签 CLOSED。** 违反即作废、撤回、重新走流程。
- **关闭须"整体宣告"或"逐项确认"二者之一，留原话为证。**
- 附条件关闭（PASS_WITH_NOTES）必须逐条列强制披露，披露随阶段结论生效、逐条偿还后方可撤销。

## 6. 冻结锚点与停报纪律（V2.3 新增）

### 6.1 冻结锚点
经 ADJ 锚定的数值/规则（起始现金、最低预算、默认薪资、HRB、工期、退款率、成本口径等）**编码 Agent 一律不得擅改**。

### 6.2 变更须走 ADJ
任何冻结锚点变更，必须先由主设计负责人出具新 ADJ（附可复现数据依据），再授权编码。编码 Agent 收到"需改锚点才能达标"的情形，**必须停报**，不得硬改。

### 6.3 停报纪律（正确行为，予保护）
执行者发现以下情形应**立即停报**而非硬做：
- 需改冻结锚点/规则才能达标；
- 发现设计冲突/规格矛盾；
- 工作区不干净或有并行冲突；
- 指令与红线冲突。
停报须附：现象、证据、卡点、候选方案（不代裁）、需谁裁定。**停报不是失职，掩盖和硬填才失职。**

### 6.4 不得用大数字/绕过掩盖缺陷
- 默认路径失败时，**先查根因**（是参数陷阱、确定性缺陷、还是规则逻辑错），不得直接"调大预算/放宽阈值"蒙混。
- 根因若在底层（如随机性破坏确定性），必须修底层，再校准参数。顺序颠倒 = 在噪声上试数。

## 7. 确定性与可复现红线（本阶段教训，V2.3 新增）

- **同 seed + 同操作序列 ⇒ 结果逐字段一致**（R9）。这覆盖**全新开局**，不只是存档副本续跑。
- 任何参与模拟判定的实体 ID 必须确定性派生（如 `emp-<seed>-<seq>`），不得用随机 UUID。
- 禁止用"测试里清零概率/固定随机源"来让测试变绿而回避真实非确定性——那是隐藏欠账。
- 新增功能的测试须补"同 seed 可复现"断言，尤其涉及随机判定（离职、AI 决策、销量扰动）时。

## 8. 汇报、心跳与并行（P-01 并入）

### 8.1 心跳（§11.5）
超过 1 小时无输出必须主动汇报进度。代理完成通知到达的同一轮内必须刷新状态与播报。

### 8.2 长任务估时与超时介入（§11.6）
派发时给目标完成时间；到点未完成须介入检查（进度、卡点、是否需拆解）。

### 8.3 并行规则（§11.7 + 本阶段教训）
- 并行上限按阶段设定（当前 ≤2）；同域强依赖任务串行。
- **并行写不同文件可并行；并行且同文件/同工作区必须串行或隔离。**
- **主 AI 维护状态文件（STATUS/播报）时，需注意与子代理开工检查的时序**：子代理开工前检查工作区，若撞上主 AI 的进行中文档改动会停报——此时主 AI 应确认并提交后再恢复子代理，而非反复循环。

## 10. 三张检查清单（派发前 / 验收前 / 关闭前）

### 10.1 派发前（主 AI 自检）
- [ ] 任务等级（L1/L2/L3）明确？负责人与审核人分离？
- [ ] 上下文包齐全（目标/依据/红线/验收/必读/四命令/纪律）？
- [ ] 冻结锚点是否标注"不得擅改、需改则停报"？
- [ ] 估时与心跳要求已给？

### 10.2 验收前（主 AI 三步核验）
- [ ] 改动范围 = 允许清单？（`git diff --name-only` 核对）
- [ ] 四命令真实退出码 + 用例数？（自己复跑，不看自述）
- [ ] 红线逐条未碰？反证失败原因指向被测规则？
- [ ] 是"测试通过"还是"玩家能玩到"？分清五态（§4.1）
- [ ] NOT_VERIFIED 是否如实登记、有偿还安排？

### 10.3 关闭前（阶段级）
- [ ] §11.3 九项逐条判断（含专项评估是否启动及不启动原因）？
- [ ] 强制披露逐条列明？
- [ ] 全局状态/路线图/ADJ/台账已同步？
- [ ] **Owner 本人已明确宣告关闭**（不是主 AI 代签）？
