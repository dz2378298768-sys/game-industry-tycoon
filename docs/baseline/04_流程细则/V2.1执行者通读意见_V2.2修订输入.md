## 一、总体判断

V2.1 的骨架成立且在实战中被依赖：三级任务分级（L1/L2/L3）、专项评估按需启动、统一任务记录、证据等级 E1~E5、§8.4 质量验收原则、§8.5 禁止虚报，均为有效条款。主要缺陷是**原则层与操作层断裂**，以及**与项目实际运行词汇体系脱节**——规范写得最完整的章节（阶段评估）恰是执行频率最低的，而执行频率最高的日常编码/审核循环只有原则没有操作细则。

## 二、结构性问题（V2.2 必改）

### P-1 词汇体系与项目实践脱节

- §6.1 状态集（BACKLOG/READY_FOR_DEV/DEVELOPING/CODE_REVIEW/ACCEPTANCE…）与项目实际任务卡用词（READY_FOR_CODE/IN_PROGRESS/IMPLEMENTED/CLOSED）不一致，执行中每份文档需双词汇翻译。
- §2.4/2.6 审核结论 A/B/C 三档，项目实际用 PASS / PASS_WITH_CONDITIONS / FAIL；五级问题分类（BLOCKER~SUGGESTION）只在 §5.6 阶段评估章出现，未贯通日常审核章。
- **修订建议**：V2.2 统一采用项目实际词汇（状态集与结论档以实践为准），五级分类上移到日常审核章并与阶段评估章共用。

### P-2 项目实战补强条款未收录

以下条款在项目 CODEBUDDY.md §13 中以真实事故为代价迭代出来，V2.1 应全部吸收：

1. **数值单位双写**（§13.1）：凡金额/天数/比例，任务书必须同时写业务值与代码单位值（起因：$4,000 被写成 4,000,000 cents）。
2. **数值量级自检**（§13.4）：审核涉及数值常量时对照同文件同单位常量心算量级。
3. **规格承诺核对表**（§13.2/13.3）：每条验收口径必须落到具体测试文件:用例名；零覆盖常量=漏实现；反证必须两个方向都测（该拒绝的被拒绝 + 该保留的被保留）。
4. **反证判据是失败原因而非退出码非零**（§13.12）：环境缺依赖、空匹配产生的假红一律无效。
5. **主 AI 三步核验**（§13.11）：先亲跑四命令再派发、验设计审核后才置 READY、亲读权威文件；"四命令全绿 ≠ 正确"（§13.7）。

### P-3 操作层空白

V2.1 全文假设执行环境稳定、单 Agent 独占运行。已以附录 G 补齐三条细则（长任务分段提交与中断恢复 G-1、并行红相归因协议 G-2、派发环境须知 G-3）。**V2.2 应将附录 G 三条正式并入正文**：G-1 → 新 §7.5；G-2 → §7.3 细化 + 编码审核义务；G-3 → 附录 A 环境须知节。

## 三、条款级补强（V2.2 应加）

1. **裁定回填义务**：任何在任务执行期间生效的主 AI 裁定（ADJ），必须回填受影响任务卡或以追加指令形式下达；允许"编码按旧口径在跑、裁定悬空"即重演 CODE-FIN-RUNWAY formulaVersion 漏 bump 事故（I-1）。
2. **集成检查时机**：§7.3"并行开发完成后必须进行集成检查"应明确为"每个并行批次收口时 + 阶段验收前"两级。
3. **测试基线管理**：验收标准应含"全仓测试用例数只增不减（0 skip）"的量化基线条款（实践已执行，规范未写）。
4. **裁定登记制挂钩**：§5.7 的 ACCEPTED/FIX_NOW/DEFERRED/REJECTED/NEEDS_VALIDATION 五状态应与项目 ADJ 编号登记制建立映射，否则定义了没人用。
