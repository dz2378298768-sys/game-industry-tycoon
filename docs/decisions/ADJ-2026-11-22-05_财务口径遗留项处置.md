## 1. D1 — P3-04 `one_off` 窗口前到期未兑现

### 1.1 问题复现（审核 Agent 探针 D5）
现金 3,000,000；2025-12 有一笔 50,000 的 `one_off` 承诺未兑现；评估窗口 2026-01..2026-06。实测 `AvailableCash = 3,000,000`（未扣 50,000）。

### 1.2 为什么必须扣
`AvailableCash` 的用途是回答「未来 N 个月还能花多少」。一笔**已经到期但还没付出去**的一次性承诺，是**确定会发生**的现金流出，只是延迟了。把它排除在窗口求交之外，等于告诉玩家"你还有 3,000,000 可花"，而实际上有 50,000 是别人已经开好发票、只是还没扣款的。

这与 HRB（玩家预算承诺 + 单向可行性检查）的设计精神直接冲突：HRB 的前提是"不能承诺超过真实可负担的额度"。高估可用现金 → HRB 放行一个实际付不起的预算 → 玩家在项目中途现金断裂 → 这是**最坏的一类失败**（玩家已经投入时间，且失败原因不可归因）。

### 1.3 裁定
**对 `endIdx < windowStart` 的未兑现 `one_off` 承诺，在窗口起点全额扣减**（扣 `amountCents − realizedCents`）。

- 不引入任何新乘子、不做时间折现、不区分"迟到几天/几个月"。
- 若同一承诺在窗口内也有兑现点，仍按原有窗口内口径计算，**不得重复扣减**（实现须保证"窗口前一次性补扣"与"窗口内按月扣"互斥）。
- 必须补用例：`P3-04` 场景（2025-12 / 50,000 / 窗口 2026-01 起）断言 `AvailableCash = 2,950,000`。

### 1.4 与规格的关系
FIN V0.2 §6.2 括号内 `one_off: amountCents − realizedCents` 的解释本意就是"全额计入"，本次裁定是该解释在窗口边界上的**自然延伸**，不构成语义变更。故：
- **不升 `financeFormulaVersion`**；
- 但须在 FIN V0.2 §6.2 追加一句边界说明（由主 AI 直接补，见 §2.1），避免下次审核再被判"实现与规格冲突"。

## 2. D2 — 跑道双重扣减（OPEN-F3′）

> ⚠️ **本节处置结论已于 2026-11-22 被 `ADJ-2026-11-22-11` 推翻，请勿据此施工。**
> 被推翻的是 §2.2 第 2 条「**本任务不改公式**」及其全部理由（「P1 只求内核正确」「属安全方向偏差」）。
> 推翻理由：V3.1 把 G1 定义为「可交给外部试玩」的纵向切片后，「跑道低估只是让玩家少花钱」不再成立——错误跑道会**直接驱动危机状态机**，把真实 7 个月的公司判为濒临破产，玩家据此裁员砍项目，**把假危机变成真危机**（自我实现）。
> 仍然有效的部分：§2.1 的缺陷陈述（算例 700k/100k/6 → 1 个月 vs 真实 7 个月）、§2.3 的「两个量不能合并」论证（它正是 ADJ-11 §2 三概念分离的基础）。
> **现行处置见 `ADJ-2026-11-22-11`**：升级为 G1 阻断项，要求 `RunwayMonths` 从 `CashBalance` 起算、新增 `INV-RUNWAY`、阈值同批重标定、三条可证伪反例。


### 2.1 缺陷陈述
设现金 700,000、月净烧 100,000、horizon 6 个月、月内承诺合计 100,000/月：

- `AvailableCash` = 700,000 − Σ(horizon 内全部承诺 600,000) = **100,000**
- `runwayMonths` = 100,000 / 100,000 = **1 个月**
- 而**真实可支撑**：700,000 / 100,000 = **7 个月**

同一笔承诺被扣了两次（一次进 `AvailableCash`，一次进 `NetBurn`），导致跑道被系统性低估 6 倍量级。

### 2.2 裁定
1. **确认是规格缺陷**，不是实现缺陷（实现与 §6.1/§6.2 字面一致，审核 Agent 判定正确）。
2. **本任务不改公式**。理由：
   - 跑道是 UI 与危机状态机（`warning`/`bankrupt` 阈值）的共同输入，改公式会同时移动危机入口与破产判定，属**跨系统数值影响**；
   - P1 的验收门槛是"可玩闭环"，跑道低估会让玩家**过度保守**（少花钱），属**安全方向**偏差，不阻断交付；
   - 修正需要重新校准 `cashWarningThresholdCents` / `cashRecoveryThresholdCents` 与 `runwayWarningMonths`，必须与 P2 数值校准一起做，否则会引入新的阈值错配。
3. **CODE-04 须做的两件事**：
   - (a) 在 `finance-formulas.ts` 的 `runwayMonths` 计算处加**显式注释**指向 `OPEN-F3′`，说明"此处存在已知双重扣减，P2 校准轮修正"；
   - (b) 加一条**症状锁用例**：固定输入（上述 700,000/100,000/6 场景），断言当前输出为 `1`，并在用例标题里写明 `KNOWN-DEFECT OPEN-F3`。**目的是让缺陷可见、防止被误当正确行为而扩散到 UI 文案**；当 P2 修正公式时，这条用例必须一起改，从而强迫修正者面对该缺陷。
4. **登记**：OPEN-F3′ 写入 FIN V0.2 §20 未决项表（主 AI 直接补），责任 P2 校准轮，优先级 **P1 交付前须在 UI 侧加说明**（见 §4 附注）。

### 2.3 为什么不用"冻结 `AvailableCash` 语义、改 `CumAvailable`"这类单向修法
`AvailableCash`（HRB 用）与 `runwayMonths`（危机机/UI 用）需要的是**两个不同的量**：
- `AvailableCash` 要回答"我能承诺多少"⇒ **必须**扣掉全部已承诺额度（否则 HRB 会放行超额承诺）；
- `runwayMonths` 要回答"我还能活多久"⇒ 应当只扣**一次**（因为月烧里已含这些承诺）。

所以正确修法是**让 `runwayMonths` 从"未扣承诺的原始现金"出发**，而不是让 `AvailableCash` 不扣。这一条记入 OPEN-F3′ 的修正方向，P2 执行时不必再重新推导。

## 3. D3 — FIN-INT-01 `cancelCommitment` 生效期

### 3.1 背景
D-03 §5.4 RULE-11 / §6.3 / §7.2 需要"某人离职后薪资承诺自次月起停"，即 `cancelCommitment(effectiveMonth = monthOf(endDay) + 1)`。现 FIN V0.2 只定义了语义（§4.1/§10.3），未定义接口形参。

> ⚠️ **本段原写 `effectiveMonth = monthOf(endDay)`（缺 `+ 1`），已由 `ADJ-2026-11-22-09` 推翻。** 现行口径为**次月停**：离职当月只要有 ≥1 天在职即计 1 整月照常兑现。依据见 §3.3 第 4 条与 D-03 §0.6/§6.3。

### 3.2 裁定：准予扩展
签名扩展为：

```ts
cancelCommitment(
  commitment: BudgetCommitment,
  effectiveMonth: MonthKey,        // 必填，不得默认
): CancelCommitmentResult
```

`CancelCommitmentResult` 须包含（字段名由编码 Agent 定，语义不得少）：
- `realizedPeriods: number` — 生效月之前**已赚取**的周期数（不冲回）
- `releasedPeriods: number` — 生效月及之后**被释放**的周期数
- `realizedCents: Cents` — **已实际 post 的金额之和**（见下方 ⚠️ 修正）
- `releasedCents: Cents` — 释放金额，`= totalPlannedCents − realizedCents`
- 恒等式断言：`realizedCents + releasedCents == 原承诺总额`；`realizedPeriods + releasedPeriods == periodCount`

> ⚠️ **`realizedCents` 口径修正（ADJ-2026-11-22-10，2026-11-22 追加）**
>
> 本段原写 `realizedCents = realizedPeriods × 单位周期金额`，**该式已废弃**。它让取消路径按"月份差"推算金额，与 `realizeCommitment` 的逐笔累加形成**两套口径**，导致：
> ① 一笔交易都没 post 就取消，承诺声称已兑现（与账本永久分叉）；
> ② 月中取消后若补记当月那笔（ADJ-09 要求必须能补），会与推算值**重复计算**。
>
> **现行口径**：`realizedCents` ≡ 该承诺**已实际 post 的交易金额之和**，容差 0，只能由真实交易驱动。
> `realizedPeriods` 仍按月份规则计算，表达"已赚取应付费的期数"，**只用于 `releasedPeriods` 与恒等式，不得用来推金额**。
> 二者在"月中取消、当月尚未到 `settlementDay`"时会**故意不等**（`realizedPeriods` 已 +1、`realizedCents` 未增），这是正确状态，须保持到该期真的 post。

### 3.3 硬性约束
1. **语义服从 FIN**：「已入账不冲回」是 FIN 的唯一例外，禁止为对齐 D-03 而改成"冲回"。
2. **`effectiveMonth` 必填**：不给默认值，防止"忘了传"导致静默按创建月取消（那是灾难性的：会把已付的钱退回）。
3. **边界**：`effectiveMonth` 早于承诺起始月 ⇒ 全额释放（`realized=0`）；晚于承诺结束月 ⇒ 全额已兑现（`released=0`）。两端都要有测试。
4. **回归锚点**：D-03 §7.2 算例 —— 承诺 2026-02~2026-07（6 笔、500,000/月）。**`effectiveMonth = 2026-05` ⇒ `realizedPeriods = 3`（02/03/04）、`realizedCents = 1_500_000`、`releasedPeriods = 3`**。该数值必须被测试锁死。
   > ⚠️ **原锚点 `effectiveMonth = 2026-04 ⇒ 2 笔` 已作废**（ADJ-2026-11-22-09 修正：`effectiveMonth` 应取 `monthOf(endDay) + 1`，离职当月照常兑现；取 2026-04 会让"干满整月的人在结算日被解雇后工资为 0"，形成套利）。若实现仍以 2026-04 为锚点，即为按旧裁定实现，须改。
5. **不修改 FIN 规格正文**：仅在 FIN V0.2 §4.1 追加一段"接口形参（实现层对齐）"，标明本裁定编号。规格的**语义**部分（§4.1/§10.3）一字不改。
