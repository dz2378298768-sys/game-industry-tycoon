## 1. P1-1 `newWorkload` 可缺省 → 半新半旧快照

### 1.1 为什么比审核判得更重
审核写的是"切后逐 WP 快照一致"。但真正的危害不止于不一致：**`project.snapshotId` 指向 SNAP-2，WP 仍指向 SNAP-1**，意味着"这个项目当前适用哪套设计参数"这个问题有了两个答案。后续任何按 `snapshotId` 取 `W_d`、取 `f_skill` 权重、取 `costPerUnit` 的计算，都会在不同模块里读到不同的快照——这是**同一份状态的两个事实源**，属于本项目反复强调的红线同类问题（对照 CODE-02 的 P2-04：假成功、漏冲销，也是"接口报告成功但事实没发生"）。

### 1.2 裁定要求（编码 Agent 必须全部满足）
1. `newWorkload` 改为**必填**，类型层面不可省（`newWorkload: Workload`，不是 `?`）。
2. 若运行时传入 `undefined` / 残缺学科集合，**抛 `PROJ_SNAPSHOT_SWITCH_BLOCKED`**（错误码已定义未用，正好用上）。
3. 切快照必须**原子**：`rebaseline` 成功 且 全量 NORMAL WP 的 `snapshotId` 已更新 且 `Σbaseline == ΣW_d(new)` 三条同时成立，才允许改 `project.snapshotId`；任一不成立则**回滚整个切换**（不得留下"快照已切、WP 未更"的中间态）。
4. 补反证测试 3 组：① 缺参；② 学科残缺（少一个学科的新 `W_d`）；③ 正常路径后断言 `所有 NORMAL WP.snapshotId === project.snapshotId`。

### 1.3 主 AI 补充
审核探针 P11 实测 `switched=true, project=SNAP-2, wp=SNAP-1` —— 这说明**当前代码在正常调用面就可能产生脏状态**，不只是"调用方忘了传参"。整改时请先确认：`completeRework` 的现有测试是否正是因为这条捷径才全绿。若是，那些测试等于在验证错误行为，需一并改。

## 2. P1-2 闸门三通道旁路

### 2.1 这是复发问题
CODE-01 的首轮审核 R01 就是"闸门漏 E-10/E-11，实测空主类型+空平台 `pass:true`"。当时结论是"闸门必须 fail-closed"。现在 CODE-03 又出现"只查 `violations`、放过 `refViolations`/`hardRuleViolations`"。**同一个错误犯两次，说明不是笔误，是入参设计给了犯错的空间。**

### 2.2 裁定：不采用"三通道合并判定"，改采用"收敛为单一入参"
审核给了两个方案（合并三通道 / 收敛为 D-01 `RevalidationResult` 单一 `violations`）。**主 AI 选后者**，理由：

- 方案"合并三通道"要求 Project 域知道 D-01 闸门输出的内部结构（哪些字段算违规通道），这是**跨域耦合**，下次 D-01 增一个通道，Project 又漏一次；
- 方案"收敛为单一入参"把判断权交回 D-01：Project 只接收"是否通过 + 违规列表"，**D-01 内部有几个通道、怎么合并，是 D-01 的事**。这与"RevalidationGate fail-closed"的设计原意一致。

### 2.3 具体要求
1. `completeRework` / `submitDelivery` 的 gate 入参类型改为**只接受** `{ pass: boolean; violations: Violation[] }`（或直接复用 D-01 `RevalidationResult`），**删除** `refViolations` / `hardRuleViolations` 字段。
2. 判定逻辑保持：`gatePass = pass === true && violations.filter(v => v.severity === 'E').length === 0`。
3. **额外要求（审核未提，主 AI 加）**：`pass === true` 但 `violations` 含 E 的**矛盾输入**，当前代码判 `false`（正确），但**没有任何告警**。要求补一条 `PROJ_GATE_INCONSISTENT` 诊断输出（不改变 fail-closed 行为），因为"上游说通过、又说有 E 违规"本身就是上游 bug 信号，静默吞掉会掩盖问题。
4. 补反证：返工侧 3 组（E 在 violations / `pass=false` 无违规 / 矛盾输入）、交付侧 3 组，共 6 例。

## 3. P1-3 rebaseline 守恒缺口

### 3.1 问题本质
某学科所有 WP 已 DONE，新快照 `W_art(new)=80`，但没有任何"未完成 WP"可以承载这 80。当前实现**静默丢弃**（探针 P4：`Σbaseline=50, Σremaining=0`）。更糟的是 `checkRemainingInvariant` 用**自己算出来的 `totalBaseline`** 做断言，等于自证——**一个永远通过的检查比没有检查更危险**，因为它会让人以为已经守护了。

### 3.2 裁定
**fail-closed，不允许"想办法圆过去"。**

1. 无承载 WP 且 `W_d(new) > 0` ⇒ **拒绝切快照**，抛 `PROJ_REBASELINE_UNBALANCED`（新增错误码），并把差异（学科、缺口量）放进错误详情。
2. **不采用**审核建议的"按新 `W_d` 生成新 WP"作为默认行为。理由：返工完成时凭空生成一批新 WP，等于让玩家付出"返工成本"后又拿到新的工作量，这与"返工 = 把改坏的部分改回来"的语义相反，会变成"越返工活越多"的荒谬正反馈。生成新 WP 只有在**明确对应新快照真实新增内容**时才成立，那是 D-02/后续任务的事，不是本内核的默认路径。
3. `checkRemainingInvariant` 改为对**传入的 `W_d(new)`** 断言 `Σremaining == ΣW_d(new) − Σdelivered`，**禁止使用函数内部自算的 `totalBaseline`**。
4. `delivered > baseline` 必须单独失败（P3-4），不得用 `min(delivered, baseline)` 掩盖。
5. 补测 2 组：① "已 DONE 学科新增工作量" → 断言抛错；② 部分完成学科 → 断言守恒成立。

### 3.3 主 AI 补充
如果整改过程中发现"某些正常返工场景必然触发这条 fail-closed"，那说明 **`completeRework` 的工作量语义本身有问题**（返工不是"重新分配全部 W_d"，而是"对受影响部分加权重做"）。此时**不要放宽 fail-closed**，而是把问题提交主 AI，我们改设计语义。

## 4. P1-4 预算承诺未落地 —— 跨任务拆分裁定

### 4.1 根因确认（主 AI 独立核验）
```
project-execution-engine.ts:240-253  →  createCommitment(...)  返回值被 void 丢弃
project-execution-engine.ts:282-296  →  topUpBudget 同样只把 id 推进数组
finance/index.ts                     →  只导出 UnifiedLedger 与纯函数 createCommitment
ledger.ts                            →  无任何 commitment 存储/查询
finance-commitment.ts:77-84          →  createCommitment 是纯函数，仅做校验并返回对象
```
结论：**FIN 内核根本没有承诺注册表**。编码 Agent 在报告里写"经 CODE-02 `UnifiedLedger` 建 `BudgetCommitment`"是不准确的——它确实调用了 `createCommitment`，但对象创建后即被丢弃。审核 P1-4 的判断成立。

但责任归属要说清楚：
- **不是编码 Agent 偷懒**——它在现有 API 下做不到更多，因为账本没有给地方存；
- **是 CODE-02 的范围缺口**：CODE-02 任务卡范围是"账本 + 承诺值对象"，但不含"承诺生命周期管理"，于是承诺成了孤儿；
- **不是可接受状态**：`commitmentIds` 只是字符串数组，无法查询、无法释放，`cancelProject` 无处释放承诺，`descope` 也无处释放。这意味着**玩家取消项目后，承诺仍会占着 `AvailableCash`** —— 直接影响 HRB 与跑道，是可观察的玩法 bug。

### 4.2 裁定：拆成两个任务，串行执行
| 步骤 | 任务 | 内容 | 责任 |
|---|---|---|---|
| 1 | **CODE-04**（账本收敛） | 在 `UnifiedLedger` 增承诺注册表：`registerCommitment(c, opts)` / `getCommitments(companyId)` / `getCommitment(id)` / `releaseCommitment(id, effectiveMonth)` / `settleCommitment(id, amountCents, txId)`；实现 ADJ-05 §3 的 `cancelCommitment(effectiveMonth)`；承诺参与 `AvailableCash` 计算（FIN §6.2 已要求，但当前无承诺集合可算） | 编码 Agent |
| 2 | **CODE-03 整改** | `createCommitment` 改为 `ledger.registerCommitment(...)`，返回值存入账本；`commitmentIds` 保留但仅作索引；`cancelProject` / descope 路径显式释放；TC-15/TC-22 改为**从账本承诺集合求和**断言 | 编码 Agent |

**执行顺序**：先做 CODE-04 的 §4.2 步骤 1，再回头做 CODE-03 整改。原计划"CODE-03 先收口、CODE-04 后做"改为**交错执行**：CODE-03 的 P1-1/P1-2/P1-3/P2 组先改（不依赖承诺 API），P1-4 等 CODE-04 的承诺 API 落地后接入，最后**一次复审收口全部条件**。

> 这样安排的理由：P1-1/P1-2/P1-3 是纯本域缺陷，改动独立，先修完可以让 CODE-04 与 CODE-03 整改并行；而 P1-4 硬要拆开两半反而制造两次返工。

### 4.3 对审核报告 §8.1 C-4 的回应
审核说"TC-15 状态改为 NOT_VERIFIED/BLOCKED 并上报主 AI"。**主 AI 裁定：TC-15 状态改为 `BLOCKED_UPSTREAM`（FIN 缺承诺注册 API），由 CODE-04 解除，不由编码 Agent 背这个锅，但也不允许在报告里宣称"已对接"。** 实施报告 §7（账本对接）须逐句核对，所有"经 UnifiedLedger 建承诺"的表述改为准确描述。

## 5. P2 组：为何不接受"书面接受风险"

审核允许 P2 走"书面接受"。主 AI **全部要求闭环**，逐项给理由：

| 编号 | 事项 | 为何必须闭环 |
|---|---|---|
| P2-1 | PAUSED 超 60 天可 resume 绕过强制 CANCELLED | 规格的"强制"二字被绕过 = 状态机有后门。玩家可以靠反复 resume 无限期挂起项目，**规避返工与失败判定**，是玩法漏洞而非工程瑕疵 |
| P2-2 | 跨学科依赖被丢弃；成环静默回滚而非拒绝 | "静默丢边"会让 DAG 变成森林，工期计算随之失真，且**不报错**意味着玩家永远不知道自己被坑了。这类静默降级是本项目明令禁止的 |
| P2-3 | 返工任务不自动完成，需调未文档化函数 | 端到端返工链路不可用 = CODE-03 的核心目标（返工 → 闸门 → 切快照）实际跑不通，只是被测试捷径掩盖。**这是"测试全绿但功能不存在"的典型** |
| P2-4 | `Cost_est` 把返工工作量重复计入 | 直接影响 HRB 可行性判定（`ratio` 变大 ⇒ 误判"需缩减"），是**玩家可见的错误决策输入** |
| P2-5 | 返工 WP 一律归 design | 无 design 团队时返工永久停滞 = 死锁；且成本归集学科错，会让"哪门学科在烧钱"的报表全部失真 |
| P2-6 | 场景 A/B 数值证据不足；恒真断言 | **恒真断言必须删**——它比没有测试更坏（见 §3.1 同理）。规格场景数值未复现可以接受（P2 校准轮才对数值），但必须在报告里明确写"仅机制验证，数值未对齐规格 §15"，不得含混 |
| P2-7 | `ProjectExecutionArchive` 缺参数快照 | 存档无法复现同一结果 = 违背确定性原则，且 TC-18 结构上不成立 |

**唯一让步**：P2-6 的"规格 §15 数值未复现"部分，允许在报告中标注 `NUMERIC_PENDING_P2`，不要求本任务对齐具体数值（因为 P2 才做数值校准）。但**恒真断言、以及把"未复现"写成"已复现"**，一律不允许。

## 7. 给审核 Agent 的复审提示

复审时请额外确认（不属于原报告范围，但为本次裁定新增）：
1. **闸门单一入参**重构后，`RevalidationResult` 的所有 E 级来源是否真的都进了 `violations`（对照 D-01 §7.2.1 逐条）。
2. **fail-closed 是否 fail 得干净**：拒绝切快照后，`project` 与全部 WP 的状态必须与调用前**逐字段相等**（深比较），不允许"部分字段已改但快照没切"。
3. **恒真断言清扫**：全仓库新增测试里，凡是 `expect(x).toBe(x)` 形式、或期望值来自被测函数内部变量的断言，一律列出。
4. **承诺释放链**：`cancelProject` / descope 后，账本承诺集合中该项目的承诺状态是否为 `cancelled` 且 `AvailableCash` 已回升。
