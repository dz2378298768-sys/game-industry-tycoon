## 1. 为什么不能在编码阶段再定

审核给的是"允许编码、交付前补"。这条在别的场景可以接受，在这里不行：

1. **编码 Agent 必然要在这个分叉上做一次隐式选择**。它写 `settlementOrder` 相关代码时，要么先算薪资再改状态，要么先改状态再算薪资——这不是"实现细节"，这是**决定玩家在离职当月付不付钱**的产品规则。让编码 Agent 顺手决定一条玩家可见的金钱规则，等于把设计权下放给实现层。
2. **一旦实现定型，规格就会"追认"实现**。历史经验（D-01 的 HRB 冲突、FIN 的 INV-1 矛盾）都是"实现先跑、规格后补"，结果补的时候发现实现方向错了，返工面比当初定一下大得多。
3. **成本极低**：我已经查清现有代码的行为（§3），只需把事实写成条款，20 行的事。

## 2. 裁定：月末离职当月**不付**

### 2.1 规则
> **`endDay` 落在当月结算日（月末最后一个执行日）当天时，该月薪资周期不计入、不产生交易。**
> 即 `cancelCommitment(effectiveMonth = monthOf(endDay))` 的"已入账"判定以**日循环内的执行顺序**为准：**人事变更先于薪资结算**。

### 2.2 三个场景的最终值（6 笔 × 500,000，2026-02~2026-07，起始 2026-02-15）

| 离职日 | 归属月 | 笔数 | `realizedCents` | 说明 |
|---|---|---|---|---|
| 月中 `2026-04-10` | 02、03 | **2** | 1,000,000 | 与 FIN 一致（原 C4′ 锚点） |
| 月初 `2026-04-01` | 02、03 | **2** | 1,000,000 | 同上 |
| **月末 `2026-04-30`（结算日当天）** | 02、03 | **2** | 1,000,000 | **本裁定确定：不付 4 月** |
| 结算日次日 `2026-05-01` | 02、03、04 | **3** | 1,500,000 | 4 月已入账，不冲回 |
| `2026-02-01`（起始月首日） | — | **0** | 0 | 起始月即离，无已入账周期 |

> 关键区别不在"哪天走"，而在"**走的时候当月那笔钱 post 了没有**"。人事先执行 ⇒ 月末当天走，当月还没 post ⇒ 停。

### 2.3 为什么选"不付"而不是"付"

| 维度 | 不付（本裁定） | 付（3 笔） |
|---|---|---|
| **与现有代码一致性** | ✅ 现有 `daily-scheduler.ts` 中 `applyEmployeeDailyUpdate`（第 101 行）在 `applyMonthlySettlement`（第 107 行）之前，且 `fireEmployee` 当场把 `status` 置为 `fired`，而薪资循环 `emp.status !== 'hired'` 直接跳过 ⇒ **现有行为就是不付** | ❌ 需改动既有排程顺序，影响所有依赖该顺序的既有测试 |
| **对玩家的可解释性** | "他月末最后一天走，当月工资按已工作天数算"（P1 不做按日折算，标 DEF-3，所以是 0）——虽然不完全公平，但**方向保守** | "他月末走，还多拿一个月"——玩家会觉得是 bug |
| **与 FIN 的边界** | 不需要动用 FIN 的"已入账不冲回"例外 | 也不需要，但要多一条"结算日当天计入"的例外 |
| **与 DEF-3 的关系** | 一致：P1 明确不做按日折算，所以边界月要么全付要么全不付。选"不付"与"离职即停"的直觉一致 | 选"付"则等于给离职当月发全月，这在没有按日折算的前提下是**多付** |

**结论**：选"不付"。它同时满足"与现有代码一致、改动最小、方向保守、可解释"。

### 2.4 必须同时承认的不公平
P1 不做按日折算（DEF-3），所以"月中走"和"月末走"结果一样（都是 0 笔当月）。这是**已知的粗糙**，不是遗漏。玩家在 `2026-04-10` 离职和在 `2026-04-29` 离职拿到的总薪资完全相同——这在 P1 可接受（玩家不会为了几百块钱去调离职日），但 P2 做 DEF-3 按日折算时必须重新审视本条。**在 D-03 §18 DEF-3 加一句交叉引用**。

## 3. 代码事实核验（裁定依据，非推断）

```
daily-scheduler.ts:101   state = this.applyEmployeeDailyUpdate(state, dayIndex)
daily-scheduler.ts:107   state = this.applyMonthlySettlement(state, dayIndex)
                          ↑ 人事每日更新在前，月度结算在后

daily-scheduler.ts:334-335  // 每个员工月末仅一笔 salary 现金交易
                            if (emp.companyId !== company.id || emp.status !== 'hired') continue
                            ↑ 只看 status，不看 endDay；当天已 fired 即跳过

employee-service.ts:82-88   const fired: Employee = { ..., status: 'fired' }
                            ↑ 解雇/离职当场改状态，不延迟到次日
```

因此：**`endDay` = 结算日当天离职 ⇒ 当日薪资循环已看不到该员工 ⇒ 不产生当月交易。** 裁定与现有实现同向，无需改动既有排程。

> **勘误（2026-11-22，依据 D-03 V0.1.3 复审的 D03-35 / D03-36）**：
> 1. §2.3 与本文多处写"置 `status` 非 `active`"**不准确**。`active` 是 D-03 `EmploymentStatus` 的取值，**基线 `EmployeeStatus` 枚举里没有 `active`**（实际为 `hired`/`on_leave`/`resigned`/`fired`），薪资循环的真实判据是 `status !== 'hired'`。裁定**结论不受影响**（`terminated` 映射后均为非 `hired`），但字面表述已修正。
> 2. §3 把"薪资结算"当成单条流水线**不准确**。现状有**两条**：① `applyMonthlySettlement` 的裸 `postTransaction` 分摊（`daily-scheduler.ts:337`）——本裁定**已生效**；② FIN 承诺兑现（`settleCommitment` / `cancelCommitment`）——**薪酬结算尚未接入该链路**，故本裁定在实际薪资上只走 ①，② 需 CODE-06 接入后才成立。裁定在产品规则层闭合，**在实现层部分未生效**。
> 3. ORD-01 的**权威不在 D-03/FIN**，而在 `DailyScheduler.executeDay` 的步骤序列；D-03 与 FIN 是依赖方，不是契约签署方。
