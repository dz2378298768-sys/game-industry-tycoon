## 1. 事项一：交付闸门 FAIL 后 `state` 保持 `ACTIVE` 还是 `READY_TO_DELIVER`

### 1.1 规格矛盾定位
- **§4.3 转换表**：`READY_TO_DELIVER → ACTIVE`，触发"交付闸门 FAIL"，副作用"回路返工（建新会话）；不生成 Build"。
- **§5.6-3**：`FAIL 期间 state 保持 READY_TO_DELIVER/ACTIVE，权威快照不变`。

两处并存 ⇒ 实现者可以任选一个，且 §5.6 的"`READY_TO_DELIVER`/`ACTIVE`"用斜杠并列，本身就没有给出判定条件。CODE-03 实现选了 `ACTIVE`（§7 P3-5 记录"仅切 ACTIVE，未建新返工会话"）。

### 1.2 裁定：保持 `READY_TO_DELIVER`，不退回 `ACTIVE`

| 理由 | 说明 |
|---|---|
| **语义正确** | 交付失败意味着"东西还没通过验收"，但**研发工作本身已经做完**（所有 WP `DONE`）。退回 `ACTIVE` 会错误地宣称"还有活要干"，从而让日推进重新分配产能——但产能没有可干的活，会空转或误算 `burden_d` |
| **返工是叠加态，不是回退** | 返工在 D-01/Project 里是 `ACTIVE + ReworkSession(active)` 的**呈现标签**（任务卡明确"不得新增 REWORKING 枚举"）。若交付失败要走返工，正确做法是 `READY_TO_DELIVER → ACTIVE(返工标签)` **且立即建 `ReworkSession`**，两者必须原子成对。单切状态不建会话 = 制造了 §7 P3-5 那个"只切 ACTIVE、无返工会话"的悬空态 |
| **可观测性** | `READY_TO_DELIVER` 是玩家可见的"待交付"提示。FAIL 后若静默变 `ACTIVE`，玩家会以为"莫名其妙退回开发中"，找不到失败原因。保持 `READY_TO_DELIVER` + 展示失败原因码，是唯一可解释的 UI 表达 |

### 1.3 修正后的确定规则（替换 §5.6-3 的斜杠表述）
```
交付闸门 FAIL：
  state 保持 READY_TO_DELIVER（不变）
  deliveryFailures += 1（新增审计计数）
  lastDeliveryFailure = { day, reasonCodes[], eViolations[] }
  不生成 Build；权威 snapshotId 不变
  玩家可再次提交（同一 state 再次触发闸门），无次数上限
  若失败原因含"设计缺陷"类（D-01 E 级且属蓝图内容）⇒ 玩家需主动发起设计变更（§4.3 ACTIVE 返工行），
  此时才走 READY_TO_DELIVER → ACTIVE（返工标签）+ 建 ReworkSession（原子）
```
**关键**：PROJECT 内核**不得**在交付 FAIL 时自动建 `ReworkSession`。返工是玩家的决策（要不要改设计、改多少），不是系统替玩家决定。CODE-03 的 §7 P3-5 因此**降级为"实现符合裁定"**——但必须补上 `lastDeliveryFailure` 记录，否则失败原因丢失。

### 1.4 需修订规格
Project V0.1.1 §4.3 的 `READY_TO_DELIVER → ACTIVE` 行改为：**触发条件加限定"玩家就交付失败原因发起设计变更"**；§5.6-3 删掉斜杠并列，按 §1.3 重写。由主 AI 直接补（见 §3 执行记录）。

## 2. 事项二：返工 WP 一律归 `design` 学科

### 2.1 问题（CODE-03 §7 P2-5 + 审核探针 P13）
`project-execution-engine.ts:617-622` 把返工 WP 的学科硬编码为 `design`。后果：
1. **死锁**：团队里没有 design 学科的人时，返工 WP 永远无法推进 ⇒ 项目永久卡在返工态。
2. **成本归集失真**：返工烧的是 code/art 的工时，却全记在 design 头上，"哪门学科在烧钱"的报表全错。
3. **产能错配**：`Cap_d` 按 design 算，与真实瓶颈学科无关，`Cost_est` 与 `remaining` 全部偏离。

这是一个**明确的实现缺陷**，不是设计留白。

### 2.2 裁定：按受影响学科生成，无法确定则 fail-closed
1. **返工工作量按学科拆分**：`ReworkSession` 的受影响范围（`affected`）必须携带**学科维度**。若原设计变更（D-01 `DesignChange`）只给出"改了哪些模块"，则由 **D-01 的 `skillDemand` 四通道估算**反查受影响学科（D-01 已有该通道，不得另建）。
2. **一个返工生成多个 WP**：每个受影响学科一个 `kind=REWORK` 的 WP，各自 `baseline = 该学科的返工工作量`。
3. **无法确定受影响学科 ⇒ fail-closed**：抛 `PROJ_REWORK_SCOPE_UNKNOWN`（新增码），**不允许**默认 `design`。理由：默认值会让错误静默传播，且会制造上述死锁。
4. **受影响学科在工作量分摊后为 0 ⇒ 不生成该学科的返工 WP**（避免 0 baseline WP，与 P3-2 同口径）。

### 2.3 为什么不能"至少取受影响学科集合"就完事
审核建议"按 `affected` 的学科生成（或至少取受影响学科集合）"。**"至少"不够**：如果 `affected` 只到模块级没有学科级，取集合仍然是猜。所以本裁定的第 3 条（fail-closed）是必须的，它把"猜"变成"报错"，逼迫上游（D-01 的技能需求估算）提供学科维度。
