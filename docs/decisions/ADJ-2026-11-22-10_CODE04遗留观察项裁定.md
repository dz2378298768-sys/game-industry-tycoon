## 1. O-1：取消后能否补记"已赚取周期"

### 1.1 事实

实施报告 §5.4 / §7-O-1 记载："当前 `cancelled` 一律拒绝新兑现"。任务卡的意图是"取消 = 不再接受新兑现"，实现即照此做了。

### 1.2 为什么这是错的

`cancelled` 的语义在 FIN §4.1（R-03 补充）与 ADJ-09 中已经定死，关键在"未来周期"的定义：

> 「未来周期」= `effectiveMonth` 及之后的周期。`effectiveMonth` **之前**的周期为**已赚取周期**：即使尚未 `post`，也不因取消而消失，仍在各自的 `settlementDay` 照常兑现。

即：**取消只停未来，不停已赚取未入账的部分。** 一个统一拒绝所有兑现的实现，在下面这个场景会直接出错：

| 时点 | 事件 |
|---|---|
| 2026-04-10 | 员工离职 ⇒ `cancelCommitment(c, effectiveMonth = 2026-05)` |
| 2026-04-30 | 4 月 `settlementDay`——4 月工资**已赚取**（4 月出勤 10 天），必须照常兑现 |
| 若实现"一律拒绝" | 4 月这一笔被吞 ⇒ 员工干了 10 天，工资为 0 |

这与 ADJ-09 想堵死的套利漏洞**是同一个洞的另一种形态**：ADJ-09 保证了"取消语义正确"，但这个实现又把"已赚取周期的兑现入口"关掉了。D-03 的 TC-11b 场景 ②（离职 04-10 ⇒ **3 笔**）在真实运行时链路下会跑成 **2 笔**。

### 1.3 裁定

1. `cancelled` 状态下，**允许**兑现 `settlementDay < startOf(effectiveMonth)` 的周期（即已赚取未入账的欠款），**拒绝** `effectiveMonth` 及之后的周期。
2. 新增错误码区分两种拒绝：`FIN_COMMITMENT_ALREADY_CANCELLED`（未来周期，正常拒绝）与"允许补记"路径不报错。
3. 用例必须锁定：取消于 04-10 ⇒ 04-30 补记 1 笔成功、05-31 拒绝。总额 `realizedCents` 最终为 3 笔 = 1,500,000。

### 1.4 为什么现在修而不是交给 CODE-06

CODE-06 的月薪要迁到 FIN 承诺链路（流水线 ②），而 D-03 TC-11b 七场景**依赖这条语义**。若留到 CODE-06 才发现，等于让 D-03 的测试去修 FIN 的内核——这正是本项目反复出现的"上游语义缺口被下游实现吸收"模式。在 CODE-04 内修完，代价最小。

### 1.5 ⚠️ 补丁的连带缺陷（主 AI 推演发现，比 O-1 本身更隐蔽）

修 O-1 时必定撞上 `computeCancelCommitment` 里的这一行（`finance-commitment.ts:212`）：

```ts
realizedCents: Math.max(c.realizedCents, realizedCents),   // realizedCents = realizedPeriods × amountCents
```

它按**月份差**算出"应已兑现期数"，然后把 `realizedCents` **抬升**到该值——**不检查这些月份是否真的 post 过**。

只要 O-1 放开"已赚取周期可在取消后补记"，两者就会**重复计算**：

| 时点 | 事实 | `realizedCents` |
|---|---|---|
| 04-10 取消（02-01 入职、`effectiveMonth=2026-05`） | 实际只 post 了 02、03 = 1,000,000 | `Math.max` 抬到 **1,500,000** |
| 04-30 补记 04 月 | 再 post 500,000 | **2,000,000** |
| 应有终态 | 3 期 | **1,500_000** |

⇒ **多算 500,000，且账本的 `realizedCents` 与 `Σ 已 post 交易` 不再相等，破坏 INV-1 的同源要求。**

**裁定**：`realizedCents` 必须严格等于该承诺**已实际 post 的金额**，不得用月份差提前计入。`realizedPeriods` 可保留月份差语义（它表达"已赚取应付费的期数"，用于恒等式），但不得据此抬升金额。连带要求见补丁任务卡 R6。

## 2. O-2：释放后 `AvailableCash` 回升幅度

> **本节在第六轮复审后被重写（R6-02）。** 初稿用的是"已兑现 2 期后取消"的场景，而该场景**在 ADJ-09 口径下不存在**（见 2.2），据此得出的结论虽数值巧合成立，但推理链是错的。现按现行口径重写。

### 2.1 事实

实施报告 §5.2 记：承诺 6 期 × 500,000（`totalPlannedCents = 3,000,000`），取消后"释放 2 期、`releasedCents = 1,000,000`"，但 `AvailableCash` 回升 **2,000,000**。编码 Agent 认为这与任务卡"回升幅度 == 释放金额"对不上，遂上报，未自行改口径。

### 2.2 原场景为什么不成立

ADJ-09 的规则是"某自然月只要有 ≥1 天在职即计 1 整月，`effectiveMonth = monthOf(endDay) + 1`"。承诺从 2026-02 起算，则：

- 员工若在 **4 月内任何一天**离职 ⇒ `effectiveMonth = 2026-05` ⇒ 已赚取周期 = **02、03、04 共 3 期** ⇒ `realizedPeriods ≥ 3`
- 员工若在 **3 月内**离职 ⇒ `effectiveMonth = 2026-04` ⇒ 已赚取 = **02、03 共 2 期**

也就是说"6 期里已兑现 2 期"**只能**对应"3 月内离职"。但实施报告并未给出离职日，而是把它当成一个抽象的"兑现了 2 期"状态——**这个抽象恰好抹掉了 ADJ-09 最关心的边界**（月内离职那一笔算不算）。

### 2.3 用真实场景重算（3 月 15 日离职）

| 量 | 值 | 说明 |
|---|---|---|
| `totalPlannedCents` | 3,000,000 | 6 × 500,000 |
| `effectiveMonth` | **2026-04** | `monthOf(03-15) + 1` |
| `realizedPeriods` / `realizedCents` | **2 / 1,000,000** | 02、03 两期已赚取且已 post |
| `releasedPeriods` | **4** | 04、05、06、07 |
| `releasedCents` | **2,000,000** | `totalPlannedCents − realizedCents` |
| 取消**前**扣除项 | 2,000,000 | 只含未兑现的 4 期；已 post 的 2 期不在其中 |
| 取消**后**扣除项 | 0 | FIN §6.2：`cancelled` 整体不计入 |
| 回升幅度 | **2,000,000** | == `releasedCents` ✓ |

**结论在数值上与初稿一致（回升 2,000,000 == `releasedCents` 2,000,000），但现在的推导是可复算的、且符合 ADJ-09。**

### 2.4 裁定

1. **口径无误**：`releasedCents = totalPlannedCents − realizedCents`；`AvailableCash` 回升幅度 **恒等于** `releasedCents`。FIN §6.2 与任务卡**并不冲突**。
2. **任务卡的缺陷在于没写恒等式**，让双方无法自证。已补入：`realizedCents + releasedCents == totalPlannedCents`、`realizedPeriods + releasedPeriods == periodCount`。
3. **实施报告 §5.2 的文字需更正**：`releasedPeriods` 应写成与离职日匹配的值（3 月内离职 ⇒ 4）；`releasedCents` 为 2,000,000。**代码不改**——`computeCancelCommitment` 的 `releasedPeriods = periodCount − realizedPeriods` 实现正确。
4. **D-03 的薪资算例（2026-04-10 离职）是另一组数**：`realizedPeriods = 3`、`releasedPeriods = 3`、两者金额均为 1,500,000。两组数不冲突，**不得互相套用**。

> **教训**：我初稿选了一个"看起来更干净"的抽象场景（已兑现 2 期），结果抹掉了边界条件。**涉及时间边界的裁定，必须用带具体日期的场景，不能用抽象期数。**

## 4. O-4：`reverseTransaction` 语义变更

### 4.1 事实

原语义：改原交易 `status`（如置 `reversed`）。
新语义：新增一笔 `amountCents` 相反的交易（冲销），原交易状态一并更新。

### 4.2 裁定：接受新语义

INV-1（`cashBalanceCents == Σ(全部 Transaction.amountCents)`，`status` 仅审计不参与求和）**要求**冲销必须是新交易。若只改原交易 `status` 而金额留在账上，要么求和结果与实际现金流不符，要么就得让求和去看 `status`——后者已被 F-01 方案 a 明确否掉。

所以 O-4 不是"语义漂移"，**是 INV-1 的必然推论**。原语义在 INV-1 下根本无法成立。

### 4.3 交付补充要求

1. `reverseTransaction` 的 JSDoc 必须写明"产生新交易，原交易保留"，并附 INV-1 理由；
2. 所有读方（UI 交易列表）必须能正确展示"冲销对"——CODE-07 的 UI 口径需覆盖：不得只显示冲销笔而漏原笔，也不得把两笔都当独立收入/支出统计；
3. 现有唯一调用方为 `finance-service.test.ts`，无生产调用方，风险可控。

## 7. PATCH1 复审追认记录（2026-11-22，主 AI 裁定）

> 来源：`CODE-04-PATCH1 独立复审报告 V0.1`（编码审核 Agent，对 `ede93c4`）问题清单 M-03。

**追认内容**：`releasedCents` 的实现口径为 **`releasedPeriods × amountCents`**（`finance-commitment.ts:218`），而非任务卡 R2 / 本裁定 §2.4 字面的 `totalPlannedCents − realizedCents`。

**裁定理由**：

1. 若按字面口径，R3 扣除项 `max(0, total − realized − released)` 恒为 0，会**高估** `AvailableCash`，方向危险（HRB 可能放行超额承诺）；
2. 实现口径与 R3 / V6 验证自洽，且属**保守**方向（少算可释放资源）；
3. 与本裁定 §2.4 场景（已赚取期全部已 post）数值一致，无行为冲突。

**效力**：以实现口径为准。任务卡 R2 字面表述视为笔误；本裁定 §2.4 不因此推翻（O-2 的"回升恒等于 releasedCents"结论不变，`releasedCents` 定义按本节执行）。FIN 规格在下次修订时同步补注释，编码侧不返工。
