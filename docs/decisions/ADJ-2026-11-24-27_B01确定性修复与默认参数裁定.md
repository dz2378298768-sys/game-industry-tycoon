## 一、裁定结论摘要

REC-02 扫描暴露"默认玩家必败"（B-01），但深入核查发现**根因不是预算数字太小，而是两个独立缺陷叠加**：

1. **确定性缺陷（真 BLOCKER，先修）**：`uuid()` 用 `crypto.randomUUID()`/`Math.random()` 生成实体 ID（`src/domain/types.ts:6-14`），其中 `employmentId`（`personnel-service.ts:216,434`）参与离职判定 `hash01(employmentId, day)`（`personnel-service.ts:593`）。导致**同一 seed 两次全新开局结果不同**（扫描 N=8 同帽 2/8~8/8 波动）。这违反 R9「同 seed 确定性」硬门槛（P1 验收清单 §三 R9 / §六），并直接违背 DP-3「真实计算逻辑」——不可复现的计算不是可信计算。
2. **默认参数陷阱（B-01 表症）**：默认预算帽 $9,000 不足以支撑 4 人团队 200 天，Day90 耗尽 → Day118 取消。

**裁定原则：先修确定性根因，再用修复后的稳定模型重新校准默认参数，禁止用"调大预算帽到 $70,000" probabilistic 地掩盖随机性**（那正是 DP-4 禁止的"绕过而非解决"，与 CODE-06 测试清零离职概率同类错误）。

## 二、逐项裁定（对应实施报告 §1.4 六项 + 新增一项）

### 2.1 【新增·最高优先】确定性根因修复 — 裁定：必须修

| 项 | 裁定 | 实现方向 |
|---|---|---|
| `uuid()` 用于参与玩法判定的实体 ID | ✅ **必须修复**：把 `employmentId` 等**参与 `hash01` 判定的实体 ID 改为确定性派生**（seed + 序号/实体计数），使同 seed 同操作序列产生同 ID | 保留 `uuid()` 用于纯标识符（事件 ID、会话 ID、不参与模拟判定的展示 ID）；新增 `deterministicId(prefix, seq)` 或让 `hireEmployee` 接受显式 `employmentId`（`cmd.employmentId ?? uuid()` 已有入参，见 `personnel-service.ts:216`——由调用方 game-world 传确定性 ID） |

**验收**：新增红线测试「同 seed 两次全新开局：招聘 → 逐日推进 200 天 → 项目结局/现金/离职结果逐字段相等」。此测试补上现有 R9 盲区（现有测试只测存档副本续跑与纯函数，不测新开局 ID 生成）。**此测试不过，B-01 不得宣告完成。**

### 2.2 默认预算帽校准 — 裁定：确定性修复后重测再定值

| 项 | 裁定 |
|---|---|
| 可行帽 $70,000（8/8，随机态） | ⛔ **不采纳为最终值**。该数字是在随机性未修复下的鲁棒估计，修复确定性后必须重测 |
| 校准顺序 | ① 先完成 2.1 确定性修复 → ② 用确定性模型重跑预算帽扫描（同帽结果应 100% 一致）→ ③ 取"能稳定上市且公司现金健康"的最小帽 → ④ 据此调整 UI 默认预算容量或 HRB |
| 实现约束 | 默认开局（$120,000 + 默认 4 人招聘 + 默认 HRB）必须能在 200 天内走到上市成功；保留低预算策略作可解释的失败对照（PATH-A 断言保留） |

### 2.3 实施报告 §1.4 六项逐项裁定

| # | 对象 | 裁定 | 理由 |
|---|---|---|---|
| 1 | `startingCashCents` $120,000 | ⛔ **不改**（本轮） | 起始现金是经济平衡锚点（ADJ-12 S1-1）；随机性修复后帽需求会变，先不动。若确定性修复后仍需提高，另案裁定 |
| 2 | `hrbConservativeRatio` 0.45 | ⛔ **不改**（本轮） | HRB 是玩家决策参数语义（保守/标准两档），不应为掩盖默认必败而提高；优先调 UI 默认预算容量 |
| 3 | `defaultStartingSalaryCents` $1,300 | ⛔ **不改** | 薪资影响人才市场与财务全局，牵一发动全身；不作为 B-01 首选杠杆 |
| 4 | `defaultLaunchHorizonDays` 200 | 🟡 **待确定性修复后评估** | `PRJ_LAUNCH_TOO_EARLY` 是否合理属玩法节奏问题；扫描显示 READY 最早 Day23、200 天期限过宽，但先不动，观察修复后数据 |
| 5 | 容量守卫校验整笔容量 vs 现金 | 🟡 **保持现状，登记 OPEN-DET-DEFAULT-CAP** | 该守卫语义是"不承诺超过可用现金"，逻辑自洽；问题是默认值搭配不当，不是守卫错。不因 B-01 改守卫规则 |
| 6 | `PRJ_LAUNCH_TOO_EARLY` | 🟡 **保持现状，登记 OPEN-DET-DEFAULT-HORIZON** | 按计划上市日上市是合理玩法约束（玩家承诺了发布时间）；默认期限是否过宽属数值校准，非规则缺陷 |

**裁定要点**：六项里五项本轮不改，一项（工期）观察后再定。因为真正的病根是确定性缺陷（2.1），它是所有波动的来源；不先修它，任何锚点调整都是在噪声上试数。

### 2.4 为什么这是正确的裁定顺序

- 扫描 E（N=8）显示**同帽结果 2/8~8/8 波动**——在这个噪声水平上校准 $59k vs $70k 毫无意义（$100k 都出现 7/8）。
- 波动的唯一来源是 `uuid()` 随机 ID → `hash01` 离职判定（CODE-06 早已发现并用测试清零绕过，见 `monthly-settlement.test.ts:20-24`）。
- 因此：**修复确定性 → 噪声归零 → 扫描可复现 → 默认值可精确校准**。这是唯一不掩盖问题的路径。

## 五、NOT_VERIFIED / 风险

1. 确定性修复的工程范围：`uuid()` 调用点众多（30+），但**只有参与 `hash01`/模拟判定的 ID 需要确定性化**（核心是 `employmentId`）；事件 ID、展示 ID 可保留随机。需在批次 1 精确界定，避免过度改动。
2. 随机性长期影响：分数级波动是否还影响销量/AI 决策，需在批次 1 后专项复核（本裁定聚焦离职链）。
3. 本裁定不撤销任何 G1 披露；披露 1/2 维持至 REC-04/REC-11 真机复验。
