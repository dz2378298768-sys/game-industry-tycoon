## 一、设计问题

当前 P1 候选池每次最多生成 5 名候选，五学科独立随机分配。REC-04 ExecutionProject 同时需要 `design`、`code`、`art`、`audio`、`qa` 五个可执行学科；随机池不保证五学科覆盖，导致玩家可能已经完成立项，却因缺少关键岗位而无法开始有效研发。等待候选刷新又会继续产生工资和日常现金压力。

这属于首个核心闭环的可玩性前置条件缺失，不应直接解释为玩家的战略失败，也不应通过提高起始资金掩盖。

## 二、提议机制

### 2.1 触发条件

首个条件同时满足时启用“首项目保障池”：

1. 公司为玩家公司（`isPlayer=true`），不是 AI 公司；
2. 该公司此前没有创建过任何 ExecutionProject；
3. 玩家确认创建第一个 REC-04 ExecutionProject，且项目使用五学科生产路径；
4. 项目所需学科集合固定为 `design`、`code`、`art`、`audio`、`qa`。

**触发时点是第一个玩家 REC-04 ExecutionProject 创建成功的同一命令。** 创建命令必须先读取并清理当前候选池（移除已过期、已占用、重复条目），然后立即按本提案补齐缺失学科；不能等玩家重新进入招聘页，也不能等下一次日 tick 才启用保障。

保障状态以公司隔离的领域状态持久化，不能因刷新页面、读档或重新进入招聘页重复触发。建议存档字段为：

```ts
rec04RecruitingGuardByCompany?: Record<string, {
  state: 'eligible' | 'active' | 'completed' | 'cancelled'
  projectId: string | null
  requiredDisciplines: Array<'design' | 'code' | 'art' | 'audio' | 'qa'>
  supplementSequence: number
}>
```

`Record` 的 key 必须是 `company.id`，旧存档缺失该字段时按 `{}` 读取，不追溯补发保障；AI 公司 key 不触发逻辑。编码 Agent 可在实现审核时调整字段名，但必须保留上述语义和默认值。

建议在 `WorldState` / `save-schema.ts` 增加该可选字段，schema 默认值为 `{}`；schemaVersion 是否升级由编码 Agent 按项目存档迁移规则确认。旧档迁移不得推断一个已有公司的历史首项目资格，也不得把 AI 公司映射成玩家公司。

### 2.1.1 状态机

```text
eligible --首个玩家 REC-04 ExecutionProject 创建成功并立即补池--> active
active --五学科各至少一名已雇员工--> completed
active --首项目取消--> cancelled
active --首项目暂停/读档/重开同一存档--> active
completed / cancelled --后续新项目或重开新局外的任何操作--> 不再触发
```

- `active` 在首项目取消前持续有效；取消后进入 `cancelled` 并停止补位，不允许新建项目重新触发。
- 暂停不等于取消；恢复同一项目后保障继续有效。
- 玩家若因删除存档重开新局，按新公司新存档处理；正常读档不能重置状态。
- 五名员工不要求同一日入职，但必须在同一家公司当前 occupying，且各学科都有至少一名 skillLevel 1..5 员工时才算 `completed`。

### 2.2 覆盖保证

保障池必须至少包含五个**可用候选**，且每个必需学科至少一名 `skillLevel=5` 的候选：

| 学科 | 是否必须覆盖 |
|---|---:|
| `design` | 是 |
| `code` | 是 |
| `art` | 是 |
| `audio` | 是 |
| `qa` | 是 |

低于 5 级的候选仍可作为普通候选保留，但不能满足 REC-04 首项目的保障覆盖。保障只保证**五学科各有一名 5 级候选**，不保证：

- 技能等级；
- 期望薪资高低；
- 可入职日完全相同；
- 候选人的姓名、年龄、地区或其他质量属性。

候选技能、薪资、可入职日仍使用现有确定性生成和 D-03 规则，避免把保障池变成固定最优团队。

保障补位候选固定为 `skillLevel=5`；普通候选池仍允许现行 `0..5`。这是首项目的可行路径选项保障，不是强制招聘或成功保证。

### 2.3 普通候选池

首个项目保障完成后，后续项目继续使用现有有限随机候选池：池上限、确定性 seed、技能区间、薪资区间、已雇佣人物过滤和普通刷新规则均保持不变。后续项目不自动获得五学科覆盖保证。

### 2.4 招聘到岗时序边界（本提案明确排除）

本提案选择**方案 A：仅实现首项目候选池保障**。当前实现中，`recruitFromCandidate()` / `hire()` 在招聘确认日创建 `Employment` 并兑现招聘费；`candidate.availableFromDay` 目前只返回给调用方，未用于延迟创建雇佣关系。本提案不改变这一现状，也不声称修复 D-03 的到岗时序契约。

- 保障覆盖只表示候选池中五个必需学科各有一名 `skillLevel=5` 的可招聘候选；不得将其解释成到岗保障或产能即时可用保障。
- 首项目创建命令的即时补池与候选的 `availableFromDay` 无关；补位不得绕过现有 `hire()` 守卫，也不得基于“到岗延迟已实现”推导可用团队或 READY。
- `arrivalDay = hireConfirmDay + recruitLeadDays(candidate)` 的生产行为，以及 Employment、薪资、招聘费按到岗日生效的时序差异，登记为独立 D-03/SUP 任务；由设计负责人裁定目标契约和范围，工程实现，数值 Agent 量化等待/成本影响，体验 Agent 验证 UI 呈现。该任务在被单独排期并验收前保持未解决。

1. 候选仍遵守 D-03 的 `expiresAtDay`；过期候选按现有规则移除。
2. `state=active` 且五学科尚未全部有**已雇员工**时，每次合法刷新先清理池，再按“缺失学科 = 没有 Lv5 未占用候选”计算缺口并补位。
3. 玩家招聘某学科唯一的 Lv5 候选后，该学科在保障尚未完成时保持缺口；下一次合法刷新补回一名新的 Lv5 候选。
4. 候选被雇用或过期后，补位使用新的 `supplementSequence`，不能复用已占用/已过期人物或 candidateId。
5. 五学科各有已雇员工后转为 `completed`，此后不再为该公司补保障候选。
6. 读档、暂停、切换页面不推进刷新；日推进仍是刷新边界的唯一时间来源。首个项目创建成功后的立即补齐是唯一的非日 tick 补位。
7. 保障池不得绕过管理容量、招聘费、月薪承诺、公司状态或 AvailableCash 守卫；本任务沿用当前招聘确认日生效的实现，不新增候选可入职日守卫。

### 3.1 `candidatePoolSize=5` 冲突处理

本提案选择“**保障期间临时扩展池容量**”，不淘汰玩家当前可见候选：

- 普通池继续使用 `candidatePoolSize=5`；
- `state=active` 时，有效容量为 `max(5, 清理后保留候选数 + 缺失学科数)`，所以已有 5 名候选但缺 4 个学科时，保障池可暂时达到 9 名；
- 保障逻辑只补缺口，不随机删除已有候选；
- 当五学科各有已雇员工后转为 `completed`，下一次刷新恢复普通池上限；若候选超过 5 名，按 `candidateId` 字典序稳定保留前 5 名，其余产生可审计的池收缩记录并从可见池移除。

保障补位使用独立 seed 命名空间 `rec04a-guard:${companyId}:${projectId}:${supplementSequence}:${discipline}`，不使用现行 `${day}-${i}`；`supplementSequence` 每次生成补位候选递增并随保障状态持久化，避免与普通池或同日补位发生 ID 冲突。

## 四、与项目流程的关系

推荐的首局流程是：

1. 玩家创建公司；
2. 玩家先创建第一个 ExecutionProject，锁定预算承诺和项目快照；
3. 首项目创建命令立即在既有候选池上执行清理和缺口补齐；招聘页明确显示五学科候选覆盖状态；
4. 玩家根据技能、薪资、现金跑道选择并招聘最小团队；
5. 玩家显式分配团队，推进研发。

“先立项后招聘”是默认推荐顺序，因为项目承诺应先占用预算额度；该顺序不取消招聘决策，也不保证玩家选择的高技能组合一定能在预算和现金内完成。招聘确认卡仍必须展示中介费、月薪承诺、AvailableCash 与 Runway 的前后变化。

## 五、非目标

- 不引入完整劳动力市场、跨公司挖角或人才搜索系统。
- 不自动分配员工到项目。
- 不保证高技能、低薪或特定候选组合。
- 不调整起始资金、默认薪资、HRB 两档、六个月承诺窗口、预算公式或财务守卫。
- 不通过提高初始资金或隐藏承诺来制造“可玩”假象。
- 不改变普通后续项目的随机人才市场。

## 六、验收场景

### 设计验收

1. 仅玩家公司创建首个 REC-04 ExecutionProject 时触发；AI 公司、非 REC-04 项目、后续项目均不触发。
2. 若招聘页已懒刷新出普通候选，首项目创建成功的同一命令立即保留合法候选并补齐缺岗；不得清空或覆盖现有有效候选。
3. 初始池恰为五名且学科重复时，保障池临时扩容并补齐 `design/code/art/audio/qa`，每学科至少一名 `skillLevel=5` 候选。
4. 低技能普通候选仍可保留；保障补位等级固定为 5，薪资仍按现有确定性规则生成。
5. 招聘某学科唯一可用候选后，该学科仍未有已雇员工；下一次日 tick 补回，不重复生成已占用人物或 candidateId。
6. 五学科各有已雇员工时状态转 `completed`；项目取消转 `cancelled`；暂停、读档和重开同一存档保持原状态；取消后创建另一个项目不重新触发。
7. `listCandidates()` 的空池懒刷新与 `personnelTick` 日刷新必须调用同一个保障补齐入口，保证相同状态/seed 得到相同候选集合；首项目创建成功时也调用该入口。
8. 保障期间允许候选池超过 5；保障完成后的下一次日刷新确定性裁剪至 5，并记录稳定裁剪结果。
9. 保存、读档、旧档缺字段、同一公司重复进入招聘页、两个公司状态隔离和补位 seed 无碰撞均有领域/存档测试。
10. 缺岗、过期、资金不足和容量不足沿用当前机制并保持可解释、fail-closed；玩家仍需显式分配员工。`availableFromDay`、`arrivalDay` 延迟到岗及相关招聘费时序不在本次验收范围，归入独立 D-03/SUP 任务。
11. 不改变招聘确认日创建 Employment / 兑现招聘费的现行实现；不得据 REC-04A 宣称 D-03 到岗时序已符合规格。

### 数值 Agent 待验证

数值 Agent 只验证参数与结果，不决定上述机制：

1. 保障池与现行随机池的岗位覆盖率、平均等待天数和最坏等待天数比较；
2. 技能等级 `0..5` 与薪资区间下，最小五学科团队的招聘承诺分布；
3. “先立项后招聘”在默认起始资金、预算承诺和六个月 AvailableCash 口径下的现金跑道；
4. 首项目保障对自然 READY、预算耗尽、破产和完成率的影响；
5. 保障池候选过期/补回边界的确定性、存档往返和多 seed 结果；
6. 若结果仍无法在默认路径内开始研发，提交参数风险报告，不自行修改设计锚点。

### 体验 Agent 待验证

机制实现后由体验 Agent 独立验证：

1. 真实电脑端新档能看懂五学科缺口和保障状态；
2. 玩家能从首项目创建、招聘、分配到研发推进；
3. 招聘确认卡能理解承诺额、可用现金和跑道变化；
4. 保障机制不会被 UI 文案误读为“保证项目成功”。

## 七、需要形成的正式裁定

本提案进入 READY 前，主设计负责人/Owner 需确认：

1. 是否接受“首个 ExecutionProject 五学科覆盖保障”；
2. 是否接受保障候选固定为 Lv5 可选项，而普通随机候选仍允许 0..5；
3. 是否接受 `candidatePoolSize=5` 在保障期间临时扩容、completed 后下一次日刷新再裁剪至 5；
4. 是否接受只针对玩家公司首个 REC-04 ExecutionProject，取消后本公司不再获得保障；
5. 是否接受推荐的 `WorldState` / `save-schema.ts` 可选状态字段与旧档 `{}` 缺省；
6. 保障补位只在首项目创建成功时即时执行，之后在下一次日 tick 补位；
7. 接受后由编码 Agent 提交候选池保障实现与 schema 方案，设计审核 Agent、编码审核 Agent 分别复核，数值 Agent 验证结果，体验 Agent 验证真实电脑端路径。
8. 确认本提案不包含招聘到岗时序修复；D-03/SUP 独立任务另行裁定、排期和验收。

Owner 已在 2026-11-26 明确要求实现本方案，视为第七节机制范围的批准。设计审核结论为 `PASS_WITH_NOTES`。本文件作为 REC-04A 的生效实现规格；到岗时序与 `availableFromDay` 仍明确排除，独立 D-03/SUP 任务未被本 ADJ 关闭。REC-04A 实现完成不等于 REC-04 或 SUP-01 CLOSED，仍需编码审核、数值验证和体验 Agent 专项验证。
