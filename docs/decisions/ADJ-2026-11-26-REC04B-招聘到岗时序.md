## 1. 问题与根因

D-03 V0.1.2 §6.3 已明确 `arrivalDay = hireConfirmDay + recruitLeadDays(candidate)`，并规定招聘费承诺在确认日创建、到岗日兑现；§7.2 又规定薪资承诺从 `Employment.startDay` 所在月开始。当前实现返回了 `arrivalDay`，但没有让该日期控制 Employment 生效：`recruitFromCandidate()` 在确认日调用 `hire()`，立即创建 `occupiesPerson=true` 的 `probation` Employment、可分配的 legacy Employee 和从确认月开始的薪资承诺；`hire()` 也以确认日为招聘费日期并立即兑现。候选按钮与确认卡目前也未显示规格要求的可入职日/到岗日。

另有两个公式/数据来源断点：候选人物生成将 `Person.seniority` 固定为 `junior`；候选 `availableFromDay` 只加 `baseLeadDays`，未按 §6.3 为 senior 增加 `kLead`。招聘守卫只检查确认日是否过期，没有检查 `arrivalDay > candidate.expiresAtDay`。

这不是单独的 UI 延迟显示问题，而是招聘命令、人员唯一性/容量、产能、Payroll 和 FIN 承诺起算日没有共享同一到岗时点。

## 2. 规则来源与裁定边界

Owner 已要求继续完成 REC-04，并接受先落完整时序契约、再编码和分层验收的执行方式。下列新规则按本文件实现；若实现审核发现与冻结 D-03 正文冲突，必须先停在 `REVISE_REQUIRED`，不得用代码猜测覆盖规格。

### 2.1 D-03 已冻结，本任务必须遵守

1. `recruitLeadDays(candidate) = baseLeadDays + kLead × 1[seniority == senior]`；`arrivalDay = hireConfirmDay + recruitLeadDays(candidate)`。
2. 若 `arrivalDay > candidate.expiresAtDay`，招聘必须以 `D03_CANDIDATE_EXPIRED` 拒绝，不能创建半成品承诺或任职状态。
3. 招聘费**金额不在本任务重裁**：沿用已批准 ADJ-2026-11-22-12 S5-3 / 当前 TUNING `recruitFeeMonths=1`，按谈判月薪 × 1 个月。D-03 V0.1.2 §6.3 的 `hireCostRatio=0.15` 与已批准金额锚点存在文字冲突，应由主设计负责人另行做文档一致性勘误；REC-04B 不擅自改变当前金额行为。费用类型/引用/幂等沿用 D-03/C9：`one_off` / `contract_obligation`，`sourceRef=employmentId`，兑现交易 `category=project_expense`；确认日建立承诺，到岗日兑现一次，幂等键 `<commitmentId>:one_off`。
4. 月薪按自然月整月计费：Employment 的到岗日所在月有至少一天在职，就在该月计一笔整月工资；月中离职仍按 ADJ-09 在离职月计一笔，次月停付。
5. 薪资承诺在招聘确认时建立并进入 FIN `CommittedBurn` / AvailableCash；承诺本身不直接改现金。承诺 `startAt` 从 `Employment.startDay` 所在月月初起算，首期长度仍是 `initialTermMonths` 个自然月。
6. `Person.currentEmploymentId != null` 必须指向 `occupiesPerson=true` 的 Employment；全库每人最多一条 occupying Employment。不得用 `occupiesPerson=false` 的伪 Employment 冒充待到岗状态，因为这会违反 D-03 INV-2。
7. P1 人事不自动分配到项目。招聘确认不能自动创建项目 Assignment。

### 2.2 必须由主设计负责人/Owner 批准的新规则

D-03 V0.1.2 §4.3 的人物状态转换表将“hire 确认 → 新建 occupying Employment”写作即时生效，与 §6.3/§7.2 的延迟到岗/费用时点不一致。因此以下不是工程自行解释，须在批准本 ADJ 时明确采纳：

1. 待到岗期间采用独立 `PendingHire`，不创建 Employment；到岗日才创建 occupying Employment。`Person` 保持 `available`、`currentEmploymentId=null`，不参加产能、工资实际结算或项目分配。
2. PendingHire 占用该 Person 和公司的管理容量，防止重复招聘或超额承诺；但它不占用 Project 产能，也不出现在在职员工列表中。
3. 薪资承诺在确认日创建，`startAt` 使用到岗月月初，`endAt` 为到岗月开始后的第 `initialTermMonths` 个自然月月末。因此确认日即预留未来薪资，但到岗月之前不计实际工资。
4. 玩家可在 `arrivalDay` 前取消待到岗招聘。取消不产生招聘费或遣散费；取消薪资承诺自其首个生效月起释放；候选人物在仍未过期时回到候选池，否则保持未雇佣人物记录但不回池。
5. 公司在 `arrivalDay` 前进入 `bankrupt` 时，自动取消尚未到岗的 PendingHire 并释放未来承诺；到岗日当天先按既定日循环顺序生效、后续当日破产检查不追溯撤销当天已发生的雇佣。公司进入 `dissolved` 时无条件取消全部 PendingHire。破产后恢复公司不自动恢复已取消招聘，玩家需要重新招聘。
6. 待到岗人员计入管理容量上限；容量 UI 同时展示在职数和待到岗数，防止玩家误以为仍有空位。
7. Seniority 以候选所关联 `Person.seniority` 为权威，不在 Candidate 上复制第二份可漂移字段；候选刷新需按批准规则确定生成的 Person seniority。若没有既有生成规则，推荐采用 `skillLevel >= 4 ? senior : junior`，但该映射会令技能同时影响薪资职级和到岗时长，须由设计批准，不作为已冻结规则。
8. 重复提交采用招聘 `requestId` 幂等：同 requestId、同 payload 返回同一 PendingHire/Employment 结果；同 requestId、不同 payload 返回稳定冲突错误。没有 requestId 的既有调用可继续使用“候选已被预留/已招聘”守卫，禁止创建第二份承诺。

## 3. 目标状态与数据接口

### 3.1 PendingHire 独立记录

建议新增 `PendingHire`，不要将其塞入 Employment 状态枚举。最小字段：

```ts
interface PendingHire {
  pendingHireId: string
  requestId: string
  payloadHash: string
  employmentId: string
  personId: string
  companyId: string
  candidateId: string
  candidateExpiresAtDay: number
  role: EmployeeRole
  discipline: D03Discipline
  seniority: 'junior' | 'senior'
  skillLevel: number
  negotiatedSalaryCents: number
  initialTermMonths: number
  hireConfirmDay: number
  arrivalDay: number
  salaryCommitmentId: string
  recruitFeeCommitmentId: string
  state: 'pending' | 'arrived' | 'cancelled'
  cancelledAtDay: number | null
}
```

字段名可由编码 Agent 调整，但语义不可删减。`state='arrived'/'cancelled'` 的历史记录可保留作审计；也可在迁移/压缩策略中归档到事件，但必须保证相同 requestId 重放可返回原结果，且已兑现费用/薪资不会重复。

WorldState 增加可选 `pendingHires`，新档默认 `[]`。存档 parser 应对旧档缺字段使用 `[]`；不得把已存在的 Employment 推断成待到岗或更改其 `startDay`。到岗转换使用预留 `employmentId`，不在 arrival tick 再生成不同 ID。

### 3.2 唯一状态机

```text
Candidate (available, currentEmploymentId=null)
  └─ 招聘确认日 D：校验报价/过期/容量/现金；移出候选池；登记两项承诺
       └─ PendingHire(pending, D, arrivalDay=A)
            ├─ A 到达，Company.active → 创建 Employment(startDay=A, probation, occupying=true)
            │    Person.currentEmploymentId=employmentId；兑现招聘费一次；PendingHire=arrived
            ├─ 玩家在 A 前取消 → 释放薪资承诺；取消招聘费承诺；无交易/遣散；PendingHire=cancelled
            ├─ arrivalDay > candidate.expiresAtDay → 确认时直接拒绝，不产生 PendingHire
            ├─ A 前公司 bankrupt → 自动取消未到岗项；释放承诺；不自动恢复
            └─ 公司 dissolved → 自动取消全部未到岗项并终止后续生效
```

招聘确认原子边界：现金/容量/人物资格/候选到岗有效期全部校验成功后，才登记 salary + recruitment fee 两个承诺、持久化 PendingHire、从池中移除候选。任一承诺注册失败时必须回滚本次此前注册内容，候选与容量不变。到岗原子边界：Employment、Person.currentEmploymentId、legacy Employee 投影、费用兑现必须同日一致；失败不得留下半到岗状态。

### 3.3 确认日、到岗日与财务时点

| 时点 | 预期行为 |
|---|---|
| 招聘确认日 D | 计算并冻结 `arrivalDay`；确认 `arrivalDay <= expiresAtDay`；注册月薪承诺（startAt = arrival month 月初）和招聘费 one_off 承诺（startAt = arrivalDay）；两项进入 CommittedBurn/AvailableCash；Company.cash 不因承诺创建变化；无 Employment、无员工人数增加、无产能、不可分配、无招聘费交易、无工资交易 |
| D 至 A−1 | PendingHire 持久化且占公司名额/人物预留；可取消；不出现在在职员工列表；承诺继续显示在现金预留中；候选不再公开可重复招聘 |
| 到岗日 A | DailyScheduler 在 personnel arrival 阶段（先于当日月薪结算）验证公司仍 active；创建 `Employment.startDay=A`、`status=probation`、`occupiesPerson=true`；Person currentEmploymentId/status 对齐；legacy Employee 生成；一次性招聘费按幂等键兑现；薪资仅从 A 所在自然月开始，满足“碰过当月即计一笔” |
| 取消日 C < A | release 薪资承诺，自到岗月首月起不再兑现；cancel one_off 招聘费承诺；不产生现金交易或遣散；候选未过期才回池；PendingHire 状态变为 cancelled |

**工资边界例子**：若确认日在 4 月 28 日、到岗日在 5 月 1 日，则 4 月不计工资，首笔为 5 月月末；若到岗日在 4 月 30 日，则按既有 ADJ-09 规则计整笔 4 月工资。确认日 AvailableCash 已预留从到岗月开始的完整首期承诺，不得用确认月替代到岗月。

### 3.4 Candidate seniority 与 lead days

1. `Person.seniority` 是职级唯一权威；PendingHire 保存确认时的 seniority 快照，以固定已展示的到岗日和薪资报价，避免后续人物字段变更影响合同。
2. Candidate 接口不再维护第二个 seniority 来源；候选刷新创建 Person 时确定 seniority，并保证从 Person 查询到的值参与报价和 lead days。
3. `recruitLeadDays = params.baseLeadDays + (seniority === 'senior' ? params.kLead : 0)`；`arrivalDay = hireConfirmDay + recruitLeadDays`。不得用候选技能临时推算到岗日期，除非新设计裁定明确把 `skillLevel -> seniority` 映射冻结。
4. 候选显示的到岗日、确认卡的 arrivalDay 和后台 PendingHire.arrivalDay 必须来自同一纯函数/同一输入快照；报价确认后不再因参数版本或存档版本漂移重算。

## 4. 失败、取消与幂等边界

| 场景 | 结果 |
|---|---|
| `arrivalDay > expiresAtDay` | `D03_CANDIDATE_EXPIRED`；候选仍在池中直至正常过期；不得创建 pending、Employment 或财务承诺 |
| 人物已 occupying 或已有同人物 PendingHire | 返回 `D03_ALREADY_EMPLOYED` 或新增稳定的 `D03_HIRE_PENDING`；不得重复占用/承诺 |
| 管理容量满（在职 + pending） | `D03_HEADCOUNT_FULL`；不删候选、不创建承诺 |
| 可用现金不足以容纳薪资 + 招聘费承诺 | `FIN_INSUFFICIENT_CASH` 或既有招聘错误码；原子拒绝，不出现部分承诺。可用现金仍由既有公式计算 |
| 到岗前玩家取消 | 新命令 `cancelPendingHire(pendingHireId)`；只有 `pending` 且当前日 `< arrivalDay` 可取消。重复同请求取消幂等；到岗日及之后返回 `D03_HIRE_ALREADY_ARRIVED` |
| 当日到岗与玩家取消竞争 | 游戏单线程命令序：当日 scheduler arrival 已执行后，取消失败；在 scheduler 前执行且 `day < arrivalDay` 才可取消。不能出现取消和到岗均成功 |
| 破产前已取消招聘 | 保持 cancelled，不恢复；不得因公司恢复重放费用/工资 |
| 公司 dissolved | 所有 pending 自动 cancelled；薪资与招聘费承诺均释放/取消，不增新支出；存档终态可审计 |
| 重复招聘提交 | 同 `requestId` + 同 payload 返回原 pending/结果；相同 requestId 不同 payload 返回冲突；不同 requestId 竞争同候选只有首个成功 |
| 到岗 scheduler 重跑/读档回放 | `state=pending` 才转换；招聘费使用既定 `<commitmentId>:one_off`；Employment ID 固定；重复日推进不重复创建 Employment 或交易 |
| 旧档没有 PendingHire 字段 | 解析为空列表；旧 Employment 和账本完全保持原状，不补收费用、不延后员工生效 |

**费用释放语义**：在 arrivalDay 前取消时，薪资承诺尚未进入生效月份，不应有已赚取周期。若 FIN 当前 `releaseCommitment` 的默认边界会释放全部未兑现期，必须用明确的 `effectiveMonth=startMonth(arrivalDay)`；招聘费 one_off 必须显式 cancel/release，不得创建反向现金交易。

## 5. UI 接口

1. 候选卡展示姓名、地区、学科/技能、薪资、`可入职日`、`候选有效至`；不得显示 `candidateId` 或 seed 作为主要名称。
2. 招聘确认卡展示固定的 `arrivalDay`、一次性招聘费、月薪、承诺月数、AvailableCash/Runway 前后变化；明确招聘确认后“待到岗”，避免被理解为即时产能。
3. 招聘页或员工页展示“待到岗 N 人”分组及姓名、岗位、到岗日、薪资承诺；显式呈现其占用管理名额但尚无产能。
4. 待到岗记录提供取消按钮，并展示取消后预计释放的未来薪资承诺；若已到岗则取消按钮消失/禁用并给可读原因。
5. UI 日期文案由一个 DayIndex formatter 产生；报价预览和候选卡不能各自独立重算 lead days。
6. 招聘/取消错误码映射中补足过期、已预留、已到岗、容量不足、资金不足、公司破产/已解散等可读提示，不显示内部 PendingHire ID。

## 7. 文件边界与职责

- 设计负责人/Owner：批准 §2.2 中标记为新产品规则的选项，并同步 D-03 V0.1.2 §4.3/§6.3/§7.2/§9.2，保持单一权威契约。
- 编码 Agent：实现 Candidate/Person seniority 生成、PendingHire 领域状态、GameWorld/每日调度接线、原子 FIN 承诺/释放、旧档兼容和定向测试；不改薪资/费用/AvailableCash 锚点。
- 独立编码审核 Agent：审核状态不变量、事务回滚、破产/解散、幂等与存档边界。
- 数值 Agent：仅核对薪资承诺起始月、确认时 AvailableCash 预留、到岗/取消对现金和跑道的影响；不裁定 pending 玩法。
- 体验 Agent：用真实电脑端路径验证招聘确认、待到岗、取消、到岗和分配反馈；不由主 AI 代做。
- 主 AI：锁定接口与依赖，协调实现/复审/数值/体验验收，更新 REC-04/SUP-01 台账；不得把测试全绿等同于玩家闭环通过。

## 8. 与 REC-04 关闭的关系

REC-04B 通过只关闭招聘到岗时序子任务。REC-04/SUP-01 仍需完成默认经济下的完整自然路径，并在电脑端真实验证 `READY_TO_DELIVER → 交付确认 → 上市 → 销量/收入`。到岗前不产能与项目现金跑道风险须在同一真实路径中如实观察，不能提高初始资金或手写状态替代证据。

## 9. 自洽性检查

- 不新增 `EmploymentStatus='pending'`，故不破坏 `occupiesPerson ⇔ status∈{probation,active,resigning}`。
- 确认日薪资承诺可计入 AvailableCash，但因 `startAt` 从 arrival 月开始，不会把确认月误当作已到岗工资月。
- 到岗月按 D-03/ADJ-09 的“碰过该月即计 1 笔”执行，不引入日薪折算。
- 到岗日既是候选有效期最后一天时允许成功；到岗日严格晚于 `expiresAtDay` 时确认失败，边界可判定。
- 招聘费金额沿用已批准 ADJ-12 S5-3 / `recruitFeeMonths=1`，REC-04B 只修兑现时序；只通过原 one_off commitment 幂等键兑现；取消只释放承诺，不用现金冲销伪造“未发生”。
- 旧档无 pending 项，保持现有即时 Employment 的历史事实，不进行不可逆追溯改写。
- §2.2 的公司破产/解散自动取消、名额计数、seniority 生成和请求幂等输入按 REC-04B 明确的新规则处理；Owner 已要求完成 REC-04 并授权按本接口继续实现。设计审核仍需确认无冲突，编码审核仍需独立验收。
