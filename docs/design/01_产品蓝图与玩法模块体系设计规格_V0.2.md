## 0. 本规格的立场与阅读方式

### 0.1 一句话主张

产品设计系统的唯一职责，是**把玩家做出的若干个离散设计选择，转换成一组可被研发、市场与档案三个下游系统消费的结构化事实**；它不做销售计算，不做团队排产，也不做完整度裁判。

### 0.2 一条核心原则

> **设计选择必须同时产生"成本侧后果"和"市场侧后果"，且两条后果不能互相抵消。**

若某个设计选项只增加成本而不改变市场匹配（或反之），它就是无效参数，不得进入设计项。这条原则是对基线 §7.2「高级深度设计必须改变工作量、技术要求、受众匹配或产品表现」的可执行化。

### 0.3 已做的六项主动取舍（阅读本文档时请先看这里）

| # | 取舍 | 放弃的方案 | 理由 |
|---|---|---|---|
| T1 | **模块实例即单位**：同一模板可多次装配为不同实例（如"战斗"与"驾驶"都是战斗域但不同数值档） | 每个模块模板只能装一次 | 一次性排除会强迫玩家在"多类型混搭"上失去表达力，与 P2「相同类型不同玩法组合可形成不同受众」冲突 |
| T2 | **影响力分四通道独立输出**（工作量/技能负载/技术门槛/市场匹配），不合成"设计价值分" | 合成一个设计综合评分 | 基线红线 §14「不用单一综合分数掩盖产品质量、完整度和市场匹配的差异」 |
| T3 | **废弃无返工**：设计项在锁定后不可删除，只能"停用"（Deactivating） | 允许研发中删模块并全额返还 | 删除会伪造"没做过的工作"，破坏因果可追溯性；停用保留沉没成本 |
| T4 | **新增即返工且不可自动批准**：执行中变更必产生返工，费用"分档可估"但**实际值在任务推进时才确定** | 返工费用精确预估并锁死 | 精确预估会诱导玩家寻找"最优点击顺序"，把设计决策退化为数值优化 |
| T5 | **首版新类型生成只做"命名 + 标签 + 识别"**，不做新机制生成、不做新品类核心循环 | 动态生成全新机制的玩法概念 | 基线与阶段规划均要求逐步开放；过早承诺会拖垮 P1/P2 |
| T6 | **估算一律给区间**，显示为"低/中/高"带宽而非单值 | 显示精确工期/成本 | 与系统地图 §6「预测必须显示区间、更新时间和关键假设」一致 |

## 1. 系统目标与玩家体验目标

### 1.1 系统目标（可判定）

| 编号 | 目标 | 判定方式 |
|---|---|---|
| G1 | 让玩家设计的每一个产品在结构上可区分 | 任意两份成功的 `ProductBlueprint` 至少在 1 个 `differentiating` 维度上不同（判定见 §5.5） |
| G2 | 让设计决策产生可解释的生产后果 | 任一代价变化，均可回溯到具体的 `SlotBinding` / `ModuleInstance` / `OptionSelection` |
| G3 | 让设计决策产生可解释的市场侧后果 | 系统输出 `MarketAppealProfile`，D-04 可直接消费，无需二次解释 |
| G4 | 替代 V2.1.7 的"规模参数 + 复杂度分" | 不存在的字段：`scale`、`complexityScore`；规模仅作为预设（`BlueprintPreset`） |
| G5 | 让研发中改设计有代价且可追溯 | 所有变更产生 `DesignChangeRecord`，关联 `ReworkTask` 与成本 |
| G6 | 让产品设计成为长期资产 | 蓝图锁定后进入产品档案，可被续作/更新引用（D-07 接口） |

### 1.2 玩家体验目标

| 编号 | 体验 | 对应的机制抓手 | 反例（必须避免） |
|---|---|---|---|
| X1 | **创造感**：我造的是"一款有性格的游戏" | 定位层 6 个差异化维度 + 玩法槽 + 标志性卖点（最多 3 个） | 玩家只调预算和工期 |
| X2 | **取舍感**：加了就得减 | 人力预算承诺 `HRB`（§6.2.1）：结构先导出工作量，再由预算做单向可行性检查，不足则玩家决定砍范围/加预算/延期/降目标 | 无成本地堆模块；或用预算乘子把工作量"压"到自洽 |
| X3 | **可预期又不可预测**：大方向可估，细节靠团队 | 设计意图（玩家定）× 实现质量（团队定）分离 | 玩家直接看到"最终评分 87" |
| X4 | **品味责任**：市场不接受不是 bug | 市场匹配来自"玩家宣称受众"与"实际模块构成"的差距 | 系统自动选最优受众 |
| X5 | **局部失手的痛感**：一个错误决策拖住整个项目 | 关键路径与技能瓶颈（§6.3） | 全模块平均拉平，无局部失败 |

### 1.3 与基线核心体验的对应

- 创造感（基线 §2.3）→ X1，落在 §4.2 定位层与 §4.4 玩法层。
- 经营张力（§2.3）→ X2，落在 §6.2 结构导出工作量与 §6.2.1 预算可行性闸门、§6.3 瓶颈。
- 因果理解（§2.3）→ G2/G3，落在 §6 全节与 §9.3 解释面板。

## 3. 系统在整体架构中的位置

### 3.1 数据流方向（主链单向；D-04 词表为前置输入）

**主链单向**（设计权威 → 执行权威 → 档案权威，不得回写）：

```
市场洞察 + 技术可用性 + 创意种子
        ↓（玩家）
   ProductBlueprint（设计权威）
        ↓ DesignVersionSnapshot（锁定快照）
   Project（执行权威）——引用快照，不反向改蓝图
        ↓ WorkloadEstimate / SkillDemand / TechRequirement / MarketAppealProfile
   WorkPackage / 团队执行 → Build → Product
        ↓ Product.attributeProfile
   D-04 市场与消费者
        ↓
   D-07 历史档案
```

**前置输入与反馈输入的澄清（关闭 R-13）**：D-01 与 D-04 存在两条方向不同、作用在不同数据对象上的接口，**不构成同一数据的回写环**：

| 接口 | 方向 | 数据对象 | 阶段 | 性质 |
|---|---|---|---|---|
| D-04 → D-01 | 前置输入 | `SegmentTag` 受众标签词表（§8.1） | 创建/编辑蓝图时 | 只读词表，仅供玩家宣称选择；蓝图只存 `targetSegmentClaims` 引用 |
| D-01 → D-04 | 下游输出 | `MarketAppealProfile`（含 `affinity`/`positioningFit`/`genreFit`/`uspSupported`；§6.5/§8.2） | 锁定后 / 估算刷新 | 只读画像，D-04 自行换算需求，不回写蓝图 |

"单向"仅指**主执行链**上 `Project` 不回写 `ProductBlueprint`、快照不可变；D-04 的词表是设计开始前的**前置依赖**，D-04 的需求模型是设计完成后的**下游消费者**，二者不属于主链回写。依赖顺序：D-04 词表就绪 → D-01 可编辑 → D-01 画像输出 → D-04 需求换算。
### 3.2 权威归属（对齐系统地图 §2.2）

- **设计权威**：`ProductBlueprint` 拥有定位与玩法构成本身。
- **执行权威**：`Project` 只引用某个 `DesignVersionSnapshot`，执行期间的"实现现状"由 Project 记录，不得回写蓝图。
- **估算权威**：所有 `Estimate` 都是**派生只读对象**，由蓝图 + 外部输入（技术/人才/市场）在当前时刻重算；不得作为蓝图字段持久化为"事实"。
- **档案权威**：产品上市后的档案由 D-07 持有；蓝图在锁定后进入只读冻结态供其引用。

| 字段 | 类型 | 含义 | 是否差异化维度 | 约束 |
|---|---|---|---|---|
| `primaryTypeId` | ref GameplayArchetype(数据) | 主类型（如 RPG / 策略 / 模拟经营） | ✔ `differentiating` | 必须非空才能锁定版本 |
| `secondaryTypeIds` | list<ref>, ≤2 | 次类型 | ✔ | 不得与主类型重复；组合规则 §5.3 |
| `settingIds` | list<ref SettingTag>, 1–3 | 题材 | ✔ | 时代可用性检查（D-06/P4） |
| `perspectiveId` | enum{side_scroll, top_down, isometric, first_person, third_person, text} | 视角 | ✔ | 经常量表 `PERSPECTIVE_GATE`（§6.4）映射为 `TechGate`，随门槛集合校验 |
| `structureId` | enum{linear, open_zone, sandbox, level_based, roguelike, persistent_online_scope_out} | 结构 | ✔ | `persistent_online` 标 `REJECTED`（联机不进入当前规划）；经常量表 `STRUCTURE_GATE`（§6.4）映射为额外门槛 |
| `targetSegmentClaims` | list<ref SegmentTag>, 1–3 | **玩家宣称**的目标受众标签 | ✔ | D-04 提供标签词表（前置输入，§3.1）；玩家只能宣称，不能直接选群体 |
| `sellingPoints` | list<ref USPId>, 1–3 条 | 卖点 | ✔ | 每条卖点须由蓝图内某个 active 模块/选项支撑（硬规则 `R-COM-7`，§5.4；违规 `E-USP`，§11） |
| `platformTargets` | list<ref Platform>, ≥1 | 目标平台 | ✘（非差异化，但影响成本） | 平台存在性由平台系统校验 |
| `commercialPositioning` | enum{premium, budget, free_to_play_later, subscription_later} | 商业定位 | ✘ | 当前只允许 `premium`（早期）；其余标 `DEFERRED`，枚举保留占位 |
| `presetId` | ref BlueprintPreset / null | 起点预设 | ✘ | 创建后即失效，不再参与计算 |

**关键裁定（DESIGN_BASELINE）**：定位层只有 7 个 `differentiating` 维度参与"可区分性判定"（§5.5）。平台与商业定位不计入区分维度——他们影响**成本与可及性**，不影响"这是什么游戏"。

**已撤除的旧字段（REWORK）**：`scale`（规模 1–5）、`complexityScore`。规模由"槽位数量 + 模块档位 + 内容包档位"自然导出；复杂度由四个估算通道分别表达。**禁止**在实现中重新引入单一规模或复杂度字段。

### 4.4 `GameplaySlot`（玩法层结构位）

槽位是玩家**看得见的"骨架"**，模块填进去。

| 字段 | 类型 | 含义 | 约束 |

### 4.8 规则实体

`CombineRule`：`ruleId, whenTags: list<Tag>, allow: bool, addWorkMultiplier: decimal, note`

`TechGate`：`gateId, domainId(ref D-06), minCapabilityLevel, note`（**接口格式由本文档定义，档位含义由 D-06 定义**）

**TechGate 的四类取值来源（关闭 R-03）**——公式 `T` 集合的每个成员必须能追溯到下表之一：

| 来源 | 字段/常量 | 定义位置 | 备注 |
|---|---|---|---|
| 模块模板 | `i.template.techGates`（active 实例） | §4.6 | list<TechGate> |

| 结构 | `STRUCTURE_GATE[positioning.structureId]` | §6.4 常量表 | TUNING |

**规则编号登记表（关闭 R-06）**——文档内所有 `ruleId` 引用必须能在此表定位：

| 规则 ID | 定义位置 | 内容摘要 | 级别 |
|---|---|---|---|

### 4.10 深度层（DEFERRED 主体，仅定义容器）

深度层在 `ModuleInstance` 上以 `depthSelection` + `optionSelections` 表达。**本文档只定义**：
1. 容器结构（选项组 = 互斥选项；选项带 `costDelta`、`skillLoadDelta`、`audienceAffinityDelta`、`riskDelta`、`techGates`）；
2. 对成本与风险的**贡献方式**（§6.4 公式项 `∑ optionDelta`）；
3. 校验规则（R-OPT-1..3）。

**容器与选项字段定义（关闭 R-01/R-03/R-16）**：

```
OptionGroup: {
  optionGroupId: id,
  name: string,
  required: bool,          // true = 必须选一项；对应 §11 E-16 的 E-OPT
  options: list<Option>    // 组内互斥，最多选 1 项（R-OPT-1）
}
Option: {
  optionId: id,
  costDelta:         map<discipline, WorkUnit>,      // §6.2 工作量增量
  skillLoadDelta:    map<discipline, SkillWeight>,   // §6.3 技能负载增量
  audienceAffinityDelta: map<SegmentTag, weight>,    // §6.5 亲和增量（统一命名）
  riskDelta:         decimal,                        // ≥0，计入 §6.4 协同风险
  techGates:         list<TechGate>,                 // §6.4 门槛集合来源之一
  supportedUspIds:   list<ref USPId>                 // 可支撑卖点，供 R-COM-7
}
```

`ModuleInstance.optionSelections: map<optionGroupId, optionId>` 的每个 value 必须指向所属 `OptionGroup` 内存在的 `optionId`（R-OPT-2）；被选 Option 的字段即 §6 公式中的 `o.*`。

**R-OPT-3（红线）**：每个 Option 必须至少改变 `workload / skillLoad / audienceAffinity / risk` 中的一项，否则不得进入选项组（§0.2 原则的程序化落地）。

**不定义**：选项的具体玩法语义、选项内部的参数化配置、单元级机制编辑。完整深度层另立 **D-01b（PLAYER_CONFIG_DEPTH）**。

**深度层设计红线（DESIGN_BASELINE）**：同上 R-OPT-3。

### 4.13 `GameplayArchetype`（类型库数据条目，关闭 R-04）

`GameplayArchetype` 是类型库中的**玩法类型数据条目**，是 `PositioningProfile.primaryTypeId` / `secondaryTypeIds` 的引用目标，也是 §14 L3 类型库扩展的写入目标。它与 `ModuleArchetype`（一次组合的**临时识别结果**）是不同实体：`ModuleArchetype` 经 §14.4 提升后才成为一条 `GameplayArchetype` 数据。

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `archetypeId` | id | 类型唯一标识，稳定不可变 | 不可变 |
| `name` | string(1–24) | 类型名（如 RPG / ARPG / 模拟经营） | provisional 时由玩家确认（§14.2） |
| `coreSlotDomains` | list<ref GameplayDomain> | 核心槽接受域集合 | 至少 1 个；用于 §4.4 `requiredForType` / `domainAcceptance` 的派生；提升时须与既有类型不冲突（§14.4） |
| `typeAffinity` | map<GameplayDomain, decimal> | 对各玩法域的推荐强度 | 值 ∈ [0,1]；供 §6.5 `genreFit` 与 §5.2 软关系；不阻止装配 |
| `subtypeTableId` | ref / null | 子类型表引用（若该类存在子类型） | §14.2 二级匹配用 |
| `isProvisional` | bool | 是否临时类型 | true 时只能作次类型（§14.4） |
| `state` | enum{provisional, active, deprecated} | 生命周期状态 | 见下 |
| `successCount` | int | 作次类型成功上市累计次数 | 达 `K`（TUNING）后 `provisional → active`（§14.4） |
| `source` | enum{seed_data, player_created, ai_created} | 来源 | AI 与玩家共享类型库（§14.4） |
| `createdAt` / `promotedAt` | datetime / null | 创建与升级时间 | 由 Calendar 提供 |

**生命周期与状态转换**：

```
[种子数据] ──seed_data──► [active]  （首批预置类型，可直接作主类型）
[ModuleArchetype 提升] ──§14.4──► [provisional]  （isProvisional=true，仅可作次类型）
[provisional] ──successCount ≥ K──► [active]  （可作主类型；promotedAt 设置）
[active|provisional] ──长期无产品/内容库改版──► [deprecated]  （只读保留，不再作为新版本可选；旧档案仍引用）
```

**与其他实体的关系**：
- `PositioningProfile.primaryTypeId` 必须引用 `state=active` 的条目；`secondaryTypeIds` 可引用 `active` 或 `provisional`。
- §14.2 的相似度匹配对象是类型库中 `state ∈ {active, provisional}` 的 `GameplayArchetype`。
- 提升后的 `coreSlotDomains` 用于生成/校验 `GameplaySlot.requiredForType` 与 `domainAcceptance`（§4.4）。

## 5. 业务规则

### 5.1 玩法域分类（分类体系）

两级：**玩法域（GameplayDomain）→ 模块模板（ModuleTemplate）**。

玩法域（10 个，DESIGN_BASELINE）：

| 域 | 定义边界 | 典型标签 | 不负责 |
|---|---|---|---|
| `combat` | 直接对抗冲突的规则 | real_time / turn_based | 难度曲线（属选项） |
| `exploration` | 空间/信息的发现与移动 | open / linear / procedural | 叙事（`narrative`） |
| `progression` | 能力/资源/阵营的成长 | leveling / gear / skill_tree | 数值平衡 |
| `narrative` | 剧情/角色/分支呈现 | branching / linear / environmental | 对话量（属 content） |
| `management` | 资源调度与效率优化 | economy_loop / scheduling | — |
| `building` | 空间/设施构造 | free_build / grid | — |
| `social_sp` | 单机内的角色/关系系统（非联机） | companion / faction | 联机（`REJECTED`） |
| `puzzle` | 规则约束下的求解 | logic / physics | — |
| `rhythm` | 时序输入 | music / action | — |
| `simulation` | 系统状态推演 | economy_sim / life_sim | — |

**约束 R-DOM-1**：一个 `ModuleInstance` 的域由模板决定，不可在实例上改域。跨域混搭通过"多个实例"实现，而不是"混合模块"。

### 5.2 定位字段之间的关系（类型/题材/视角/结构）

| 关系 | 规则 | 级别 |
|---|---|---|
| 类型 ↔ 槽位 | 主类型决定必选槽与槽位接受域 | 硬 |
| 类型 ↔ 模块 | 主类型（`GameplayArchetype.typeAffinity`）给出对某些域的"推荐强度"，经 §6.5 `genreFit` 影响 `MarketAppealProfile`，**不阻止**装配 | 软 |
| 题材 ↔ 时代 | 题材标签带 `eraRange`；越界仅提示（历史可能不存在该题材） | 软 |
| 视角 ↔ 技术 | 视角经 `PERSPECTIVE_GATE`（§6.4）映射为 `TechGate` | 硬（技术门） |
| 结构 ↔ 内容 | `open_zone` / `sandbox` 要求 content 槽为 `sandbox_seed`，`roguelike` 要求 `procedural` 标签 | 硬 |
| 受众宣称 ↔ 模块 | 亲和差距 → `positioningFit` 指标（§6.5），影响市场匹配 | 软但高影响 |
| 卖点 ↔ 模块 | 卖点须有支撑（R-COM-7） | 硬 |
| 平台 ↔ 输入方式 | 视角+结构与平台输入能力（手柄/键鼠/触屏）兼容检查 | 硬（技术门） |

### 5.3 组合限制（CombineRule）

1. **槽位容量**：`len(slot.bindings) ≤ slot.maxInstances`（硬）。
2. **域接受**：`instance.domain ∈ slot.domainAcceptance`（硬）。
3. **时代可用**：`template.era.fromYear ≤ year ≤ template.era.toYear`（硬，P4 起强制）。
4. **互斥标签**：同一栈内出现互斥标签对时，`ConflictRule.severity=hard` 禁止（例：同一产品的"实时"与"回合"核心战斗不得同时为主核心，除非有 `hybrid` 标签切换项）。
5. **结构约束**：见 §5.2 结构行。
6. **内容包约束**：content 槽必须绑定 `ContentPack`，且 `compatibleDomains` 覆盖内容槽语义（硬）。
7. **卖点支撑**（`R-COM-7`，硬）：每条 USP 至少被一个 active 模块（`template.uspIds`）或被选选项（`supportedUspIds`）支撑；否则 `E-USP`。
8. **区分度下限**（软）：若不满足 §5.5 的"可区分性"，给出"与其他近期产品高度相似"警告，不阻止锁定。

**批量处理上限（关闭 R-14）**：主类型切换或批量装配时，单次操作最多处理 `k_batch_limit = 8`（TUNING）个模块实例；超出部分系统分多次批量呈现，不要求玩家单次处理全部。不兼容模块的解决动作集见 §10.2。

### 5.4 依赖与冲突判定（算法）

**输入**：`active` 的 `ModuleInstance` 集合 `M`、其 `optionSelections`、`positioning`。

**求解顺序**（确定性，顺序固定）：

1. `HardConflict` 检测：对每对 `(a,b) ∈ M`，若满足 `ConflictRule` 且 `severity=hard` → 违规 `E-CONFLICT`。
2. `SoftConflict` 检测：同上，`severity=soft` → 违规 `W-CONFLICT`，并写入 `RiskProfile.synergyPenalty`。
3. `RequireRule` 解析（见算法 R1）：
   - 按 `severity` 降序处理（hard 先）；
   - 对每个 `subject`（模板或选项或卖点），检查 `requires` 是否满足；
   - 若未满足且 `hard` → `E-DEP`；`soft` → `W-DEP` 并计入 `penalty`。
4. 依赖链闭包：`RequireRule` 的 `requires` 可能再引依赖（如 A 需 B，B 需 C）。**判定为传递闭包**，若闭包内出现环 → 违规 `E-CYCLE`（§10.2）。
5. 输出：`ViolationSet`（含每个违规的 `ruleId`、涉及实例、建议修复方向）。

**规则 `R-COM-7`（卖点支撑，硬）— 在 §4.3/§4.6/§5.2/§5.3 被引用，此处给出唯一权威条款（关闭 R-06）**：

```
对每条 u ∈ positioning.sellingPoints:
  supported = ∃ i ∈ M(active) :
        u ∈ i.template.uspIds
     ∨ ∃ o ∈ i.optionSelections.values : u ∈ o.supportedUspIds
  if not supported: emit E-USP(subject=u, ruleId="R-COM-7")
```

该规则在**锁定校验、返工完成闸门、交付闸门**三处均须执行（§7.2）。禁止使用未定义编号；UI 错误对象 `ruleId` 一律取自 §4.8 规则编号登记表。

**算法 R1（RequireRule 求值）**

```
for rule in rules sorted by severity(hard first):
    for subject in active_subjects_matching(rule.subject):
        satisfied = all(req in requires : exists_active_support(req))
        if not satisfied:
            emit violation(rule, subject)
```
`exists_active_support(req)` 定义：`req` 为模板 → 存在 active 实例且 `templateId == req`；为标签 → 存在 active 实例带该 `combineTag`；为选项 → 存在实例选择该 option。

**重要裁定（DESIGN_BASELINE）**：依赖只做**检查**，不做**自动补全**。系统不得自动替玩家添加模块——自动补全会掩盖设计决策。

### 5.5 可区分性判定（G1 的落地）

两个蓝图 `A`、`B` 在 `differentiating` 维度集合 D = {primaryType, secondaryTypes(集合), settingIds(集合), perspective, structure, targetSegmentClaims(集合), sellingPoints(集合)} 上比较。

- 若 `∀d ∈ D : A.d == B.d` → 判定 A、B 为同一设计（生成 `W-SIMILAR`）。
- 只要一个维度不同即视为不同设计，但**同类相似度高**（≥ 5/7 维度相同）时给出"与《X》结构高度相似"提示，供玩家判断差异化。

### 5.6 版本提升规则

- 新锁定版本若与上一锁定版本（`supersedesVersionId` 链上）无任何设计项差异 → 不产生新版本，只更新说明（避免版本膨胀）。
- 版本号在**每次锁定**递增；内部草稿迭代不递增 `versionNo`。

## 6. 计算公式

> 约定：所有常量以 `k_*` 表记，全部 `TUNING`。所有公式输出**区间**：给定 `Δ`（相对不确定度，默认 ±25%，TUNING），输出 `[v·(1-Δ), v·(1+Δ)]`。

### 6.1 计算总览

```
蓝图 ──► ①工作量(W)  ──► 项目排期/成本
      ├─► ②技能负载(S) ──► 团队需求/瓶颈
      ├─► ③技术门槛(T)  ──► 可行性/技术风险
      └─► ④市场匹配(A)  ──► D-04 需求换算
```

四个通道**互不合成单一分数**（T2）。

### 6.2 ① 工作量 `WorkloadEstimate`

**符号全部在 §6.7 定义**；学科集合 `Discipline = {design, code, art, audio, qa}`。

```
对每个学科 d ∈ Discipline，对每个 active 模块实例 i:

W_d(i) = i.template.baseWorkUnits[d]
       × i.template.intensityCurve[i.intensity]
       × depthMultiplier(i.depthSelection)
       + Σ_{o ∈ selectedOptions(i)} o.costDelta[d]

对每个已绑定内容包 c:

W_d(c) = c.workUnitsPerTier[d] × c.tier^α        (α ≈ 0.85, TUNING)

产品级原始工作量:

W_d^raw = Σ_{i ∈ M_active} W_d(i) + Σ_{c ∈ C_bound} W_d(c)
```

- `M_active` = `state=active` 的 `ModuleInstance` 集合（**deactivated 模块贡献 0**，其工作量已沉没，见 §15.2）。
- `selectedOptions(i)` = `i.optionSelections` 的所有 value 对应的 `Option`（§4.10）。
- `depthMultiplier`：{shallow: 0.8, standard: 1.0, deep: 1.3}（**TUNING**，覆盖 §11 E-16 之外的三档）。

**协同增益（按学科）**：

```
tags(M_active) = 多重集：所有 i ∈ M_active 的 i.template.combineTags 之和
total = |tags(M_active)|                  // 含重复的出现次数
distinct = |set(tags(M_active))|          // 去重后的标签数

synergy_d = if total == 0 then 0 else 1 − distinct / total    // 除零边界：无标签时取 0

W_d = W_d^raw × (1 − synergy_d × k_syn[d])
```

- `synergy_d ∈ [0,1)`；`k_syn[d] ∈ [0, 0.25]`（TUNING），故系数 `1 − synergy_d × k_syn[d] ≥ 0.75`，恒正。
- `k_syn` 为**按学科向量**（TUNING）：`{design:0.05, code:0.22, art:0.18, audio:0.12, qa:0.15}`——code/art 复用收益较大，design/audio 较小（叙事与音频资产难复用）。
- **重要（关闭 R-08）**：`W_d` **不含任何 HRB 项**。工作量只由产品结构导出；HRB 只在 §6.2.1 做单向可行性检查，**禁止** `HRB_scale × W_d` 形式的公式。

#### 6.2.1 人力资源预算 `HRB`（玩家预算承诺 + 单向可行性检查）

> **执行主 AI 裁定 ADJ-2026-11-21-01**。HRB 不是全局工作量乘子，不是产品规模的描述；它是玩家显式作出的**人力/资金预算承诺**。工作量 `W_d` 只由 §6.2 的产品结构公式导出，HRB **不得反向缩放 `W_d`**。

**字段**：`HRB ∈ [0,1]`（归一化承诺水平，默认 0.5；0 = 最小可行投入，1 = 玩家愿投入的上限）。绝对预算金额由 Project 依据企业当前预算容量解析（下游输入，见 §8.1），本系统不定义金额。

**可行性检查（单向，禁止反向缩放）**：

```
Budget_cap   = HRB × BudgetCapacity(company, project)        // 由 Project 提供，下游输入
Cost_est     = Project.resolveCost(W_d, teamCapacity)         // 由 Project 提供，下游输入
ratio        = Cost_est / Budget_cap        （Budget_cap > 0；若 =0 则 ratio = +∞）

verdict =
   可行            if ratio ≤ 1.0
   需追加预算/需延期 if 1.0 < ratio ≤ 1.2        （玩家二选一）
   需缩减范围/需降低质量目标 if ratio > 1.2      （玩家二选一）
（阈值 1.0 / 1.2 为 TUNING）
```

**输出产物 `HRBFeasibility`**（只读，供 UI 与 Project 消费）：
`{ HRB, Budget_cap, Cost_est, ratio, verdict, reasons[] }`，其中 `reasons` 列出前三个成本驱动（模块/选项/学科）。

**硬约束（裁定条款）**：
1. HRB 只影响 `verdict` 与提示，**不改变** `W_d`、`SkillDemandProfile`、`TechRequirement`、`MarketAppealProfile`。
2. 预算不足时，系统**只提示并等待玩家决策**，不得自动缩小工作量或自动降低质量来"自洽"。
3. HRB 与企业总预算不得混同（`R-ORG-2`）；`BudgetCapacity` 来自 Project/企业经营，本系统只读引用。
4. **不承诺** `qualityCeilingBand`：HRB 与质量上限的映射属 `OPEN-O5`（TUNING），在 D-02/Project 对齐前，输出契约中不含该字段（§8.2、§16）。冲突时"降低质量目标"仅作为 `verdict` 的文本提示，不携带具体数值带宽。

> 说明：§4.3「规模由槽位数量 + 模块档位 + 内容包档位自然导出」与「禁止单一规模字段」仍然成立；HRB 是预算决策，不参与规模导出，二者不冲突。

### 6.3 ② 技能负载 `SkillDemandProfile`

```
S_d = W_d / k_peakEfficiency[d]           # 该学科"需要多少人手同时在场"的峰值量
```

输出：
- `ΣS = Σ_d S_d`；`peakFraction[d] = if ΣS == 0 then 0 else S_d / ΣS`（**除零边界**：空设计时为 0）；
- `peakWindow` —— 由 Project 依据 `Rule` 决定，本文档只要求 Project 在"关键路径"上参考 `peakFraction`。

`k_peakEfficiency[d] > 0`（TUNING，§6.7）保证 `S_d` 有限；`W_d ≥ 0`。

**玩家可见表述**：「程序需求高」「美术需求极高」「叙事需求低」，不显示具体人数（人数是 Project 的事）。

### 6.4 ③ 技术门槛 `TechRequirement` 与 `RiskProfile`

**门槛集合 `T`（每个成员可追溯到 §4.8 来源表）**：

```
T = ⋃ { i.template.techGates }                       for i ∈ M_active
  ∪ { PERSPECTIVE_GATE[positioning.perspectiveId] }   // 常量表，下
  ∪ ⋃ { p.techStandards }                            for p ∈ positioning.platformTargets  (平台系统输入)
  ∪ { STRUCTURE_GATE[positioning.structureId] }       // 常量表，下
  ∪ ⋃ { o.techGates }                                for o ∈ selectedOptions(active)
```

**`PERSPECTIVE_GATE`（TUNING，`TechGate` 的 domainId 为 D-06 领域引用，档位含义由 D-06 定义）**：

| perspectiveId | gateId | domainId | minCapabilityLevel |
|---|---|---|---|
| side_scroll | g_pers_side | rendering_2d | 1 |
| top_down | g_pers_top | rendering_2d | 1 |
| isometric | g_pers_iso | rendering_3d | 2 |
| third_person | g_pers_3rd | rendering_3d | 2 |
| first_person | g_pers_1st | rendering_3d | 3 |
| text | g_pers_text | ui_text | 0 |

**`STRUCTURE_GATE`（TUNING）**：

| structureId | gateId | domainId | minCapabilityLevel |
|---|---|---|---|
| linear / level_based | — | — | （无额外门槛，空集） |
| open_zone | g_struct_open | world_streaming | 2 |
| sandbox | g_struct_sbx | world_streaming | 3 |
| roguelike | g_struct_proc | procedural_gen | 2 |
| persistent_online_scope_out | — | — | `REJECTED`，不应出现 |

**不满足项**：`T_unsat = { g ∈ T : capability(g.domainId) < g.minCapabilityLevel }`。`capability(domain) → int ≥ 0` 由 D-06 提供（§8.1 前置输入）；`minCapabilityLevel = 0` 的门槛恒满足，不进入 `T_unsat`。

**技术风险**（不满足项的加权）：

```
R_tech = 1 − exp(− Σ_{g ∈ T_unsat} k_tech × (1 − capability(g.domainId) / g.minCapabilityLevel))
```

`k_tech > 0`（TUNING）；仅 `minCapabilityLevel > 0` 的项参与（避免除零）。取值 ∈ [0,1)；显著 → Project 显示"高风险技术，预计测试期缺陷率上升"（缺陷率公式归 Project/QA，本文档不定义）。

**协同风险（软冲突，归一化）**：

```
penalty_sum = Σ_{soft conflict} ConflictRule.penalty + Σ_{W-DEP} RequireRule.penalty    （§5.4 第 2/3 步）
R_synergy   = 1 − exp(− penalty_sum)            // 归一化到 [0,1)，无额外 TUNING 常量
```

**范围风险**（超规模预警）：

```
W_total = Σ_{d ∈ Discipline} W_d
R_scope = clamp( (W_total / W_baseline_type) / k_scope_max , 0, 1 )
```

`W_baseline_type > 0` 为该主类型在当前时代的典型单产品工作量中位数（TUNING，按类型表，来自内容库）；`k_scope_max > 0`（TUNING）。`R_scope ≥ 0.8` 触发 `W-SCOPE`：系统提示"范围远超同类典型规模，预计交付周期显著延长"，**但不阻止**（玩家可自行承担风险）。

**三风险 → 单一展示用 `riskLevel`（关闭 R-03）**：

```
maxRisk  = max(R_tech, R_synergy, R_scope)
riskLevel = HIGH  if maxRisk ≥ τ_high (0.7, TUNING)
          = MEDIUM if maxRisk ≥ τ_med  (0.4, TUNING)
          = LOW    otherwise
```

采用 **max 分级**而非加权求和，避免合成掩盖差异（T2：三个子风险仍在 §10.4 分别显示，`riskLevel` 仅为 D-LOCK/P-ESTIMATE 的展示分类，不是"设计价值分"）。

### 6.5 ④ 市场吸引力 `MarketAppealProfile`

本文档**只产出画像**，D-04 负责把画像换算成需求。输出字段（所有符号见 §6.7）：

| 字段 | 公式/来源 | 说明 |
|---|---|---|
| `affinity[SegmentTag]` | `Σ_{i ∈ M_active} i.template.audienceAffinity[tag] × intensityWeight(i) + Σ_{o ∈ selectedOptions} o.audienceAffinityDelta[tag]` | 原始亲和；`intensityWeight(i) = i.template.affinityIntensity[i.intensity]`（§4.6，TUNING） |
| `positioningFit` | `Jaccard(C, S) = if |C∪S| == 0 then 0 else |C∩S| / |C∪S|`。`C = set(targetSegmentClaims)`；`S = { tag : affinity[tag] > 0 }`（**有支撑标签集**） | 集合式（关闭 R-02 的向量/Jaccard 误用）；展示带：≥0.8 高 / 0.5–0.8 中 / <0.5 低（TUNING） |
| `genreFit` | `cosine( typeAffinityVector(primaryType), domainDistributionVector(M_active) )`。前者来自 `GameplayArchetype.typeAffinity`（§4.13）；后者为 active 模块 `domain` 的归一化计数向量 | **补齐 R-13 缺失字段**；D-04 消费；两个操作数均为实向量，余弦有定义（两向量零向量时取 0） |
| `uspSupported[uspId]` | 布尔：`R-COM-7` 对每条卖点的支撑判定结果（§5.4） | **可确定性输出**：是否至少有一个 active 模块/选项支撑该卖点 |
| `uspCredibility[uspId]` | **OPEN-O1 — 本系统不计算** | `支撑强度/宣称强度` 依赖 D-02 评价口径与 D-04 群体偏好。D-01 只提供 `uspSupported` 布尔与 `affinity` 画像作为下游输入；可信度数值待 D-02/D-04 对齐后提供，不得在 D-01 伪装为确定公式 |
| `noveltyNote` | 与近 `N = 20`（TUNING，R-16）个同类型产品的相似度（来自 `ModuleArchetype` 判定，§14） | 只做提示，不进入数值 |
| `contentVolumeBand` | 由 `Σ c.tier` 映射到 低/中/高（**供 D-02 完整度用**，本文档不做判断） | 映射阈值 TUNING |

**红线**：`MarketAppealProfile` **不得**包含任何"预计销量/预计评分/卖点可信度数值"字段。销量属于 D-04 + 产品运营；可信度属于 OPEN-O1（D-02/D-04）。

**向量/集合定义补充**：
- `typeAffinityVector(a)`：以全体 `GameplayDomain`（10 个，§5.1）为固定维度顺序，取 `a.typeAffinity[d]`，缺省为 0。
- `domainDistributionVector(M_active)`：同维度顺序，取 `count(d in M_active) / |M_active|`；`M_active` 为空时为零向量。
- 两向量均为实向量，`cosine(u,v) = (u·v)/(‖u‖‖v‖)`；任一范数为 0 时取 0（除零边界）。

### 6.6 公式的确定性要求

- 所有公式**纯函数**：同输入（含 `RandomService` 派生子流种子）必得同输出。
- 任何公式变更需版本化（`formulaVersion`），存档记录版本以支持回溯重放。
- 区间来源必须可分离：`Δ_base`（模型不确定度）+ `Δ_team`（团队能力不确定度，来自 Project）——两者分别显示，不得合并成一个"误差"。
- **估算变化的两种来源（关闭 R-10）**：① `formulaVersion` 变化 → **口径性跳变**，允许数值显著变化并注明版本变更；② `formulaVersion` 不变但**外部输入变化**（技术能力 `capability`、市场档案词表/群体、`Δ_team` 团队能力、`platform.techStandards`）→ 估算**可以也应当变化**，但必须显示"为什么变了"的原因（比较最近 `EstimateHistory`，§12 S3）。不得把②误判为异常、也不得因②而强制版本号递增。

## 7. 状态与状态转换

### 7.1 设计版本状态机

**状态（关闭 R-09：`REWORK` 已从枚举与状态图移除）**：
`DRAFT`（草稿）、`IN_REVIEW`（评审/校验中）、`LOCKED`（已锁定，待立项或待执行）、`EXECUTING`（执行中）、`COMPLETED`（对应项目已交付）、`ABANDONED`（废弃）。

> `REWORK` **不是状态枚举值**，而是 `EXECUTING` + `ReworkSession`（返工会话）的**呈现式标签**（裁定见 §7.2）。`BlueprintVersion.state` 永远不会被赋值为 `REWORK`。返工期间 `state` 保持 `EXECUTING`，权威快照始终只有一份。

```
                 ┌─────────────(玩家放弃)──────────────┐
                 ▼                                     │
   [DRAFT] ──fix──► [DRAFT]                            │
      │                                                │
      │ request_lock                                    │
      ▼                                                │
  [IN_REVIEW] ──校验通过 & 玩家确认──► [LOCKED]         │
      │                                    │           │
      │ 校验失败/玩家取消                    │ 立项Project│
      └────────────► [DRAFT]                ▼           │
                                        [EXECUTING] ◄───┤
                                          │  ↑          │
                       启动返工会话(标签) ──┘  │ 返工完成闸门通过
                       返工取消(标签消失) ─────┘  → 切换新快照(出生=EXECUTING)
                                          │ 交付闸门通过
                                          ▼           │
                                     [COMPLETED]      │
                                          │           │
                       任一状态 ──项目取消─► [ABANDONED]◄┘
```

### 7.2 转换表

| From | To | 触发 | 前置条件 | 副作用/事件 |
|---|---|---|---|---|
| DRAFT | DRAFT | 任一设计修改 | 玩家有编辑权 | 追加 `DesignChangeRecord`（草稿级，不产生返工） |
| DRAFT | IN_REVIEW | `request_lock` | 必填项齐备（§5.3 硬规则） | 生成 `EvaluationSummary`；冻结编辑 |
| IN_REVIEW | LOCKED | 玩家确认（审核项全部为 W 级） | 无 `E-*` 违规 | 生成 `DesignVersionSnapshot`；`versionNo++`；写入 `templateRevisionRefs` |
| IN_REVIEW | DRAFT | 校验失败/取消 | — | 保留草稿 |
| LOCKED | EXECUTING | Project 立项成功且绑定 `snapshotId` | 同企业 | 快照冻结；编辑入口关闭 |
| LOCKED | ABANDONED | 放弃 | — | 版本灰显 |
| EXECUTING | EXECUTING（启动返工会话） | 玩家在研发中提交设计变更并确认返工 | 见 §15 | 生成 `DesignChangeRecord` + `ReworkTask` + `ReworkSession`；`state` 保持 `EXECUTING`；旧快照仍为权威 |
| EXECUTING | EXECUTING（返工完成） | 返工完成且**返工完成闸门通过** | `ReworkTask` 全完成 **且** §7.2.1 闸门零 E 级违规 | 生成新 `BlueprintVersion`（`supersedes` 指向旧，`birthState=EXECUTING`，`versionNo++`）+ 新快照；`Project.snapshotId` 切换；旧快照保留为历史 |
| EXECUTING | COMPLETED | 项目交付且**交付闸门通过** | §7.2.1 闸门零 E 级违规（针对权威快照当前结构） | 锁定版本进入产品档案 |
| 任意 | ABANDONED | 项目取消/产品放弃 | — | 保留全部历史（不允许删除） |

**裁定（DESIGN_BASELINE，关闭 R-09）**：`REWORK` 不是独立状态机分支，而是"EXECUTING + 返工会话"的呈现式标签。目的是避免"版本一半在旧快照一半在新快照"的权威歧义——**快照始终只有一份被 Project 引用**，新快照在返工完成且闸门通过时才切换。返工新版本出生状态明确为 `EXECUTING`（因设计变更已在返工会话内完成评审与校验，闸门复用 §11 全部 E 级硬规则及 §5.3/§5.4 硬规则），**不**回到 `DRAFT/IN_REVIEW/LOCKED`，也不产生"先锁定再立项"的重复流程。

#### 7.2.1 返工完成闸门与交付闸门（关闭 R-05）

返回 `EXECUTING` 之前、以及 `EXECUTING → COMPLETED` 交付之前，**必须**对"即将成为权威的新结构（返工目标草稿 / 当前权威快照）"执行 `RevalidationGate`：

```
RevalidationGate(structure S):
  // 主 AI 裁定 ADJ-2026-11-21-02：词表引用解析为独立强制前置
  refViolations = resolveRefs(S) // 校验 SegmentTag/GameplayArchetype/Platform 引用存在、非 deprecated、版本兼容，
                                 // 且主类型 archetype 必须为 active（D-04 §5.4 R3）
                                 // 失败码 E04-*（见 §11 E-20；完整清单以 D-04 §5.4 为准），按 E 级硬违规处理
  violations = RunHardRules(S)   // 复用 §11 全部 E 级硬规则及 §5.3/§5.4 硬规则，至少含：
     E-EMPTY    必选槽为空
     E-USP      卖点无支撑（R-COM-7）
     E-CONFLICT 硬冲突
     E-DEP      硬依赖未满足
     E-CYCLE    依赖环
     E-TECH / E-ERA / E-EMPTY-CONTENT / E-OPT / E-INCOMPAT（其余 E 级）
  violations = violations ∪ refViolations
  if violations 含任一 E 级:
     return FAIL(violations)      // 禁止切换权威快照 / 禁止交付
  else:
     return PASS
```

**失败时的行为（禁止绕过硬规则）**：
1. **不切换** `Project.snapshotId`，旧权威快照继续生效；`state` 保持 `EXECUTING`。
2. `ReworkSession.status` 保持 `active`，附 `ViolationSet` 返回玩法画布，要求玩家修正后重新提交"返工完成"。
3. **撤销路径**：玩家可选择"撤销返工" → 丢弃目标草稿与新快照，`ReworkSession.status=cancelled`，旧快照继续生效（§15.3）；若无法修正，可放弃项目 → `ABANDONED`。
4. 交付闸门失败时同理：阻断 `COMPLETED`，回路返回返工流程（生成新的返工会话），不得"带病上市"。

> 该闸门直接封堵审核报告 R-05 的反证：停用唯一支撑模块后，`E-EMPTY` + `E-USP` 会在切换前触发，空核心槽与虚假卖点的产品无法通过闸门。

### 7.3 蓝图层状态

`ProductBlueprint.state ∈ {active, archived}`。
- `active`：可创建新版本；
- `archived`：产品退役或公司放弃，只能查看。

## 9. 玩家操作方式与自动化行为

### 9.1 玩家定（有决策意义）

| 决策 | 层级 | 代价 |
|---|---|---|
| 主类型 + 次类型 | 战略级 | 决定必选槽与受众 |
| 题材、视角、结构 | 战略级 | 技术门槛、内容结构 |
| 宣称受众 | 战略级 | 影响 `positioningFit` |
| 卖点（≤3） | 战术级 | 必须被支撑，否则可信度低 |
| 槽位内模块选择与命名 | 战术级 | 工作量、技能负载、亲和 |
| 强度档 1–5 | 战术级 | 成本非线性 |
| 深度档 + 选项 | 执行级 | 成本与风险微调 |
| `HRB`（预算承诺） | 战术级 | 只触发可行性结论：范围/预算/工期/质量目标由玩家决策 |
| 是否锁定、是否返工 | 闸门级 | 沉没成本；返工完成/交付须过硬规则闸门（§7.2.1） |

### 9.2 系统算（自动化）

- 工作量、技能负载、门槛、风险、画像；
- 违规检测与修复建议；
- `ModuleArchetype` 判定（命名 + 标签）；
- 与近期产品的相似度提示；
- 估算区间与置信度。

### 9.3 不自动化（红线）

- 不自动补依赖模块；
- 不自动替换冲突模块；
- 不自动选择受众或卖点；
- 不自动判定"应该锁定"。

### 9.4 玩家可见的解释（对齐系统地图 §6）

- 结果：估算区间（低/中/高）、`riskLevel`（HIGH/MED/LOW）与三个子风险；
- 原因：前三个驱动因素（哪个模块、哪个选项、哪条协同）；
- 置信度：区分"模型不确定 `Δ_base`"和"团队不确定 `Δ_team`"；
- 影响：工期、成本、风险等级、HRB 可行性结论与代价提示；
- 后续选择：可削减哪一项、代价是什么；
- 变化说明：若与历史估算不同，显示变化原因（外部输入变化或 `formulaVersion` 变更，§6.6/§12 S3）；
- 卖点：显示"是否被支撑"（`uspSupported`），**不显示**"卖点可信度数值"（OPEN-O1）。

### 10.3 P-MODULE-LIB：模块浏览面板

- 筛选：玩法域、时代可用、技术可用性、槽位兼容、标签；

### 10.4 P-ESTIMATE：影响估算

四个分区（工作量/技能/技术/市场），每区：

### 10.5 P-VALIDATION：校验结果

- 分两类：**阻断（E，红）**、**警告（W，黄）**；

- 空状态："无问题，可锁定"。

### 10.6 D-LOCK：锁定确认

- 摘要：定位 7 维、槽位数量、active 模块数、估算区间、风险等级；

- 警告项列表；
- 新类型识别结果（若有）："该组合接近全新子类型「X」"（见 §14）；
- 按钮：取消 / 锁定并生成快照；
- 锁定后跳转：立项页 / 返回工作台（只读）。

### 10.7 D-REWORK：返工确认（执行中变更）

- 变更摘要：新增/停用/改档/改选项；
- 沉没成本：受影响模块的已投入工作量（来自 Project）；
- 返工估算：低/中/高（分档，§15.2）；
- 风险提示：预计工期延长、质量影响区间；
- 按钮：取消 / 确认并开始返工 / 仅保存为"下一版草案"（不影响当前项目）；
- **"确认并开始返工"不可逆**，需二次确认。

## 11. 异常与边界处理

| 编号 | 情形 | 处理 |
|---|---|---|
| E-1 | 空组合（无任何 active 模块） | 草稿可保存；`request_lock` 时阻断 `E-EMPTY`（必选槽为空）。 |
| E-2 | 循环依赖 | 求值前先检测 `RequireRule` 的传递闭包；出现环 → `E-CYCLE` 并列出环路径。**不自动打破环**。 |
| E-3 | 硬冲突组合 | `E-CONFLICT`，阻断锁定；UI 高亮两个模块并提供"去替换"按钮。 |
| E-4 | 超规模 | `R_scope ≥ 0.8` → `W-SCOPE` 警告，不阻断；D-LOCK 必须显示"预计交付风险：高"。 |
| E-5 | 研发中改设计 | 走 §15 返工流程；不允许"无痕修改"。 |
| E-6 | 技术前提不满足但玩家仍要设计 | 草稿允许；锁定允许但强制生成"高风险"标记与 Project 侧风险提示（技术可能被开发出来也可能失败，符合"科技动态突破"）。该标记写入快照作为**锁定当时**的档案值；执行期每月重算后 UI 以**当前**门槛状态提示（§4.12），二者不互相覆盖。**若 D-06 判定该技术在本时代不可能**（硬不可用），则阻断 `E-TECH`。 |
| E-7 | 时代不可用的模块 | 面板灰显；若玩家强行通过 API/旧存档带入 → 打开时校验并标记 `E-ERA`。 |
| E-8 | 同一槽位多实例超上限 | 阻断添加，按钮禁用 + 原因。 |
| E-9 | 卖点无支撑 | 锁定校验 `E-USP`；草稿警告。 |
| E-10 | 断言空值（必填未填） | `IN_REVIEW` 前必填校验，阻断。 |
| E-11 | 平台缺失 | 至少 1 个平台，否则阻断。 |
| E-12 | 版本冲突（两玩家/AI 同时编辑同一蓝图） | 单机可忽略；**若未来联机（DEFERRED）** 采用乐观锁 `payloadHash`，冲突时要求人工合并，不自动合并。 |
| E-13 | 蓝图被删除前已有锁定版本 | 禁止删除，只允许 `ABANDONED`/`archived`。 |
| E-14 | 数值溢出/超长文本 | 名称长度上限校验；`intensity` 越界拒绝。 |
| E-15 | 空内容包 | content 槽必须绑定，否则 `E-EMPTY-CONTENT`。 |
| E-16 | 选项组全空 | 允许（表示默认）；若选项组 `required=true`（§4.10）则阻断 `E-OPT`。 |
| E-17 | 蓝图层级 `HRB=0` | 允许。`HRB` 只是预算承诺，**不影响工作量**；`Budget_cap` 极小时 `verdict=需追加预算/需缩减范围`，提示玩家决策（§6.2.1）。旧 `HRB_scale` 下限保护已随裁定废止。 |
| E-18 | 返工完成/交付闸门失败 | §7.2.1：`E-EMPTY/E-USP/E-CONFLICT/E-DEP/E-CYCLE` 等任一 E 级违规 → 禁止切换权威快照/禁止交付，返回修正或撤销返工。 |
| E-19 | 不兼容模块未处理 | 主类型切换后"待处理不兼容"队列非空 → 锁定阻断 `E-INCOMPAT`（§10.2）。 |
| E-20 | 词表引用失效（ADJ-2026-11-21-02；N-1 补全） | `E04-DEPRECATED-TAG` / `E04-UNKNOWN-TAG` / `E04-DEPRECATED-PLATFORM` / `E04-UNKNOWN-PLATFORM` / `E04-UNKNOWN-ARCHETYPE` / `E04-NONACTIVE-ARCHETYPE` / `E04-DEPRECATED-ARCHETYPE`：`resolveRefs` 失败，返工完成/交付闸门按 E 级硬违规阻断（§7.2.1）。完整 E04 码表以 D-04 词表包 §5.4 为准（本行为非穷举登记）。 |

**通用错误输出格式**（UI 与日志共用）：
`{ code, severity(E|W), ruleId, subjectIds[], message, suggestedAction }`

## 14. 模块组合产生新子类型/新类型的阶段边界

### 14.1 三级能力定义

| 级别 | 名称 | 能力 | 阶段 |
|---|---|---|---|
| L1 | **组合即类型** | 玩家自由组合已有模块；类型仅作为“定位标签”使用 | P1 |
| L2 | **子类型识别** | 系统从组合中**识别**出近似新子类型，给出名称与标签，允许作为**产品档案标签**（不影响核心机制生成） | P2 |
| L3 | **类型库扩展** | 识别结果可提升为**数据条目**（进入类型库，供 AI/后续玩家作为 `primaryTypeId` 选择），仍不生成新机制 | P3+ 且内容库 ≥ N 模板（OPEN-O2） |
| — | **机制生成** | 从零生成新玩法机制并自动定价 | **DEFERRED**（不在本文档承诺） |

### 14.2 判定算法（L2/L3 共用）

```
输入：active 模块集合 M 的 (domain, combineTags)、定位 7 维
1. 构造特征向量 V = [domain 分布, tag 计数, structure, perspective]
2. 对类型库中每个已有 GameplayArchetype 计算相似度 sim(A, V)
3. best = argmax sim
4. if best.sim ≥ τ_match (TUNING, 约 0.75): 归入 best（子类型，若存在该类的子类型表则继续匹配）
   elif best.sim ∈ [τ_novel_low, τ_match): 判定为"近似 new sub-type" → 生成 ModuleArchetype(provisional)
   else: 判定为"new archetype" → 生成 ModuleArchetype(provisional)
5. provisional 命名 = 规则模板："{主域词} + {结构词} + {核心标签词}"，需玩家确认命名
6. L2 只写档案标签；L3 才写入类型库
```

### 14.3 阶段边界判定规则（何时允许）

| 条件 | 允许的级别 |
|---|---|
| 内容库模板数 < N_min（OPEN） | 仅 L1 |
| N_min ≤ 模板数 < N_full | L1+L2 |
| 模板数 ≥ N_full 且 L2 连续 M 次识别稳定（相同或高度相似） | L3 |
| 任何阶段 | 不生成新机制 |

### 14.4 新类型提升的约束（产出 `GameplayArchetype`，关闭 R-04）

- 提升后的类型写入**类型库**，成为一条 `GameplayArchetype` 数据（§4.13），其 `coreSlotDomains` 须至少有一个与既有类型不冲突；否则拒绝提升并记录原因。
- 提升时 `GameplayArchetype.state = provisional`、`isProvisional=true`、**只能作为次类型**；`successCount` 累计达 `K`（TUNING）次成功产品后升级为 `active`，方可作主类型（设置 `promotedAt`）。
- **AI 与玩家共享类型库**；AI 创造的类型（`source=ai_created`）对玩家可见。`primaryTypeId` 只能引用 `state=active` 的条目（§4.13）。
- `ModuleArchetype`（识别结果）在被提升前不写入类型库；提升动作即 §4.13 生命周期的 `provisional` 入口。

## 15. 设计版本与项目执行版本关联、返工规则

### 15.1 关联模型

```
Blueprint (1) ── (n) BlueprintVersion ── (0..1) DesignVersionSnapshot ── (1) Project
                                        └── (0..1) 为返工生成的新快照
```

- **Project 只能引用一个快照**；引用在返工完成时才切换到新快照（§15.3）。
- Project 记录其引用的 `snapshotId` 与 `formulaVersion`，以便重放。
- 蓝图版本与 Project 是 1:1（一个设计版本对应最多一个项目）；同一蓝图不同版本可对应不同项目（续作/复刻）。

### 15.2 返工触发与成本规则

**触发**：在 `EXECUTING` 状态下玩家修改设计项并确认返工。修改分五类：

| 类别 | 例子 | 是否返工 | 成本估算分档 |
|---|---|---|---|
| A 元数据 | 改显示名、改描述 | 否 | 0 |
| B 停用 | active → deactivated | 是（沉没不返还） | 已投入工作量全额沉没 + 少量“清理” |
| C 参数调整 | 改 intensity、改选项 | 是 | 按受影响模块 `ΔW_d × progress_d` 分档 |
| D 新增 | 新模块、新槽位绑定 | 是（且必为返工，T4） | 完整 `W_d(新)` + 集成成本 `k_integ × W_d(新)` |
| E 定位变更 | 改主类型/视角/结构/受众 | 是（且可能强制重估全局） | 全部受影响模块 `ΔW × progress` + `k_reposition` 全局惩罚 |

**成本公式（分档）**：

```
ReworkCost_mode ∈ {minimal, partial, full}  # 以区间呈现，实际值在返工推进时由 Project 落实
```

| 档 | 判定 | 有效工作量返还比例 | 附加 |
|---|---|---|---|
| `minimal` | 新增/停用小模块，`W_d(变更) < 10% W_total` | 已投入的 70% 可复用 | — |
| `partial` | 变更 10–40% | 已投入 50% 可复用 | 工期延长 5–15% |
| `full` | 变更 > 40% 或修改定位 | 已投入 20% 可复用 | 建议"新项目"并保留旧项目产物的存档 |

**返工计数**：每个 Project 记录 `reworkCount`；≥ `k_rework_limit`（TUNING，初始 3）后，UI 提示"项目返工次数过多，风险显著上升"，并在 Project 侧计入额外风险（Project 定）。

### 15.3 快照切换时机（返工完成闸门，关闭 R-05）

- 返工开始：**保留旧快照为 `Project` 的权威**，生成 `ReworkSession`（`status=active`，含 `targetDraftVersionId` 指向目标草稿）与 `ReworkTask`；`state` 保持 `EXECUTING`。
- 返工完成：`ReworkTask` 全完成后，**先执行 §7.2.1 `RevalidationGate`**：
  - **PASS** → 生成新快照（含 `templateRevisionRefs`），`Project.snapshotId` 切换，旧快照保留为历史；派生新 `BlueprintVersion`（`birthState=EXECUTING`，`supersedes` 指向旧）；`ReworkSession.status=completed`。
  - **FAIL** → **不切换**权威快照，旧快照继续生效；`ReworkSession` 保持 `active` 并附 `ViolationSet` 返回修正；或玩家选择撤销返工（`status=cancelled`，丢弃目标草稿）。
- 返工中若玩家取消 → 丢弃目标快照，`ReworkSession.status=cancelled`，旧快照继续生效（不损失当前项目进度）。
- 交付前置：执行 §7.2.1 交付闸门，零 E 级违规方可进入 `COMPLETED`（封堵"带病上市"）。

> 该规则确保：**执行中始终有且仅有一个"生效快照"**，且切换前硬规则不被绕过（直接封堵审核报告 R-05 反证）。

### 15.4 研发中改设计的不可逆性

- 已停用的模块不可重新启用，只能通过“新增同类模块”替代（记录为不同 `instanceId`）。
- 已锁定的版本不可编辑，只可派生新版本。

### 15.5 变更与历史

每次变更生成 `DesignChangeRecord`：`changeId, versionId, category(A–E), diff(结构差异), requestedBy, requestedAt, reworkRequired(bool), reworkTaskIds[], reworkSessionId(可为 null), sunkCostEstimate`。
