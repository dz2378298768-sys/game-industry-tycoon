**状态标记**（沿用 `docs/baseline/README.md`）：
`CONFIRMED` 用户已确认方向；`DESIGN_BASELINE` 总设计师默认裁定，可经证据推翻；`TUNING` 结构确定、参数待校准；`OPEN` 需后续专项设计，不伪装为已定；`DEFERRED` 明确后置；`REJECTED` 当前规划不做。

**红线（全文不可违反）**：
- R-D02-0：**设计质量、实现质量、产品完整度三者独立计算、独立呈现、独立存储**。禁止 `overallQuality`、`quality = α·dq + β·iq + γ·c`、`mean(dq, iq, c)` 或任何等价合成。
- R-D02-1：**产品完整度不是单一进度百分比**。它是按产品类型与交付形式定义的`ChecklistItem` 集合的分项覆盖向量 + 阻断项闸门。禁止用 `satisfied/total` 的单一数冒充完整度或作为交付判定。
- R-D02-2：`qualityCeilingBand`（D-01 OPEN-O5）在 P1 为 `ABSENT_P1`；禁止把它写成确定数值、乘子，或用它反向缩放工作量（ADJ-2026-11-21-01）。
- R-D02-3：缺失核心模块时系统**不自动补齐、不自动替换、不自动降级交付形式**（D-01 §9.3 红线延续）；只呈现有代价的可选动作。

## 1. 系统目标与玩家体验目标

### 1.1 系统目标（可判定）

| 编号 | 目标 | 判定方式 |
|---|---|---|
| G1 | 按"产品类型 × 交付形式"给出**可执行的核心交付清单**，并能在任意快照上确定性求值 | §5 清单谓词在 TC-02/03/04 逐项可计算；同输入同输出 |
| G2 | **设计质量 / 实现质量 / 完整度**三者独立产出，结构上不存在合成字段 | §6 + TC-01（数据中无 `overallQuality` 类字段） |
| G3 | 交付形式（full / early_access / demo）有明确资格判定；缺失项时给出"带披露通过 / 阻断 / 需返工"的可判定结论 | §4.2 + TC-05/06 |
| G4 | 缺失核心模块的影响沿"评价 → 退款/预期 → 品牌 → 后续开发"四个方向可解释传递，且每个方向只给**方向与档位**，不伪装成 D-04 销量 | §5.4 + §7.3 + TC-09 |
| G5 | 交付闸门与 D-01 `RevalidationGate` 在**同一动作提交点同步**执行，任一 E 级违规即阻断 `COMPLETED` | §7.2 + TC-10/11；与 P0-B §3.6 S3 一致 |
| G6 | `qualityCeilingBand`（OPEN-O5）与 D-01 HRB 的对齐关系明确定义，但 P1 **不产出确定值** | §6.5 + TC-07 |

### 1.2 玩家体验目标

| 编号 | 体验目标 | 对应系统目标 |
|---|---|---|
| E1 | 玩家知道"为什么还不能称为完整产品"，而不是被告知一个百分比 | G1/R-D02-1 |
| E2 | 玩家能做**有代价的交付选择**：补齐、返工、带披露降级、 abandon，并看到每项代价 | G3/G4 |
| E3 | 玩家能区分"设计得好"与"做得好"与"做完了"，不会被一个综合分误导 | G2/§14 |
| E4 | 抢先体验版转正式版时，玩家理解这不是改个标志，而是一次重新评估与更高清单要求 | §4.3/§10.2 |
| E5 | 玩家能解释产品市场表现的前三个原因（与系统地图 §6、P0-B 场景 A/B 一致） | §7.3 |

### 1.3 与验收门槛的对应

路线图 §5 P2「必须具备」中的两条由本文落地：**设计质量、实现质量、完整度独立计算**；**按产品类型定义核心交付标准**。路线图 §11 跨阶段质量门槛要求"质量维度可分、可追溯"由 §14 论证与 §11 存档支撑。

### 3.1 `CompletenessChecklist`（清单模板）

| 字段 | 类型 | 含义 | 约束 |

### 3.2 `ChecklistItem`（清单项）

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `itemId` | id | 清单项标识 | 稳定 |
| `category` | enum{core_loop, support, content, tech, delivery} | 分项归属 | 完整度按此分摊向量，不合成总分 |
| `label` | string | 玩家可读描述 | 不含数值承诺 |
| `criticality` | enum{blocking, expected, optional} | 该项在当前 `(class, form)` 下的刚性 | 见 §5.3 决策表；`blocking` 项未满足 → 闸门 FAIL |
| `predicate` | `ChecklistPredicate`（§3.3） | 可确定性求值的证据条件 | 不得引用未定义符号 |
| `gapActionIds` | list<ref `ResolutionAction`> | 未满足时的可选动作 | 至少 1 个；不得为空自动补齐 |
| `sourceVersion` | string | 引入该清单项的设计版本 | 可追溯 |

### 3.3 `ChecklistPredicate`（谓词，P1 词表）

谓词是对 `EvaluationContext`（§3.5）的布尔/数值判定。P1 固定词表如下；新谓词需经设计审核后追加并升 `formulaVersion`。

| 谓词 | 语义 | 数据来源 |
|---|---|---|
| `slotActive(slotKind, minCount)` | 该槽种类中 `state=active` 的实例数 ≥ minCount | D-01 快照 `slots/bindings` |
| `contentTierAtLeast(t)` | content 槽绑定内容包 `tier ≥ t`（TUNING 阈值） | D-01 `ContentPack.tier` / `contentVolumeBand` |
| `techGatesSatisfied(domainSet)` | `T_unsat ∩ domainSet = ∅` | D-01 §6.4 `TechRequirement` |
| `segmentCovered(tag, τ)` | `MarketAppealProfile.affinity[tag] ≥ τ`（TUNING） | D-01 §6.5 |
| `uspBackedBy(slotKind)` | 每条 `sellingPoints` 被该槽内 active 实例支撑（`uspSupported=true`） | D-01 `R-COM-7` / `uspSupported` |
| `defectFree(sevSet)` | 无严重度属于 `sevSet` 的缺陷 | QA（接口 OPEN-D02-O2） |
| `platformStdMet(platformId)` | 平台技术标准满足 | D-01 §6.4 门槛集合 |
| `fieldNonEmpty(field)` | 字段非空（如 `finalTitle`） | 快照 / Product |
| `depthAtLeast(level)` | 核心实例 `depthSelection` 达 level | D-01 §4.5 |

> 谓词只判定"是否达成"，**不产出质量分数**；完整度分量由 §6.3 的覆盖向量给出。

### 3.4 `DeliveryForm`（交付形式标准）

D-01 枚举 `{full, early_access, demo}` 不变；D-02 为每形式定义标准（不新增枚举值）：

| 字段 | 类型 | 含义 | 约束 |

### 3.9 `DeliveryGateResult` / `DeliveryDecisionRecord`

- `DeliveryGateResult = { gate: PASS|FAIL, blockingUnmet[], formQualification, qcbState, checkedAt, formulaVersion }` —— 供 Project 在动作提交点同步消费。
- `DeliveryDecisionRecord = { snapshotId, form, checklistRevision, gateResult, disclosedGaps[], dqVector, iqVector, completenessVector, qcbState, reasonNote }` —— 供 D-07 归档；**不可变**。`reasonNote` 记录 HRB `verdict` 的文本提示（如"需降低质量目标"），不携带数值带宽（§6.5）。

## 4. 状态与转换

### 4.1 `QualityAssessment` 生命周期

```
PENDING ──Build 生成──► PROVISIONAL ──交付闸门 PASS 且封版──► FINAL
FINAL ──抢先体验版转正式版（新 Build + 新评估）──► SUPERSEDED（旧评估保留）
FINAL ──产品退役入 D-07──► ARCHIVED
PROVISIONAL ──闸门 FAIL──► PENDING（回路返工，不产生 FINAL）
```

- `FINAL` 与 `ARCHIVED` 不可变；任何"改质量"必须走新 Build/新评估，不允许原地覆盖（与 D-01 快照不可变一致）。
- `SUPERSEDED` 不删除旧记录：D-07 档案保留 EA 版评估链（§7.4）。

### 4.2 交付形式 `qualification` 状态机

```
not_evaluated ──求值(EvaluationContext)──┬─ 有 blocking 未满足 ─► not_qualified
                                          ├─ 全满足 ───────────► qualified
                                          └─ 仅 expected 未满足 + 已附披露 ─► qualified_with_disclosure
not_qualified / qualified_with_disclosure ──快照/清单revision/缺陷集变化──► not_evaluated（重算）
not_qualified ──返工完成并切新快照──► not_evaluated（重算）
```

- `qualified_with_disclosure` 只在 `disclosurePolicy=required` 且披露声明齐备时成立；否则为 `not_qualified`（`D02-DISCLOSURE-REQUIRED`）。
- 求值发生在**玩家提交交付动作时**（同步），不在每日 tick（P0-B §3.6 S3）。

### 4.3 交付形式间的转换

| 转换 | 条件 | 处理 |
|---|---|---|
| `early_access → full` | 新 Build、按 `full` 清单重算、E 级缺陷零、披露清退 | 产生**新** `QualityAssessment`，旧评估 `SUPERSEDED`；不得仅改枚举标志 |
| `demo → full` | 不允许直接转 | demo 是独立清单子集；须重新按 full 立项/补齐（§10.3） |
| `full → early_access` | 不允许倒退 | full 已封版；如要降级须走返工 + 新版本（D-01 §15） |
| 跨 `archetypeClass` 交付 | 类别由快照重分类或玩家覆盖，清单 revision 随之变 | 原资格作废，重新求值（§10.4 X-1/X-2） |

### 4.4 `CompletenessChecklist` 模板生命周期

```
draft ──审核通过──► active ──内容库/规则改版──► deprecated（revision++，新 active 生效）
```
- 已 `FINAL` 的评估记录其 `checklistRevision`，模板 `deprecated` 不影响历史可重放（§11 S2 同构）。
- `active` 模板同一 `(archetypeClass, deliveryForm)` 至多一份。

## 5. 业务规则：按产品类型的核心交付清单

### 5.1 清单结构与公共项 / 闸门桥接条件（所有类别 × 所有形式）

公共项（`archetypeClass=generic`）：C-01–C-05 为**清单分项**（进入 `c_k`），任何产品都要过；C-06/C-07 为**闸门桥接条件**（不进入 `c_k`），对所有形式（含 demo）由闸门恒执行（§6.3 `gate`、§7.3 S2）。二者层级不同，不重复计入。

| itemId | category | criticality | predicate | 层级 | 说明 |
|---|---|---|---|---|---|
| C-01 | core_loop | blocking | `slotActive(core_loop, 1)` | 清单分项（入 `c_k`） | 空核心槽 → D-01 `E-EMPTY` 同义 |
| C-02 | core_loop | blocking | `uspBackedBy(any)` | 清单分项（入 `c_k`） | 卖点无支撑 → D-01 `E-USP`（R-COM-7） |
| C-03 | delivery | blocking | `fieldNonEmpty(finalTitle)` | 清单分项（入 `c_k`） | 上市前必须有正式名 |
| C-04 | delivery | blocking | `platformStdMet(any)` | 清单分项（入 `c_k`） | 至少 1 平台且标准满足 |
| C-05 | content | blocking | `slotActive(content, 1)` | 清单分项（入 `c_k`） | content 槽必绑定（D-01 `E-EMPTY-CONTENT`） |
| C-06 | tech | blocking（闸门） | `defectFree({E})` | **闸门桥接条件（不入 `c_k`）** | E 级缺陷零容忍（`D02-E-DEFECT`），由 `gate` 恒执行 |
| C-07 | delivery | blocking（闸门） | `RevalidationGate = PASS` | **闸门桥接条件（不入 `c_k`）** | 复用 D-01 §7.2.1 全部 E 级结构违规，由 `gate` 恒执行 |

> C-06/C-07 是关键桥接：D-01 的结构硬规则在交付闸门**原样复用**，D-02 只追加 C-06 的 E 级缺陷条件。二者是闸门条件而非清单分项，**不进入 `c_k`、不随 demo 子集裁剪而缺席**；demo 一律恒执行 `RevalidationGate=PASS ∧ defectFree({E})`（与 §5.3、§6.3、§7.3 S2 同口径）。

### 5.2 类别分类（P1 规则框架）

`archetypeClass` 是**从快照确定性派生**的标签，不是新的玩家字段（避免与 D-01 七维冲突）。分类顺序固定（先判 technical，再判 niche，余为 broad）：

```
technical  if  T_unsat ≠ ∅  OR  perspectiveId ∈ {first_person, isometric}
                            OR  structureId ∈ {open_zone, sandbox, roguelike}
niche      else if |targetSegmentClaims| == 1  AND  core intensity ≥ τ_niche (TUNING)
broad      else if |targetSegmentClaims| ≥ τ_broad_tags (TUNING)
generic    otherwise（如空草稿：只套公共项）
```

- 阈值 `τ_niche`、`τ_broad_tags` 为 `TUNING`；分类结果写入 `EvaluationContext.archetypeClass`，带 `formulaVersion`。
- **P1 开放覆盖（`CONFIRMED`，本版已裁定）**：玩家/QA 可**显式指定** `archetypeClass`，必须附理由并写入 `DeliveryDecisionRecord`。覆盖触发：更新清单 `templateRevision` + 原 `DeliveryFormQualification` 作废 → `not_evaluated` → 按新类别重算（流程已具备，直接引用 §4.3 跨类别行、§10.4 X-2）；全程留痕，系统不阻止覆盖。`OPEN-D02-O3` 据此关闭。
- 类别与 D-01 `GameplayArchetype` 数据条目**不是同一实体**：前者是交付标准分组，后者是玩法类型数据（D-01 §4.13）。两者通过 `primaryTypeId` 的 `coreSlotDomains`/`typeAffinity` 间接关联。

### 5.3 各类别专属清单（P1 框架）

**broad（广谱）——要求"覆盖宣称的多个群体"：**

| itemId | category | criticality(full / EA / demo) | predicate |
|---|---|---|---|
| B-01 | content | blocking / blocking / optional | `contentTierAtLeast(t_broad_content)`（TUNING） |
| B-02 | core_loop | blocking / expected / optional | `slotActive(support, 1)`（广度需支撑系统） |
| B-03 | core_loop | expected / expected / optional | ∀tag ∈ `targetSegmentClaims`: `segmentCovered(tag, τ_cover_broad)`（TUNING） |

**niche（窄众）——要求"核心深度与卖点收敛"：**

| itemId | category | criticality(full / EA / demo) | predicate |
|---|---|---|---|
| N-01 | core_loop | blocking / blocking / optional | `depthAtLeast(deep)` 或 `intensity ≥ τ_niche_deep`（TUNING） |
| N-02 | core_loop | blocking / expected / optional | `uspBackedBy(core_loop)`（卖点必须由核心而非支撑系统支撑） |
| N-03 | content | expected / expected / optional | `contentTierAtLeast(t_niche_content)`（TUNING，通常低于 broad） |

**technical（技术型）——要求"技术门槛交付时已闭合"：**

| itemId | category | criticality(full / EA / demo) | predicate |
|---|---|---|---|
| T-01 | tech | blocking / blocking / blocking | `techGatesSatisfied(all)`，即交付时 `T_unsat = ∅` |
| T-02 | tech | blocking / expected / optional | `defectFree({E, D})`（E 与 D 级均零；严重度枚举 OPEN-D02-O2） |
| T-03 | content | expected / expected / optional | `contentTierAtLeast(t_tech_content)`（TUNING） |

**demo（试玩版）——独立子集**：只套 C-01/C-02/C-04/C-05 + `B/N/T` 中标 `optional` 的演示片段项，并强制披露"非完整产品"（`disclosurePolicy=required`）。demo 不继承 full/EA 的 expected 项。**闸门桥接条件 C-06/C-07 不写入 demo 清单项集，但由 §6.3 `gate` 与 §7.3 S2 对 demo 同样恒执行（`defectFree({E}) ∧ RevalidationGate=PASS`），不进入 `c_k`**，故 demo 不因清单裁剪而规避 E 级门槛。**例外**：technical 的 T-01 对 demo 仍为 `blocking`——技术型试玩若技术门槛未闭合则无法运行，此例外不因形式放宽而取消。

### 5.4 缺失模块的处理决策表

| 缺失类型 | `full` | `early_access` | `demo` | 可选玩家动作（不自动执行） |
|---|---|---|---|---|

|---|---|---|---|
| 评价 | 不可交付（无此路径） | 设计/实现质量向量不变；完整度对应分项下降 | 同左 + 欺骗性营销标记 |

## 6. 计算公式（三质量独立）

> 全部符号在 §6.6 总表定义。`TUNING` 不填终值；`OPEN` 不写入确定公式。**任何公式不得返回可与其他两类合并的单一标量**（R-D02-0）。

### 6.1 设计质量 `DesignQuality`（设计期、来自 D-01 快照）

设计质量评价"方案本身"，与团队执行无关。输出为**四维向量**，无总分：

```
DQ = {
  structure,          // 结构完整性
  innovation,         // 创新性
  experiencePotential,// 体验潜力
  marketFit           // 市场匹配
}

structure          = filledRequiredSlots / max(1, |requiredSlots|)        // ∈[0,1]；空设计=0
innovation         = UNAVAILABLE_P1     // 需 D-07 archiveSimilarity；OPEN-D02-O4，P1 显示 "—"
experiencePotential= clamp( (Σ_{i∈M_active} a_i × w_int(i) × w_depth(i)) / (k_exp × |M_active|) , 0, 1 )
   a_i        = Σ_{tag ∈ targetSegmentClaims} affinity_i[tag]      // D-01 §6.5 画像（只读）
   w_int(i)   = ModuleTemplate.affinityIntensity[i.intensity]      // D-01 §4.6 默认 {1:.6,2:.8,3:1,4:1.2,5:1.4}
   w_depth(i) = {shallow:0.6, standard:1.0, deep:1.4}             // TUNING
   k_exp      = TUNING 归一化常量；|M_active|=0 时分子分母均为 0 → 定义 experiencePotential=0
marketFit      = clamp( w₁·positioningFit + w₂·genreFit + w₃·uspSupportRatio , 0, 1 )
   uspSupportRatio = |{u ∈ sellingPoints : uspSupported[u]}| / max(1, |sellingPoints|)
   w₁+w₂+w₃ = 1（TUNING）
```

- `positioningFit`/`genreFit`/`uspSupported` 全部来自 D-01 §6.5 只读画像（D-02 不重算市场画像）。
- `innovation` 在 P1 为 `UNAVAILABLE_P1`，不是 0、不是 1；UI 显示"—"，闸门**不要求**该维。
- `clamp(x,0,1) = min(1, max(0,x))`。

### 6.2 实现质量 `ImplementationQuality`（执行期、来自 QA/Project）

实现质量评价"团队做得多好"，与设计意图无关。输出四维向量，无总分：

```
IQ = {
  stability,          // 技术稳定
  contentFidelity,    // 内容还原
  defectLoad,         // 缺陷负载
  deliveryAdherence   // 交付偏差
}

stability         = 1 − R_tech_delivery      // R_tech_delivery 为交付时 D-01 §6.4 当前值；T_unsat=∅ → 1
contentFidelity   = if plannedTier == 0 then 1
                    else clamp(deliveredTier / plannedTier, 0, 1)   // Project Build vs 快照 ContentPack.tier
defectLoad        = clamp( 1 − (Σ_{sev} w_def[sev] · n_sev) / k_defectNorm , 0, 1 )
                    // w_def、k_defectNorm 为 TUNING；严重度枚举 OPEN-D02-O2
deliveryAdherence = if costEst == 0 then UNAVAILABLE_P1
                    else clamp( 1 − |actualCost − costEst| / costEst , 0, 1 )  // Project 数据 OPEN-D02-O5
```

- `defectLoad` 的严重度权重仅在枚举确定后校准；P1 若 QA 只给 E 级计数，则以 `w_def[E]` 单独计入（`D02-E-DEFECT` 仍独立阻断）。
- `deliveryAdherence` 在 P1 多为 `UNAVAILABLE_P1`（Project 成本口径未定），显示"—"，闸门不要求。
- **实现质量任何一维都不反向影响 DQ**，也不影响 `W_d`（HRB 单向原则延伸）。

### 6.3 产品完整度 `CompletenessReport`（清单期、来自 §5 清单求值）

完整度评价"是否做完该类型该形式要求的内容/系统/技术/交付件"。**输出分项覆盖向量 + 闸门，禁止单一百分比**：

```
对每个 category k ∈ {core_loop, support, content, tech, delivery}:
  R_k = { item ∈ checklist.items : item.category=k ∧ item.criticality ∈ requiredFor(form)
          ∧ item.itemId ∉ {C-06, C-07} }        // 闸门桥接条件不计入清单分项
  S_k = { item ∈ R_k : evaluate(item.predicate, EvaluationContext) = true }
  c_k = if |R_k| == 0 then 1 else |S_k| / |R_k|        // 除零边界：无要求视为已满足

CompletenessReport = {
  byCategory : { core_loop:c₁, support:c₂, content:c₃, tech:c₄, delivery:c₅ },  // 分量，不合并
  blockingUnmet : [ item ∈ checklist.items : item.criticality=blocking ∧ ¬satisfied ],
  gate : PASS iff blockingUnmet = ∅ ∧ RevalidationGate = PASS ∧ defectFree({E}) ; else FAIL
}
```

- **禁止** `overall = mean(c₁..c₅)` 或任何加权和作为完整度；`byCategory` 必须逐项展示（R-D02-1）。
- `c_k` 是诊断用的分项覆盖率，不是"完成度百分比"；`gate` 只由 blocking 项决定，与 `c_k` 数值无直接关系（4/4 核心满足但 0/6 可选满足不影响 gate）。
- 清单项满足与否是**布尔谓词**，没有"部分满足"的半分；避免用连续百分比掩盖缺口。
- **C-06/C-07 双层表达消解**：`defectFree({E})` 与 `RevalidationGate=PASS` 唯一在 `gate` 中求值（含 demo），不进入任何 `R_k`/`c_k`；§5.1 的 C-06/C-07 仅为闸门条件的清单展示位，不重复计入 coverage，消除"清单分项 vs gate"双重表达。

### 6.4 三质量的关系约束（非合成）

| 约束 | 内容 |
|---|---|
| IND-1 | DQ 只由快照/设计画像导出；IQ 只由 QA/Project 执行事实导出；C 只由清单谓词导出。**输入存在共享但用途隔离**：DQ 与 C 共享只读设计快照；IQ 与 C 共享 QA 缺陷事实（IQ 计 `defectLoad` 负载，C 作 E 级零容忍闸门 `defectFree({E})`）。三者**无合成字段、无输入混合公式**，共享原始事实不等于合成。 |
| IND-2 | 不存在 `quality = f(DQ, IQ, C)`；UI 不展示综合仪表盘；存档不含合成字段（TC-01）。 |
| IND-3 | 三者可**相互矛盾**：高 DQ + 低 IQ（好设计做砸）、低 DQ + 高 IQ（烂设计做精）、高 DQ/IQ + 低 C（做完了核心但缺交付件）都必须可表达。 |
| IND-4 | 交付闸门只看 C.gate 与 E 级项；**不因 DQ/IQ 高而放行**（防"带病上市"，D-01 §7.2.1）。 |

### 6.5 `qualityCeilingBand`（OPEN-O5）与 D-01 HRB 的对齐

**P1 状态**：`qualityCeilingBand = ABSENT_P1`（`D02-QCB-UNDEFINED` 用于拦截误消费）。依据 ADJ-2026-11-21-01 第 5 条与 D-01 §8.2：D-01 已从输出契约移除该字段，下游不得按已交付接口消费。

**对齐接口形状（结构确定，值 OPEN/TUNING）**：

```
输入（全部只读）：
  HRB ∈ [0,1]                     // D-01 §6.2.1 玩家预算承诺
  HRBFeasibility.verdict          // {可行, 需追加预算/需延期, 需缩减范围/需降低质量目标}
  archetypeClass, deliveryForm    // §5.2 / D-01 lockTargetReleaseForm
  formulaVersion                  // 版本化

未来公式（OPEN-O5，待 D-02 与 Project 规格对齐后经版本化公式补充）：
  qualityCeilingBand = f_ceiling(HRB, verdict, archetypeClass, deliveryForm, formulaVersion)
                       → {unconstrained, low, medium, high}   // 阈值 TUNING

允许的用途（仅在映射确定后）：
  • 作为 DQ/IQ 可达**档位的上限**用于市场预期与披露（capping），不是乘子
  • 与 `verdict` 文本共同解释"为什么可达质量受限"

禁止的用途（现在与未来均禁止）：
  • 不得作为 W_d / 工作量 / 项目成本的乘子（ADJ-2026-11-21-01 第 1/3 条）
  • 不得替代 DQ/IQ/C 任一分量，不得参与任何合成
  • 不得在 f_ceiling 未定义时被赋默认值（尤其不得默认 high 或 1.0）
```

**P1 行为**：D-01 的 `verdict` 含"需降低质量目标"时，D-02 仅把它当作**文本提示**记录到 `DeliveryDecisionRecord.reasonNote`，`qualityCeilingBand` 仍为 `ABSENT_P1`。任何下游若读取该字段，按 `D02-QCB-UNDEFINED` 契约错误拦截。

**对齐前置条件（为何仍 OPEN）**：① Project 的 `BudgetCapacity`/`Cost_est` 口径未定（P0-B §5 优先级 2/4）；② 档位边界需 P2 模拟校准（`TUNING`）；③ 需确认上限是"设计可达上限"还是"实现可达上限"或二者分别一条（`OPEN-D02-O6`）。

**阈值顺序与聚合约束（保证公式可执行）**：

1. `core intensity = max{ i.intensity : i ∈ M_active ∧ slot(i)=core_loop }`，取最深核心而非均值；无核心实例时为 0。`i.intensity` 取值域为整数 `{1,2,3,4,5}`（D-01 §4.6）。
2. `τ_niche`、`τ_niche_deep` 与 `intensity` 同域（`{1,2,3,4,5}`）；`τ_cover_broad ∈ [0,1]` 为 `affinity` 阈值；`τ_broad_tags` 为标签计数（≥1 整数）；`t_*_content` 为内容档序号（TUNING）。
3. **强制阈值顺序 `τ_niche ≤ τ_niche_deep`**：niche 分类门槛不得高于"深度满足"门槛，否则任一 niche 产品（`core intensity ≥ τ_niche`）将自动满足 N-01 的 `intensity ≥ τ_niche_deep` 分支，使 N-01 失去区分力（TC-03 依赖此顺序）。
4. `any` 仅为谓词参数的存在量词；`uspBackedBy(any)` 仍要求"每条 `sellingPoints` 被至少一个 active 实例支撑"，即外层 `∃ slotKind`、内层 `∀ u ∈ sellingPoints`；`|sellingPoints|=0` 时按 §6.7 视为通过，不误报。
5. `clamp` 与阈值顺序求值：先计算加权和/归一化表达式，再用 `clamp(·,0,1)` 截断；`clamp` 不改变比较阈值的判定顺序。

### 6.7 除零与边界汇总

| 情形 | 处理 |
|---|---|
| `M_active = ∅` | `structure=0`、`experiencePotential=0`；闸门由 C-01 阻断 |
| `|sellingPoints| = 0` | `uspSupportRatio = 0`；C-02 按 D-01 `E-USP` 判定（卖点为空时该谓词视为通过，不误报） |
| `|R_k| = 0` | `c_k = 1`（无要求视为已满足），不进入闸门 |
| `plannedTier = 0` | `contentFidelity = 1` |
| `costEst = 0` | `deliveryAdherence = UNAVAILABLE_P1`，不显示数值 |
| `HRB = 0` | `verdict` 由 D-01 §6.2.1 给出；D-02 不改工作量、不赋质量上限（OPEN-O5） |
| `innovation` / `deliveryAdherence` UNAVAILABLE | 显示"—"，不计入闸门，不按 0 处理 |

## 8. 玩家操作与自动化

### 8.1 玩家定（有决策意义）

| 决策 | 层级 | 代价 |
|---|---|---|
| 选择目标交付形式（full/EA/demo） | 闸门级 | 形式越完整，清单越严；EA/demo 需承担预期与品牌后果 |
| 覆盖 `archetypeClass`（P1 开放，`CONFIRMED`） | 战术级 | 清单 `templateRevision` 更新 + 原资格作废并按新类别重算（§4.3/§10.4 X-2），留痕 |
| 缺失 blocking 项：替换 / 返工 / abandon | 闸门级 | 沉没成本、工期、机会成本（D-01 §15） |
| 缺失 expected 项：补齐 / 接受披露通过 | 闸门级 | 预期/退款/品牌档位变化 |
| 提交披露声明 | 闸门级 | 声明内容进入 `DeliveryDecisionRecord`，不可事后删除 |
| EA→full 升级时机 | 战略级 | 需新 Build + 更严清单 + 清退披露 |

### 8.2 系统算（自动化）

- 清单谓词求值、`byCategory` 向量、`blockingUnmet`；
- `DQ`/`IQ`/`C` 三向量计算（互相隔离）；
- `DeliveryFormQualification` 状态转换；
- `DeliveryGateResult` 生成与同步返回；
- `ModuleContribution.missing/substituted` 标记与 `substitutableBy` 建议；
- `ExpectationProfile` 方向与档位生成。

### 8.3 不自动化（红线）

- 不自动补齐缺失模块（R-D02-3）；
- 不自动替换冲突/缺失模块（D-01 §9.3）；
- 不自动把 full 降级为 EA 来"自洽"（需玩家选择 + 披露）；
- 不自动赋 `qualityCeilingBand` 数值（OPEN-O5）；
- 不自动判定"应该交付"（闸门只算 PASS/FAIL，决策在玩家）。

### 8.4 玩家可见解释（对齐系统地图 §6）

- 结果：三质量向量分项 + `blockingUnmet` 列表 + 闸门结论；
- 原因：前三个未满足清单项（itemId + label + gapAction）；
- 置信度：区分"已观测事实（缺陷/内容量）"与"不可用维（innovation/deliveryAdherence 显示—）"；
- 影响：预期/退款/品牌档位方向与后续可用行动；
- 后续选择：每个 `ResolutionAction` 的代价提示；
- 变化说明：清单revision 或 `formulaVersion` 变化时标注原因。

## 9. UI/UX 页面结构级规格

> 仅结构级：用途、布局、区域、控件、默认值、状态、空/错状态、跳转。像素/配色/动效不在范围。

### 9.1 `P-QA-01` 交付清单板

- **用途**：让玩家看到"按当前类型与形式，还差什么"。
- **布局**：左=类别分组（core_loop/support/content/tech/delivery）；中=清单项列表；右=三质量分量摘要（只读）。
- **区域/控件**：类别 Tab；清单项行（itemId、label、criticality 徽标、谓词状态图标、gapAction 按钮）；`byCategory` 五个分量条（各自独立，无汇总条）；筛选（仅看未满足）。
- **默认值**：形式 = 快照 `lockTargetReleaseForm`；类别 = 全部；筛选 = 仅未满足。
- **状态**：加载中/已求值/重算中；`blockingUnmet>0` 时顶部红条"未达交付标准"。
- **空状态**：无 active 快照 → "尚无设计版本，无法评估"。
- **错状态**：谓词依赖不可用（如 QA 未接入）→ 该项显示"—（依赖未就绪）"，不计 FAIL。
- **跳转**：点击 gapAction → `P-QA-04`；点击"三质量摘要" → `P-QA-02`。

### 9.2 `P-QA-02` 三质量分离视图

- **用途**：明确区分设计/实现/完整度，杜绝综合分误导。
- **布局**：三列并排，**无第四列"综合"**；每列内为分量条列表。
- **区域/控件**：
  - 设计质量列：structure/innovation/experiencePotential/marketFit 四条；`innovation` 显示"—"。
  - 实现质量列：stability/contentFidelity/defectLoad/deliveryAdherence 四条；不可用显示"—"。
  - 完整度列：`byCategory` 五条 + `gate` 徽标（PASS/FAIL）+ `blockingUnmet` 折叠列表。
- **默认值**：全部展开。
- **状态**：`provisional`（灰）/`final`（锁定图标）/`superseded`（历史标记）。
- **空状态**：无评估 → "尚未生成评估"。
- **错状态**：尝试展示综合分 → 不渲染该控件（结构上不存在）。
- **跳转**：点击完整度列 → `P-QA-01`；点击"资格" → `P-QA-03`。

### 9.3 `P-QA-03` 交付形式资格面板

- **用途**：显示 full/EA/demo 三种形式的资格与代价。
- **布局**：三卡片；每卡显示 status、blockingUnmet 数、requiredDisclosures 数、预期/退款/品牌档位。
- **控件**：形式选择单选；"查看披露要求"；"选择此形式并继续"。
- **默认值**：目标形式 = 快照预期形式；若 `not_qualified`，默认选中最近的合格形式（若有）。
- **状态**：`not_evaluated`/`qualified`/`qualified_with_disclosure`/`not_qualified`。
- **空状态**：无快照 → 三卡均灰。
- **错状态**：`D02-QCB-UNDEFINED`（下游已尝试消费 qcb）→ 隐藏该字段并显示"—（未对齐）"。
- **跳转**：确定形式 → `P-QA-05`；需处理缺失 → `P-QA-04`。

### 9.4 `P-QA-04` 缺失模块处理面板

- **用途**：对每个 `blockingUnmet`/未满足 expected 项给出有代价的 `ResolutionAction`。
- **布局**：问题列表 + 每项的解决动作按钮组（替换/返工/披露/放弃）。
- **控件**：动作单选 + 代价预览（沉没成本/工期/档位变化）；"确认选择"。
- **默认值**：不预选任何动作（强制玩家决策，R-D02-3）。
- **状态**：可处理/处理中/已处理。
- **空状态**：无缺失 → "全部满足"，隐藏本页动作区。
- **错状态**：动作会产生 `not_qualified` → 按钮禁用 + 原因。
- **跳转**：确认后回 `P-QA-01` 重算；返工 → D-01 返工画布（§15）。

### 9.5 `P-QA-05` 交付闸门结果

- **用途**：提交交付前一刻的同步闸门结论。
- **布局**：顶部大结论（PASS/FAIL）；下方复用项清单（C-01..C-05 清单项 + 闸门桥接条件 C-06/C-07〔E 级缺陷 / `RevalidationGate`〕 + 类别专属项）逐项勾叉；C-06/C-07 标注"闸门恒执行"。
- **控件**："确认交付" / "返回修正" / "查看返工"；披露声明输入框（若 required）。
- **默认值**：按钮"确认交付"在 FAIL 时禁用。
- **状态**：检查中（同步，≤性能预算）/ PASS / FAIL。
- **空状态**：不适用（总有至少一项检查）。
- **错状态**：同步检查超时/依赖不可用 → 不返回 PASS，显示"无法确认，保持 EXECUTING"（fail-closed）。
- **跳转**：PASS → 上市流程（Project/D-01 `COMPLETED`）；FAIL → `P-QA-04`。

### 9.6 `P-QA-06` 市场预期与披露声明

- **用途**：让玩家理解交付形式带来的预期后果，并记录披露。
- **布局**：左=预期/退款/品牌档位（方向箭头）；右=已披露缺口清单 + 编辑区。
- **控件**：披露文本编辑；"确认披露"；档位说明展开。
- **默认值**：自动填入未满足 expected 项列表（不可删，只能补充文案）。
- **状态**：草稿/已确认；已确认后只读（进入 `DeliveryDecisionRecord`）。
- **空状态**：无缺口 → "无需披露"，隐藏编辑区。
- **错状态**：未披露却试图 full/EA 交付 → `D02-DISCLOSURE-REQUIRED` 阻断。
- **跳转**：确认 → `P-QA-05`。

## 10. 异常与边界

### 10.1 缺失核心模块

`blocking` 项无 active 支撑 → `D02-MISSING-CORE`，所有形式闸门 FAIL。路径：替换 / 返工 / abandon（§5.4）。系统不自动补齐。与 D-01 `E-EMPTY`/`E-USP` 为同一阻断来源，不重复记账。

### 10.2 抢先体验版转正式版

EA `FINAL` → 触发新 Build → 按 `full` 清单重算（expected 项升为必须）→ 新 `QualityAssessment`。旧评估 `SUPERSEDED` 保留。若补齐未完成，闸门 FAIL，EA 版继续在市（不强制下架，但新 full 不可上市）。披露清退后写入 `DeliveryDecisionRecord`。**不允许仅改枚举标志完成升级**。

### 10.3 跨形式交付

- demo → full：不允许直接转（demo 是独立子集）；须重新按 full 立项/补齐。
- full → EA：不允许倒退（full 已封版）；降级须返工 + 新版本（D-01 §15）。
- EA → demo：不允许（降级且清单不同）。

### 10.4 跨类型交付与冲突登记

| 编号 | 情形 | 处理 |
|---|---|---|

## 14. 设计质量 / 实现质量 / 完整度三分离的论证与反证

### 14.1 为什么不能合成一个分数（正向论证）

1. **信息来源与用途不同**：DQ 来自设计快照与 D-01 只读画像（决策前）；IQ 来自 QA/Project 执行事实（决策后）；C 来自类型×形式的清单谓词（规则判定）。DQ/C 共享只读设计快照、IQ/C 共享 QA 缺陷事实，但用途隔离（IND-1：IQ 计缺陷负载、C 作 E 级零容忍闸门），三者无合成字段、无输入混合公式；合并等于把"意图""执行""合规"三类不同证据压进一个不可解释的数。
2. **可控性不同**：玩家直接控制设计（DQ），间接影响执行（IQ），受规则约束地选择形式与补齐（C）。合成会抹掉"玩家该为哪一项负责"的反馈（体验目标 E1/E3）。
3. **时间性不同**：DQ 在锁定时刻基本确定；IQ 随缺陷修复变化；C 在交付动作点一次性判定。合并后无法表达"设计时很好、执行时变差"的动态。
4. **市场后果不同**：DQ 主要影响品类吸引与口碑潜力（经 D-04），IQ 影响兑现与退款，C 影响"是否算完整产品"与欺骗性营销判定。合成会让一个高分掩盖另一维度的具体风险，违反系统地图 §6「区分已知事实、估算与不确定性」。
5. **基线硬要求**：总纲 §7.4 明确"不得把三者压缩成一个百分比"，系统地图 §4.2 明确"不用单一进度百分比冒充"。D-01 T2 已用 max 分级而非加权和处理三风险，体现同一设计哲学。

### 14.2 反证（若合成会发生什么）

| 反证 | 构造 | 合成后的错误 | 本文如何避免 |
|---|---|---|---|
| A：高低互补掩盖 | 产品甲 DQ=0.9、IQ=0.9、C=0.2（缺核心），合成 0.67→"不错" | 带病上市，违反 D-01 §7.2.1 | `gate` 只看 C.gate/E 级（IND-4），甲必 FAIL |
| B：百分比冒充完整度 | 产品乙满足 4/4 核心项、0/6 可选项，合成 40%"未完成" | 阻断一个本可交付的产品 | `c_k` 按类别分项、gate 只看 blocking；4/4 核心满足即 PASS |
| C：好设计 ≠ 好实现 | 丙 DQ=0.95、IQ=0.3（缺陷多） | 合成中等分，玩家不知是"做砸了" | DQ/IQ 分列，IQ.defectLoad 与 D02-E-DEFECT 独立呈现 |
| D：烂设计 ≠ 做不好 | 丁 DQ=0.2、IQ=0.95（执行完美） | 合成中等分，误判值得投入 | 两向量独立，玩家能解释"执行好但设计差" |
| E：质量上限冒充质量 | `qualityCeilingBand=high` 被当作 DQ/IQ 高 | 预算承诺被误读为质量结果 | P1 恒 `ABSENT_P1`，禁止乘子/替代（§6.5） |

### 14.3 可表达性检验

要求规格能同时表达以下状态（合成模型无法做到）：
- (高 DQ, 高 IQ, 低 C) —— 做完了核心但缺**交付件/expected 项**（如缺 `finalTitle` 或支撑广度不足），此时 IQ 仍可高、C 因分项未满足而低（TC-04）。**不以"带 E 缺陷"作此例证**：E 缺陷同时压低 `IQ.defectLoad` 并触发 `D02-E-DEFECT` 阻断（IND-1 的共享输入），无法同时构造高 IQ；该类自洽路径仅"缺交付件"成立；
- (高 DQ, 低 IQ, 高 C) —— 好设计被做砸但内容齐全（反证 C）；
- (低 DQ, 高 IQ, 高 C) —— 精品执行的平庸设计（反证 D）；
- (三向量中部分维 UNAVAILABLE) —— 数据未接入时不伪造 0（§6.7）。

满足以上四点即证明三分离建模完整。

### 14.4 与 D-01 §14「新子类型/新类型边界」的关系（2.3B 第 14 项）

2.3B 要求的"新子类型/新类型边界"由 D-01 §14（L1 组合即类型 / L2 子类型识别 / L3 类型库扩展 / 机制生成 DEFERRED）完整定义，本文**不重复、不扩展玩法类型生成规则**。D-02 的 `archetypeClass`（broad/niche/technical/generic）是**交付标准分组**，与 D-01 `GameplayArchetype`（玩法类型数据条目）是不同实体、不同用途：

| 维度 | D-01 `GameplayArchetype` | D-02 `archetypeClass` |
|---|---|---|
| 来源 | 种子数据 / 玩家创建 / AI 创建（§14.4 提升） | 由快照确定性派生（§5.2），可显式覆盖并留痕 |
| 用途 | 决定必选槽、玩法域推荐强度、市场画像 | 决定用哪份核心交付清单 |
| 生命周期 | provisional → active → deprecated | 无独立生命周期，随快照重算 |
| 新条目产生 | L2/L3 由组合识别提升（D-01 §14） | **不产生新条目**；仅四值枚举，扩展需设计审核升 `formulaVersion` |

边界裁定：`GameplayArchetype` 从 provisional 提升为 active 会改变 `requiredSlots`/`domainAcceptance`，从而间接改变 C-01/B-02/N-01 等谓词的求值结果，但**不改变清单模板结构本身**；若某新类型无法归入四类，应评估是否需要新增 `archetypeClass`（设计审核，`OPEN-D02-O7`），不得由 AI/玩家自行创造交付标准。
