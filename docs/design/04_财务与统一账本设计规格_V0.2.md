## 0. 一句话立场（最高原则）

**唯一现金入口**：企业现金只能在统一账本（`FinanceService.postTransaction`）因一笔 `Transaction` 入账/出账而变动；任何业务系统、UI、脚本都不得直接读写 `Company.cash`。现金余额是账本的**派生快照**，不是可写字段。

**破产是经营失败的因果结果，不是随机惩罚。** 玩家每一次失败都可追溯到一条链：承诺支出（招聘/租金/项目预算/合同）→ 跑道缩短 → 现金逼近预警线 → 有限补救窗口 → 未在窗口内改善 → 危机升级 → 破产。预警必须"可理解"（显示原因与倒计时），补救必须"可执行"（列出动作、代价、风险）。任何"凭空扣钱""随机破产""隐藏费用"均违反本规格（对齐基线 §12、§14 红线）。

## 1. 系统目标与玩家体验目标

### 1.1 系统目标

1. **权威账本**：为全游戏提供唯一、不可变、可审计、可重放的现金事实来源，封堵 V2.1.7 迁移分析 §2.3 所指"现金流无经营/投资/融资三分、无应收账款实体"缺口。
2. **因果可视化**：把"现金、利润、承诺支出、应收应付、项目投入、产品收入、合同义务、未来跑道"之间的关系建模为可解释数据（基线 §12）。
3. **危机可玩**：提供分级预警 + 有限补救窗口 + 有后果的重整，让失败成为可读的经营叙事而非黑箱（基线 §12/§13）。
4. **同源规则**：AI 企业与玩家共用账本与危机规则，AI 不得获得隐性现金、免费资金或更宽补救窗口（系统地图 §4.4、基线 §14）。

### 1.2 玩家体验目标（对齐基线 §13 四问）

| 界面四问 | 本系统回答 |
|---|---|
| 当前发生了什么？ | 现金余额（账本派生）、现金警告横幅、当前危机等级 |
| 为什么发生？ | 每笔交易带来源 `referenceId` 与原因码；跑道变化显示"招聘/追加预算/返工"等驱动 |
| 有哪些有意义的选择？ | 危机面板列出可用补救动作（缩减范围/暂停项目/裁员/转租/终止合同/出售资产/寻求预付款/重整） |
| 代价与风险？ | 每个补救动作按 §8.4 代价公式显示对现金、跑道、债务、声誉、人才、控制权的可计算影响预览 |

### 1.3 关键玩家价值（任务卡）

- 玩家能理解跑道，理解"追加预算/缩减范围"的代价（场景 A 步 6、场景 B 步 6）。
- 失败前有可识别预警（L1 现金警告 + L0 跑道预警）与可执行补救窗口。

## 2. 范围 / 不包含内容

### 2.1 范围内（P1 最小）

- `Transaction` 分类、幂等记账、冲销、现金流三分（经营/投资/融资）。
- `LedgerAccount`、`BudgetCommitment`（承诺支出）、`Payable`/`Receivable`、`CashForecast`、`CrisisState` 五类实体。
- 跑道月数、承诺扣除后可用现金、预测区间、预警阈值（TUNING）。
- 收入确认、退款、合同付款与分成统一走账本框架。
- 危机状态机与有限补救窗口；破产与重整后果；沙盒观察态。
- 与 D-01 `HRBFeasibility`、Project 成本、销售/合同/薪酬的接口。
- 存档：`Transaction` 不可变、可审计、可重放、版本迁移。

### 2.2 不包含（明确非目标）

- **不做 IPO、股票、公开市场融资、并购、股权激励**（任务卡非目标、基线 §14）。
- **不做复杂融资**：P1 仅保留"发行预付款 `advance`"一种融资类流入，且作为有限补救动作；无贷款契约、利息、信用评级、债转股（`DEFERRED`）。`advance` 在账本上形成"未来分成抵扣义务"（无利息、无到期日契约，见 §8.4），不属贷款契约。
- 不实现银行的借贷/还款滚动账户、多币种、跨地区结算（P4 `DEFERRED`）。
- 不定义定价/转化/营销/退款窗口的**具体公式**（属产品运营/D-04，本文只定义账本接口，`OPEN`）。
- 不写任何代码；不改 D-01、基线或 `spec/` 冻结正文。

## 3. 核心实体与字段

> 字段名/类型/约束均为设计口径；金额一律用整数美分 `int cents`，并同时给出业务值（CODEBUDDY.md §13.1）。`id` 为稳定唯一标识；`ref` 为引用不复制主数据（P0-B §1.4）。

| `status` | `enum{posted,reversed}` | 初始 `posted`；冲销只改状态，不删记录 | **仅作审计标记，不参与余额计算**（F-01 方案 a） |
| `reversedBy` | `ref(Transaction)/null` | 冲销交易 id | 指向反向交易 |

**不变量 INV-1（F-01 整改，方案 a）**：`LedgerAccount.cashBalanceCents == Σ(全部 Transaction.amountCents)`。

- 求和范围为**该账户全部交易**，不按 `status` 过滤；`status` 仅作"是否已被冲销"的审计标记，**不参与余额计算**。
- 冲销语义因此自洽：原交易 `+100` 置 `reversed` 后**仍计入**求和，其反向交易 `−100` 也计入，二者相加自然为 0；全额退款后余额回到冲销前基准（若原为 $100 销售且无其他交易，则回到 0）。
- `replay` 从 `Transaction[]` 按同一求和口径重建余额并校验 INV-1；任何退款/冲销后均须通过（TC-01、TC-18）。

### 3.3 BudgetCommitment（预算承诺 / 承诺支出）— F-02 整改

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `commitmentId` | `id` | | |
| `companyId` | `ref(Company)` | | |
| `sourceType` | `enum{employment_salary,office_rent,project_budget,contract_obligation}` | | 承诺来源 |
| `sourceRef` | `ref` | 指向 Employment/Office/Project/Contract | 不复制主数据 |
| `amountCents` | `int` | >0 | **每周期**计划支出（正值表示流出规模）；`monthly` 承诺每一兑现周期均以此金额产生一笔交易 |
| `period` | `enum{monthly,one_off}` | | |
| `periodCount` | `int` `NEW` | `one_off`=1；`monthly`≥1，由 `startAt..endAt` 覆盖的日历月数确定 | 累计基准的周期数（F-02） |

| `realizedCents` | `int` | `0..totalPlannedCents` | 已通过 Transaction 兑现的**跨周期累计额**（F-02：上限由 `amountCents` 放宽为 `totalPlannedCents`） |
| `state` | `enum{committed,partially_realized,realized,cancelled}` | 承诺状态。**`cancelled` 允许 `realizedCents > 0`**（已兑现周期不冲回，ADJ-2026-11-22-09 §R-03 裁定 (a)）；`cancelled` 是**可覆盖 `partially_realized` 的终态**，优先于 F-02 的周期判定 | 分周期判定见 §4.1（F-02）；取消语义见 §4.1 末 |
| `startAt`/`endAt` | `date` | `endAt ≥ startAt` | 跨月承诺按周期兑现（§10.3） |
| `linkedTxIds` | `list<ref(Transaction)>` | | 兑现证据；`monthly` **未取消时**应恰有 `periodCount` 笔，取消后为 `realizedPeriods` 笔（§4.1 末） |

**硬约束 BR-3**：承诺本身**永不改变现金**；只有"兑现事件"提交 `Transaction` 才改变现金。

**F-02 累计基准定义**：
- `one_off`：`periodCount=1`，`totalPlannedCents=amountCents`，`realizedCents ∈ [0, amountCents]`。
- `monthly`：`periodCount` = `startAt` 与 `endAt` 之间（含首尾）覆盖的**不同日历月个数**（如 2026-01 至 2026-06 = 6）；`totalPlannedCents = amountCents × periodCount`；`realizedCents ∈ [0, totalPlannedCents]`。每兑现一个月度周期，`realizedCents += amountCents` 并追加一笔交易。
- `monthly` 承诺的 `realizedCents` 是跨周期累计数，不再被单月 `amountCents` 截断；已 `realized` 仅表示"全部周期已兑现"，不停止中间周期的兑现（§4.1、§10.3）。

| `remediationWindowDays` | `int` | TUNING（有限，见 §6.4；默认候选值 60） | 补救窗口天数 |
| `remediationDeadline` | `date/null` | `critical` 起必填 | 窗口截止日；**重入 `critical` 不重置**（F-06） |
| `availableRemedies` | `list<enum(Remedy)>` | | 当前可用补救动作（§8.4） |
| `restructuringConsequences` | `struct/null` `NEW` | 进入重整/破产时必填 | 结构化为字段（F-07），见 §8.5 |
| `phase` | `enum{restructuring,winddown}/null` | 映射现有 `BankruptcyPhase` | 见 §4.2 映射 |
| `crisisRulesVersion` | `string` `NEW` | 必填（F-09） | 进入该态时生效的危机阈值/规则版本；读档按此版本回放判定，不用当前 TUNING 覆盖 |
| `history` | `list<{from,to,at,reason}>` | | 状态迁移日志（持久化） |

**F-09 持久化口径**：`CrisisState` 是**持久化为准的权威状态**，不纯靠账本重算。`replay` 后用重建账本做一致性校验，但危机态以其持久化的 `enteredAt/reasonCodes/remediationDeadline/crisisRulesVersion/state/history` 为准恢复（详见 §10.5、§11.3），从而避免阈值 TUNING 跨版本变化导致读档漂移。

### 3.7 CrisisLevel 枚举（危机等级）

`healthy` → `watch`（关注）→ `warning`（预警）→ `critical`（危急，开补救窗口）→ `restructuring`（重整中）→ `bankrupt`（破产）→ `sandbox_observe`（沙盒观察）。

- `watch`/`warning` 为"预警"；`critical` 为"补救窗口"；`restructuring`/`bankrupt` 对应破产流程；`sandbox_observe` 为失败后继续观察（基线 §12，玩家选择）。
- 与企业状态映射（**F-08 统一**）：
  - `watch/warning/critical` → `LedgerAccount.state=active`；
  - `restructuring` → `frozen`（重整执行中，停止新增玩家义务，既有固定结算继续）；
  - `bankrupt` → `Company.status='bankrupt'`（现有实现），`phase=winddown`；账户在最终清算解散前置 `frozen`，清算解散后置 `closed`；
  - `sandbox_observe` → `LedgerAccount.state=frozen`（**非 `closed`**，F-08），玩家可见观察态，世界/AI 继续运行。

### 3.8 原因码（reasonCodes，因果可追溯）

`LOW_RUNWAY`（跑道低于预警月数）、`LOW_CASH`（现金低于警告线）、`COMMITTED_EXCEEDS_CASH`（承诺支出超过可用现金）、`PAYABLE_OVERDUE`（应付逾期）、`NEGATIVE_CASH`（出现负现金）、`BUDGET_OVERRUN`（项目超支，消费 D-01 ratio）、`REWORK_SUNK`（返工沉没成本）。每个非健康态至少带一个原因码，供 UI"为什么发生"与档案下钻。

### 3.9 TransactionCategory（12 类，复用现有枚举）与现金流三分映射

现有 12 类（`enums/index.ts:L30-L42`）：`salary`、`office_rent`、`project_expense`、`marketing`、`sales_revenue`、`customer_refund`、`platform_fee`、`contract_payment`、`tax`、`advance`、`severance`、`asset_sale`。

| 类别 | `cashFlowType`（TUNING 映射，默认候选值待校准） | 方向 |
|---|---|---|
| `salary` / `office_rent` / `marketing` / `project_expense` / `tax` / `platform_fee` / `customer_refund` | `operating` | 流出（refund 为收入冲减） |
| `sales_revenue` / `contract_payment`（收入侧） | `operating` | 流入 |
| `advance` | `financing`（P1 唯一融资流入） | 流入 |
| `asset_sale` | `investing` | 流入 |
| `severance` | `operating`（裁员一次性，金额见 §8.4） | 流出 |
| `contract_payment`（付款侧 / `advance` 抵扣） | `operating` | 流出 |

> 映射表为 `TUNING`（FIN-T1）；公式层禁止读取 TUNING，必须由调用方注入映射快照（沿用 `tuning.ts` 注释约定）。`contract_payment` 同类别可流出入，实际方向由 `amountCents` 符号决定，`cashFlowType` 建议按对手方/合同类型在 TUNING 细分——`OPEN-F1`。

## 4. 状态与转换

### 4.1 承诺 → 实际交易 → 结算 — F-02 整改

```
BudgetCommitment(committed)
   │ 兑现事件（月薪计提 / 租金到期 / 项目里程碑 / 合同义务到期）
   ▼
postTransaction(...)  → 现金变动（唯一入口），link referenceId
   │ linkedTxIds += tx；realizedCents += 单周期兑现额
   │
   ├─ one_off:  realizedCents ∈ (0, amountCents) → partially_realized
   │            realizedCents = amountCents        → realized
   │
   └─ monthly:  realizedCents < totalPlannedCents  → partially_realized
                realizedCents = totalPlannedCents  → realized（全部周期已兑现）
取消（cancelCommitment） → cancelled（**终态，优先于周期判定**）
                            · 不产生反向交易，已 post 周期一律不冲回
                            · realizedCents 可为 0（未兑现即取消）或 > 0（部分兑现后取消）
                            · 仅停止 effectiveMonth 及之后周期的兑现
```

- **F-02 状态判定**：`monthly` 与 `one_off` 分别以 `totalPlannedCents` 与 `amountCents` 为累计基准；`monthly` 在中间周期 `realizedCents` 可等于 `k × amountCents`（k<periodCount）仍为 `partially_realized`，"已 realized"仅在全部周期完成后置位，不提前终止兑现。
- `Payable/Receivable`：`open → partially_settled → settled`；到期未清 → `overdue`；放弃 → `written_off`（`written_off` 不冲回已入账现金，仅停止后续兑现）。
- 所有状态迁移由账本服务在某个 `Transaction` 成功入账后同步更新，保持"单一事实"。

> **`cancelled` 的终态语义（ADJ-2026-11-22-09，2026-11-22 追加）**
> F-02 的周期判定（`realizedCents < totalPlannedCents ⇒ partially_realized`）只适用于**未取消**的承诺。一旦调用 `cancelCommitment`，无论 `realizedCents` 是 0、介于中间、还是等于 `totalPlannedCents`，状态一律置 **`cancelled`**（终态，不再迁移）。
> 理由：取消是一个**外部动作事实**，不能用金额推断。若坚持"部分兑现后仍是 `partially_realized`"，则"这个承诺还会不会继续兑"这个问题无法从状态判断，下游（`AvailableCash`、`CommittedBurn`）必须额外查 `endAt` 与取消标记，等于把状态机的职责推给每个消费方。
> `cancelled` 承诺的 `releasedCents = totalPlannedCents − realizedCents` 视为**已释放**，不再计入 `AvailableCash` 的扣除项。
> 回归锚点：6 笔 × 500,000、`effectiveMonth = 2026-05` ⇒ `realizedPeriods=3`、`realizedCents=1_500_000`、`releasedCents=1_500_000`、**`state='cancelled'`**。

> **取消的生效期形参（ADJ-2026-11-22-05 §3，2026-11-22 追加）**
> 「中途取消只停止未来周期」需要明确「未来」从哪个月算起。实现层签名扩展为 `cancelCommitment(commitment, effectiveMonth: MonthKey) -> CancelCommitmentResult`，**`effectiveMonth` 必填、不得默认**（缺省会退化为按创建月取消，等于把已付周期一并释放）。
> 返回结构须给出 `realizedPeriods` / `releasedPeriods` / `realizedCents` / `releasedCents`，并满足 `realizedCents + releasedCents == 原承诺总额`。
> 边界：`effectiveMonth` 早于承诺起始月 ⇒ 全额释放（`realized=0`）；晚于结束月 ⇒ 全额已兑现（`released=0`）。
> 回归锚点（D-03 §7.2 / 本节 TC-19）：承诺 2026-02~2026-07 共 6 笔、500,000/月。**`effectiveMonth=2026-05` ⇒ `realizedPeriods=3`（02/03/04）、`realizedCents=1_500_000`、`releasedPeriods=3`**（ADJ-2026-11-22-09 修正；原"`effectiveMonth=2026-04` ⇒ 2 笔"锚点已作废，见下行）。
> 本节**仅补充接口形参**，§4.1 的语义（含「已入账不冲回」这一唯一例外）一字不改；跨规格登记见 D-03 §18.5 **FIN-INT-01**（由 CODE-04 关闭）。

> **「未来周期」的定义（ADJ-2026-11-22-09 §1.3，2026-11-22 追加）**
> 「中途取消只停止**未来**周期」中的「未来周期」= **`effectiveMonth` 及之后的周期**。`effectiveMonth` **之前**的周期为**已赚取周期**：即使尚未 `post`，也不因取消而消失，仍在各自的 `settlementDay` 照常兑现。
> 这条定义解决的问题：工资是**在当月劳动中赚取**的，`settlementDay` 只是**记账时点**，不是赚取时点。若把"离职当月"当成"未来周期"而取消，就会产生"干满整月、工资为零"的荒谬结果（玩家只需把解雇日放在结算日即可省下一整月工资，且按天可控 ⇒ 稳定套利）。
> **由此确定的标准映射**：雇佣关系终止 ⇒ `cancelCommitment(commitment, effectiveMonth = monthOf(endDay) + 1)`，即**自离职月的次月起停止**，离职当月照常兑现一笔。
> 该映射**不违反**本节语义，而是本节语义在"月薪"这一具体承诺类型上的唯一自然读法。对 `one_off` 与租金类 `monthly` 承诺同样适用本定义（`effectiveMonth` 之前的周期一律不因取消消失）。

### 4.2 危机状态机与现有 BankruptcyPhase 映射 — F-03 / F-06 整改

```
healthy
  ├─ 跑道/现金触发 → watch → warning
  └─ 跌破危急阈值 或 负现金 → critical（开补救窗口 remediationDeadline）
critical
  ├─ 玩家选"重整"且窗口内 → restructuring（phase=restructuring，账户 frozen）
  ├─ 现金恢复到 recovery 线（严格高于 warning 线） → watch（带真实滞后带，§6.4）
  └─ remediationDeadline 到期 且 现金仍 < 0（负现金未解） → bankrupt（phase=winddown）
restructuring
  ├─ 按重整方案兑现且满足恢复条件 → watch（带 §8.5 后果）
  └─ 失败 → bankrupt（phase=winddown）
bankrupt
  └─ 玩家选择"继续观察" → sandbox_observe（账户 frozen，世界继续，玩家不再授权新支出）
```

**F-03 破产判据（AND，全篇统一）**：
- 负现金本身**不是**破产判定线：负现金 → `critical` + `NEGATIVE_CASH` 原因码（可补救）。
- **破产唯一判定式**：`remediationDeadline 到期 AND 现金 < 0（负现金未解）` → `bankrupt`。
- 删除一切"窗口耗尽 **或** 负现金即破产"的 OR 表述（§5.9/§6.4/§10.1 已按此统一）。
- 边缘情形：窗口到期时现金已 ≥0 但未达 recovery 线，视为补救未完全成功——沿用**原** `remediationDeadline`（**不重置**，F-06）保持 `critical` 直至达到 recovery 线脱离或再次转负后按上式破产；是否引入"连续 N 日负现金"判定见 `OPEN-F5`（默认仍为 `<0` + 窗口耗尽）。

**F-06 滞后带与窗口不重置**：
- recovery 线严格高于 warning 线，形成真实滞后带（现金在两线之间维持当前态，不反复切换），参数见 §6.4。
- 重入 `critical`（现金短暂越过 recovery 后又回落）**沿用原 `remediationDeadline`，不重新计算窗口**；玩家不能通过"踩线再恢复"刷新 60 天窗口。

**映射**：`restructuring` ↔ `BankruptcyPhase='restructuring'`；`bankrupt` ↔ `BankruptcyPhase='winddown'`。`watch/warning/critical` 不进入 `BankruptcyPhase`（仍 `active`）。`sandbox_observe` 为 P1 新增的玩家可见观察态，现有实现需扩展（标 `NEW`/`OPEN-F2` 与 M1.2 UI 对齐方式）。

### 4.3 状态迁移约束

- **S-FIN-1（动作点同步）**：危机升级、补救兑现、重整判定在触发动作提交点同步执行，不延迟到下一日批量（对齐 P0-B S3 精神）；但 L0 每日"财务检查"（P0-B §3.2 步 6）负责阈值探测与横幅刷新。
- **S-FIN-2（单一生效态）**：每公司至多一个 `active` `CrisisState`；迁移写入 `history`，不覆盖旧态。
- **S-FIN-3（同源）**：AI 企业用同一状态机与同一 `remediationWindowDays`，不得更宽或有豁免；AI 破产公司的 `sandbox_observe` 由 `DailyScheduler` 破产检查按同一状态机自动进入，无需玩家选择（玩家公司的"继续观察"才是玩家选项，F-08）。

## 5. 业务规则

### 5.1 BR-1 唯一现金入口（最高红线）

- 只有 `FinanceService.postTransaction / bulkPostTransactions / reverseTransaction / replay` 能改变 `LedgerAccount.cashBalanceCents`（进而同步兼容字段 `Company.cash`）。
- 任何系统只能"提交交易"（`postTransaction` 调用），不得直接赋值现金；`Company.cash` 为只读兼容快照（**F-10**：业务系统与 UI 均不得以它为读源）。
- 开局注资必须以一笔固定幂等键的 `advance` 交易入账（现有实现规则：`finance-service.ts:30`），不允许 `registerCompany` 直接塞现金（其初始余额固定为 0）。
- **反证锚点（TC-02）**：必须存在测试证明"移除/绕过 `postTransaction` 后任何业务路径都无法改变现金"。

### 5.2 BR-2 交易分类

- 每笔交易必须有 `category`（12 类）与派生的 `cashFlowType`（三分）；必须带 `referenceId` 与 `source`，否则视为不合规入账（拒绝或标 `OPEN` 待补）。
- 金额符号语义固定：正=流入、负=流出；零额拒绝（`FIN_AMOUNT_ZERO`）。

### 5.3 BR-3 承诺支出不可直接改现金

- `BudgetCommitment`、`Payable/Receivable` 只是计划/义务；创建、修改、取消都不产生现金变动。
- 现金变动的唯一途径是"兑现事件提交 `Transaction`"，且一笔兑现对应一笔交易（幂等键绑定承诺 id + 周期，**F-02**：`monthly` 幂等键须含月份，如 `<commitmentId>:<YYYY-MM>`）。
- 场景 A 步 3：招聘 5 人 → 生成 5 条薪酬承诺，跑道**在承诺创建时即可预见地缩短**（预测层反映），但现金直到月末计提才实际流出——两者不同，UI 需区分"预计跑道"与"实际现金"。

### 5.4 BR-4 应收应付与防重复结算

- 应收应付按 `dueDate` 进入预测；到期通过一笔 `Transaction` 结算，`settledCents` 累加。
- 同一 `(sourceRef, period, direction)` 只允许一次成功结算；重复提交由幂等键去重（§5.7）。
- 应收不是现金：预计销售产生的 `Receivable` 不增加现金，直到 `SalesRecord` 结算提交 `sales_revenue`。

### 5.5 BR-5 收入确认

- P1 采用"销售结算确认"：`SalesRecord` 生成时提交 `sales_revenue`（`+revenue`）；平台抽成提交 `platform_fee`（`−fee`）；二者净额构成经营流入。
- **OPEN-F3**：收入确认时点（交付即确认 vs 回款确认）与总额法/净额法，属产品运营/D-04 与 D-05 口径；本文只约定"以 `Transaction` 入账为确认标志"，不锁定具体时点。合同分成按"净销售 − 退款"结算（现有 `contract-service.ts:L3-L5` 口径），本文沿用其净额口径，不另建规则。
- 退款时 `platform_fee` 的冲回按 §5.6（**F-11** 默认裁定），与上述净额口径一致。

### 5.6 BR-6 退款 — F-01 / F-11 整改

- 退款通过 `reverseTransaction(originalId, reason, newKey)` 生成一笔**符号相反**的 `Transaction`（`customer_refund`），原交易 `status=reversed` 并记 `reversedBy`；反向交易记 `reversalOf`。
- **F-01**：原交易与反向交易**均计入 INV-1 求和**（`status` 仅审计），退款后余额按全部交易求和自动回到正确值，`replay` 通过（TC-18）。
- **F-11 默认裁定（平台费随退）**：退款以"净销售 − 退款"为结算基数，并按退款比例**同步冲回对应的 `platform_fee`**。即每笔 `sales_revenue` 入账时同时记录其关联 `platform_fee` 金额；退款冲销销售收入的同一比例，同时以一笔反向 `platform_fee` 交易（`reversalOf` 指向原 `platform_fee` 交易）冲减对应手续费。全额退款后该笔销售的收入与手续费均回冲，公司对该笔销售净现金影响为 0，不产生手续费净损失（除非 D-05 另定独立支付通道费）。
  - 口径依据：D-05 净额口径"当日净销售 − 当日 posted 退款"为唯一分成基数（迁移 §2.18/§5.1 已锁定），手续费按同一净额基数计提，故退款时按同费率冲回；与"结算在退款之后"的时序一致。
  - 本文对 `platform_fee` 退款处理给**默认裁定**；D-05 正式稿如另定（`OPEN-F7`），以其为准并回写本文。
- 退款幂等：`newKey` 由调用方固定（如 `refund:<originalId>:<source>`）；跨期仍靠 `transactionByKey` 判定（§11.3）。
- 禁止"删除原交易"来退款——账本不可变（§11.1）。

### 5.7 BR-7 幂等与去重

- 每笔交易带唯一 `idempotencyKey`；重复提交返回原交易并标 `idempotent=true`，**不重复改变现金**。
- `idempotencyIndex` 30 天清理；`transactionByKey` 跨期保留，供退款等跨期幂等（迁移 §2.3 正确性关键，不得破坏）。

### 5.8 BR-8 合同付款与分成走同一框架

- `Contract` 记录义务与分成规则（合同权威），但**不自建第二套付款/分成账**；`Contract.settlementRefs` 指向 `Transaction`。
- 合同付款、平台分成、里程碑结算一律经 `FinanceService` 入账，类别为 `contract_payment` / `platform_fee`，并绑定 `referenceId=contractId`。
- 合作场景不得"私下改现金"或记第二本账（系统地图 §2.2、P0-B §1.2 D）。

### 5.9 BR-9 负现金（区分自主与固定结算）— F-03 统一

沿用现有 `allowNegativeBalance` 语义：
- **自主支出**（玩家主动追加预算、新增招聘、自愿营销等）余额不足 → 拒绝，返回 `FIN_INSUFFICIENT_CASH`。
- **固定结算**（薪酬、租金、税、退款兑现、合同到期）允许负现金（`allowNegativeBalance=true`），并触发 `NEGATIVE_CASH` 原因码 → `critical`。
- **负现金本身不是破产判定线**（破产线 TUNING 默认候选值 $0，见 §6.4），而是危机升级信号；**负现金且补救窗口耗尽才破产**（AND，F-03）。不采用 OR 口径。

## 6. 计算公式（参数 TUNING）

> 所有金额先用 cents 计算，展示时换算为美元。公式层禁止直接读取 TUNING，由调用方注入快照。文中的具体初值均为"默认候选值（TUNING，待校准）"（F-12）。

### 6.1 跑道月数（runwayMonths）— F-04 整改

```
NetBurn_m        = max(0, CommittedBurn_m − ExpectedIn_m)   // 与 §6.1 原口径一致
CommittedBurn_m  = Σ period=monthly 且 startAt≤m≤endAt 的 amountCents
ExpectedIn_m     = Σ 预测月 m 流入（应收到期 + 预计销售），按 confidence 折减

// CumAvailable(m) 显式定义（F-04）：以 §6.2 AvailableCash 为起点按月递推
CumAvailable(0)  = AvailableCash
CumAvailable(m)  = AvailableCash − Σ_{i=1..m} NetBurn_i      // m ≥ 1

runwayMonths =
   若存在整数 m ∈ [0, horizonMonths] 使 CumAvailable(m) ≤ 0：
      设 k = 满足 CumAvailable(k) > 0 且 CumAvailable(k+1) ≤ 0 的最大整数
      小数插值：runwayMonths = k + CumAvailable(k) / ( CumAvailable(k) − CumAvailable(k+1) )
                （分母>0；结果落在 (k, k+1]）
   若全窗口 CumAvailable(m) > 0： +∞
```

- `CumAvailable(0)=AvailableCash` 直接衔接 §6.2，消除"从现金余额还是 AvailableCash 起算"的歧义；`NetBurn_i` 已是裁剪后的非负值，故 `CumAvailable` 单调不增，首次 crossing 唯一，插值有定义。
- 若 `k+1 > horizonMonths` 窗口内未 crossing，记 `+∞`（与上方第二分支一致）。
- **场景 A 步 3**：开局现金 `$120k = 12_000_000 cents`；5 人月薪承诺后 `CommittedBurn` 上升、`AvailableCash` 与 `runwayMonths` 下降（可观察）；研发期无销售 `ExpectedIn≈0` 时 `runway ≈ AvailableCash / CommittedBurn`。

### 6.2 承诺扣除后的可用现金（AvailableCash）

```
AvailableCash = LedgerAccount.cashBalanceCents
              − Σ(未兑现的承诺支出，horizon 内)   // one_off: amountCents − realizedCents
                                                   // monthly: (amountCents × 剩余周期数) = totalPlannedCents − realizedCents
              − Σ(未结算应付，horizon 内)          // Payable.amountCents − settledCents
              + Σ(高置信应收，可选)                // TUNING FIN-T2：是否计入应收
```

- 这是玩家"真正能动用的钱"，区别于账面现金；UI 必须同时显示 `cashBalanceCents` 与 `AvailableCash`。
- `AvailableCash < 0` 触发 `COMMITTED_EXCEEDS_CASH` 原因码。
- **F-04 衔接**：`AvailableCash` 同时是 §6.1 `CumAvailable(0)` 的起点，两节口径一致。

> **窗口边界澄清（ADJ-2026-11-22-05 §1，2026-11-22 追加）**
> 「horizon 内」应理解为**「截至 horizon 末端仍未兑现的承诺」**，而非「兑现日期落在 horizon 内的承诺」。具体地，`endAt < horizonStart` 且 `realizedCents < totalPlannedCents` 的承诺（窗口前已到期仍未付清），须在窗口起点**全额扣减** `amountCents − realizedCents`（`monthly` 为 `totalPlannedCents − realizedCents`）。
> 理由：已到期未兑现的承诺是**确定发生**的现金流出，仅时点延迟；排除它会高估可用现金，进而使 HRB 单向可行性检查放行实际付不起的预算（安全方向错误）。
> 同一承诺**不得**既在"窗口前补扣"又在"窗口内按月扣"（二者互斥）。本条为既有口径在边界上的延伸，**不构成语义变更、不升 `financeFormulaVersion`**。
>
> **已知缺陷登记（ADJ-2026-11-22-05 §2，处置已由 ADJ-2026-11-22-11 取代）**：`AvailableCash` 已扣除 horizon 内承诺，而 §6.1 `CumAvailable(m)` 又以 `NetBurn_i`（其中已含同一承诺）逐月递推，构成**对同一承诺的双重扣减**，使 `runwayMonths` 系统性偏短（算例：现金 700,000、月净烧 100,000、horizon 6 → 实算 1 个月，真实 7 个月）。该缺陷确认存在，登记为 **OPEN-F3′**（§20）。
>
> ⚠️ **处置结论已变更（ADJ-2026-11-22-11）**：原判"**不在 P1 修正**"作废，现升级为 **G1 阻断项**，必须在 G1 验收前修复。升级理由：`runwayMonths` 直接驱动危机状态机（`LOW_RUNWAY` / `warning` / `critical` / 补救窗口），错误跑道会让"真实 7 个月的公司在第一个月被宣布濒临破产"，玩家据此裁员砍项目，把假危机变成真危机（自我实现）。**这不是 UI 口径说明能兜住的**——原"P1 UI 须加口径说明"的兜底同步取消。
>
> 修复方向（见 ADJ-11 §2 / §R-2）：三概念分离——`CashBalance`（账本唯一来源）／`AvailableCash`（扣全部未兑现承诺，**仅供 HRB，不得放松**）／`RunwayMonths`（起点 = `CashBalance`，支出侧只计一次，**不得重复扣同一承诺**）。新增不变量 **`INV-RUNWAY`**：任一承诺 `inclusionMode` 恰为 `IN_FORECAST` 或 `RESERVED_ONLY` 之一，且其在 `runwayMonths` 支出侧被计入**恰好一次**（要么经 `netCashByMonth`，要么经承诺表直接加，**不得两者都加**——这是双重扣减的唯一形态）。⚠️ `inclusionMode` **不决定** `AvailableCash` 扣不扣，后者对每笔未兑现未释放承诺恒扣一次。危机阈值 `runwayWarningMonths` / `runwayCriticalMonths` / `remediationWindowDays` 必须**同批重标定**（ADJ-11 §R-3），且须满足两条自洽约束：`critical × 30 ≤ remediationWindowDays`、`warning ≥ critical × 1.5`。

### 6.3 预测区间（netCashByMonth）— F-05 整改

四个（扩展为六个）置信系数的方向固定如下，取值均为 `TUNING`（FIN-T3，默认候选值待校准）；所有三带**统一包含应付**（expected payable）：

| 系数 | 方向 | 语义 | 默认候选值（TUNING，待校准） |
|---|---|---|---|
| `p_in_low` | `<1` | 下行情景流入折扣 | 0.8 |
| `p_in_high` | `>1` | 上行情景流入放大 | 1.2 |
| `p_out_low` | `<1` | 上行情景承诺支出折减（少支出） | 0.9 |
| `p_out_high` | `>1` | 下行情景承诺支出放大 | 1.1 |
| `p_pay_low` | `<1` | 上行情景应付折减 | 0.9 |
| `p_pay_high` | `>1` | 下行情景应付放大（原语义修正：非"折减"） | 1.2 |

```
Cash_m(worst/low) = Cash_0 + Σ_{i≤m}(ExpectedIn_i × p_in_low  − CommittedOut_i × p_out_high − ExpectedPayable_i × p_pay_high)
Cash_m(expected)  = Cash_0 + Σ_{i≤m}(ExpectedIn_i            − CommittedOut_i           − ExpectedPayable_i)
Cash_m(best/high) = Cash_0 + Σ_{i≤m}(ExpectedIn_i × p_in_high − CommittedOut_i × p_out_low  − ExpectedPayable_i × p_pay_low)
```

- **F-05 修正点**：① `p_pay_high>1` 用于放大下行情景应付（原"折减"语义矛盾已消除）；② best 带**显式含应付**并以 `p_pay_low<1` 折减（原"应付不发生"未声明的错误已消除）；③ 三带全部含 `CommittedOut` 与 `ExpectedPayable`，系数方向保证 `Cash(low) ≤ Cash(expected) ≤ Cash(high)`，UI"最好/预期/最差"三带可比。
- `Cash_0` 取 `LedgerAccount.cashBalanceCents`；`lowCashDate` 取 `Cash_m(low)` 首次跌破警告线之月。
- FIN-T3 同步：预测系数由 4 个扩展为上述 6 个，方向固定、取值 TUNING。

### 6.4 预警阈值与滞后（TUNING，锚定现有实现）— F-06 / F-12 整改

> 表中所有数值均为**默认候选值（TUNING，待校准）**，仅作实现初值，不构成终值（F-12）。`hrbVerdictWarn/Cut` 虽引用 D-01 §6.2.1 锚点，按 D-01 口径同样标注为默认候选 TUNING。

| 参数 | 默认候选值（cents / 业务值，TUNING 待校准） | 口径 |
|---|---|---|
| `cashWarningThresholdCents` | `400_000` = **$4,000** | L1 现金警告线：现金**跌破** → `watch/warning` + 顶部横幅 |
| `cashRecoveryThresholdCents` | `600_000` = **$6,000** | 恢复线：**严格高于**警告线（`> warning`），现金**回升超过**才脱离预警 → 真实滞后带 `$4,000~$6,000`（F-06） |
| `cashBankruptThresholdCents` | `0` = **$0** | L2 破产参考线：现金低于 0 即负现金 → `critical`；**负现金且窗口耗尽才破产**（AND，F-03） |
| `budgetOverrunWarnAt` | `1.0`（比例） | 预算超支警告（消费 D-01 `ratio`） |
| `runwayWarningMonths` | TUNING（默认候选值 3） | 跑道低于此月数 → `watch` |
| `runwayCriticalMonths` | TUNING（默认候选值 1） | 跑道低于此月数 → `critical` |
| `remediationWindowDays` | TUNING（有限，默认候选值 60） | `critical` 起补救窗口，**必须有限**；重入不重置（F-06） |
| `hrbVerdictWarn` / `hrbVerdictCut` | `1.0` / `1.2`（D-01 §6.2.1；默认候选 TUNING） | HRB 可行性结论阈值 |

**F-06 滞后带机制**：
- 下行穿越 warning 线（$4k）→ 进入 `watch/warning`；上行必须穿越 recovery 线（$6k）→ 才回到 `healthy`。现金在 `$4k~$6k` 之间维持当前态，不反复切换横幅（对比 V0.1 中两线同为 $4k 的零宽度滞后）。
- `critical` 的恢复同样以 recovery 线（$6k）为准；短暂越过 $6k 后又跌落不会刷新 `remediationDeadline`（沿用原截止日）。

> 单位纪律：任何新 cents 常量必须同时写业务值与代码单位值，并做量级自检（CODEBUDDY.md §13.1/§13.4）。

## 8. 玩家操作与自动化

### 8.1 玩家授权（生成 `source=player_authorized` 的交易/承诺）

- 创办公司（开局注资 `advance`）、设定 `HRB`/预算承诺。
- 招聘/解雇（薪酬承诺/遣散 `severance`）、追加预算、缩减范围、暂停项目。
- 发起重整、选择补救动作（终止合同、出售资产、裁员、寻求预付款 `advance`）。
- 玩家请求退款、批准合同/分成方案。
- 选择进入/退出沙盒观察态。

### 8.2 系统自动记账（`source=system_auto`）

- 每日销售 `sales_revenue` 与 `platform_fee` 入账、自动窗口退款 `customer_refund`（含按 §5.6 冲回 `platform_fee`）。
- 月末薪酬 `salary`、租金 `office_rent`、税 `tax` 计提。
- 合同里程碑/到期结算、应付到期结算；`advance` 分成抵扣。
- 幂等去重、预测重算、危机阈值探测与预警升级、读档 `replay` 重建。

### 8.3 自动化边界（基线 §13）

默认自动化处理重复记账；玩家只在关键节点（预算承诺、超支应对、危机补救、重整）做有意义决策，不被迫微观管理每笔日常交易。日常交易不打断，重大风险/合同承诺/危机明确提示（通知分级）。

### 8.4 补救动作代价公式（F-07 整改）

> 每类补救动作的输入与代价公式定义如下，使 §9.4"代价预览"可计算、可验收（TC-21）。所有参数为 `TUNING`（默认候选值待校准），公式层禁止读 TUNING，由调用方注入快照。预览值 = 按当前公司数据代入公式的结果，动作确认后据以生成交易 / 更新承诺 / 写入后果。

| 补救动作（Remedy） | 输入 | 现金影响（即期 Transaction） | 代价 / 后果 |
|---|---|---|---|
| `descope`（缩减范围） | 取消工作包剩余预算承诺 `C_rem` | 无即期现金（释放未来 `CommittedBurn`） | 已完成沉没成本不可回收；声誉/质量风险（方向经 D-01/D-02，`OPEN`） |
| `pause_project`（暂停项目） | 暂停工作包剩余承诺 `C_rem` | 无即期现金 | 进度延迟、市场时机风险（方向 / `OPEN`） |
| `cut_staff`（裁员） | 人数 `n`、人均遣散 `severancePerEmployee` | `−(n × severancePerEmployee)` → `severance` 交易 | 即期现金流出；`talentLoss += n`；声誉下降 |
| `sublet_office`（转租） | 月租 `R`、转租比例 `α`、剩余月数 `M` | `+(R × α × M)` 分期入账（每期一笔 `sales_revenue` 或独立类别） | 办公室容量下降，影响后续产能（方向 / `OPEN`） |
| `terminate_contract`（终止合同） | 剩余义务 `O_rem`、违约金率 `penaltyRate` | `−(O_rem × penaltyRate)` → `contract_payment` 交易 | 即期现金流出；声誉下降；控制权可能变化 |
| `sell_asset`（出售资产） | 资产账面值 `V`、折价率 `d` | `+(V × (1−d))` → `asset_sale` 交易 | 资产减少（`restructuringConsequences.assetChanges`） |
| `advance`（寻求预付款） | 预付款额 `A`、分成抵扣率 `advanceRepaymentRate` | `+A` → `advance` 交易 | 形成"未来分成抵扣义务"（§3.4 `Payable`），每期销售按 `advanceRepaymentRate` 抵扣至还清；**无利息、无到期日契约**（§2.2） |
| `restructure`（重整） | 上述动作组合 + 重整方案 | 依组合动作 | 按 §8.5 写入 `restructuringConsequences` |

- `severance` 金额口径：每人遣散费 = `severancePerEmployee`（TUNING 默认候选值待校准），故裁员即期流出 = `n × severancePerEmployee`（cents），以 `severance` 交易入账。
- `advance` 不形成贷款契约：仅以 `Payable` 跟踪抵扣计划，无利息、无信用评级、无到期日（对齐 §2.2 非目标）。
- 前置条件不满足（如现金不足支付遣散费）→ §9.4 置灰并说明（错态）。

### 8.5 重整后果结构（restructuringConsequences，F-07 整改）

把 §3.6 的 `restructuringConsequences` 从无字段 `object` 结构化为：

```
restructuringConsequences: {
  debtCents: int,                                  // 新增/承接的偿还义务（含 advance 抵扣义务余额），>0 表示负债
  assetChanges: [ { assetRef, deltaCents, description } ],  // 资产出售/减值明细，deltaCents<0 表示减少
  reputationDelta: int,                            // 声誉档位变化（有符号，量级 TUNING）
  talentLoss: int,                                 // 流失员工数（≥0）
  controlChange: enum{none,reduced,shared},        // 控制权变化（如让渡 / 共管），来自合同 controlLevel 语义
  summary: string                                  // 玩家可读的一句话后果
}
```

**写入规则**：
- 进入 `restructuring` 或 `bankrupt` 时，按 §8.4 已执行的补救动作累积写入：出售资产→`assetChanges`；预付款/终止合同违约金→`debtCents`；裁员/转租失败→`talentLoss`；声誉类代价→`reputationDelta`；控制权让渡→`controlChange`。
- 写入随 `CrisisState` 持久化（§3.6、§11.2），并进入 `history` 供审计。

**玩家可见预览**：
- §9.4 危机面板在动作确认前调用 §8.4 公式计算预览值，并在"重整后果清单"区显示拟写入的 `restructuringConsequences` 各字段（汇总为 `summary`）；确认执行后与实际写入比对。
- **TC-14 判据**：重整成功脱离 `critical` 后，`restructuringConsequences` 必填且至少 `debtCents>0` 或 `assetChanges` 非空或 `talentLoss>0` 或 `controlChange≠none` 之一成立（即"非免费复活"），且玩家在危机面板可见该后果清单。

## 9. UI/UX 页面结构级规格

> 结构级（非像素级）：页面、区块、状态、空/错/跳转。每个页面回答基线 §13 四问。
>
> **F-10 全局口径**：所有页面读取现金一律经账本派生视图（`LedgerAccount.cashBalanceCents`、`AvailableCash`、`CashForecast`、`CrisisState`）；`Company.cash` 不是 UI 读源。

### 9.1 财务概览（Overview）

- **区块**：现金余额（`cashBalanceCents` 派生视图）+ 可用现金（`AvailableCash`）；跑道月数（含"为什么变了"：招聘/追加预算/返工）；顶部现金警告横幅（现金 < 警告线时）；本月净流；最近 5 笔交易。
- **状态**：`healthy`（无横幅）、`watch/warning`（黄色横幅 + 原因码）、`critical`（红色横幅 + 倒计时）、`bankrupt`（破产态横幅）。
- **空态**：未创办公司→"尚无账本" + 跳转创办流程。
- **错态**：INV-1 校验失败→"账本不一致" + 跳转审计/读档修复入口，禁止继续入账（F-01 修复后不再因正常退款误触发）。
- **跳转**：→现金流、→预测、→危机面板。

### 9.2 现金流（Cashflow）

- **区块**：交易流水表（日期/类别/现金流三分/金额/来源/关联实体下钻），按类别与时间段筛选；经营/投资/融资三栏汇总。
- **空态**：无交易→"尚无交易记录"（开局注资后至少 1 笔）。
- **错态**：筛选无结果→"该时间段无交易"；加载失败→重试。
- **跳转**：点交易→关联实体（销售/合同/项目/员工）；→预测。

### 9.3 现金预测（Forecast）

- **区块**：跑道曲线（预期/最好/最差三带，§6.3 统一含应付）、`lowCashDate`、承诺支出构成（薪酬/租金/项目/合同）、假设参数（TUNING，高级可展开）。
- **空态**：无承诺→"尚无承诺支出，跑道无限"。
- **错态**：预测依赖缺失（如 `BudgetCapacity` 未解析）→标 `OPEN` 提示"数据未就绪"，不显示伪造曲线。
- **跳转**：→概览调整预算；→危机面板。

### 9.4 危机面板（Crisis）

- **区块**：当前等级 + 原因码列表（"为什么"）；补救窗口倒计时（`remediationDeadline`，重入不重置）；可用补救动作卡片，每张按 §8.4 显示可计算的代价/风险预览（对现金、跑道、债务、声誉、人才、控制权）；重整后果清单（§8.5 `restructuringConsequences` 预览）；沙盒观察开关。
- **状态**：`warning`（预警说明 + 建议）、`critical`（强制呈现补救动作 + 倒计时）、`restructuring`（方案执行进度 + 后果）、`bankrupt`（终态 + 观察选项）。
- **空态**：`healthy`→"财务状况健康" + 最近一次脱离危机的记录。
- **错态**：补救动作前置条件不满足（如现金不足无法裁员补偿）→置灰并说明原因。
- **跳转**：→现金流查原因、→预测看后果、→项目页执行缩减范围。

## 10. 异常与边界

### 10.1 负现金（NEGATIVE_CASH）— F-03 统一

固定结算允许负现金并触发 `critical`（BR-9）；自主支出被拒（`FIN_INSUFFICIENT_CASH`）。**负现金不直接等于破产**（AND）：仅当 `remediationDeadline 到期 AND 现金仍 < 0（负现金未解）` 才进入 `bankrupt`；负现金但窗口未耗尽仍处 `critical` 可补救。不采用"负现金或窗口耗尽即破产"的 OR 口径（TC-12）。

### 10.2 重复记账

幂等键去重（BR-7）；跨期退款靠 `transactionByKey`。重复提交返回原交易且不改变现金；测试必须锁定（TC-03/TC-04）。

### 10.3 跨月承诺 — F-02 整改

`BudgetCommitment.startAt/endAt` 跨月时，每月按 `period=monthly` 生成一笔兑现交易（幂等键含承诺 id + **月份**，如 `<commitmentId>:<YYYY-MM>`）；`realizedCents` 逐月累加，上限为 `totalPlannedCents = amountCents × periodCount`；中途取消只停止未来周期兑现，已入账不冲回；`monthly` **未取消时**必须恰产生 `periodCount` 笔兑现交易（6 个月 = 6 笔，TC-19）；**取消后**实际兑现笔数为 `realizedPeriods < periodCount`，`state` 置 `cancelled`（见 §4.1 末）。

### 10.4 破产后继续观察（沙盒）— F-08 整改

`sandbox_observe` 态规则（与 M1.2 破产命令守卫对齐，UI 细节 `OPEN-F2`）：

- **账户 state**：`frozen`（非 `closed`；`closed` 仅在最终清算解散时置位）。
- **可 post 交易范围**：既有固定结算（`salary`/`office_rent`/`tax`/退款兑现/合同到期）继续按规则 `postTransaction`（允许负现金），由 `source=system_auto` 产生；棚内世界/AI 继续运行。
- **义务停止**：停止新增玩家义务——`source=player_authorized` 的新支出交易与新 `BudgetCommitment`（新招聘/新项目/追加预算）被命令守卫拒绝；不新增义务，既有义务按到期继续兑现。
- **AI 破产处理**：AI 公司进入 `sandbox_observe` 由 `DailyScheduler` 破产检查按同一状态机（S-FIN-3）自动进入，无需玩家选择；进入后账户同样 `frozen`，继续固定结算，不再生成新的扩张型战略动作（其破产前恢复动作 `SELL_ASSET→RESTRUCTURE→CLEARANCE` 属 `critical/restructuring` 阶段，不属观察态，对齐迁移 §2.20）。
- **玩家选择**：是否继续观察由玩家决定（基线 §12）；"退出观察"仅恢复玩家可见性，不改变世界继续运行的事实。

### 10.5 读档恢复 — F-09 整改

`replay` 从持久化 `Transaction[]` 按 INV-1（对全部交易求和，`status` 不参与）重建所有账户余额与索引；不一致则拒绝读档并报 `LEDGER_INCONSISTENT`。

- **账本**：以重建为准（权威事实来自交易）。
- **危机态**：以持久化的 `CrisisState`（`state/enteredAt/reasonCodes/remediationDeadline/crisisRulesVersion/history/restructuringConsequences`）为准恢复，**不**由重建账本重新推导危机等级（避免阈值 TUNING 跨版本变化导致读档漂移）；读档时按 `crisisRulesVersion` 回放阈值判定以校验一致性，但版本内不自相矛盾时以持久化值为权威。
- **预测**：`CashForecast` 可按重建账本重算（不持久化预测快照作为事实），保留 `formulaVersion/assumptionsVersion`（对齐 P0-B S2、§11.3）。
- 三者关系：账本重建 → 危机态按版本恢复 → 预测按版本重算；各带各自版本锚点，互不漂移。

## 11. 存档要求

### 11.1 不可变（append-only）

- `Transaction` 入账后不可编辑、不可删除；冲销以新增反向交易实现（BR-6），且原交易与反向交易均计入 INV-1 求和（F-01）。
- `status` 只允许 `posted → reversed` 单向；无 `pending → posted` 中途态在 P1（退款批次 `pending` 属产品运营，未兑现前不是交易）。

### 11.2 可审计

- 每笔交易保存 `idempotencyKey, day, category, cashFlowType, amountCents, balanceAfterCents, referenceId, source, reversalOf`（`status` 为审计标记）；可重放、可对账、可下钻因果。
- `CrisisState.history`、原因码、`crisisRulesVersion`、`restructuringConsequences` 一并持久化，支撑"破产非随机"的审计叙事（F-09、F-07）。

### 11.3 版本迁移

- 沿用存档 v3 框架与幂等键跨期保留（`finance-service.ts:L43-L48,L250-L259`）。
- 迁移为旧交易补 `cashFlowType`（按 §3.9 TUNING 映射）、`source`（默认 `system_auto`，开局注资标 `player_authorized`）、`reversalOf`；保留 `idempotencyKey`/`transactionByKey`，不破坏跨期幂等。
- 迁移后跑 `replay` 按 F-01 求和口径校验 INV-1；`formulaVersion`/`assumptionsVersion` 随存以保证预测可复现（OPEN-F4）。
- **F-09**：新增 `crisisRulesVersion` 随 `CrisisState` 持久化（对齐预测版本做法）；读档按该版本回放危机阈值判定，不套用当前 TUNING 阈值。旧档无该字段时以迁移时的规则版本回填。

## 12. 性能要求

- `postTransaction`：均摊 O(1)；依赖 `idempotencyIndex`、`transactionById`、`transactionByKey` 索引，禁止按 id/category 全表扫描。
- `bulkPostTransactions`：沿用增量回滚（记录起始长度与余额快照，失败截断），不整表复制（迁移 §2.3 实现约束）。
- `pruneIdempotency`：30 天保留策略，避免每日 O(n)；`transactionByKey` 不随清理删除。
- `CashForecast` 重算：仅 L0 探测 + 条件变更时重算，复杂度 O(`horizonMonths × commitments`)，不进逐日热路径。
- `replay`：仅读档时 O(n)，应为可接受的加载期成本；目标上限 `TUNING`（FIN-T5，如十万级流水加载 < 2s，待编码基准校准）。
- 性能优化不得改变玩家可见的经济因果（系统地图 §4.8/基线约束）。
