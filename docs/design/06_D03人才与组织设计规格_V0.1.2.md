### 0.6 边界规则的最终统一（ADJ-2026-11-22-09，**推翻 §0.4 与 ADJ-04/ADJ-07**）

> 触发：V0.1.4 复审的 D03-41 —— 入职侧（月末入职付整月）与离职侧（月末离职付 0）对同一个月的处理相反。顺着这条线检查反方向，发现 ADJ-07 本身产生了**可套利漏洞**。

#### 0.6.1 漏洞（为什么必须推翻）

```
员工 2/15 入职，连续工作到 4/30（4 月最后一天 = 结算日）
玩家在 4/30 解雇
⇒ ADJ-07：effectiveMonth = 2026-04 ⇒ 4 月不计
⇒ 该员工 4 月出勤 21 个工作日，工资 0
```

玩家省下一整月工资，且**按天可控、可对全团队重复**。在现金压力为核心的游戏里，这等于把工资系统变成可选项。这是我前两轮都漏掉的，因为每一轮都只在"是否服从 FIN"这个维度上验证。

#### 0.6.2 现行规则（唯一口径）

> **某自然月内只要有 ≥1 天在职（`occupied`），该月即计 1 个完整周期、全额兑现。**
> **停付唯一入口**：`cancelCommitment(c, effectiveMonth = monthOf(endDay) + 1)` —— 自离职月**次月**起停，**离职当月照常兑现**。

| 场景（6 笔 × 500,000，起始 2026-02-15） | 笔数 |
|---|---|
| 未取消 | 6 |
| 离职 04-10 / 04-01 / **04-30（结算日）** | **均为 3**（02、03、04） |
| 离职 03-31 | 2（02、03） |
| 离职 02-15（起始月内） | 1（02） |
| **入职 04-30** | 首月 1（04） |

#### 0.6.3 与旧结论的差异（**审计锚点已变**）

| 旧（ADJ-04 / ADJ-07） | 新（ADJ-09） |
|---|---|
| 离职 04-10 ⇒ **2 笔** | 离职 04-10 ⇒ **3 笔** |
| 离职 04-30（结算日）⇒ 2 笔 | ⇒ **3 笔** |
| 离职 02-15（起始月首日）⇒ 0 笔 | ⇒ **1 笔** |
| 入职 04-30 ⇒ 1 笔（特例） | ⇒ 1 笔（通用规则的自然结果） |
| FIN 锚点 `effectiveMonth=2026-04 ⇒ 2 笔` | `effectiveMonth=2026-05 ⇒ 3 笔` |

> **任何仍断言 2 笔的测试、算例、报告都按已作废口径，须改。** 判 FAIL 的唯一标准是"碰了该月却 0 笔"。

## 4. 状态与生命周期

### 4.1 `PersonStatus`（人物状态，派生）
`available` 未任职 · `assigned` 已任职且有至少一个活跃分配 · `on_leave` 任职但无分配 · `departed` 已无 occupying Employment（仍为产业中的人物）。

> **权威层级（D03-14 关闭）**：`Person.status` **不是独立存储的权威**，唯一权威是 §4.3 派生式（输入 = `currentEmploymentId` 与活跃分配数）。下表为**派生结果的转移表**（免责说明），不新增写者。

| 当前 | 触发（均经 Employment 变更或 Assignment 变更） | 目标（派生结果） | 条件 | 可逆 |
|---|---|---|---|---|
| —（新建） | `hire` 确认 → 新建 occupying Employment | `assigned`（有分配）或 `on_leave`（无分配） | §4.3 | 是 |
| `available` | `hire` | 同上 | | — |
| `assigned` | 全部 `Assignment` 失效 / 撤分配 | `on_leave` | 活跃分配数 = 0 | 是 |
| `on_leave` | 新增活跃 `Assignment` | `assigned` | 活跃分配数 > 0 | 是 |
| `assigned` / `on_leave` | `Employment`→`resigning` | **不变**（仍占人，有分配则 `assigned`、无分配则 `on_leave`） | `occupiesPerson` 仍 true | — |
| `assigned` / `on_leave` | `Employment`→`terminated` / `contract_ended` | `departed` | `occupiesPerson` 置 false | **否**（再雇需新建 Employment） |
| `departed` | 重新 `hire` | `assigned`/`on_leave` | `currentEmploymentId=null` ⇒ 新建 Employment；`rehireCount+=1` | — |

**退休（D03-13 关闭）**：退休**不是** `Person.status` 的第三种写者。退休判定发生在每日 tick：
```
if age >= retireAge and no Employment with status == resigning:
    triggerResign(employment, reason = 'retire')   # 与自愿离职同路径：active → resigning
# resigning 期满 ⇒ terminated(terminationKind = contract_end) + emit(retired)
# Person.status 随之由 §4.3 派生为 departed
```
即"退休 = 触发 `resigning` 的一种原因"，与 §4.2 `resigning` 期满唯一的转移路径一致，`Person.status` 仍**只由 Employment 派生**（不存在"直接写 departed"的路径）。

**不可退出状态反证**：`departed` 为终态但不冻结技能——重新入职读同一 `SkillProfile`（R-D03-1 反证）；`assigned` 不锁死——撤分配即回 `on_leave`；`resigning` 有唯一出口（`noticeDays` 满 → `terminated`，或挽留 → `active`），不存在"永久 resigning"。

### 4.2 `EmploymentStatus`（任职状态）

```
probation ──(probationEnd 到期 ∧ morale ≥ probationFailMorale)──▶ active
    ├──(probationEnd 到期 ∧ morale <  probationFailMorale)──────▶ terminated(terminated)
    └──(玩家提前解雇)────────────────────────────────────────────▶ terminated(terminated)
任意 occupying 态 ──(自愿辞职 / 退休 / 离职判定命中)──▶ resigning ──(noticeDays 满)──▶ terminated
任意 occupying 态 ──(玩家解雇)──────────────────────────▶ terminated(terminated)  ← 立即
active ──(合同自然到期且不续约 / 到龄)──▶ contract_ended
resigning ──(挽留成功：调薪且 morale 回升)──▶ active
```

**试用期截止日（C12，唯一口径）**：

```
probationEndDay(employment) = startDay + probationMonths × workingDaysPerMonth
# 到达判据：day ≥ probationEndDay ⇒ 试用期到期（进入"通过/失败"判定）；day < probationEndDay ⇒ 仍在 probation
# 全部按工作日制；不存在"probationMonths × 30 自然日"的近似写法（V0.1.1 的该表述已删除）
```

| 当前 | 事件 | 目标 | `occupiesPerson` | 说明 |
|---|---|---|---|---|
| —（new） | hire | `probation` | true | `probationMonths`（TUNING） |
| `probation` | 到期且通过 | `active` | true | `renewalCount+1`；重建薪资承诺至新 `endAt`（§7.2） |
| `probation` | 到期且失败 / 提前解雇 | `terminated` | false | `terminationKind=terminated`；遣散触发 |
| `active` | 自愿辞职 / 退休 / §6.7 命中 | `resigning` | true | 写 `noticeStartDay`；**仍可产出至 `endDay`**（§6.1 Z2），不得新增分配（RULE-09） |
| `resigning` | `noticeDays` 满 | `terminated` | false | `terminationKind = voluntary`（辞职）或 `contract_end`（退休） |
| `resigning` | 挽留成功 | `active` | true | 需 §6.3 调薪且 morale 回升 |
| `active` | 玩家解雇 | `terminated` | false | 立即；遣散（§6.4） |
| `active` | 合同到期 / 到龄 | `contract_ended` | false | 结算同 `terminated` |
| `terminated` / `contract_ended` | — | — | false | **终态**，再雇 = 新建 Employment |

**不可退出状态反证**：两个终态禁止改回 `active`（防"幽灵在职"重复计薪与重复 `Cap_d`）；`resigning` 保证"人走前有通知窗口"（E3）。

### 4.3 两状态机一致性（唯一派生式）
`Employment.status` 是 `Person.status` 的**唯一驱动**：
```
Person.status(e) =
    if currentEmploymentId == null                                  → available            # 从未任职 / 已被本公司移出
    else if Employment(currentEmploymentId).occupiesPerson == false  → departed             # 终态 Employment，§10 E4 修复路径
    else if Σ 活跃分配 > 0                                          → assigned
    else                                                            → on_leave
```
- 注：`departed` 表示"已无 occupying Employment"；同时该 `Person` 仍可在产业中存在（进候选池）。
- 禁止直接写 `Person.status`。与派生式不符（含 INV-2 冲突）时，**不在读路径上"剔除该人"**：由 §4.3 重算修正派生值，并按 §7.1 `D03_PERSON_STATUS_DESYNC` **返回该人 + `available=false` + 告警 + 修复建议**（C14；不得使其从 `members` 中消失）。

## 5. 业务规则

### 5.1 分离与唯一占用（R-D03-1）
- **RULE-01**：`Person` 与 `Employment` 是 1:N；任一时刻最多一条 `occupiesPerson=true`。
- **RULE-02**：`hire` 时若该 `personId` 存在 `occupiesPerson=true` 的 Employment（**不论 `resigning`**）→ 拒绝 `D03_ALREADY_EMPLOYED`。
- **RULE-03**：跳槽 `transfer(personId, toCompanyId)` 只关闭旧 Employment（写 `endDay`、`occupiesPerson=false`）、新建新 Employment，`personId` 不变、`SkillProfile` 不重建。
- **反证锁**：以 `personId` 建唯一索引于 `occupiesPerson=true` 的 Employment（写时）；读档另做全库唯一性校验（§11 S1、§10 E4）。

### 5.2 招聘规则
- **RULE-04**：只能从 `Candidate` 池按 `candidateId` 招；不可"凭空造人"。
- **RULE-05**：候选池规模上限 `candidatePoolSize`（TUNING），每游戏日刷新一次（§12）；若候选已被任一公司 `occupiesPerson=true` 雇佣，不得出现（防挖角，O1）。
- **RULE-06**：入职后 `currentEmploymentId` 指向新 Employment；同人不可同时在池中两份。

### 5.3 分摊上限
- **RULE-07**：单人 `Σ_{活跃分配 p} allocationRatio ≤ 1.0`，超出拒绝 `D03_OVER_ALLOCATED`。
- **RULE-08**：同一 `(employmentId, projectId, discipline)` 同一时刻仅一条有效 `Assignment`；跨学科可多条（§3.4 注）。
- **RULE-09**：`resigning` 的 Employment **不得新增分配**，已有分配保留到 `effectiveTo` 或 `endDay`。

### 5.4 离职 / 解雇规则
- **RULE-10**：**自愿离职 / 退休 / 离职判定**均只经 `active → resigning`（§6.7/§4.1），**不允许 0 通知**。
- **RULE-11**：**解雇**是玩家显式命令：`terminated`（立即）→（a）终止全部 `Assignment`（`effectiveTo=当日`）、（b）`cancelCommitment(salaryCommitment, effectiveMonth = monthOf(endDay) + 1)`——按 FIN §4.1"中途取消只停止未来周期"（"未来"= 次月及以后，ADJ-09），**离职当月照常计 1 笔**（§6.3、§7.2）、（c）一次 `one_off` 遣散承诺并兑现（§7.2）。
- **RULE-12**：解雇的**士气外溢**：同项目同学科在职者 `moraleModifier -= k_layoffSpill`（TUNING），写 `PersonEvent`。
- **RULE-13**：解雇**不得使项目某学科 `team_d=∅` 却静默**——立即告警并推 Project（§10 E2）。

### 5.5 士气与离职诱因
- **RULE-14**：`morale = clamp(baseMorale + moraleModifier, 0, 100)`；`moraleModifier` 只由 §6.6 单一递推式更新，任何调整（调薪、外溢）都作为 `Δ` 输入，不直接写 `morale`。
- **RULE-15**：离职诱因**仅四类**（可追溯）：① `morale` < `resignMoraleThreshold`；② 薪资 < `marketSalary(role, region)` 的 `underpayRatio`（§6.3）；③ 所在项目失败/取消（`project_failed`）；④ 长期无分配（`idleDays > idleWarnDays`）。**退休属 `contract_end` 一类，不进入随机离职判定**（§4.1 确定性触发）。P1 不引入外部挖角、不引入私人原因。
- **RULE-16**：`baseMorale` 长期下降不回弹到原值——离职后 `baseMorale` 保留，进新公司时按 `startingMoraleFloor` 下限（TUNING）。

### 6.2 多项目分摊：`share` / `eff_share` / `allocationLoad_d`

> **命名登记（C2/D03-02）**：本节自有量 **`allocationLoad_d`**，与 Project §5.3-2 的 `burden_d`（单位：天）**无任何关系、不同量纲、不同用途**；D-03 全文不定义 `burden_d`。

```
# 定义域：对每个 (e, p, d)，p 为“该人所属的项目”
allocs(e, d)   = { a ∈ Assignment : a.employmentId = e ∧ a.discipline = d ∧ a.projectId = p
                   ∧ 有效 : a.effectiveFrom ≤ day ≤ (a.effectiveTo ?: +∞) }
# 显式空集分支（D03-11）：allocs(e,d) = ∅ ⇒ share(e,p) := 0（公式分支，不是注释）
share(e, p, d) = 0                                   if allocs(e, d) = ∅
               = a.allocationRatio / Σ_{a' ∈ allocs(e,d)} a'.allocationRatio   otherwise
# 性质：share ∈ [0,1]；对固定的 (e, d)，在全部项目上求和有 Σ_{p} share(e,p,d) = 1（当 allocs≠∅ 时）。
# 分母范围（C16）：分母 = allocs(e,d) 的**全体**分配，即该人该学科在**全部项目**上的分配之和，
#   **不是**"该项目内的分配"；否则 share ≡ 1。
# 反证锁（C16）：若实现把分母改成"该项目自身的分配" ⇒ share ≡ 1 ⇒ effort > 1（§6.8）⇒ FAIL。

# 单人产能可用系数（P1 冻结疲劳/请假）
eff_share(e, p, day) = share(e, p, d) × fatigue_or_leave_factor(e, day)
fatigue_or_leave_factor(e, day) = 1                  # P1（OPEN-D03-3）；D-03 不外推
# 定义域：eff_share ∈ [0,1]；求和范围仅在语义位置显式标注（见 §6.8，不在此处给“总和”）

# 项目学科级“分配负荷”（D-03 自有量，无量纲，仅 UI / 成本视角；不参与 Cap_d）
allocationLoad_d(project, day) = ( Σ_{e ∈ T_d} eff_share(e, project, day) ) / max(1, |T_d|)
# 其中 T_d = { e : ∃ a ∈ teamRefs 的 Employment，a 是 e 在 project 上、学科为 d 的活跃 Assignment }
# ε 分支：T_d = ∅ ⇒ allocationLoad_d = 0；max(1,·) 防除零
```

- **`T_d` 与 `team_d` 的关系（必须分清）**：`T_d` 只是"该项目该学科有分配的 Employment"（用于份额与 UI）；**`team_d`（`Cap_d` 的成员集）由 Project §6.2 决定，可为 `T_d` 的超集**（如 `code` 技能者未被分到 `code` 仍进 `team_code`）。二者**不得互相替代**。
- **`allocationLoad_d` 的用途**：仅 UI（"程序组 6 人、满负荷、分布 2 个项目"）与 P2 `costPerUnit_d` 细化；**不参与 P1 `Cap_d`，不用于瓶颈排序**（瓶颈排序由 Project 的 `burden_d = remainingWorkUnits_d / max(ε, Cap_d)` 负责，D-03 只供 `Cap_d` 的输入）。
- **P1 不乘 `eff_share`**：P1 采用 Project §6.2 原式。`Cap_d^share = k_output × Σ[f_skill × eff_share]` 为 P2 候选，**不是 D-03 公式**。
- **版本闸门（D03-10 关闭）**：在 `projectFormulaVersion` 升级且主 AI 裁定前，**D-03 不得在任何接口向 Project 返回 `effShare`/`allocationLoadD` 用于 `Cap_d`**；§7.1 `PersonnelProjection.effShare` 保留为 D-03 内部字段，标注 `notForCap: true`，Project 不得读取。

| 名 | 量纲 | 定义者 | 用途 | 调用方注意 |
|---|---|---|---|---|
| `Cap_d` | workUnits/day | Project §6.2 | 派工、工期、成本 | D-03 只供输入 |
| `burden_d` | **天** | Project §5.3-2 | 瓶颈 `argmax` | **D-03 不定义**；禁止用 `allocationLoad_d` 顶替 |
| `allocationLoad_d` | 无量纲 [0,1] | 本文 §6.2 | UI/成本视角 | 不参与 `Cap_d`、不参与瓶颈 |

### 6.3 招聘周期 / 周期成本 / 薪资定价

```
# 招聘周期
recruitLeadDays(candidate) = baseLeadDays + k_lead × 1[seniority == senior]         # TUNING
arrivalDay                 = hireConfirmDay + recruitLeadDays(candidate)
# arrivalDay > candidate.expiresAtDay ⇒ 不可招（D03_CANDIDATE_EXPIRED）

# 招聘一次性成本（C9/D03-04 关闭：P1 确定裁定）
recruitCostCents = round( negotiatedSalary × hireCostRatio )                        # hireCostRatio 迁移 KEEP（默认 0.15）
# 兑现时序：hireConfirmDay 创建 period=one_off 承诺（§7.2）；arrivalDay（入职日）由 FIN 兑现一次，
#           幂等键 <commitmentId>:one_off；兑现交易 category = project_expense（ref=employmentId）。
#           若 arrivalDay 前候选失效（合同未成立）⇒ cancelCommitment，不产生交易。

# 薪资定价（确定式；V0.1 的“地区趋势/k_marketDrift”已删除，P1 不做市场漂移）
marketSalary(role, region) = baseSalary[role][region] × seniorityMultiplier[seniority]   # TUNING 表
askingRange(candidate)     = [ floorPrice, ceilingPrice ]                          # TUNING（如 market × [0.85, 1.10]）
negotiatedSalary           = clamp(playerOffer, floorPrice, ceilingPrice)
# playerOffer < floorPrice ⇒ 拒绝（D03_OFFER_BELOW_FLOOR），候选保留
# playerOffer > ceilingPrice ⇒ 接受但 morale 不加（防“用钱买士气”）
# 市场漂移（原 `k_marketDrift × 地区趋势`）标 DEFERRED（§18 DEF-7）；P1 市场中位价恒定。
# 地区差异全部由 baseSalary[role][region] 承载（§15 citySalaryMultiplier 迁入该表）。

# 调薪（挽留 resigning 用）
raise(newSalary): 需 newSalary > salaryMonthlyCents
                  ⇒ pendingSalary = newSalary；pendingEffectiveDay = day + k_salaryEffectiveLag
                  ⇒ 到期重建薪资承诺（终止旧承诺、新建至新的 endAt，§7.2）
```

**周期成本与月内/月首边界（C4 / C4′ / D03-26 / ADJ-2026-11-22-09；OPEN-D03-5 关闭口径）**：薪资承诺为**月度周期**，`amountCents = salaryMonthlyCents`，每自然月兑现一笔。

**统一规则（唯一边界口径，取代 ADJ-04/ADJ-07 的旧结论）**：

> 某自然月内只要有 **≥1 天**处于在职状态（`occupied`），该月即计 **1 个完整周期**并按 `salaryMonthlyCents` 全额兑现。停止兑现的唯一入口是 `cancelCommitment(commitment, effectiveMonth = monthOf(endDay) + 1)`——**自离职月的次月起停，离职当月照常兑现**。

- **为什么是"次月停"而不是"当月停"（ADJ-09 §0）**：工资是在当月劳动中**赚取**的，`settlementDay` 只是**记账时点**。若当月停，则"干满整月 + 结算日当天解雇"⇒ 当月工资为 0，玩家按天可控地省下一整月薪 ⇒ **稳定套利**。次月停是唯一同时满足 FIN"只停未来周期"与"不产生免费劳动"的映射。
- **为什么是"≥1 天即整月"而不是按日折算**：P1 不做按日折算（§18 DEF-3）。在整月计费的前提下，只有"碰了就算"能保证无套利。代价是**出勤 1 天也付整月**——方向是**玩家多付**，属可接受的保守粗糙；"能白拿"不可接受。
- **入职侧与离职侧同一规则**（解 D03-41 的不对称）：招聘月只要在职即计 1 笔，与离职月相同。**没有"某个月免费"的情形。**

  | 场景（6 笔 × 500,000，2026-02~2026-07，起始 `2026-02-15`） | `effectiveMonth` | 笔数 | `realizedCents` |
  |---|---|---|---|
  | 未取消 | — | **6**（02–07） | 3,000,000 |
  | 离职 `2026-04-10`（月中） | 2026-05 | **3**（02、03、04） | 1,500,000 |
  | 离职 `2026-04-01`（月初） | 2026-05 | **3**（02、03、04） | 1,500,000 |
  | 离职 `2026-04-30`（**结算日当天**） | 2026-05 | **3**（02、03、04） | 1,500,000 |
  | 离职 `2026-03-31`（结算日当天，前一月） | 2026-04 | **2**（02、03） | 1,000,000 |
  | 离职 `2026-02-15`（起始月内） | 2026-03 | **1**（02） | 500,000 |
  | **入职 `2026-04-30`**（新承诺 `startAt=2026-04-01`） | 未取消 | 首月 **1**（04） | 500,000 |

  > 判据不是"哪天走"，而是"**这个月碰了没有**"。**"结算日"定义**：该月最后一个自然日（`settlementDay(m)`，§6.9；与 `daily-scheduler.ts` 月末判据一致）。
  > **旧锚点作废**：ADJ-04/ADJ-07 的"2 笔"及"起始月首日 0 笔"**均已不成立**，任何仍断言 2 笔的测试须改为 3 笔（ADJ-09 §2）。

- **术语澄清（D03-35）**：`active` 是本文 `EmploymentStatus`（§4.2：`probation`/`active`/`resigning`/`terminated`）的取值，**不是**基线 `EmployeeStatus`（`hired`/`on_leave`/`resigned`/`fired`）的取值。实现代码读映射后的 `EmployeeStatus`，薪资循环判据为 `!== 'hired'`。
- **停付入口唯一（D03-43）**：`cancelCommitment` 是**唯一**判定"是否该停"的入口；`settleCommitment` 只做兑现金额累积，**不判定停付**。实现**不得**在结算侧另加"到 `endDay` 就跳过"的隐式逻辑——那会形成第二个判据，与承诺侧不一致。

  **三条流水线的覆盖范围（D03-36 / R-02）**——**本规则当前在 ① ② 两条流水线上均未生效**（① 结构上无法表达、② 尚未接入）；CODE-06 必须迁到 ② 并停用 ① 的薪资分支：

  | # | 流水线 | 现状 | 本规则适用 |
  |---|---|---|---|
  | ① | `applyMonthlySettlement` 的 Project `costAllocations` 分摊（`category:'salary'` 裸 `postTransaction`，`daily-scheduler.ts:337`） | **已存在** | ⚠️ **无法实现本规则**（见下） |
  | ② | FIN 承诺兑现（`cancelCommitment` 停付 + `settleCommitment` 累积） | `cancelCommitment(c, effectiveMonth)` 已存在但**薪酬结算尚未接入** | **未生效**：CODE-06 必须接入，并保证同一日循环顺序 |
  | ③ | Project 返工/项目成本分摊 | 已存在（CODE-03） | 不适用（与薪资周期无关） |

  > ORD-01 的**权威在仿真编排层**（`DailyScheduler.executeDay` 的步骤序列），D-03 与 FIN 是**依赖方**而非契约签署方。任一方改动结算时点须同步回归本表 ①②。

  > **① 为什么无法实现本规则（重要，CODE-06 必读）**：① 的判据是**结算当日的 `status`**（`status !== 'hired'` 即跳过）。按本规则，"离职 `2026-02-15` ⇒ 2 月计 1 笔"，但 2 月的薪资在 **2 月末结算日**才 post，那一刻该人已 `terminated` ⇒ ① 会跳过 ⇒ 2 月不付。**规则要求的是"当月任一天在职"，而 ① 只能看"结算日当天是否在职"**，二者在"月内离职"与"月内入职"两类情形下必然冲突。
  > 因此：**CODE-06 必须把月薪从 ① 迁到 ②（承诺兑现，`realizedPeriods` 由 `cancelCommitment(effectiveMonth = monthOf(endDay)+1)` 决定）**，并在迁移完成后**停用 ① 的薪资分支**（改由 ② 统一产出 `category='salary'` 交易，幂等键不变 `<commitmentId>:<YYYY-MM>`）。**不得**在 ① 里把判据改成"当月任一天在职"再算一遍——那会与 ② 形成两个事实源、重复入账。

- **"可用但无薪"不是矛盾（D03-39）**：§6.1 Z2 的 `available` 描述**出勤窗口**（能否产出），本节描述**付款窗口**。二者判据不同、结果允许不一致——`endDay` 当天可产出且该月已整月计费（规则已覆盖），不存在"出勤却无薪"的月份。若强行让当天不可用，反与 TC-15「含 `endDay` 当日」相反。
- **例外只剩 FIN 的"已入账不冲回"**：取消不产生反向交易，已 post 的周期保留；`realizedCents + releasedCents == totalPlannedCents` 恒成立。
- 由此，4 月离职（§7.2 算例）= 02、03、04 共 **3 笔**；**6 笔是未取消时的口径**，两者不可混用（ADJ-09）。
- 按日折算（不足整月按日计提）标 `DEFERRED`（§18 DEF-3）；P2 实施时必须重审本节全部边界（尤其"1 天 = 1 月"的多付）。

**地区薪资系数（`citySalaryMultiplier` 的迁入）**：现状 `citySalaryMultiplier(cityId) = City.avgSalaryMultiplier`（`cities.json`，按城市而非地区；缺失默认 1.0）。P1 将 `avgSalaryMultiplier` 视为 `baseSalary[role][region]` 的**城市级乘子**，即实际中位价：
```
marketSalary(role, region, cityId) = baseSalary[role][region] × City(cityId).avgSalaryMultiplier
                                     × seniorityMultiplier[seniority]
```
这样现状 `hireEmployee` 的 `Math.round(salary × citySalaryMultiplier)` 行为在数值上得以保留（迁移 §15）；该数字与 `regionId` 的映射由 §15 声明为 `City.regionId → Region`。

### 6.6 士气变化（**单一递推式**，C3/D03-12）

```
# 每日结算：moraleModifier 为唯一状态量；morale 恒为派生量
Δmorale(employment, day) =
    − k_idlePressure     × 1[Σ 活跃分配 = 0 ∧ 所属 Project 在产]
    − k_projectStruggle  × 1[所属项目存在 paused/descoped 且超过 k_struggleDays]
    + k_projectSuccess   × 1[当日收到项目交付 PASS 事件且质量 ≥ 阈值]      # 事件驱动，一次性
    − k_layoffSpill      × (当日该公司解雇人数 / max(1, 团队人数))

# 唯一递推式（衰减 + 增量 + 上下界，一式计算）
moraleModifier(d+1) = clamp( (1 − moraleRecoveryRate) × moraleModifier(d) + Δmorale(·, d),
                             −moraleModifierBound, +moraleModifierBound )      # TUNING，如 30
morale(d)           = clamp( baseMorale + moraleModifier(d), 0, 100 )           # 派生，恒在 [0,100]

# 基线（d = 0，入职日）：moraleModifier(0) = 0 ⇒ morale(0) = clamp(baseMorale, 0, 100)
# baseMorale 变更（RULE-16）只改基座，不改 moraleModifier；下一日 morale 自动重算。
```

- **只有一条递推式**（V0.1 的"先 `clamp(m + Δ)` 再 `m × (1−rate) + Δ` 两式并存、后式覆盖前式"已删除）。`clamp` 在每一日都生效，`moraleModifier` 不可能越界。
- 无事件日 `Δmorale = 0` 时，`moraleModifier` 按 `(1 − moraleRecoveryRate)` 缓慢回零（回归基线）。
- 士气**不进 `Cap_d`**（R-D03-2、Project §6.2 无 morale 项），只影响 §6.7 离职与 UI。

### 6.7 离职概率（每日）

```
    p_base
      + w_morale  × max(0, resignMoraleThreshold − morale) / 100
      + w_under   × max(0, 1 − salaryMonthlyCents / marketSalary_e)
      + w_idle    × max(0, idleDays − idleWarnDays) / max(1, idleWarnDays)   # idleWarnDays > 0（TUNING 约束）

      + 1[projectFailedFlag] × w_projectFail
dailyResignProb ← clamp(dailyResignProb, 0, p_max)                       # TUNING
# 判定：确定性伪随机 u = hash01(employmentId, day)；u < dailyResignProb ⇒ active → resigning

```

### 6.8 技能成长（与 §7.3 输入路径打通，C8/D03-11）

```
# 输入（§7.3）：Project 日推进产出日志条目 log = (employmentId, discipline, day, out_wp, projectId)
# 由 Project 写入，D-03 只读；无日志当日视为未参与。

# effort：某人在当日某学科上“实际投入比例”之和（按项目求和，定义域显式）
effort(e, d, day) = Σ_{p ∈ P(e,d,day)} eff_share(e, p, day)
    where P(e,d,day) = { p : ∃ log ∈ logs(day) 满足 log.employmentId = e ∧ log.discipline = d
                          ∧ log.projectId = p ∧ log.out_wp > 0 }
# 性质：effort(e,d,day) ∈ [0, 1]（因 Σ_p share(e,p,d) ≤ 1）；无产出 ⇒ P = ∅ ⇒ effort = 0
# 反证锁（C16）：上界完全依赖 §6.2 `share` 的分母按 (e,d) 跨全部项目求和；
#   若实现按 (e,d,p) 分组取分母 ⇒ share ≡ 1 ⇒ effort > 1 ⇒ 成长速率被放大 ⇒ FAIL（TC-21 同测 effort ≤ 1）。
# 说明：eff_share 的求和范围 = “当日该人该学科有 out_wp>0 的那些项目”，不是全部分配项目；
#       因此“被分配但项目当日无产出”不产生经验（与 Project 派工实际投入一致）。

exp[e][d] ← exp[e][d] + effort(e,d,day) × k_expPerDay[level]        # 经验增量
if exp[e][d] ≥ expCap[level] ∧ day − lastLevelUpDay[d] ≥ growthCooldownDays:
    level[d] += 1 (max 5); exp[e][d] = 0; lastLevelUpDay[d] = day; emit PersonEvent(level_up)
```

- **跨学科**（Project OPEN-PROJ-4）：P1 不做转移（`level` 各学科独立，不互相加成），裁定 DEFERRED（§18 DEF-5）。

## 7. 输入输出与系统关系

### 7.1 Project 读取的输入契约（多学科支持，C1）

```
# D-03 侧提供（只读投影，不写 Project；不携带 discipline 判定）
interface PersonnelProjection {
  employmentId: string
  personId: string
  skillLevels: map<Discipline, 0..5>   // 全部五学科；缺键=0（对齐 Project B-9）
  available: boolean                   // §6.1 Z2（仅 Employment 可用性）
  effShare: number                     // D-03 内部字段；notForCap: true（§6.2 版本闸门）
  salaryMonthlyCents: number
}

// 每日一次（tick 前）、玩家改分配后、读档时调用
queryTeam(projectId: string, day: number): {
  members: PersonnelProjection[]   // 与 Project.teamRefs 一一对应，逐条 available；不做学科收窄
  errors: D03Error[]
}
```

- `members` 与 `Project.teamRefs` 逐条对应；`available` 在投影中按 `true/false` 输出（供 Project 直接用在 `team_d` 谓词）。**D-03 不替 Project 过滤 `skillLevel>0`，也不按 dicipline 过滤成员**。
- `skillLevels` 为五学科 map，**不是单值 discipline**（V0.1 单值 `discipline` 字段已删除）；Project 用 `skillLevels[d]` 组合 `team_d`。

**错误码**：

| 错误码 | 触发 | 处置 |
|---|---|---|
| `D03_TEAM_EMPTY` | 项目 `teamRefs=∅` | Project `Cap_d=0`、`Cost_est=+∞`（B-2） |
| `D03_DANGLING_TEAMREF` | `teamRefs` 含查不到的 `employmentId` | 该引用不入 `members`，记录并推送告警；不抛异常 |
| `D03_UNKNOWN_SKILL` | `Assignment.discipline ∉ {design,code,art,audio,qa}` | 该分配不参与 `share`（视为 0 权重）；记错误；**不影响 `team_d`** |
| `D03_OVER_ALLOCATED` | 玩家提交分配导致 ΣRatio>1 | 命令侧拒绝 |
| `D03_PERSON_STATUS_DESYNC` | `Person.status` 与 §4.3 派生式不符（含 INV-2 冲突） | **返回该人**（`members` 与 `teamRefs` 逐条对应，**不得剔除**，C14）+ 该条 `available=false` + 告警 + **修复建议**（按 §4.3 重算 `Person.status`；若根因是 `Employment` 状态，走 §10 E4 修复）+ 写 `D03_DATA_REPAIR`；不抛异常 |

> 已终止成员（`terminated`/`contract_ended`）不再有独立错误码：其 `occupiesPerson=false` ⇒ `available=false`（§6.1 Z2），与其余不可用原因走**同一条**过滤路径。

**异常路径成员集不变（C14）**：除 `D03_DANGLING_TEAMREF`（引用本身无法解析为 Employment，无从投影）外，**任何单条成员异常都不得改变 `members` 的条数**——异常一律以"返回该条 + `available=false` + 错误码/告警"表达，**禁止静默剔除成员**（否则 Project `team_d` 少人 ⇒ `Cap_d` 偏小，即 D03-01 在异常路径上的复发）。

**契约要求**：纯函数、只读；同一 `(projectId, day, 存档快照)` 必须产出完全相同结果；D-03 不缓存 Project 的 `Cap_d`。

### 7.2 薪资 → 账本（FIN，C4/C9）

```
# 薪资承诺（C4/D03-03：endAt = 合同期末；periodCount 可数）
S_months   = initialTermMonths                                  # 首期合同月数
startMonth = monthOf(startDay)
endMonth   = startMonth + S_months − 1                          # 单月承诺结束在合同期末
salaryCommitment = FIN.createCommitment({
  companyId, sourceType: 'employment_salary', sourceRef: employmentId,
  amountCents: salaryMonthlyCents, period: 'monthly',
  startAt: startOf(startMonth), endAt: endOf(endMonth),
})
# ⇒ periodCount = S_months；totalPlannedCents = salaryMonthlyCents × S_months（创建时固化）
# 合同到期续约（renewalCount+1）⇒ 终止旧承诺、以新 endMonth 新建承诺；不得改变已固化承诺的 totalPlannedCents。

# 调薪（pendingEffectiveDay 到期）：cancel 旧承诺（effectiveMonth = 调薪生效月，R-13），新建新承诺：
#   startAt = startOf(调薪生效月)，endAt = 原合同期末（不变）
#   ⇒ 生效月由新承诺计费、旧承诺自该月起停，两段首尾相接，**当月不出现 0 计费、也不双计**。

# 解雇/离职：服从 FIN §4.1"中途取消只停止未来周期"——"未来"= effectiveMonth 及之后（ADJ-09）
FIN.cancelCommitment(salaryCommitment, effectiveMonth = monthOf(employment.endDay) + 1)
# 自离职月的【次月】起停；离职当月已出勤 ⇒ 照常兑现 1 笔（§1.2 统一规则）。
# effectiveMonth 必填、不得默认；缺省会退化为按创建月取消，把已赚取周期一并释放。
# 注：FIN 接口形参由 CODE-04 补（跨规格 TODO FIN-INT-01，§18.5）。

# 招聘费（one_off，C9）：hireConfirmDay 创建，arrivalDay 由 FIN 兑现一次
FIN.createCommitment({ companyId, sourceType: 'contract_obligation',
                       sourceRef: employmentId, amountCents: recruitCostCents,
                       period: 'one_off', startAt: arrivalDay, endAt: arrivalDay })
# 兑现：category = 'project_expense'，ref = employmentId

# 遣散（one_off，§6.4）：terminated/contract_ended 当日创建并兑现
FIN.createCommitment({ companyId, sourceType: 'contract_obligation', sourceRef: employmentId,
                       amountCents: severanceCents, period: 'one_off', startAt: endDay, endAt: endDay })
# 兑现：category = 'severance'，ref = employmentId
```

**月承诺可数算例（C4）**：`startDay = 2026-02-15`、`initialTermMonths = 6`、`salaryMonthlyCents = 500_000`（$5,000）。
- `startMonth = 2026-02`，`endMonth = 2026-07`，`startAt = 2026-02-01`，`endAt = 2026-07-31`。
- `periodCount = 6`（FIN §3.3"含首尾不同日历月"）；`totalPlannedCents = 3_000_000`（$30,000）。
- 兑现：2026-02 至 2026-07 **逐月恰好 6 笔**交易，每笔 500_000；`realizedCents` 逐月 `+500_000`，7 月后 `= totalPlannedCents` → `state=realized`。
- **6 个月 = 6 笔**（对齐 FIN §10.3 / FIN TC-19）——这是**未取消**时的口径。
- **中途离职算例（ADJ-2026-11-22-09，取代 ADJ-04/07 的 2 笔口径）**：若 2026-04-10 离职 ⇒ `cancelCommitment(effectiveMonth = 2026-05)` ⇒ 2026-02、03、04 共 **3 笔**（`realizedCents = 1_500_000`），2026-05~07 不再产生（`state=cancelled`，`totalPlannedCents` 仍 3_000_000）。
- **为什么是 3 笔而不是 2 笔**：4 月已出勤 ⇒ 4 月工资已赚取；`settlementDay` 只是记账时点。取消"未来周期"= 取消 5 月及以后，不是取消 4 月。若按 2 笔（取消 4 月起生效），玩家只需把解雇日定在 4 月最后一天，就能让"干满整月"的人工资为 0 —— 按天可控的稳定套利，不可接受。
- **为什么不是 `endDay` 所在月停而是次月停**：这是唯一同时满足"FIN 只停未来周期"与"不产生免费劳动"映射（推导见 ADJ-09 §0.3）。
- **代价（已知粗糙）**：4 月 1 日离职也计 1 笔（出勤 1 天付整月），方向是**玩家多付**。在 P1 不做按日折算（DEF-3）的前提下，"多付"是可接受方向，"能白拿"不是。

**规则**：D-03 **从不调用 `postTransaction`**；只创建/取消承诺；`idempotencyKey` 由 FIN 生成（`monthly` 含 `<YYYY-MM>`，`one_off` 用 `<commitmentId>:one_off`），D-03 只提供 `sourceRef`。

### 7.3 技能成长 ← 项目经历（反向，C8）
Project 日推进在写 `DailyOutput` 时向 D-03 提供产出日志条目 `(employmentId, discipline, day, out_wp, projectId)`（只读、append-only）。D-03 用 §6.8 的 `P(e,d,day)` 求 `effort`：**仅当该条日志 `out_wp>0` 且 `projectId` 对应的 `Assignment(employmentId, projectId, discipline)` 存在**时计为投入；`out_wp=0` 或日志缺失 ⇒ `effort=0`。D-03 不回写 Project（R-D03-2）。

### 7.4 D-01 / D-07 关系
- **D-01 `SkillDemandProfile`**：D-03 只消费 `peakFraction`（`S_d`）用于 UI 提示。
- **D-07 档案**：`PersonEvent` 全量写入（含 `retired`）；`Employment` 历史保留（不删除）。

## 8. 玩家操作与自动化

### 8.1 玩家决策（有代价）
| 决策 | 层级 | 代价/约束 |
|---|---|---|
| 招聘候选 | 战术 | `recruitCostCents` + 新增月薪承诺；`arrivalDay` 延迟；候选过期 |
| 调整报价 | 战术 | 低于 `floorPrice` 被拒；过高浪费钱但不会加士气 |
| 分配/撤分配 | 战术 | 受 `ΣRatio≤1`；`resigning` 不准新增；撤出后项目 `Cap_d` 下降 |
| 调薪挽留 | 战术 | 到期生效；现金跑道缩短；只重建承诺，不改现金 |
| 解雇 | 战术/危机 | 立即 `terminated` + 遣散兑现 + 士气外溢 |
| 设项目 `priority`（战略） | 战略 | 只影响 Project 派工顺序（Project §5.3-4 `priority`），**不自动分配人员**（§8.2） |
| 招多少（headcount） | 战略 | `headcountCap` 上限；组织扩张 DEFERRED |

### 8.2 系统自动（玩家不逐日操作，C10/D03-16）
- 每日：`available`/`skillLevel` 投影、士气递推（§6.6）、离职判定（§6.7）、成长积累（§6.8）。
- 月度：薪资承诺由 FIN 兑现（D-03 不参与）；合同到期续约判定。
- **自动分配：P1 不做**（确定裁定）。V0.1 的"未分配时将空闲员工自动加入最高优先级项目"与"默认 = 不自动分配"互相矛盾，V0.1.1 **删除自动分配路径**：玩家必须显式创建 `Assignment`；`Project.priority` 只影响 Project 内部派工顺序，不影响人员分配。若 P2 需要自动分配，另行设计（§18 DEF-8）。

## 9. UI/UX 页面结构级规格

> 只做结构级（页面/区块/字段/状态/跳转），不做像素。

### 9.1 团队总览（TeamOverview）
- **区块**：`头部`（在职人数/空闲人数/月薪总额/跑道影响）、`按学科分组列表`（design/code/art/audio/qa）、`每行`（姓名、职级、当前项目+学科、`allocationRatio`、`allocationLoad_d` 条、士气条、状态徽章）。
- **状态**：空 ⇒ "暂无员工，去招聘"；加载；错误 ⇒ 重试。
- **交互**：点击行进详情；搜索/筛选（学科、状态）；"招聘"主按钮。
- **数据来源**：`Person`+`Employment`+`Assignment` 投影；只显示合成 `morale`，不显示 `baseMorale`/`moraleModifier` 内部字段。

### 9.2 招聘面板（Recruitment）
- **列表**：候选（姓名、地区、学科+等级、期望月薪、可入职日、过期日）。
- **报价对话框**：显示 `recruitCostCents`、新增月承诺（含 `periodCount` 月数）、`arrivalDay`；低于 `floorPrice` 灰化确认并写原因。
- **状态**：候选池空；过期；名额已满（`headcountCap`）；资金不足（FIN `AvailableCash` 只读）。
- **错误码 → UI**：`D03_ALREADY_EMPLOYED`、`D03_CANDIDATE_EXPIRED`、`D03_OFFER_BELOW_FLOOR`、`D03_HEADCOUNT_FULL`。

### 9.3 分配面板（ProjectAssignment，Project 侧入口）
- **列表**：项目下拉 / 学科分组 / 可分配员工。
- **每行**：输入 `allocationRatio`（≤剩余比例）；显示该人 `skillLevels` 中各学科等级与 `allocationLoad_d`。
- **实时反馈**：当前项目该学科 `Cap_d` 预估值（由 Project 提供，含"跨学科贡献"提示：如"该员工程序 3 级，虽分到美术仍为程序产能"）。
- **状态**：`resigning` 禁止新增（灰）。
- **错误码**：`D03_OVER_ALLOCATED`。

### 9.4 员工详情（PersonDetail）
- **区块**：身份、`SkillProfile` 五学科条、当前任职（岗位/薪资/状态/入职日/通知日）、当前分配列表、`PersonEvent` 时间线（含 `retired`）。
- **操作**：调薪、解雇（二次确认+代价预览）、撤分配。
- **状态**：`departed` ⇒ 只读（仍可在候选池再招）。

### 9.5 跳转
- TeamOverview → PersonDetail；TeamOverview → Recruitment；ProjectAssignment ⇄ TeamOverview；ProjectDetail → ProjectAssignment。

## 10. 异常与边界

| 编号 | 情形 | 处理 |
|---|---|---|
| E1 | 无人可用（全员 `departed`/无在职） | `D03_TEAM_EMPTY`；Project `Cap_d=0` ⇒ `Cost_est=+∞`；UI 引导招聘 |
| E2 | 项目某学科 `team_d=∅` | Project §6.2 自然得 `Cap_d=0`（本文不再按分配过滤）；UI 标"该学科无人会"（OPEN-D03-1） |
| E3 | 超额分配（Σ>1） | 命令侧拒绝 `D03_OVER_ALLOCATED`；旧档/读档若出现 ⇒ 按 §6.2 `share` 归一化（只影响 UI 负荷，不改 `team_d`） |
| E4 | 同一人双重雇佣（读档发现全库存在 2 条 `occupiesPerson=true`） | **修复只改状态、不产生财务后果**：保留 `startDay` 最早一条（并列时取 `employmentId` 字典序小者），其余置 `occupiesPerson=false` + `status=terminated` + `terminationKind=terminated`，**不创建遣散承诺、不调用任何 FIN 接口**；写 `PersonEvent(terminated, payload.reason='read_repair')` 与迁移日志 `D03_DATA_REPAIR`（C10/D03-08） |
| E5 | `Cap_d` 计算时 `team_d=∅` | 不除零，直接 `Cap_d=0`（Project B-2）；`allocationLoad_d=0` |
| E6 | 项目中途离职（D03-19） | `resigning` 期间 `available=true` **直到 `endDay`**（`endDay = noticeStartDay + noticeDays`）；`day = endDay` 当日仍 true，`day > endDay` 后 false ⇒ Project 下次 tick 自动剔除，`Cap_d` 立即降，UI 告警（TC-15） |
| E7 | `teamRefs` 含悬空 `employmentId` | `D03_DANGLING_TEAMREF`：该引用不入 `members`；若该学科无余 ⇒ `Cap_d=0` |
| E8 | 读档恢复 | `dailyResignProb` 用确定性种子；`probation` 到期、`noticeStart`、`pendingSalary` 均按 `dayIndex` 恢复并补算转换（§11 S1） |
| E9 | `skillLevel=0` 出现在 `teamRefs` | 不抛错；Project `team_d` 的 `skillLevel>0` 过滤自然排除（贡献 0） |
| E10 | 同一人在两个项目同学科 | 允许；`share=0.5` 各；P1 Project `Cap_d` 不减半（§6.2）；UI 以 `allocationLoad_d` 提醒 |
| E11 | 候选同人重复入池 | 去重；`D03_DUPLICATE_CANDIDATE` |
| E12 | `retireAge` 到但正忙于项目 | 不强制，转 `resigning`（§4.1 退休路径，走通知窗口）；`resigning` 期间不得被"解雇后立即重招"绕过（`occupiesPerson` 仍 true ⇒ RULE-02 拒绝） |
| E13 | 人格/诉求 = null / `audio` 等级缺键 | 所有分支 `?? null` / `?? 0`，P1 不得因 null 崩溃（DEF-1） |
| E14 | `Assignment.discipline` 非法值 | `D03_UNKNOWN_SKILL`；该分配不参与 `share`；不改变 `team_d`（§7.1） |
| E15 | `Person.status` 与 §4.3 派生式失步（外部改写/迁移半途） | `D03_PERSON_STATUS_DESYNC`：**照常返回该人**、`available=false`、告警 + 修复建议 + 写 `D03_DATA_REPAIR`（C14）；`members` 条数 = `teamRefs` 条数，**不剔除成员**；该人对 `team_d` 贡献 0 由 Project 的 `available` 谓词自然处理（TC-24） |

## 11. 存档要求

| 存档段 | 必须持久化 | 读档行为 |
|---|---|---|
| S1 `Person` | `personId/displayName/birthDay/regionId/skills/seniority/status/currentEmploymentId/baseMorale/rehireCount` | ① 校验 `currentEmploymentId` 指向的 Employment 为 `occupiesPerson=true`，否则置 null；② **全库 `occupiesPerson=true` 的 `personId` 唯一性校验**（违反走 §10 E4）；③ 按 §4.3 重算 `status`，不符即重算（`status` 为派生字段，不信任存档值） |
| S2 `Employment` | 全部字段（含 `pendingSalary`/`startDay`/`endDay`/`moraleModifier`/`salaryCommitmentId`/`initialTermMonths`） | `salaryCommitmentId` 必须能在 FIN 找到（缺则按 §7.2 重建，并记迁移日志） |
| S3 `Assignment` | 全部 | `effectiveTo < day` ⇒ 不计入 `allocationLoad_d`/`effort`（**不影响 `team_d`**，§6.1） |
| S4 `Candidate` | 全部 | 过期自动移除；已 occupying 雇佣的从池中移除 |
| S5 `PersonEvent` | append-only 全量 | 不重算、不压缩 |
| S6 随机种子 | `hash(employmentId, day)`，**不持久化随机状态** | 天然可重放 |
| S7 版本 | `d03SchemaVersion`（V0.1.1 = 2；**因参数快照转为必存字段，编码时升为 3**）；**必存**：`personnelFormulaVersion` + 参数快照三元组 `{version, params, createdAt}`（**C13：与 Project §11 S4 同级别的必存字段**，不是建议项，§18.3） | 旧档 `Employee` → `Person`+`Employment`（§15.3 两步迁移）；缺快照 ⇒ 以已存派生值为冻结事实、不重算，并记迁移日志 |

- **确定性**：任何随机（离职、候选池刷新）必须用确定性种子 `hash(entityId, day, salt)`，存档不含 `Math.random` 结果。
- **读档一致性**：`available`/`skillLevel` 由 D-03 重算，不信任旧缓存。

### 13.1 TC-05 数值算例（C1 核心证明）

**共享输入（Project §6.2 TUNING）**：`k_output = 10`（workUnits/day，示例值）；`f_skill = {0:0, 1:0.6, 2:0.8, 3:1.0, 4:1.2, 5:1.4}`。

**场景**：项目 P1，`teamRefs = {e1, e2, e3, e4}`，`W_code > 0`：

| e | Person 技能 `level` | `Assignment(P1,·)` | `occupiesPerson` / `status` / `endDay`（day=D） |
|---|---|---|---|
| e1 | `{design:4, code:3}` | `discipline=art`，ratio 0.3 | true / active / null |
| e2 | `{design:1, art:2}` | `discipline=art`，ratio 0.5 | true / active / null |
| e3 | `{code:5}` | 无 Assignment（行政上未分配） | true / active / null |
| e4 | `{code:2}` | `discipline=code`，ratio 0.4 | true / **resigning** / endDay = D |

**Project 原口径**（`team_d = teamRefs ∩ available ∩ skillLevel>0`）：
- `available`（D-03 §6.1 Z2 的评估结果）：e1、e2、e3、e4 全为 true（e4 `resigning` 且 `day ≤ endDay`）。
- `team_code = {e1(3), e3(5), e4(2)}`（e2 `code=0` 被 `skillLevel>0` 过滤）。
- `Cap_code = k_output × [f_skill(3) + f_skill(5) + f_skill(2)] = 10 × [1.0 + 1.4 + 0.8] = 32` workUnits/day。
- `team_design = {e1(4), e2(1)}` ⇒ `Cap_design = 10 × [1.2 + 0.6] = 18`。
- `team_art = {e2(2)}` ⇒ `Cap_art = 10 × [0.8] = 8`（e1 分到 art 但 `art=0`，被过滤）。

**D-03 消费路径（V0.1.1）**：D-03 仅提供 `available` 与 `skillLevels`；Project 用其原文组合：
- `available(e1..e4) = (true, true, true, true)`；`skillLevels` 为各人五学科 map。
- 代入 Project §6.2 公式得 `Cap_code = 32`、`Cap_design = 18`、`Cap_art = 8`，**与上方逐符号一致**。
- 断言：`Cap_code` 含 e1（多学科员工仅分到 art 仍计 code 产能）与 e3（无 Assignment 仍在 `teamRefs` 中计产能）；若实现按 `Assignment.discipline` 过滤，则 `Cap_code` 变为 `10 × [1.4 + 0.8] = 22` ≠ 32 ⇒ **FAIL**（这正是 D03-01 的反证锁）。

**时点断言（C5）**：`day = endDay + 1` 时 e4 `available=false` ⇒ `Cap_code = 10 × [1.0 + 1.4] = 24`。

**`allocationLoad_d` 对照（不与 `burden_d` 混淆）**：`T_code = {e4}`（仅 e4 有 code 分配）⇒ `allocationLoad_code = share(e4,P1,code)=1.0 / max(1,1) = 1.0`；`T_design = ∅ ⇒ 0`；`T_art = {e1(0.375), e2(1.0)}` ⇒ `allocationLoad_art = 1.375/2 = 0.6875`。该值**不进入任何 `Cap_d`**，也不参与瓶颈排序。

### 15.3 存档迁移步骤（两步化，C10/D03-07）

```
Step 1  读旧 Employee 记录（全部公司，含 AI 公司）：
        Person(pm) ← {
          personId: 生成, displayName, regionId ← City.regionId（缺失取默认）,
          skills: {level: {primarySkill: skillLevel}, exp: {primarySkill: experience}},
          seniority: skillLevel >= 4 ? senior : junior,
          baseMorale: morale,
          status: 由 Step 2 派生, currentEmploymentId: null  // Step 2 回填
        }
Step 2  依旧 Employee.status 决定 Employment：
        'hired'    → probationEndDay = contractStartDay + probationMonths × workingDaysPerMonth   # §4.2 唯一口径
                     status = probation if 存档日 < probationEndDay else active
                     occupiesPerson=true；无 Assignment（旧 TeamAssignment 若存在则生成 Assignment）
        'on_leave' → status=active（**不是** Person.status=on_leave）；occupiesPerson=true；无 Assignment
                     ⇒ §4.3 派生 Person.status = on_leave（行为与旧档一致）
        'resigned' → status=terminated, terminationKind=voluntary, occupiesPerson=false, endDay=存档日
        'fired'    → status=terminated, terminationKind=terminated, occupiesPerson=false, endDay=存档日
        Person.currentEmploymentId ← Employment.employmentId（仅 occupying 时）
Step 3  按 §7.2 为每条 occupying Employment 创建薪资承诺（startAt = startOf(monthOf(startDay))，
        endAt = endOf(startMonth + initialTermMonths − 1)）；已结束的不创建。
Step 4  校验：全库 occupying Employment 的 personId 唯一；每个 Person.currentEmploymentId 指向 occupying；
        失败走 §10 E4（**不生成遣散**）并记 `D03_DATA_REPAIR`。
```

- **`probation` 日期判据（C12/D03-21 统一）**：唯一口径为 `probationEndDay = startDay + probationMonths × workingDaysPerMonth`（§4.2、§6.9），`存档日 ≥ probationEndDay` ⇒ `active`。V0.1.1 并存的"少于 `probationMonths × 30` 自然日置 `probation`"**已删除**（两套判据会让迁移产生两种实现，且 `workingDaysPerMonth` 与 `30` 同时存在自相矛盾）。**老员工**（`startDay` 距存档日远超阈值，如入职已 3 年）**一律 `active`，不得置 `probation`**，由 TC-19 断言。
- `OPEN-D03-8`（旧 `on_leave` 语义）由此关闭：旧 `on_leave` 被视为"在职无分配"，映射为 `active + 无 Assignment`，与 `Person.status` 无关。

### 15.4 废弃 `baseEffectiveWorkPerDay` 的论证（成立，保持）

旧式 `base × skillFactor(skillLevel) × moraleFactor(morale) × fatigueFactor(fatigue) × focusFactor` 与 Project §6.2 `k_output × Σ f_skill(level)` 存在三重差异：① 系数表不同（旧 1→0.7/5→1.3；新 1→0.6/5→1.4）；② 产能归属不同（旧"每人日产能"累加，新"团队学科总量"由 `k_output` 统一缩放）；③ 士气/疲劳是否影响产出（旧影响，新无该项）。按权威顺序 **Project > 旧代码**，P1 废弃旧式；士气只影响 §6.7 离职（OPEN-D03-3 记录 P2 若注入 `k_morale` 须升 `projectFormulaVersion`）。

## 17. 类型边界与版本关联（2.3B 第 14/15 项）

### 17.1 新子类型/新类型边界（第 14 项）
- **总裁定**：D-03 **不生成任何新实体子类型**（无 `Person` 子类、无 `Employment` 子类、无"临时工/外包/顾问"等 P1 之外的类型）。P1 六类实体（§3）为封闭集合；新增类型须走本规格修订 + 主 AI 裁定。
- **新角色/新职业边界**：`audio_designer` 已通过 REC-04 裁定登记为第 7 个 `EmployeeRole`，对应 `SkillProfile.audio`；候选池与招聘可生成，遵循既有实体封闭集合、技能范围和财务承诺规则。
- **候选池生成的类型边界**：候选池只能生成**已登记角色的 Person**（§5.2 RULE-05），不得生成"未知职业"或"双主职"；`primarySkill` 唯一（§3.3 `level` 可以有多个非零，但候选生成只给 1 个主学科 + 其余 0 或低值，TUNING）。
- **`Assignment.discipline` 的边界**：只能取 `Discipline` 枚举五值；越界返回 `D03_UNKNOWN_SKILL`（§7.1），**不影响 `team_d`**（§6.1 Z1 已删除按学科收窄）。
- **N/A 论证**：D-03 处于"消费 D-01/D-02 的类型与角色"层级，不产生新的交付标准、不生成玩法类型、不定义 `WorkPackage` 的子结构，故"新子类型生成规则"在 D-03 侧为**边界声明**而非生成器；本项真实覆盖由"封闭枚举 + 越界拒绝 + 新增须经修订"的划界成立。

### 17.2 设计版本与执行版本关联/返工（第 15 项）
- **返工 N/A 论证**：D-03 不产生 `Build`、不参与交付闸门、不在 D-01 §15.2 的"设计版本→执行版本"链上；`Rework`（Project §4.5 `ReworkSession`）对 `Person`/`Employment`/`Assignment` 无返工语义（分配不因返工回滚，士气不因返工重置）。因此"返工"在 D-03 侧 **N/A**，本项由"不参与返工链"的划界成立。
- **版本关联（真实存在，须给规则）**：D-03 的"版本关联"体现在三处，均为**执行版本随存 + 迁移映射**，不是设计版本版本化：
  1. **存档版本**：`d03SchemaVersion`（§11 S7），旧档 `Employee` → 新结构的两步迁移（§15.3），迁移日志可追溯（`legacyId → personId/employmentId`）。

  3. **与 Project 的版本联动**：D-03 的 `available`/`skillLevel` 语义若变化（如 P2 引入 `k_morale`），必须升 Project 的 `projectFormulaVersion` 才能被消费（R-D03-2）；D-03 内部 `personnelFormulaVersion` 变化**不自动**触发 Project 版本升级，二者版本号独立、由主 AI 裁定是否联动。
