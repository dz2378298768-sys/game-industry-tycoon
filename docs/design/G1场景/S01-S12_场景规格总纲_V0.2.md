## 0. 总则

### 0.1 场景在 G1 体验流程中的统一位置
G1 流程（DRAFT-02 §4.2）：创建公司 → 查看经营情况 → 市场机会 → 产品方向 → 设计产品 → 创建研发项目 → 招聘配置 → 推进研发 → 处理问题 → 测试优化 → 交付标准 → 上市 → 反馈销售 → 财务结算 → 复盘 → 第二款决策。S1–S3 为"定义"，S4–S7 为"执行"，S8–S10 为"交付与市场"，S11–S12 为"结算与延续"。

### 0.2 与 P1 验收的对应（贯穿性判据来源）
- ≥3 次有明显代价的关键决策：本总纲分配为 S5（招聘承诺）、S7（返工/缩减范围沉没成本）、S9（带缺陷交付的口碑/退款风险）；S4（追加预算）与 S6（暂停/取消）为补充池。
- 失败前存在可识别预警和合理补救：由 S11 的 crisis 状态机（ADJ-11 因果链）+ S6/S7 的项目预警共同承担。
- 玩家能解释产品表现前三个主要原因：由 S10/S12 承接（P-4 可数判据，见 §S12.7）。

## 1. 场景规格（S01–S12）

### S01 创建公司

**1. 玩家目标与位置**：建立第一家游戏公司并理解初始经营条件；G1 流程第 1 步，一切后续场景的实体出生点。

**2. 玩家操作与系统响应**
| 输入 | 系统响应（数据来源） |
|---|---|
| 输入公司名称 | 创建 `Company` 实体（p0 §2.2）；名称写 `Company.name` |
| 确认基本资料（地区：1978 北美） | `World`/`Region` 条件写入：地区工资/租金/购买力档位（p0 §4.1 步 1） |
| 查看初始资金 | 统一账本开户并登记期初交易（CODE-04；FIN §3.1/§3.2，BR-1 唯一现金入口） |
| 查看初始团队 / 市场环境 | 读初始 `Person` 集合（P1 允许 0 人开局，初始成员数 OPEN）与 `ConsumerSegment` 词表（D-04 V0.2） |
| 进入经营界面 | 切换到四区主界面（现金/团队/项目/产品，P1 清单 §四 步 1） |

**3. 必须展示的信息**
| 字段 | 来源内核 |
|---|---|
| 公司名称、当前日期（1978 年，精确起始日 OPEN） | Company / Calendar（p0 §2.1） |
| 当前现金 | 统一账本派生 `cashBalanceCents`（FIN §3.2；禁止任何第二现金来源） |
| 员工数量 | D-03 `Employment` 计数（CODE-06；G1 可为 0 人开局，OPEN） |
| 当前项目数量 | Project 计数（应为 0） |
| 地区/年份基本条件摘要 | World/Region（p0 §4.1 步 1） |
| 引导文案：拥有什么/能做什么/下一步 | UI（CODE-07）；不得直接抛报表 |

**4. 关键决策点**：G1 最小版下 S1 本身不产生代价决策（公司名/地区固定为 1978 北美，p0 §4.0），它是后续 ≥3 次代价决策的铺垫；"选地区"的代价化推迟到 P4（多地区，基线 §8）。

**5. 失败/异常分支**
- 名称非法/重复：拒绝创建，回填提示，不产生任何实体半成品。
- 创建中断（关窗/读档冲突）：不得出现"有 Company 无账本"的悬空档；创建为原子动作（存档一致性，P1 红线 R9 同源确定性）。

**6. 数据依赖**：CODE-02/04（账本开户）、p0 §2.1/§2.2 字段清单；D-04 词表（V0.2 已定稿）；初始数值以现有规格为准。

**7. 验收判据**：对应 P1 清单 §四 步 1——新开一局可见四区、无报错；账本期初现金与展示现金恒等（INV-1，P1 红线 R2 的 UI 侧抽查）；引导文案三问可答。

**8. 待裁定项**
- OPEN-S1-1：`startingCashCents` 精确值（p0 §4.0 只定档位 $100k–$150k/TUNING；G1 需固定单值）。**现有 UI 硬编码 $50,000 需重标定**：与 p0 档位 $100k–$150k、FIN 算例 $120k 冲突，须主 AI 定值后由 CODE-07 同步修改。
- OPEN-S1-2：初始团队人数（0 人自招 vs 预置创始人 1 人）。
- OPEN-S1-3：起始精确日期与难度选项是否 G1 开放。（REV-01 MAJ-11 引用更正：`create-company.tsx` 实际为"名称 + 城市选择"，页面底部**静态显示 $50,000 与年份**，缺团队/市场预览与资金影响说明——三项补齐与上述 $50,000 重标定同批走 CODE-07。）

**两档**：G1 最小版 = 固定 1978 北美 + 单一资金档 + 0 人开局 + 简短引导；完整版 = 多地区/难度/初始成员选择（实现成本高，必要性存疑，建议 G1 取最小版）。

### S02 市场分析

**1. 玩家目标与位置**：判断当前市场存在什么机会；G1 流程第 3 步，S3 定位的输入。

**2. 玩家操作与系统响应**
| 输入 | 系统响应 |
|---|---|
| 查看市场类别/类型需求 | 展示 `GameplayArchetype` 种子类型与需求方向（D-04 V0.2 词表；需求换算 OPEN-D04） |
| 查看目标消费者群体 | `ConsumerSegment`/`SegmentTag` 列表（D-04 词表切片，p0 §4.1 步 1） |
| 查看竞争产品 | P1 只有玩家自身与少量 AI 同源公司（基线 R10；竞品完整模型归 P2，此为简化占位） |
| 比较不同市场方向 | 上述数据并排比较视图（纯派生，无新实体） |
| 投入时间/资源调研 | 生成调研记录（费用走账本 `research_expense` 类交易，FIN §3.9 分类 OPEN 项）；调研减少不确定性但不保证成功（DRAFT-02 §4.4） |

**3. 必须展示的信息**：类别清单与需求趋势方向（D-04）；群体标签（SegmentTag）；竞争产品列表（P1 最小）；各方向的定性机会/风险标注（来源 D-04 affinity 换算口径，数值 OPEN）。所有成本类字段来自统一账本派生。

**4. 关键决策点**：进入哪个方向（影响 S3 的七维定位与 HRB 承诺）；是否付费调研（现金流换信息，属有代价决策补充池）。后果：方向选择决定 S3 的 `targetSegmentClaims` 可行集与 S10 的销量结构。

**5. 失败/异常分支**
- 词表未就位/数据缺口：对应方向显示"信息不足"而非伪造数字（不得 UI 造数，P1 §六-5）。
- 调研费用超可用现金：HRB/账本拒绝（FIN BR-9 `FIN_INSUFFICIENT_CASH`）。

**6. 数据依赖**：D-04 V0.2（已定稿）；CODE-04（调研费用）；竞品数据口径 OPEN（P1 最小可降阶）。

**7. 验收判据（可数判据）**：玩家从市场页回答 DRAFT-02 §4.4 四问，逐问给出最小可接受答案枚举（无数据时按 fail-closed 口径答"信息不足"亦计通过，不得伪造数值）：
1. **机会**：能说出 ≥1 个类别及其需求趋势方向档（D-04 词表内的方向标注，或答"信息不足"）；
2. **竞争激烈度**：能说出当前竞品呈现数量与形式（P1 最小：玩家自身 + 静态竞品档案，形式口径 OPEN-S2-2），或答"暂无竞品数据"；
3. **自己是否适合**：能对照当前团队学科结构（S5 现状）说出 ≥1 条适配/不适配理由（引用 D-04 affinity 方向档）；
4. **风险高低**：能对拟选方向复述 ≥1 条定性风险标注（来源 D-04 affinity 换算口径，数值 OPEN）。

四问的跨场景归因汇总并入 S12 四域归因框架（§S12.7），S2 不另建独立归因账。调研支出在账本流水可追溯（判据：交易记录含该笔）。

**8. 待裁定项**：OPEN-S2-1 调研费用数值与 `TransactionCategory` 归类（**含裁定项：复用 FIN 现有 12 类枚举 vs 扩枚举**）；OPEN-S2-2 P1 竞品呈现形式（真实 AI 公司 vs 静态竞品档案）；OPEN-S2-3 需求趋势是定档（low/medium/high）还是定量。

**两档**：G1 最小版 = 静态市场信息页 + 一次调研动作；完整版 = 动态趋势/竞品模型（P2 范围，重复性审查下不建议提前）。

### S03 产品定位与设计

**1. 玩家目标与位置**：决定第一款游戏是什么；G1 第 4 步，生成 `DesignVersionSnapshot` 的源头。

**2. 玩家操作与系统响应**
| 输入 | 系统响应 |
|---|---|
| 选市场/目标用户 | `targetSegmentClaims`（受 D-04 SegmentTag 前置约束，p0 §4.0） |
| 选产品规模（HRB 承诺 0.45/0.6 等，p0 场景 A/B） | D-01 §6.2.1 HRBFeasibility 求值 |
| 选玩法模块（槽位+强度+tier） | D-01 四通道工作量 `W_d`、`TechRequirement`、`RiskProfile`、`MarketAppealProfile`（p0 §4.1 步 4） |
| 确认定位/锁定版本 | 生成唯一 `DesignVersionSnapshot`（estimates 冻结，D-01 §15.1） |
| 查看预计研发需求/成本/风险 | `WorkloadEstimate`/`SkillDemandProfile`/`HRBFeasibility`（D-01 §6.2/§6.4） |

**3. 必须展示的信息**：产品身份五要素（名称/定位/目标用户/模块组合/方案，DRAFT-02 §4.5）；工作量四通道分布（学科负载条，供 S5 招聘参照）；`positioningFit`/`genreFit`/affinity 分布（D-01 §6.5）；`TechRequirement` 未满足项标红（p0 §4.2 步 4）；`HRBFeasibility` verdict。`qualityCeilingBand` P1 恒为 `ABSENT_P1`，**不展示**（U5，P1 清单 §五）。

**4. 关键决策点**：七维差异化定位 + HRB 预算承诺（D-01 §4.3/§6.2.1）——这是"精品 vs 低成本两条路线合理"验收（基线 §4）的发生点；保高技术门槛 vs 降门槛的取舍（p0 场景 B 步 5）。后果：锁定后进入 S4，成本/风险/市场画像全部由该快照权威冻结。

**5. 失败/异常分支**
- `E-EMPTY`/`E-EMPTY-CONTENT`/`E-USP`（空核心槽/空内容槽/卖点无支撑）：禁止锁定，逐条报原因码（D-01 §7.2.1，R-COM-7）。
- HRB verdict 不可行：可保存草稿但禁止立项，提示追加预算或降档。
- 技术门槛不满足项存在：允许草案但标红计风险（p0 §4.2），锁定时给确认弹窗。

**6. 数据依赖**：D-01（已定稿）、D-04 V0.2；CODE-01（蓝图内核 CLOSED）；CODE-03（快照消费）。

**7. 验收判据**：P1 清单 §四 步 2（选类别/平台/内容 → 看到 HRB 与 Budget_cap → 确认成功）；同一市场下场景 A/B 两套定位参数能分别通过校验并产生可区分的四通道输出（对齐 p0 §4.3 对比表）。

**8. 待裁定项**：OPEN-S3-1 基础/高级模式的 G1 切分（DRAFT-02 §4.5 允许两层，G1 最小版建议只做基础模式）；OPEN-S3-2 HRB 档位枚举 G1 暴露几档（0.45/0.6 为 p0 示例值，非规格枚举）。

**两档**：G1 最小版 = 基础模式 + 固定槽位结构；完整版 = 高级参数配置（扩展性保留，实现成本高）。

### S04 创建研发项目

**1. 玩家目标与位置**：把产品设计转化为可执行研发计划；G1 第 5 步，Project 实体出生点。

**2. 玩家操作与系统响应**
| 输入 | 系统响应 |
|---|---|
| 创建 Project（绑定快照） | `state=SETUP`→立项完成 `ACTIVE`；绑定唯一 `snapshotId`+`formulaVersion`（Project V0.1.1 §4.3） |
| 确认目标/范围/优先级 | 写 Project 字段；范围锁定 WP 拆解输入（§5.2 拆解算法） |
| 配置预算 | `budgetCapacityCents` ≤ 当时 `AvailableCash`（FIN §6.2）；登记 `one_off BudgetCommitment(amountCents=Budget_cap=hrb×budgetCapacityCents)`，**承诺不改现金**（§5.4-1，FIN BR-3） |
| 查看工作包 | 系统按 §5.2 生成 WorkPackage 列表（含学科、baselineWorkUnits、依赖） |

### S11 财务结算

**1. 玩家目标与位置**：判断公司是否能够继续经营；G1 第 12 步，危机与破产状态机所在。

**2. 玩家操作与系统响应**
| 输入 | 系统响应 |
|---|---|
| 查看月度结算 | 月度触发顺序（p0 §3.3）：薪酬兑现（settlementDay post，ADJ-09）、承诺兑现、应收结算 |
| 查看跑道与预测 | `runwayMonths` 由 `CashForecast.netCashByMonth` 派生（FIN §6.1/§6.3）；**起点恒为 `CashBalance` 账面现金**（ADJ-11 R-2）；每笔未来支出带 `inclusionMode`（IN_FORECAST/RESERVED_ONLY/EXCLUDED），**在 runway 支出侧计入恰好一次**（INV-RUNWAY，ADJ-11 §2.1） |
| 查看危机状态 | `CrisisState` 状态机（FIN §3.6/§4.2），因果链按下 §特别约束 |
| 补救行动 | 追加预算/裁撤/缩减范围（回流到 S4/S5/S7 的动作），取消承诺后 runway 回升（ADJ-10 O-2 关联，R-5 用例覆盖） |

**3. 必须展示的信息（全部账本派生，单一现金入口）**：当前现金（`cashBalanceCents`，FIN §3.2）；本月收入/支出/员工薪酬/项目成本/产品收入/退款（TransactionCategory 12 类三分映射，FIN §3.9）；现金流变化（`netCashByMonth`）；重要财务事件（原因码 `reasonCodes`，FIN §3.8）；`runwayMonths`（**直接展示正确值，U2 兜底口径说明作废**，ADJ-11 R-6/CODE-07 范围）；`AvailableCash`（承诺扣除后可用，恒等式 `CashBalance − Σ扣除 == AvailableCash`）。

**4. 危机与破产因果链（按 ADJ-11 §1.2 修正后口径，逐字约束）**
- 跑道低于 warning 线**仅触发 `watch` 状态 + `LOW_RUNWAY` 原因码**，不直接进 `warning`（只有 `warningByCash` 才进 warning）。
- 跑道低于 critical 线 → 进 `critical`，启动补救窗口。
- **破产 = AND 三条件**：`state===critical` **且** `today >= remediationDeadline` **且** `cashBalanceCents < cashBankruptThresholdCents`。三者缺一不可；现金未跌破阈值时补救窗口耗尽也**不**破产。**禁止实现或展示"进 critical 即破产"的口径**。
- 阈值（标定）：`runwayWarningMonths=4.0`、`runwayCriticalMonths=2.0`、`remediationWindowDays=60`。**权威来源 = ADJ-11 §8 阈值标定记录（2026-11-22 主 AI 补记，初值 4.0/2.0/60，P2 校准轮可调，两条自洽约束不得破坏：① warning > critical；② critical 进窗口后"deadline 到期 ∧ 现金跌破阈值"才破产）**。
- 设计含义：假预警的危险路径是"玩家依据 watch 主动裁员/砍项目"——UI 须呈现 watch 与 warning 的等级差异，让玩家能分辨"观察"与"警告"。

**5. 关键决策点**：watch/critical 下的补救组合（开源：让产品上市回款；节流：裁员/砍项目/缩范围）——对应 P1 验收"失败前存在可识别预警和合理补救，而非突然归零"。后果：任何补救都真实改变 S5/S7 的经营状态；补救不当把假危机变真危机。

**6. 失败/异常分支**
- 真实跑道 2.5 个月（仅跑道触发、现金未跌破 cash warning 线）：进 **watch**（非 warning）、不进 critical（RV-2 反例）。
- 真实跑道 0.8 个月：进 critical，补救窗口自进入日起算 60 天（RV-3）。
- 现金 700,000/月净烧 100,000/6 期承诺：`runwayMonths≈7(±0.5)` 且 healthy、无 LOW_RUNWAY（RV-1，修复前必红的直接反证）。
- 破产三条件缺一：窗口耗尽不破产，UI 持续展示窗口剩余天数与现金-阈值差距。

**7. 数据依赖**：**CODE-FIN-RUNWAY（G1 阻断，READY）**；CODE-04（CLOSED）；FIN V0.2 §3/§4/§6；ADJ-11（权威，含 §8 阈值标定记录）；ADJ-10 §7（releasedCents 口径）。

**8. 验收判据**：R-4 三反例全部绿且记录"先红后绿"证据；R-5 INV-RUNWAY 独立用例（horizon 内/外/已取消/已释放四态，inclusionMode 唯一、承诺只计一次、取消后 runway 回升）；U2 走查（财务页直接展示正确 runwayMonths，无口径说明兜底文案）；HRB 未被误改的用例（ADJ-11 §4）。P1 §六-5 否决项自查：UI 不得为跑道做任何数值修饰。

**9. 待裁定项**：OPEN-S11-1 `cashBankruptThresholdCents` **不再独立定值**：引用 FIN V0.2 §6.4（`cashBankruptThresholdCents=0`），仅保留"是否沿用"确认项；OPEN-S11-2 月度结算页时间粒度（自然月 vs 30 天）——建议沿用 FIN settlementDay 语义；OPEN-S11-3 破产后 G1 流程（结算页展示 GAME OVER？允许续档重开？）。

**两档**：G1 最小版 = 月度结算页 + 危机状态机 + 三反例验收；完整版 = 应收应付全框架/合同分成（P3 范围）。
