## 1. 一句话定义与产品愿景

> 一款以电子游戏产业为舞台、以公司经营为核心、以产品创造与市场竞争为驱动、以时代和产业演化为背景的**深度经营模拟游戏**。

玩家创办并经营自己的电子游戏企业，在不断变化的全球产业中设计产品、组织人才、配置资源、选择商业模式、建立合作关系，并亲自创造一段**可能偏离真实历史**的电子游戏产业史。

### 1.1 不设强制终极目标
玩家的最终目标由玩家自己决定。不设"必须成为全球最大 / 必须上市 / 必须活到某年 / 必须击败某对手"的唯一胜利条件。游戏提供持续运行的产业平台 + 足够丰富的机会、约束、竞争、合作和长期后果。
可以成为精品独立工作室、类型专家、知名开发商、发行商、多工作室集团、技术创新者，也可以经历失败、转型、重组或主动退出。

### 1.2 玩家身份
**企业创始人和经营决策者**，不是亲自操作每个员工的项目经理，也不是只负责研发的制作人。玩家决定企业做什么、为什么做、投入多少、与谁合作、承担什么风险；团队负责把战略转化为执行。

### 1.3 六项体验目标（验收时的"好玩"判据）
| # | 体验 | 玩家应有的感受 |
|---|---|---|
| 1 | **创造感** | 设计一款有独立身份的游戏，不是生产一组抽象数值 |
| 2 | **经营张力** | 资金、人才、工期、质量、市场窗口、机会成本互相冲突 |
| 3 | **因果理解** | 成功/失败能追溯到产品设计、团队执行、市场匹配、商业决策 |
| 4 | **产业参与感** | AI 企业、消费者、平台、技术、人才不围绕玩家静止等待 |
| 5 | **历史成就感** | 多年后能回顾某款作品、某位人才或某次决策如何改变公司乃至产业 |
| 6 | **策略自由** | 不同企业定位都能形成长期可行路线，不存在唯一最优经营模板 |

## 2. 顶层不可交易原则（DP-1~DP-4）

> 来源：`ADJ-2026-11-24-23` §1，Owner 钦定，**高于任何阶段目标、任何效率补丁、任何"先收口"考量**。

| 编号 | 原则 | 判据（怎么算做到了） | 违反后果 |
|---|---|---|---|
| **DP-1** | 玩家必须能真实玩到 | 功能必须通过**真实 UI** 可达；只能测试/代码调用 = 玩家没得到 | 该阶段不算完成，即便测试全绿 |
| **DP-2** | 点击必须有自己的反馈 | 每次关键操作有可见、语义相符的反馈；**禁用态必须给出"为什么禁用"的可读原因**，不得只是灰掉 | 静默禁用、无反馈、无原因 = 违反 |
| **DP-3** | 必须有真实计算逻辑 | 反馈来自真实内核计算，可复现；不得占位/假数据/伪造快照/恒真断言 | 伪造 = 直接违反 R-5 与 P1 否决项 |
| **DP-4** | fail-closed 是诚实暴露，不是长期实现 | 数据不足时 fail-closed 是**过渡态的正确做法**，但缺口必须进入完善义务清单并限期兑现 | fail-closed 无限期挂起 = 违反 DP-1/DP-2 |

**DP-4 补充铁律（编码层）**：任何"为了测试通过而绕过真实逻辑"的做法（测试里清零概率、手写状态、注入快照），都**不算修复**，只是把欠账藏起来。

**Owner 对"内容不完善"的容忍边界**（ADJ-23 §3）：允许阶段交付存在已知缺口（附条件收口），但**不允许**隐瞒/淡化缺口、不允许把 NOT_VERIFIED 包装成通过、不允许把"允许不完善"理解为"缺口不用补"。**容忍是有期限、有对价的**——对价就是完善补充义务必须记录并实行。

## 3. 三大核心循环（为什么这个游戏不是"数值模拟器"）

### 3.1 企业循环
观察产业与市场 → 识别机会/风险 → 制定公司战略 → 配置资金、人才和能力 → 执行产品与商业计划 → 获得市场反馈 → 调整组织和产品组合 → 形成长期资产与历史影响。

### 3.2 产品循环
发现需求或创意 → 产品定位 → 玩法与内容设计 → 可行性和项目规划 → 团队研发 → 测试与交付决策 → 发行上市 → 销售与口碑反馈 → 更新/扩展/续作/停止维护 → 产品档案与经验沉淀。

### 3.3 产业循环
企业决策 → 产品供给与竞争 → 消费者行为与市场变化 → 企业收益、声誉、人才与技术变化 → 合作/竞争关系重组 → 新企业、新产品、新技术与新趋势。

> **三环必须互相咬合**：若产品循环不影响公司长期能力，企业循环就变成财务表格；若企业循环不影响产业格局，世界就变成静态背景；若产业变化不反馈到玩家决策，历史系统就只是新闻墙。这三句是"不得做成数据展示模拟器"的具体判据。

## 5. 产品创造链（玩家实际走过的路）

> 这是**这个游戏最核心的一条线**。P1 的全部工作都是为了让它真实走通。

### 5.1 五个环节

| 环节 | 玩家做什么 | 系统做什么 | 对应规格 | 玩家必须能感知 |
|---|---|---|---|---|
| **① 定位** | 选类型、题材、视角、结构、规模、平台、受众、卖点、商业定位 | 四通道估算（工作量 `W_d`、技能需求、技术门槛 `TechRequirement`、市场亲和 `MarketAppealProfile`） | D-01 §4–§6 | 我的选择让成本/受众/质量往哪走 |
| **② 玩法组合** | 选 3–5 个玩法模块，定每个模块强度与深度 | 槽位规则、模块依赖、复杂度与工作量映射 | D-01 §5、§14 | 加一个模块贵多少、换来什么 |
| **③ 锁定与立项** | 锁定设计版本 → 设定预算容量 + HRB → 立项 | 冻结 `DesignVersionSnapshot`、解析 `Cost_est`、校验**承诺额 ≤ 可用现金** | D-01 §15、Project §4–§6 | 承诺了多少钱、多久能做完 |
| **④ 研发与测试** | 追加预算/缩范围/改优先级/暂停/取消；QA 看缺陷 | 工作包拆解、日产能、瓶颈、返工、缺陷生成 | Project §5–§6、D-02 §5–§6 | 哪里卡住、为什么慢、要不要缩 |
| **⑤ 交付与上市** | 选交付形式、定价档、营销预算 → 上市 | 交付闸门（零 E 级缺陷）、三质量独立计算、定价/销量/口碑结算 | D-02 §6、FIN §5、D-01 §6.5 | 为什么卖得多/少（前三个原因） |

### 5.2 关键设计约束
1. **设计与生产分离但互相约束**：玩家表达设计，系统拆成模块/工作包/任务，团队自动执行。玩家管目标、范围、优先级、资源，**不手动操作每一条底层任务**。
2. **设计必须影响成本**：任何高级深度配置，若不改变工作量、技术要求、受众匹配或产品表现，**不得成为无效参数**（不得做成纯装饰选项）。
3. **质量三分，不得合并**：设计质量 / 实现质量 / 产品完整度独立计算，**不得压缩成一个百分比**（红线）。
4. **交付形式有代价**：正式版 / 抢先体验版 / 测试版完整度要求不同，玩家必须承担相应市场预期与声誉后果。

## 6. 核心公式与数值口径（已裁定部分）

> 以下均为**已裁定口径**，编码不得擅自改；带 `OPEN` 标记的是真欠账，须裁定后才能定值。

### 6.1 HRB（预算承诺比）
- **语义**：HRB = 玩家承诺投入现金相对于预算容量的比例。（`ADJ-2026-11-21-01`）
- **承诺额** = `round(hrb × budgetCapacityCents)`。
- **约束（硬纪律，不放宽）**：`承诺额 ≤ availableCash`。
- **两档默认**：保守 `0.45` / 标准 `0.6`（默认选中档 0.45）。
- **HRB 只改 verdict，不改工作量 `W_d`**（D-01 §6.2.1）——提高 HRB 不会让活变少，只会让账更宽裕。

### 6.2 availableCash（可用现金口径）
`computeAvailableCash` = 现金 − **未来 6 个月薪资承诺** − **招聘费（1 个月）**。
- `horizonMonths = 6`、`recruitFeeMonths = 1` 是**冻结锚点**。
- 这是**保守财务口径，不是 bug**：4 人旧金山团队使 $120,000 现金降至 $48,656，差额是真实承诺预留。
- **容量守卫校验对象** = 承诺额（不是整笔容量）。（`ADJ-30` §3.1）

### 6.3 三质量（独立，不得合成）
| 质量 | 定义 | 来源 |
|---|---|---|
| 设计质量 | 方案的结构、创新、体验潜力、市场匹配 | D-02 §6 |
| 实现质量 | 团队执行质量、技术稳定、内容表现、缺陷情况 | D-02 §6 |
| 产品完整度 | 是否达到该类型/交付形式所需的核心内容、系统、技术、交付要求 | D-02 §5（按类型核心交付清单） |

### 6.4 项目执行
- `Cost_est` 由 `W_d`（各学科工作量）× 产能 × 薪资解析；`ratio = 实际/估算`。
- 生产三学科（design / programming / art）**各需专属角色**，均须 ≥ 90% 完成；QA 须 100%（`isQaComplete`）。**3 人及以下团队永远到不了 READY**（B-01c 实测证伪"降人数"杠杆）。
- 变更（继续/追加/缩范围/改优先级/暂停/取消/返工）**每次都要显示沉没成本、剩余工作、预计工期和质量/市场影响**。

### 6.5 定价（已裁定，`ADJ-26`）
```
priceCents(tier) = round(referencePriceCents(genre, platform, segment) × factor[tier])
factor: low = 0.75 / medium = 1.00 / high = 1.25
空组合兜底 = 2,999 cents，UI 明示"按默认参考价估算"
```

### 6.6 营销（已裁定）
- 三档日预算：`10,000 / 50,000 / 150,000` cents；三渠道同值。
- 必须真接线 `setMarketingBudget`，不得是装饰数字。

### 6.7 口碑（方案 C，`ADJ-26`）
- 复用已在运行的 `effectiveReviewScore` / `reviewLift`，**只读暴露** + 三档映射：`poor < 50 ≤ mixed < 75 ≤ positive`。
- **不建 BrandMemory**、**不回写** `Product.reviewScore`。

### 6.8 已登记数值欠账（OPEN，不得擅自定值）
| 编号 | 内容 | 处置 |

## 7. P1 玩家闭环：S01–S12 十二场景

> 来源：`docs/design/G1场景/S01-S12_场景规格总纲_V0.2.md`。每个场景都有"G1 最小版 / 完整版"两档；标注 `OPEN` 的值不得由编码或 UI 擅自定值。

| 场景 | 名称 | 玩家体验要点 | 关闭条件（概要） |
|---|---|---|---|
| **S01** | 创建公司 | 选地区 → 命名 → 建单一 Studio + Office → 账本开 $120,000 | 公司实体建立，现金唯一入口生效 |
| **S02** | 市场分析 | 看各群体规模/偏好/购买力，形成定位判断 | 群体词表就位、可读趋势 |
| **S03** | 产品定位与设计 | 选类型/题材/视角/结构/受众/卖点 + 3–5 玩法模块 | 四通道估算可见、设计可锁定 |
| **S04** | 创建研发项目 | 设预算容量 + HRB → 立项（校验承诺额 ≤ 可用现金） | `Project` 绑定快照、`EXECUTING` |
| **S05** | 招聘与人才配置 | 招 4 人（design/programming/art/QA）→ 分配角色 | `Person`/`Employment` 生成，薪资进入承诺 |
| **S06** | 研发推进 | 逐日推进、看瓶颈、追加/缩范围/暂停 | 工作包推进、成本可解释 |
| **S07** | 问题处理与设计变更 | 应对超支与返工，选择缩范围或延期 | 变更显示沉没成本与影响 |
| **S08** | 测试与优化 | 看 QA 缺陷清单，决定修/不修 | 零 E 级缺陷才能过交付闸门 |
| **S09** | 交付与上市 | 选交付形式 + 定价档 + 营销预算 → 上市 | **必须由 UI/生命周期自然进入 `READY_TO_DELIVER`，不得手写** |
| **S10** | 市场反馈与销售 | 看首月销量、口碑、群体渗透 | 玩家能说出产品表现前三个原因 |
| **S11** | 财务结算 | 看现金、跑道、承诺、破产预警 | 危机有可识别预警与补救窗口 |
| **S12** | 经营复盘与第二款产品 | 从档案复盘 → 决定第二款做什么 | 首个可玩版本的收尾（第二款"决策入口"即可） |

**P1 验收（正式，`01_开发阶段与验收门槛.md` §4）**：
1. 玩家至少做出 **3 次有明显代价**的关键决策；
2. 至少**两种产品定位**在同一市场产生**可解释的不同结果**；
3. 至少存在**精品路线**和**低成本路线**两种合理选择；
4. 玩家能解释产品表现的**前三个主要原因**；
5. 失败前存在**可识别预警和合理补救**，而非突然归零。

**首版范围（`ADJ-25` §2.3，方案 A）**：**一轮完整产品闭环 + 第二款产品决策入口**。不把"两轮完整经营且第一轮影响第二轮"设为首版门槛。

## 8. 红线（违反即返工，不接受"设计上成立"）

### 8.1 产品设计红线（V3.0 基线 §14，12 条）
不设强制终极胜利 · 不把产品做成可互换数值单元 · 不让 AI 有不透明经济特权 · 不让世界依赖玩家行动才演化 · 不模拟无经营价值的私人生活与每个消费者 · 不把商业关系做成独立重复系统 · 不把真实历史做成强制脚本 · 不把科技做成线性解锁树 · 不用员工/项目/金额简单膨胀制造后期深度 · 不用单一综合分掩盖质量/完整度/市场匹配差异 · 不因旧代码或旧冻结声明阻止产品级重规划 · 不因宏大愿景把所有系统同时塞进当前阶段。

### 8.2 工程不变量（P1 清单 §三，必须实测）
| # | 不变量 | 实测方式 |
|---|---|---|
| R1 | 单一现金入口 | `grep "cashBalanceCents\s*="` 除账本派生外为零 |
| R2 | 现金恒等式 | 200 笔混合交易后 `cash == Σ amount`；改 `status` 不影响求和 |
| R3 | 承诺不改现金 | 立项 + 追加预算后账本交易数不变 |
| R4 | 闸门 fail-closed | E 级违规任一通道 ⇒ 禁切快照 / 禁交付 |
| R5 | 三质量不合成 | 无 `overall` / 加权平均字段 |
| R6 | `team_d` 与 Project 公式一致 | `Cap_code=32 / design=18 / art=8` 固定值断言 |
| R9 | **同 seed 确定性** | 同 seed + 同操作序列 ⇒ 结果逐字段一致（**覆盖全新开局**，不只是续跑） |

### 8.3 确定性红线（本阶段新增，`ADJ-27`/`ADJ-29`）
- 任何参与模拟判定的实体 ID 必须**确定性派生**（如 `emp-<saveSeed>-<递增seq>`），**禁止随机 UUID**。
- 禁止用"测试里清零概率/固定随机源"让测试变绿而回避真实非确定性——那是隐藏欠账。
- 新增涉及随机判定（离职、AI 决策、销量扰动）的功能，测试必须补"同 seed 可复现"断言。

### 8.4 呈现红线
- 每个经营界面必须优先回答四问：**当前发生了什么 / 为什么 / 我有哪些有意义的选择 / 每个选择的代价与风险**。
- 预测必须显示**区间、更新时间、关键假设**，禁止把估算显示成确定事实。
- 通知按重要性分级并合并：重大风险/合同承诺/关键人才流失/交付决策必须明确提示；普通每日交易不打断玩家。
- 领域层**零展示文案**，所有文案走 i18n。

## 9. 不做什么（防止无限扩张）

### 9.1 不进入当前规划（V3.0 §8，9 项）
玩家经营游戏平台或硬件制造商 · 玩家把引擎当独立商业生态 · 完整股票市场/IPO/复杂融资/衍生品 · 复杂并购重组与多事业部控股 · 每个消费者个体生活模拟 · 员工家庭恋爱私人社交 · MMO/联机与创意工坊 · 未来时代的完整产业预测 · 为数据量建无玩法影响的百科数据库。

> 这些不是永久禁止，但必须**另立设计论证**，不能以"架构预留"为由提前做入口和复杂实现。

### 9.2 P1 阶段明确不做
全球/多地区经营 · 品牌长期记忆系统 · 平台历史准入与生命周期 · 科技领域与知识扩散 · 合同/合作/外包框架 · 产业编年史 · 多工作室与组织授权 · 企业文化模拟 · 抢先体验/测试版完整度差异 · 更新/续作/退市 · 联机。
