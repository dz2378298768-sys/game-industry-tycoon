## 0. 修订边界声明

本件**不是** V3.2，是 V3.1 的修订包。它只做三件事：

1. 把 8 项变更落成**可直接替换的文本**（不留在讨论层）；
2. 补齐审查中发现的跨文档不一致（阶段体系、规格状态、遗留项定性）；
3. 为每项变更给出**可被独立审核者验证的判据**——否则下一轮仍会"写完就算改了"。

**不做**：不重新定义游戏愿景；不改 V3.1 §1/§2/§7/§10/§11/§13 的原文；不改 V3.0 基线内容（V3.0 是基线，改动须走独立裁定）。

## 2. `V3.1-01` 阶段体系映射

### 2.1 替换：§5 章首（从"项目采用六个主要研发阶段"到 G0 标题之前）

**原文**

> 项目采用六个主要研发阶段，并设置持续性的基础治理工作。
>
> 阶段不是纯粹的时间划分，而是以可验证的玩家体验和工程成果作为出口条件。

**替换为**

> 项目采用六个研发里程碑（G0–G6），并设置持续性的基础治理工作。
>
> **阶段编号的权威归属**：
>
> - **P0–P7 是项目正式阶段编号与验收权威**，来自 V3.0 基线 `02_版本路线图/01_开发阶段与验收门槛.md`。任何"某阶段已通过"的结论，最终以 P 阶段的「必须具备」+「验收」全部满足为准。
> - **G0–G6 是执行层的里程碑编号**，用于拆解研发顺序、排定依赖、组织试玩与专项验证。G 是 P 的细化，**不另建一套并行阶段体系**。
>
> 三条判定规则：
>
> 1. **G 通过不蕴含 P 通过。** G1 的场景与任务全部完成，不自动代表 P1 通过。
> 2. **P 通过必须以 G 通过为必经路径。** 就当前规划而言，G1 是 P1 的唯一实现路径，故 G1 通过是 P1 通过的必要条件（非充分条件）。
> 3. **P 的验收口径不得被 G 收窄。** 若 G1 的出口条件与 P1 的验收条件冲突，以 **P1 为准**，并修订 G1 出口。
>
> 里程碑不是纯粹的时间划分，而是以可验证的玩家体验和工程成果作为出口条件。

### 2.2 新增：§5.0 `G ↔ P` 对照表

见**附录 A**（全文照录）。要点：

- **无一对是 1:1。** 7 个 G 与 8 个 P 是重新切分，不是改名。
- `G1` **越界**含 P2 的一项（完整度独立计算）；`G3` **窄于** P3（缺"合作谈判/反报价/合同履约"完整链路）；`G5` 是 **P5 + P6 的合并**。
- 因此附录 A 必须逐条标注「完全对应 / G ⊂ P / G ⊃ P / 跨阶段合并 / 部分重叠」，**不得仅凭名称相似认定等价**（这是总设计师明确要求的一条）。

## 3. `V3.1-02` G1 验收标准

### 3.1 替换：§5 G1「阶段出口」整段

**原文（7 条）**

> 新玩家能够独立完成游戏流程。／至少完成两轮产品经营。／第一轮经营结果会影响第二轮。／财务、项目、人才和产品状态一致。／UI 能够完成主要玩家任务。／不存在必须依靠开发者手动修改数据才能继续的关键流程。／体验 Agent 完成试玩并确认核心体验问题已处理。

**替换为（14 条，分三组：A 可玩性 5 / B 经营深度 5 / C 策略多样性 4）**

> **A 组：可玩性（来自 V3.1 原文，保留）**
>
> - `G1-A1` 新玩家能够独立完成从创建公司到第二款产品决策的完整流程，无需开发者介入。
> - `G1-A2` 至少完成两轮产品经营，且两轮之间存在**可观测的因果传递**（见 `G1-B3`）。
> - `G1-A3` 财务、项目、人才、产品四类状态在同一时点相互一致（账本 `INV-1` 与承诺注册表一致）。
> - `G1-A4` UI 能完成 S1–S16 全部场景的主要玩家任务，不存在"必须靠手工改数据才能继续"的流程。
> - `G1-A5` 体验 Agent 完成试玩并确认核心体验问题已处理（判据见 §8.1 第四门）。
>
> **B 组：经营深度（恢复自 V3.0 P1 验收，本次必须补回）**
>
> - `G1-B1` 玩家至少做出 **3 次有明显代价的关键决策**，且每次决策的代价在当时可观测（不只是事后总结）。
> - `G1-B2` **至少两种产品定位在同一市场产生可解释的不同结果**——不是"数字不同"，而是玩家能说出"为什么不同"。
> - `G1-B3` **第一轮经营结果在五个维度上真实影响第二轮**，且至少三个维度可被玩家感知：
>   ① 资金（现金充裕/紧张改变可选规模）；② 团队（成员经验与能力变化改变可承担的范围）；③ 企业认知与声誉（前作表现改变市场预期与议价）；④ 市场环境（前作与 AI 竞品改变需求结构）；⑤ 前作资产（产品档案、技术积累、用户基础）。
>   **判据**：若把第一轮的结局改为"成功/失败"两种极端，第二轮的初始状态必须有可量化差异；若差异仅体现在现金数字，不通过。
> - `G1-B4` 玩家能解释产品表现的前三个主要原因（设计、研发、市场三类归因至少各命中一次）。
> - `G1-B5` 失败前存在**可识别的预警**和**合理补救**，而非突然归零（见 §4 S13–S16）。
>
> **C 组：策略多样性（本次新增，防止"唯一最优解"）**
>
> - `G1-C1` **不存在全局唯一最优策略。** 至少三条路线在各自适用情境下都成立：**精品路线**（高投入/长周期/高风险/高上限）、**低成本路线**（小范围/短周期/低占用/快验证）、**快速迭代路线**（中等投入/多产品/靠更新与续作摊薄风险）。
> - `G1-C2` 三条路线**不得只差在成本数字**，必须在风险结构、市场定位、开发节奏、产品结果四处产生差异。
> - `G1-C3` 任一路线在**其不适用的情境下必须失败**（否则该路线是普适解，等于唯一解）。这是 `G1-C1` 的反证条件，必须实测。
> - `G1-C4` 策略验证由**系统模拟与数值平衡 Agent** 出报告、**体验 Agent** 验证决策是否有意义，两者结论不一致时不得判 G1 通过。

### 3.2 补：§3.2「首发必须具备」追加两项（`X-2`）

**追加**

> - **基础财务和现金预测**（V3.0 P1 必须具备项）：`CashBalance` / `AvailableCash` / `RunwayMonths` 三口径分离，跑道可用于玩家判断"还能撑多久"。
> - **破产预警与有限补救**（V3.0 P1 必须具备项）：预警可识别、补救手段可用（缩规模/砍项目/延期/取消），破产为 AND 判据、非随机。

**理由**：V3.0 P1 必须具备 8 条中，此两项在 V3.1 §3.2 的 17 条里缺失。若不补，"满足 P1 全部验收才宣布 P1 通过"这条规则永远无法达成，而 `OPEN-F3′` 也会失去归属（它正是"现金预测"的实现缺陷）。

## 9. `V3.1-08` 失败路径与经营策略验证

### 9.1 新增：§4 追加 S13–S16（失败分支）

现有 S1–S12 只描述顺利路径，必须补四个失败分支。**失败不能是弹窗，也不能突然结束游戏。**

| 场景 | 触发 | 玩家可选 | 系统必须反馈 |
|---|---|---|---|
| `S13` 项目严重延期 | 工作包阻塞、技能不匹配、范围膨胀 | 缩范围 / 改设计 / 加人 / 延期 / 暂停 / 取消 | 延期对现金与市场窗口的具体影响；剩余工作量的重新估算 |
| `S14` 质量不足仍交付 | 玩家选择降低交付目标进入市场 | 继续优化 / 降级交付（抢先体验/测试版）/ 取消 | 质量缺口如何转化为评价与退款率；不是"警告后照常卖" |
| `S15` 上市表现不佳 | 定位错配、竞品挤压、口碑崩塌 | 降价 / 营销补救 / 更新 / 停更 / 转入下一款 | 归因（设计/研发/市场三类），且玩家能看懂 |
| `S16` 现金流恶化 | 连续亏损、承诺支出堆积 | 裁员 / 砍项目 / 缩规模 / 延期付款 / 重整 | **可识别预警（跑道、LOW_RUNWAY）+ 补救窗口 + 破产为 AND 判据非随机** |

**硬性要求**：

- `S16` 的预警**必须建立在正确的 `RunwayMonths` 上**（`ADJ-11`），否则 S16 与 S11 一起失效。
- 每个失败场景必须有**至少一条可行的脱困路径**，且脱困代价可观测（不是"点一下就好"）。
- 破产只能由**明确的 AND 条件**触发（现金 < 0 且补救窗口耗尽 等），**不得随机**。

### 9.2 新增：§8.4 经营策略验证矩阵

| 路线 \ 情境 | 资金充裕 | 资金紧张 | 强竞品市场 | 空白市场 |
|---|---|---|---|---|
| 精品（高投入/长周期） | 应成立 | 应成立但高风险 | **应成立**（差异化突围） | 可能过度投入 |
| 低成本（小范围/快验证） | 可能浪费机会 | **应成立** | 应成立 | 应成立但上限低 |
| 快速迭代（中等投入/多产品） | 应成立 | 应成立 | 应成立（靠更新） | **应成立** |

**判据**：

1. 每条路线至少有一个"**应成立且确实成立**"的格子；
2. 每条路线至少有一个"**应失败且确实失败**"的格子（`G1-C3`）；
3. 不允许任何一路线在所有格子都成立（那是唯一解）；
4. 不允许任何一路线在所有格子都失败（那是死玩法）。

**责任**：系统模拟与数值平衡 Agent 出矩阵报告；体验 Agent 验证"玩家是否真的感知到路线差异"；两者不一致不得判过。
