## 六、问题证据与推导

### R-01（BLOCKER）工作量公式不可执行

**证据**：
- §6.2 第 447 行：`W_d(instance i) = baseWorkUnits[i][d] × intensityCurve[i.intensity] × depthMultiplier(i.depthSelection) + …`。全文检索 `depthMultiplier` 仅此一处；§4.10 定义深度层为 `depthSelection` + `optionSelections` + 四种 `Delta`，从未定义 `depthMultiplier` 函数或数值。
- §4.7 第 270 行定义 `workUnitsPerTier: map<discipline, WorkUnit>`（按学科键）；§6.2 第 450 行却写 `workUnitsPerTier[c.compatibleDomain][d]`（按域键再按学科），且 §4.7 第 268 行字段名为复数 `compatibleDomains: list<ref>`。
- §6.2 第 466 行 `synergy = 1 − |distinct tags| / |total tag occurrences|`，空设计/无标签时 `|total|=0` 除零；E-1 仅规定空组合在"锁定时"阻断，而 §4.11 规定估算在"每次修改"时重算，草稿空状态必然触发该计算。

**推导**：编码 Agent 实现 `W_d` 时，遇到 `depthMultiplier` 无定义 → 只能自造一个深度倍率；遇到 `workUnitsPerTier` 键类型不符 → 必须二选一（改数据结构或改公式）；草稿空状态重算 → 除零异常。三种情况均属"用临时实现替代设计决定"，违反 §2.5D。任务卡验收标准第 4 条"可执行、无空泛描述"不成立。

### R-02（BLOCKER）市场画像公式不可执行

**证据**：
- §6.5 第 540 行：`affinity[SegmentTag] = Σ_i audienceAffinity[i.template][tag] × intensityWeight(i) + Σ option.affinityDelta`。`intensityWeight` 全文仅此一处，未定义；§4.6 只定义了工作量用的 `intensityCurve`，二者语义不同。
- §4.10 第 301 行选项增量为 `audienceAffinityDelta`，公式写 `affinityDelta`，命名不一致。
- 第 541 行：`positioningFit = cosine(…) 的简化版：1 − Jaccard 距离 × k_fit`。Jaccard 距离定义在**集合**上，而此处两个操作数是"宣称受众的亲和"与"实际拓扑的亲和"（实值向量）；未给阈值化规则，数学上无定义。
- 第 542 行：`uspCredibility = 支撑强度 / 宣称强度`，而 §16 OPEN-O1 明确"每条卖点如何被'支撑强度'量化"为 **OPEN**；`宣称强度` 亦无定义（卖点是 1–3 条二元宣称）。

**反证推演（OPEN 伪装检测）**：设计 Agent 在 §16 诚实标记 OPEN-O1，却在 §6.5 把它当作已确定公式写入产出字段 `uspCredibility`，并在 §10.6 D-LOCK、§9.4 中作为"卖点可信度"展示给玩家。编码 Agent 无法计算该字段；若要实现只能自行定义支撑强度，等于把 OPEN 决策偷偷固化为规则——正是协作规范 §2.3D「不得将未确认假设伪装成确定规则」所禁止。

### R-03（BLOCKER）技术/风险公式不可执行

**证据**：
- §6.4 第 504 行 `perspective.baseTechGate`：§4.3 第 197 行 `perspectiveId` 是枚举 `{side_scroll,…}`，不含 gate 字段；§5.2 声称"视角带 baseTechGate"但无枚举→gate 映射。
- 第 507 行 `option.techGates`：§4.10 选项字段仅 `costDelta/skillLoadDelta/audienceAffinityDelta/riskDelta`，无 `techGates`。
- 第 505–506 行 `platform.techStandard gates`、`structure.extraGates`：平台为 `ref Platform`、结构为枚举，接口未给取 gate 的方法。
- 第 523 行 `R_synergy = Σ softConflict.penalty（归一化到 [0,1]）` 未给归一化式。
- §4.11 的 `RiskProfile` 含三个子风险，§10.6/§9.4 要求显示单一"风险等级"，但全文无三合一规则。

**推导**：`T` 集合的四个来源中三个无字段支撑，`R_synergy` 与总风险等级不可计算。TechGate 接口格式（§4.8）虽定义，但"从哪个实体取 gate"未定义，编码无法构造 `T_unsat`，连带 `R_tech` 与 E-TECH 判定失效。

### R-04（CRITICAL）GameplayArchetype 实体缺失

**证据**：§4.3 第 194 行 `primaryTypeId: ref GameplayArchetype(数据)`、第 195 行次类型；§14.2 第 863 行"对类型库中每个已有 GameplayArchetype 计算相似度"；§14.4 "提升的类型…可作主类型"。但 §4.1 实体总览（第 156–172 行）列出 12 类实体，**不含 GameplayArchetype**；全文无该实体的字段、状态、生命周期定义。

**推导**：主类型是锁定必填项（§4.3 约束）且是 7 维区分度首位（§5.5），其引用的实体却无定义 → 编码需要自行发明类型库数据结构；L2/L3 的相似度匹配（§14.2）无库可查，TC-11/TC-12 无法落地。

### R-05（CRITICAL）返工绕过硬规则（反证案例）

**证据**：§5.3 第 380 行卖点支撑为硬规则、§11 E-1 必选槽为空阻断锁定；§15.2 第 909 行 B 类"停用 active→deactivated"属返工；§7.2 第 594 行 REWORK→EXECUTING 的唯一前置是"ReworkTask 全完成"，无重校验；§15.3 新快照在返工完成时直接生成切换。

**反证推演（玩家可利用的漏洞）**：
1. 玩家锁定并立项一款游戏，主类型只有 1 个必选核心槽，里面只有 1 个 `combat` 模块，且该模块是卖点"激烈战斗"的唯一支撑。
2. 研发中玩家提交"停用该模块"的 B 类变更并确认返工（§15.2 允许，沉没成本自担）。
3. 返工任务完成 → 按 §7.2 生成新 `BlueprintVersion` + 新快照，`Project.snapshotId` 切换，状态回到 `EXECUTING`。
4. 此刻必选槽为空、卖点无任何支撑，但**没有任何一条规则再次执行 E-EMPTY/E-USP 校验**（锁定校验已发生过，返工完成不重校验）。
5. 项目继续到 `COMPLETED`（§7.2 交付无校验前置），产品带着空核心槽和虚假卖点上市。

结果与 §5.3 硬规则、X4「品味责任」直接矛盾。修复必须要求在"新快照生成/返工完成"处复用 §5.3 全部硬规则校验，且失败时不允许切换权威快照。

### R-06（MAJOR）R-COM-7 悬空引用

**证据**：`R-COM-7` 出现在 §4.3 第 200 行、§4.6 第 258 行、§5.2 第 369 行、§5.3 第 380 行描述中；但 §5.4（第 383–407 行）只定义 `HardConflict`/`SoftConflict`/`RequireRule`/算法 R1/传递闭包，**没有编号为 R-COM-7 的规则**，也没有任何"规则编号表"。

**推导**：多处引用指向不存在的规则 ID；编码无法据 ID 定位校验逻辑，UI 错误对象 `ruleId` 也无法填充（§11 通用错误格式要求 `ruleId`）。

### R-07（MAJOR）OPEN-O5 被当作确定输出

**证据**：§8.2 第 626 行将 `qualityCeilingBand` 列为给 Project 的只读输出契约；§6.2.1 第 480–481 行称 HRB 两端对应质量上限升/降；但 §16 OPEN-O5 明确"`HRB` 的上下限与 `qualityCeilingBand` 映射"为 **TUNING**，无映射公式。

**推导**：D-01 承诺了下游可消费的字段，却未给该字段的任何计算方式。Project 规格编写者无法定义如何消费，属于把 TUNING 项伪装成已交付接口。

### R-08（MAJOR）HRB 与规模裁定冲突

**证据**：§4.3 第 205 行"规模由槽位数量+模块档位+内容包档位自然导出"、第 207 行"禁止在实现中重新引入单一规模或复杂度字段"；G4（第 55 行）"规模仅作为预设（BlueprintPreset）"；迁移裁定表"项目规模和功能清单→REWORK：从规模参数转为…规模仅作为预设"。而 §6.2.1 第 474 行 HRB"替代旧的'规模参数'"，第 477 行 `HRB_scale` 作为全局乘子作用于全部 `W_d`，范围 0.75–1.6。

**推导**：HRB 是一个与结构无关的连续全局努力乘子，效果上就是被 REWORK 移除的"单一规模参数"换名复活。两处规格对"规模从哪来"给出互斥答案；实现者无法判断应服从 §4.3 还是 §6.2.1。此外 HRB 既称"本项目人力预算"（R-ORG-2），又通过放大工作量决定成本，与 Project 的成本口径形成未定义的循环。

### R-09（MAJOR）REWORK 状态矛盾

**证据**：§7.1 第 561 行将 `REWORK` 列为状态枚举值，状态图画出 `[REWORK]` 节点，§4.9 第 289 行 `state` 直接引用该枚举；但 §7.2 第 593–598 行裁定"`REWORK` 不是独立状态…而是'EXECUTING+返工会话'的呈现式标签"，并在转换表写 "To=REWORK、EXECUTING 保持不变"。

**推导**：编码无法判定 `BlueprintVersion.state` 是否会被赋值为 `REWORK`。更关键：第 594 行返工完成"追加新 BlueprintVersion 并重新绑定"，但该新版本出生为何状态（DRAFT/LOCKED/EXECUTING）未定义——若按 §7.1 从 DRAFT 起，则又需走一遍 IN_REVIEW/LOCKED，与 §15.3"返工完成直接切换快照"冲突。

### R-10（MAJOR）TC-16 与规格冲突（反证案例）

**证据**：TC-16（第 984 行）期望"估算重算结果与历史差异**仅在 formulaVersion 变化时出现**"；但 §6.6 第 552 行定义 `Δ_team`（团队能力不确定度，来自 Project）并单独显示，团队能力随月份变化；§4.11 第 315–318 行规定 `TechRequirement`/`MarketAppealProfile`/`RiskProfile` **每月**重算；§12 S3 第 826 行要求"打开时重算并与历史值比较（用于'为什么估算变了'提示）"。

**推导**：在同一 `formulaVersion` 下，外科技能力、市场档案相似度、团队能力变化都会使估算值改变。若编码按 TC-16 实现，将错误地把真实变化隐藏；若按 §4.11/S3 实现，则 TC-16 必然失败。验收标准自相矛盾，测试无法编写。

### R-11（MAJOR）存档状态不一致

**证据**：§12 S1 第 824 行持久化清单仅列 `ProductBlueprint/BlueprintVersion/ModuleInstance/DesignVersionSnapshot`，**不含 `ReworkTask`**（§4.1 第 168 行列为实体）也不含 §7.2 第 593 行"另存"的返工会话；§12 S3 要求"与历史值比较"，但未指定历史估算值的持久化载体（`evaluationSummary` 在 §4.9 被标为"派生，可重算"，是否持久化不明）。

**推导（长期存档反证）**：玩家在 `EXECUTING` 中启动返工并存档 → 读档后返工会话/`ReworkTask` 丢失，但版本仍停在"应处于返工"的状态，`Project.snapshotId` 指向旧快照且无任务可完成 → 状态不一致，玩家无法继续也无法退出该返工意图；只能通过"放弃项目"兜底。

### R-12（MAJOR）templateRevision 字段缺失

**证据**：§12 S2 第 825 行要求"模板版本需快照（`templateRevision`）"；§4.6 `ModuleTemplate` 字段表（第 246–259 行）无 `templateRevision`。

**推导**：S2 的目的是"模板库改版后仍能重放旧设计"，但没有版本号可快照，快照自包含性无法保证，长期存档重放会随模板改动而漂移。

### R-13（MAJOR）单向数据流矛盾与 genreFit 缺失

**证据**：§3.1 标题"数据流方向（单向）"；§8.1 第 619 行明确输入来源包含"市场（D-04）| 受众标签词表 | 仅供玩家宣称选择"，且 §4.3 `targetSegmentClaims` 依赖该词表。§5.2 第 364 行称 `typeAffinity` 影响 `MarketAppealProfile` 的 `genreFit`，但 §6.5 输出表（第 538–544 行）字段为 affinity/positioningFit/uspCredibility/noveltyNote/contentVolumeBand，**无 genreFit**。

**推导**：D-01 与 D-04 实际双向依赖（D-01 吃词表、D-04 吃画像），"单向"表述会误导依赖顺序与并行设计边界（协作规范 §5.1 要求接口确定才可并行）；`genreFit` 作为被承诺的中间量却无定义，D-04 无法消费。

### R-14（MINOR）UI 深度与类型切换

**证据**：协作规范 §2.3B UI 要求含"排序和筛选、点击/悬停/选中行为、操作反馈"；§10 全文仅 §10.3 有"筛选"无"排序"，无悬停行为，无通用操作反馈（成功保存/锁定反馈仅 §10.2 错误条涉及失败）。§10.2 第 714 行"已装模块若不再兼容 → 标记不兼容并要求玩家处理，**不自动删除**"，但未定义"处理"是替换/停用/删除，也未限制步骤数。

**推导**：设计者自列关注点 3 成立——切换主类型会重建全部槽位并使所有已装模块"不兼容"，玩家须逐个手动处理且无批量规则，可能造成大量无意义点击（违反基线 §13/规范 §6.5）。

### R-15（MINOR）关注点与 P6 无验收场景

**证据**：§18"建议审核关注点"1（k_syn 平衡"需模拟验证"）、2（返工阈值动态化）、4（L3 过保守阻碍 AI）均未进入 §17 测试场景；§13 P6 要求"简化估算不得改变最终锁定结果"，§17 无对应 TC。

**推导**：无验收场景即无法证明这些关注点被解决；若直接编码，关注点 1 的失衡与 P6 的口径分歧会潜伏到 P2/P3 才暴露。

### R-16（MINOR）字段一致性

**证据**：§11 E-16 使用 `OptionGroup.required=true`，但 §4.10 容器定义未声明 `required` 字段；§6.5 `noveltyNote` 引用"近 N 个"产品，N 无 TUNING 值；§4.6 `uspIds: list<SPId>` 与 §4.3 `USPId` 命名不一致。

### R-17（SUGGESTION）时序一致性

**证据**：§4.12 快照 `estimates` 为锁定时刻值"后续重算不覆盖"；§4.11 `TechRequirement` 每月重算；E-6 允许技术可突破时锁定并打高风险标记。

**推导**：技术突破后，冻结快照仍带"高风险"标记，而当前世界能力已满足。需明确以哪个为准（档案追溯应保留冻结值，执行期提示应反映当前值），否则 UI 与 Project 风险口径不一致。
