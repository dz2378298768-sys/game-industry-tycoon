## 六、问题证据与推导

### F-01（BLOCKER）INV-1 现金恒等式自相矛盾

**证据**：
- §3.1 INV-1（L112）：`LedgerAccount.cashBalanceCents == Σ(amountCents)`，括注"对全部 `status=posted` 交易求和，已冲销交易与其反向交易相加为 0"。
- §3.1 `status`（L107）：`enum{posted,reversed}`，"冲销只改状态，不删记录"；§5.6 BR-6（L301）：原交易 `status=reversed`，反向交易记 `reversalOf`，金额为"符号相反"。

**反证推演（重复记账/读档漂移）**：
1. 原交易 T1 `+100`、`status=posted`，按 INV-1 求和余额 = +100。
2. 退款冲销：T1 置 `reversed` 并按"只求和 posted"被**排除**；反向交易 T2 `−100`、`posted` 被计入 → 余额 = −100。
3. 但经济上 $100 销售全额退款后余额应为 0；T2 的 `balanceAfterCents`（L103）= 入账前 100 + (−100) = 0，与 INV-1 求和值 −100 直接冲突。
4. "已冲销交易与其反向交易相加为 0"只有在二者**都计入**求和时才成立（+100 + (−100) = 0），与"仅 posted 求和"互斥。
5. 后果：§10.5 `replay` 从 `Transaction[]` 按 INV-1 重建，遇任何退款必然校验失败并报 `LEDGER_INCONSISTENT`（§10.5/L496）；§9.1 错态"账本不一致→禁止继续入账"在每笔退款后触发，整个账本停摆。

**修改要求**：二选一并全篇统一——(a) INV-1 改为"对**全部**交易 `amountCents` 求和，`status` 仅作审计标记不参与余额计算"（推荐，冲销对自然为 0）；或 (b) 明确 `status=posted` 的定义包含冲销对并修正求和口径。补一条 TC：全额退款后余额回到 0 且 `replay` 通过 INV-1。

### F-02（BLOCKER）跨月 `monthly` 承诺兑现遗漏/越界

**证据**：
- §3.3（L136-139）：`amountCents`="每周期计划支出"，`realizedCents` 约束 `0..amountCents`，状态 `realized` 当 `realizedCents = amountCents`。
- §4.1（L230-234）：`realizedCents += |amountCents|`；`realizedCents < amountCents → partially_realized`，`= amountCents → realized`。
- §10.3（L488）：跨月时"每月按 `period` 生成一笔兑现交易（幂等键含承诺 id + 月份）；`realizedCents` 逐月累加；中途取消只停止未来兑现"。

**反证推演（跨月承诺遗漏）**：
1. 场景 A 步 3 的 5 人月薪为 `period=monthly`、`startAt..endAt` 跨 6 个月的承诺，`amountCents` = 单月工资。
2. 第 1 月兑现后 `realizedCents = amountCents` → 状态置 `realized`；若系统按"已 realized 不再兑现"理解（§4.1 的语义终点），第 2–6 月薪酬**不再兑现** → 跑道与现金被严重高估，场景 A/B 的"月薪承诺缩短跑道"失效。
3. 若系统忽略状态继续逐月兑现（§10.3"逐月累加"），`realizedCents` 达 2×~6× `amountCents`，**违反 `0..amountCents` 硬约束**，状态卡在 `realized` 不再表达进度。
4. 两条路径均不可接受，根因是"每周期金额"与"跨周期累计"被同一字段 `amountCents` 承载。

**修改要求**：为 `monthly` 承诺把累计基准改为"总额 = `amountCents × 周期数`"并放宽 `realizedCents` 上限，或令 `realizedCents` 按周期归零/单独记录当前周期已兑现额；状态判定对 `monthly` 与 `one_off` 分别定义；补 TC：6 个月月薪承诺恰好产生 6 笔兑现交易、`realizedCents` 合法、跑道逐月下降。

### F-03（CRITICAL）破产判定条件内部冲突

**证据**：
- §5.9（L322）："负现金本身不是破产判定线……持续为负且窗口耗尽才破产（因果链）"——要求 **AND**。
- §6.4（L373）：破产线 $0，"现金低于 0 且窗口耗尽→破产"——**AND**。
- §4.2（L250）："窗口耗尽 / 现金<0 未解 → bankrupt"——**OR**；§10.1（L480）："需窗口耗尽**或**跌破破产线才破产"——**OR**。
- 破产线 = $0，"跌破破产线"即现金 <0；故 §10.1 等价于"窗口耗尽 或 负现金 → 破产"，与 §5.9 "负现金本身不是破产判定线"直接矛盾。

**推导**：编码无法判定"固定结算导致单日负现金但补救窗口未耗尽"时是否立即破产。按 OR 实现则负现金当天破产（有随机惩罚观感、违背 §0 "非随机因果链"）；按 AND 实现则行为不同。任务卡"预警与补救可执行"与基线 §12 "有限补救窗口"均依赖该判据唯一。

**修改要求**：统一为单一可判定式，建议："负现金 → `critical` + 原因码；负现金**且**窗口耗尽 → `bankrupt`"（AND，与 §5.9/§6.4 一致），并据此修订 §4.2/§10.1 表述与 TC-12。

### F-04（MAJOR）跑道公式含未定义符号 `CumAvailable(m)`

**证据**：§6.1（L337-338）用 `CumAvailable(m) ≤ 0` 判定首次 crossing，并称"可为小数插值"；全文（grep 确认）仅此一处出现 `CumAvailable`，§6.2 只定义标量 `AvailableCash`（L346-350），无 `CumAvailable(m)` 的累计定义与插值公式。

**推导**：编码实现 `runwayMonths` 时无法确定 `CumAvailable(m)` 是"现金余额累计 − 累计净烧"还是"AvailableCash 按月递推"，也无小数插值算法；TC-10（§13 "给定现金与承诺，runwayMonths 符合 §6.1"）无法编写，属协作规范 §2.3D"用临时实现替代设计决定"。

**修改要求**：定义 `CumAvailable(m) = Cash_0 − Σ_{i≤m} NetBurn_i`（或明确以 `AvailableCash` 为起点递推），给出小数插值公式或标 `OPEN`/`TUNING`；与 §6.2/§6.3 口径统一后同步 TC-10。

### F-05（MAJOR）预测区间三带公式不自洽

**证据**：§6.3（L362-366）：
- `Cash_m(low)` 用 `ExpectedPayable_i × p_pay_high`，而 L366 把 `p_pay_high` 列为"置信**折减**系数"（应 ≤1），却在此用于放大最差情形应付，语义矛盾；
- `Cash_m(high) = Cash_0 + Σ(ExpectedIn_i × p_in_high − CommittedOut_i × p_out_low)` **完全省略 `ExpectedPayable_i`**，而 expected/low 两带均含应付；best 带隐含"应付不发生"，未声明。

**推导**：四个 `p` 系数的取值方向（哪些 >1、哪些 <1）未定义，best 带与其余两带口径不同，UI"最好/预期/最差"三带不可比；`lowCashDate` 依赖 `Cash_m(low)`，系数方向错误会颠倒预警时点。

**修改要求**：明确定义 `p_in_low<1<p_in_high`、`p_pay_high>1`、`p_out_low<1` 等方向与取值（TUNING），统一三带是否含应付并给 best 带公式；同步 FIN-T3。

### F-06（MAJOR）滞后区间零宽度 + 窗口重置漏洞

**证据**：
- §6.4（L372-374）：警告线 = 恢复线 = `$4,000`，宣称"形成滞后区间（0~$4,000 不反复切换）"；但 healthy↔watch/warning 的切换恰发生在 $4,000 处，恢复点与触发点同值 → **零宽度滞后**，现金在 $4,000 附近震荡即反复横幅开关。
- §4.2（L249）：`critical` 在"窗口内现金恢复到 recovery 线 → watch"；重入 `critical` 时 `remediationDeadline`（§3.6 L189）是否重置未定义。

**反证推演（玩家可利用）**：玩家在 `critical`、60 天窗口倒数中，只需短暂把现金推过 $4,000（如延迟一笔固定结算、确认一笔 `advance` 预付款）即脱离 `critical → watch`；随后现金回落再次进入 `critical`。若重入按"新窗口"重算 deadline，则可无限重置，任务卡"有限补救窗口"形同虚设。零宽度滞后使该踩线操作每天可重复。

**修改要求**：设恢复线严格高于警告线（如 warn=$4k / recover=$6k，TUNING），形成真实滞后带；明确"重入 `critical` 沿用原 `remediationDeadline`、不重置"；TC-12 改为验证恢复线 > 警告线且窗口不重置。

### F-07（MAJOR）补救代价与重整后果未定义到可执行

**证据**：§8.1（L419-425）列出补救动作集但无代价计算；§9.4（L468）要求每张补救卡显示"对现金、跑道、债务、声誉、人才、控制权的影响预览"，§1.2 同；§3.6 `restructuringConsequences: object/null`（L191）仅注释"债务/资产/声誉/人才/控制权后果"，无字段；TC-14（L550）要求"留下……后果，非免费复活"，无判据。§3.9 `severance` 仅标"裁员一次性"无金额口径，`advance` 无偿还义务定义（§2.2 明确无贷款契约）。

**推导**：编码无法实现"代价预览"（如遣散费金额、资产出售折价、合同终止罚金、`advance` 是否形成债务）与"重整后果"（`object` 无结构）；基线 §12 "重整不是免费复活，必须留下债务、资产、声誉、人才和控制权后果"无法落地，TC-14 无法验收。

**修改要求**：为每类补救动作定义代价的输入与公式（参数可 TUNING）；把 `restructuringConsequences` 结构化为字段（如 `debtCents`/`assetChanges`/`reputationDelta`/`talentLoss`/`controlChange`）并定义进入重整/破产时的写入规则与玩家可见预览。

### F-08（MAJOR）破产沙盒观察态与账本账户状态冲突

**证据**：§3.2（L124）`LedgerAccount.state` "破产清算后 `closed`";§10.4（L492）`sandbox_observe` 下"世界/AI 继续运行、既有固定结算按规则继续";§3.7（L200）称观察态"不改变世界继续运行"（"不改变"语义含糊）。

**推导**：若账户已 `closed`，固定结算薪酬/租金如何 `postTransaction` 未定义；破产公司是否继续产生新承诺、是否继续计负现金未定；§4.3 S-FIN-3 要求 AI 同状态机，但 AI 破产公司由谁决定进入观察态未定。状态不一致会在读档重放时放大（F-09）。

**修改要求**：明确 `sandbox_observe` 下账户 state（建议 `frozen` 而非 `closed`）、允许/禁止哪些交易 post、既有固定结算是否继续及是否停止新增义务、AI 破产公司的观察态处理，并与 M1.2 破产命令守卫口径对齐（OPEN-F2）。

### F-09（MINOR）危机态持久化/重算口径不一与读档漂移

**证据**：§10.5（L496）"CrisisState 与预测按重建账本重算，不持久化预测快照";§11.2（L510）"`CrisisState.history` 与原因码一并持久化";§11.3（L516）仅为预测保留 `formulaVersion/assumptionsVersion`，危机阈值无版本锚点。

**推导**：危机态到底是"重算"还是"持久化"不清；若重算，`remediationDeadline` 倒计时依赖进入日，且 TUNING 阈值跨版本变化会使同一账本重算出不同危机态（读档漂移），而危机规则版本未随存。

**修改要求**：明确 CrisisState 持久化为准、或重算时同时持久化"进入日/原因码/阈值版本/deadline"并回放阈值判定；把 `crisisRulesVersion` 纳入随存字段（对齐 §11.3 预测版本做法）。

### F-10（MINOR）"禁读写 `Company.cash`"与"展示快照"矛盾

**证据**：§0（L22）与 §5.1（L273）"任何业务系统、UI、脚本都不得直接读写 `Company.cash`";§3.2（L126）称 `Company.cash` 是"展示快照";§7.2（L403）向 UI 输出 `LedgerAccount.cashBalanceCents`。

**推导**：既禁 UI 读 `Company.cash`，又把它定义为展示快照，二者冲突；UI 应读账本派生值还是 `Company.cash` 不明，易被实现为"UI 直接读 Company.cash"而绕过账本口径。

**修改要求**：明确 UI 只能读 `LedgerAccount.cashBalanceCents`/`AvailableCash` 等派生视图，`Company.cash` 仅为兼容展示字段（只读、非权威），或删除该字段引用。

### F-11（MINOR）退款时平台抽成冲回未定义

**证据**：§5.5（L296）`platform_fee` 与 `sales_revenue` 分别入账；§5.6（L301）退款仅冲销原 `sales_revenue`，未涉及 `platform_fee`。

**推导**：全额退款后现金净损失手续费，是否随退未定；§5.5 称"沿用 `contract-service.ts` 净额口径"但本文未锁定 `platform_fee` 的退款处理，编码需自行决定，可能与既有结算口径分叉。

**修改要求**：明确退款是否同时冲回 `platform_fee`（或明确不冲回并说明玩家承担的手续费后果），与 D-05 净额口径保持一致。

### F-12（SUGGESTION）参数状态标注张力

**证据**：文首立场（L16）"所有参数填 TUNING 而不写终值"，但 §6.4 给出 `runwayWarningMonths`（初始 3）、`runwayCriticalMonths`（初始 1）、`remediationWindowDays`（初始 60）等具体初值；`hrbVerdictWarn/Cut=1.0/1.2` 以锚点形式给出，而 D-01 §6.2.1 明确阈值为 TUNING。

**推导**：不阻断实现（初值可作默认），但与本文自律条款及 D-01 标注口径张力，建议统一表述为"默认候选值（TUNING，待校准）"以免被当作终值。
