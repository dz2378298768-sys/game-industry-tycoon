## 一、审核结论

**FAIL（退回设计 Agent 改版后重新审核；不允许进入编码）**

判定理由（按严重度排序）：

1. **`Cap_d` 输入口径被隐性改写（CRITICAL，一致性问题 D03-01）**：§6.1 Z1 把 Project 的 `teamRefs` 成员集合改写为"存在同学科 `Assignment` 的 Employment"，并额外引入 `EffectiveFrom ≤ day ≤ EffectiveTo` 窗口过滤；§7.1 `queryTeam` 也只返回"该 Employment 当前承担学科"单值。Project §6.2 的 `e` 是成员主体、`d` 是学科维度、`team_d` 由 `skillLevel(e,d)>0` 过滤，**没有任何 discipline 维度上的成员资格限制**。按 D-03 写法，一名无 `Assignment`（或 Assignment 已到 `effectiveTo`）的多学科员工将从 `team_d` 消失，`Cap_d` **被系统性低估**；`D03_EMPLOYMENT_NOT_ACTIVE` 又规定已终止成员"剔除"，与 Z2 `available` 语义冲突。虽未直接把 `eff_share` 乘进 `k_output`（红线 R-D03-2 未被字面违反），但以"补 `available` 语义"为名的改写，实质改变了 Project 的输入集。
2. **`burden_d` 双口径并存（CRITICAL，一致性问题 D03-02）**：Project §5.3-2 定义 `burden_d = remainingWorkUnits_d / max(ε, Cap_d)`（**单位：天**，用于 `bottleneck = argmax_d burden_d`）；D-03 §6.2 把 `burden_d` 重定义为"多项目分配比例加权平均，∈[0,1]，仅 UI"。同名、同任务（"为 Project 的 `Cap_d`/`burden_d` 提供唯一权威来源"，任务卡 §1）的两个符号被赋予**不同量纲、不同语义、不同用途**，且 D-03 未登记此冲突、未升 `projectFormulaVersion`，违反红线 R-D03-2 自身"任何偏离须升版本并经主 AI 裁定"的条款。
3. **`eff_share` 归零规则与 §6.8 自相矛盾（MAJOR，可执行性 D03-11）**：§6.2 文本写"若 `allocs(e,d)=∅` ⇒ `eff_share=0`"，但 `share(e,p)` 公式只在 `p ∈ allocs(e,d)` 时有定义，对**项目自己**的分配恒有 `allocs(e,d) ≠ ∅`（否则该 `e` 不在 `team_d`），`eff_share` 实际恒为 1；而 §6.8 `effort = 1[...] × min(1, eff_share总和)` 在注释给定的 0 情形下会把**当年所有**经验增量清零。两节口径不能同时成立。
4. **薪资月承诺口径与 FIN F-02 冲突（MAJOR，D03-03）**：§7.2 以 `period: 'monthly'`、`startAt: startDay`、`endAt: null`、"逐月续"创建承诺；FIN §3.3 要求 `endAt ≥ startAt` 且 `periodCount = startAt..endAt` 覆盖的日历月数、`totalPlannedCents = amountCents × periodCount` 创建时固化、BR-3 要求 `monthly` 幂等键含 `<YYYY-MM>`。`endAt=null` 下 `periodCount` 不可数、`totalPlannedCents` 不可定、`AvailableCash`（FIN §6.2 用 `totalPlannedCents − realizedCents`）无法计算，TC-11"承诺金额 = Σ月薪"不可验收；招聘费的类别与"创建即兑现"亦与 FIN §3.9 12 类/BR-3 不一致。
5. **迁移映射未逐项裁定（MAJOR，D03-05）**：§14 未覆盖 `EmployeeService` 的 `getById`、`hasActiveWork(employeeId, assignments, phaseOf)`（代码仍在用）、`employee-service.ts:120-123` `countActiveByCompany` 只计 `hired` 的语义、`hireEmployee` 入口的 `citySalaryMultiplier` 地区系数、`mobile / 城市系数` 等现状能力；"`EmployeeService` 19 字段"计数亦不实（实为 17）。任务卡验收项"迁移映射覆盖 `employee.ts` 全部现状能力"不成立。

除上述，**红线层面成立的部分**须如实记录：Person/Employment 分离在结构上真正落地（§3.1/§3.2/§5.1 RULE-01~03 + RULE-02 拦截 + TC-03 反证锁），"同一人不可双重雇佣"有可验证规则；D-03 未直接读写 `Company.cash`（§7.2 只创建/取消承诺）；`employee.ts` 中 `baseEffectiveWorkPerDay` 的废弃论证**成立**（见 §四.5）。但存在 CRITICAL 级口径冲突与不可执行条款，按协作规范 §2.2/§7 不得降级为 PASS WITH CONDITIONS。

## 三、`Cap_d` / `burden_d` 一致性专项核查（首要）

> 权威：Project §6.2 公式、§6.3 `burden_d`、§10 B-9、§17 OPEN-PROJ-2；FIN §6.1/§6.2。

### 3.1 Project 原文口径（复述，供比对）

```
team_d     = { e ∈ teamRefs : available(e,day) ∧ skillLevel(e,d) > 0 }
Cap_d      = k_output × Σ_{e∈team_d} f_skill(skillLevel(e,d))            // workUnits/day
burden_d   = remainingWorkUnits_d / max(ε, Cap_d)                        // 单位：天
bottleneck = argmax_d burden_d
```

要点：`e` 是**成员**，`team_d` 只按 `available` 与 `skillLevel(e,d)>0` 过滤；`available(e,day)` 在 Project §6.6 标注"**D-03 Employment 可用窗口**语义；D-03 未接入时恒 true"——**只涉及"是否可用"，不涉及"是否承担该学科"**。`burden_d` 是**学科工作量 ÷ 学科日产能**的天数，用于瓶颈排序。

### 3.2 逐符号比对

| Project 符号 | D-03 §6.1/§6.2 口径 | 判定 | 证据 |
|---|---|---|---|
| `skillLevel(e,d)` | `Person.skills.level[d] ?? 0` | **一致** | §6.1 Z3；§3.3 注"缺键⇒0 对齐 Project §10 B-9" |
| `f_skill` / `k_output` | "只读不覆写" | **一致（声明层）** | §6.1 符号表；§6.2 关键说明②明确"P1 采用 Project §6.2 原式" |
| `available(e,day)` | Z2：`status∈{probation,active}` ∧ `occupiesPerson` ∧ **`EffectiveFrom ≤ day ≤ EffectiveTo`** ∧ `Person.status ≠ departed` | **实质偏离** | Z2 的 `EffectiveFrom/EffectiveTo` 属 `Assignment` 窗口，但 `available` 在 Project 中是**成员级**判定，D-03 把它变成"该 Assignment 是否在窗口内"，且 §6.1 Z1 已将 `teamRefs` 收窄为"存在同学科 Assignment 且窗口覆盖当日"的 Employment。Project 的 `teamRefs` 是 `list<ref(Employment)>`（§3.1），**不携带 discipline** |
| `team_d` | Z1：`employmentId ∈ teamRefs` **∧ 该条 `Assignment(projectId, discipline=d)` 存在且窗口覆盖** | **改写（CRITICAL）** | 见 §3.3 反证 |
| `burden_d` | §6.2：`(Σ_{e∈team_d} eff_share)/max(1,|team_d|)` ∈[0,1]，**仅 UI** | **重定义（CRITICAL）** | 与 Project §5.3-2 冲突，见 §3.4 |
| `eff_share` 进 `k_output` | §6.2 `Cap_d^share` 变体，**标 OPEN-D03-4 且 P1 不启用** | **未越权（有边界声明）** | §6.2 明确"P1 采用原式"；未把 `eff_share` 乘进 `k_output` 常量。但 OPEN-D03-4 单方面预设"P2 需 Project 裁"，未给出 `projectFormulaVersion` 升级路径的具体触发点，属 SUGGESTION（D03-10） |

### 3.3 反证：多学科员工被从 `team_d` 中剔除

构造：Employment `e1` 的 Person 技能 `{design:4, code:3}`，仅被分配到 Project P1 的 `art` 学科 Assignment（`discipline=art`，`allocationRatio=0.3`），P1 自身有 `W_code>0`。

- **Project 原口径**：`e1 ∈ teamRefs`（不涉及 discipline）⇒ `team_code` 含 `e1`（`skillLevel(e1,code)=3>0`）⇒ `Cap_code` 计入 `f_skill(3)`。
- **D-03 Z1**：P1 上不存在 `Assignment(projectId=P1, discipline=code)` ⇒ `e1 ∉ team_code` ⇒ `Cap_code` **少算一人**。
- **D-03 §7.1**：`PersonnelProjection.discipline` 为**单值**"该 Employment 当前承担的学科"，同一根本问题。

→ 该反证在 P1 常见形态（一分配一学科、禁止跨学科，§3.4）下必然发生，而 Project 的 `Cap_d` 集合并未按学科收窄。TC-05"逐符号等价"在此构造下 **FAIL**。这是**实质口径冲突**，不是"补语义"。

**额外**：`D03_EMPLOYMENT_NOT_ACTIVE`（§7.1 错误码表）规定已终止成员"剔除"，但 Z2 `available` 对 `terminated` 本应返回 false，二者对 `teamRefs` 的处理路径不同（一个"剔除成员"，一个"把成员判为不可用"），实现者会写两份过滤（D03-01 子项）。

### 3.4 反证：`burden_d` 量纲不一致导致瓶颈识别失效

构造：学科 `code` `remaining=100` units、`Cap_code=20` units/day ⇒ Project `burden_code=5` 天；学科 `art` `remaining=10` units、`Cap_art=2` units/day ⇒ `burden_art=5` 天。两者同为瓶颈，Project 以天比较；D-03 `burden_d` 取 `eff_share` 均值，在单项目单学科时恒为 1（§6.2"单项目单人 `share=1`"），**所有学科 `burden_d` 相等**，`argmax` 退化为任意选择。若下游实现误把 D-03 `burden_d` 当作 Project `burden_d`（同名，UI 同处展示），**将直接使瓶颈识别失效**。

→ 任务卡 §1 明确 D-03 要为 Project 的 `burden_d` 提供"唯一权威来源"；Project §5.3-2 尚未定义其输入来源，属**真实上游缺口**。D-03 以同名但不同义的定义填补，反而制造双口径。**不得以"仅 UI"规避**：不登记冲突即违反 R-D03-2。

### 3.5 `eff_share` / `share` / `effort` 可执行性

- `allocs(e,d)` 定义在"对每个 `(e, 学科 d)`"，但 `share(e,p)` 的分母为 `Σ_{a' ∈ allocs(e,d)} a'.allocationRatio`，**未约束 `allocs(e,d)=∅` 时 `share` 的取值**，仅在注释里写"⇒ `eff_share=0`"。注释不是公式分支。
- 由于 Z1 已把 `e` 是否属于 `team_d` 绑定到"存在覆盖当日的同学科 Assignment"，`allocs(e,project,day)` 对 `team_d` 成员**必然非空**，故 `eff_share` **恒等于 `fatigue_or_leave_factor`（=1）**。§6.8 `min(1, eff_share总和)` 的 `eff_share` 到底指"对某些项目"还是"跨项目全部"，未定义；若按注释取 0，则 `effort=0`，**全部成长停摆**。
- §6.8 `effort(e,d,day) = 1[e 在当日参与了任一 d 学科的 WP 产出] × min(1, eff_share总和)`，"参与了任一 d 学科 WP"如何由 §7.3 的 `(employmentId, discipline, day, out_wp)` 判定（`out_wp>0` 但该 Employment 当日可能未被派到该 WP）未与 Project §6.3 派工序绑定，缺可执行输入路径。

### 3.6 结论

**D-03 §6 与 Project §6.2 不严格等同**，存在一处"输入集改写"（D03-01）与一处"同名不同义"（D03-02），均属任务卡验收项"`Cap_d` 公式可执行，符号全定义，与 Project §6.3 无冲突"的**实质性不满足**。`eff_share` 未直接乘进 `k_output` 常量，此项**不构成越权**（记录为已通过项）。

## 四、Person/Employment 分离与人才红线

### 4.1 分离是否落地为可验证规则（结论：**成立**）

- §3.1 `Person` 无雇主/薪资字段；§3.2 `Employment` 以 `personId` 引用、不复制姓名技能（R-D03-4）；与系统地图 §2.2"团队配置只记录分配关系，不复制人物主数据"一致。
- RULE-02（`person.currentEmploymentId != null` 且 occupying ⇒ `D03_ALREADY_EMPLOYED`）、§5.1"反证锁：以 `personId` 建唯一索引于 occupying Employment"、TC-03"两条 hire 只成功一次"——**双重雇佣在规则层被封堵**。
- RULE-03 跳槽"只关闭旧 Employment、新建新 Employment，`personId` 不变、`SkillProfile` 不重建"，TC-02/TC-04 有反证锁。"换雇主时 Employment 终止而非删除人"**成立**（§4.2 `terminated` 终态、§4.1"再雇需新建 Employment"）。

### 4.2 分离规则的可执行缺口

1. **`resigning` 期间 `Person.status` 无状态**（§4.3"若 `currentEmploymentId != null` 且 occupying：`Person.status = (Σ活跃分配>0) ? assigned : on_leave`"——`resigning` 的 Employment 仍 occupying 且"已有分配保留"，故 `Person.status` 按此式得到 `assigned/on_leave`；而 §4.1 转换表要求"`assigned/on_leave` →（`Employment`→`resigning`）→ 保持"，两式在"`resigning` 且无分配"时一致，在"`resigning` 且有分配"时由 §4.3 覆盖为 `assigned`，**与 §4.1"保持"（= `on_leave`？）语义不在同一层**，读者无法判断哪个是权威（MINOR，D03-14）。

3. **E4 读档修复的账本后果**（§10 E4"保留 `startDay` 最早的一条，其余 `terminated`"）：对"其余"若已计薪（月承诺已兑现）或已产生 `Hired` 事件，`terminated` 将触发 FIN 遣散承诺（§6.4），**制造一笔本不存在的现金流出**；E4 只说"记 `PersonEvent`"，未要求"回滚/对账 FIN"，违反 R-D03-3 的边界（MAJOR，D03-08）。
4. **`occupiesPerson` 与 `status` 双向约束缺读档校验**：§11 S1 只校验 `currentEmploymentId` 指向，未校验"全库 occupying Employment 的 `personId` 唯一"；脏档可同时存在两条 occupying，而 §5.1 的"唯一索引"是**写时约束**而非读时约束。

- 修改要求：`share(e,p)` 给出 `allocs(e,d)=∅ ⇒ share=0` 的显式分支；`eff_share` 定义域与求和范围写明（针对**哪些项目**求和）；§6.8 `effort` 改为 `1[...] × Σ_{p: 该人当日在该项目有 out_wp>0} share(e,p)` 或直接 `Σ eff_share(e,p)`，并与 §7.3 的输入路径绑定；补全符号表。

**D03-04｜MAJOR｜招聘费类别/时点未定却写成确定规则**

- 证据：§6.3（L360–361）"这成本在 hire 动作提交时以 project-independent 的 `one_off` 承诺兑现"；§7.2（L528–531）`sourceType: 'contract_obligation'` + "建议 `project_expense` 或 `contract_payment` — 见 OPEN-D03-6"；FIN §3.9 12 类无 `hiring`。
- 修改要求：给出**确定裁定**（推荐 `project_expense`，ref `employmentId`）并说明理由；若必须 OPEN，则 §6.3 不得写死"入职时兑现"，改为"`hireDay` 创建 `one_off`，`arrivalDay` 兑现（由 FIN 幂等键 `<commitmentId>:one_off` 去重）"。

## 十三、遗留风险

1. **下游口径风险**：OPEN-PROJ-2（`skillLevel` 映射）在本规格 §6.1 被"回答"，但回答方式（Z1）本身改写输入集；若 D-03 V0.1 直接进入编码，Project 的 `Cap_d` 将系统性偏小，**且 Project 的 TC-09（code 2 人/art 0 人）不会暴露该错误**（该用例无多学科员工）。
2. **`burden_d` 同名风险**：即使 D-03 改为 `allocationLoad_d`，Project §5.3-2 的 `burden_d` 输入来源仍未关闭（`OPEN-PROJ-*`），需 Project 侧同步定义 `Cap_d` 来源。
3. **数值校准风险**：`f_skill`/`k_output`/`hireCostRatio`/`severanceMonths` 等 TUNING 在 D-03 §6 未绑定 `projectFormulaVersion` 参数快照（Project §11 S4 有），P2 校准会反向影响历史重算——建议 D-03 对齐 Project §11 S4 的"参数快照"做法。
4. **存档迁移风险**：旧档 `EmployeeStatus`（`hired/on_leave/resigned/fired`）到新 `EmploymentStatus`（`probation/active/resigning/terminated/contract_ended`）的映射未定义日期判据（`contractStartDay` 距今多久算 `probation`），迁移脚本可能把大量老员工误置 `probation`。
5. **测试可验收性**：TC-05/TC-11 按现文不可执行，TC-15/E6 按现文字面必失败——即使主链其他部分正确，本规格也未达到"每条验收口径能落到测试"的标准（协作规范 §13.5）。
