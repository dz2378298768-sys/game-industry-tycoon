### A1.2 价格实际通过哪些公式影响销量与收入（已核实）

存在**两条**价格作用路径，结论不同，必须分开：

1. **需求池路径（生产主路径）**：`referencePriceCents(genre, platform, segment)`（`src/content/c1-content.ts:212-216`）→ `computeValue(ref, price) = clamp(ref/price, 0.5, 1.5)`（`src/simulation/services/demand-pool.ts:164-167`）→ `computeAttraction` 中 `value^0.15`（`demand-pool.ts:88-99,174-194`）→ 同一 scope 内按 `attraction^θ(θ=1.5)` 分市场份额（`demand-pool.ts:210-212`）。
2. **销售管线路径**：`computePriceDeltaEffect(price, basePrice)`（`src/simulation/services/sales-formulas.ts:249-269`）用相对基准价的 log 弹性（`priceElasticityUp=0.12` / `Down=0.08`，`tuning.ts:213-216`）。**但生产调用把 `basePriceCents: priceCents` 写死为同一个价**（`src/simulation/services/market-simulation-service.ts:636-637`），故 `priceRelative ≡ 1`、价格效应恒为 0。该弹性在销售管线中**实际未生效**。

> 【A·公式可推】价格对销量的唯一生效渠道是需求池的 `value = clamp(ref/price, 0.5, 1.5)`；收入 = `grossUnits × priceCents`（`sales-formulas.ts:484`），与价格成正比。【NOT_VERIFIED】`basePriceCents=priceCents` 使弹性失效是否属预期设计，未找到裁定。

### A1.3 营销预算实际通过哪些公式影响销量与收入（已核实）

- 合法参数域：单渠道日预算必须为整数且 `1,000 ≤ x ≤ 500,000` cents，**0 = 停止投放**（`src/domain/value-objects/marketing-response.ts:11-12`；`src/simulation/services/marketing-service.ts:83-89`）。换算：**$10 ~ $5,000/天/渠道**。
- 销售管线响应：`lift = 1 − exp(−spend/scale)`，`multiplier = min(1+lift, 2.0)`（`sales-formulas.ts:271-284`）；`scale` 取生命周期档 `launch 50,000 / growth 100,000 / mature 200,000 / decline 300,000 / long_tail 300,000` cents（`tuning.ts:226-234`）。交付页在上市前，故对应 **launch 档 50,000 cents = $500**。
- 认知度路径：`awarenessDelta = (share/scale) × channelFactor × (1 − awareness/cap)`，渠道系数 expo 1.25 / social 1.0 / ads 0.75，cap=0.6（`marketing-response.ts:23-27,49-64`；`tuning.ts:236`）。认知度会很快触顶，故追加预算的主要收益在指数乘数而非认知度。
- 注意：`setMarketingBudget` 设的是**单渠道总额**，随后 `splitBudgetAcrossMarkets` 按市场均分（`marketing-service.ts:354`），进入 `SalesPipelineInput.dailyMarketingSpendCents` 的是**每市场份额**，不是总额；多市场时实际 lift 低于用总额估算的值。

## A2. 建议方案（草案，全部待 Owner 拍板）

### A2.1 定价三档

**结构（【B·锚点可推】）**：`priceCents(tier, genre, platform, segment) = round(referencePriceCents(genre, platform, segment) × factor[tier])`，`factor` 取固定三值，随组合动态派生；组合缺失时用 `C1_DEFAULT_REFERENCE_PRICE_CENTS = 2,999` 兜底并在 UI 明示"按默认参考价 $29.99 估算"。

| 档位（沿用既有 id） | 建议 factor【C·待拍板】 | 默认参考价下 cents【C·待拍板】 | 定位语义 | 预期效果（仅公式可推部分） |
|---|---|---|---|---|
| `low` 低价 | **0.75** | **2,249 cents = $22.49** | 渗透/走量；价低→价值系数上升、单件收入下降 | value = 1/0.75 = **1.3333**【A】；attraction ×**1.044**【A条件性】；scope 份额 ×**1.067**【A条件性】 |
| `medium` 中价 | **1.00** | **2,999 cents = $29.99** | 基准/对标参考价；与 AI 质量 50 分定价一致 | value = 1.0【A】；份额基准【A】 |
| `high` 高价 | **1.25** | **3,749 cents = $37.49** | 溢价/品牌定位；价高→价值系数下降、单件收入上升 | value = 1/1.25 = **0.80**【A】；attraction ×**0.967**【A条件性】；scope 份额 ×**0.951**【A条件性】 |

**数值依据交代**：
- 0.75 / 1.00 / 1.25 **恰好等于既有 `suggestedPriceCents` 在质量 0 / 50 / 100 分时的 factor**（`ai-planner.ts:285`），且全部落在权威夹逼区间 `[0.5, 1.5]×ref` 内（`ai-planner.ts:289-292`、`demand-pool.ts:166`）。这是**借用了既有可复算锚点**，因此"三值的选择范围"有依据。
- 但**"就选 0.75/1.00/1.25 这一组"本身是设计判断**——三档的间距、是否要更激进（如 0.5/1.0/1.5）或更保守（0.85/1.0/1.15），规格与 ADJ 从未给出。**必须 Owner 拍板**，不得声称是公式结论。
- 效果列中 attraction/份额倍率由 `value^0.15`、`attraction^1.5` 复算（`demand-pool.ts:92-99,184-193,219`），但**前提是单产品主导、pool 固定、其它因素不变**；【NOT_VERIFIED】三档的**净收入**区间未跑多 seed 模拟，不能由上述倍率线性外推（低价单件收入 −25%、高价 +25%，与份额变化叠加后的净效应需实测），更不构成平衡结论。

### A2.2 营销预算三档

**结构（【C·待拍板】）**：交付页只出现在上市前，统一按 launch scale = 50,000 cents 计；三档用**固定绝对 cents**（不随生命周期浮动，避免玩家在 P-09 看到会变的数）。

| 档位 | 建议日预算【C·待拍板】 | 相对 launch scale | 指数乘数 `1+1−e^(−x/50000)`【A可复算】 | 定位语义 |
|---|---|---|---|---|
| `low` | **10,000 cents = $100/天/渠道** | 0.2× | **1.181** | 低频试探 |
| `medium` | **50,000 cents = $500/天/渠道** | 1.0× | **1.632** | 标准投放，等于生命周期响应尺度 |
| `high` | **150,000 cents = $1,500/天/渠道** | 3.0× | **1.950** | 高强度，接近防御上限 2.0 但未触顶 |

**数值依据交代**：
- 三值全部落在合法域 `[1,000, 500,000]` cents 内【A】（`marketing-response.ts:11-12`）。
- 乘数由 `1 + 1 − exp(−spend/50_000)` 复算【A】（`sales-formulas.ts:271-284`）；`high` 取 3×而非 4×是为了远离防御上限 2.0（4× 时乘数 1.982，边际收益已极小）——这属于**设计判断**。
- 【A·公式可推】乘数上限数学不可达（`marketingResponseMultiplierMax=2.0` 注释为"防御性"，`tuning.ts:225`）；【NOT_VERIFIED】三档对应的**实际销量/收入差异**未跑模拟，且多市场均分、认知度 cap=0.6 会显著削弱档间差异，不得按乘数比例宣称收入提升。

### A2.3 可选替代（供 Owner 对比，非推荐）

| 方案 | 定价 factor | 营销 cents | 取舍 |
|---|---|---|---|
| 保守档距 | 0.85 / 1.00 / 1.15 | 20k / 50k / 100k | 档间差异更温和，但玩家决策感知弱（DP-2"点击有反馈"体验差） |
| 边界档距 | 0.50 / 1.00 / 1.50 | 1k / 50k / 500k | 覆盖权威夹逼带与合法预算域两端；但 0.5× 时 value 已封顶 1.5、500k 时乘数已近 2.0，存在"花钱无感"区间，且 1k 触及参数域下界 |

## B2. 三种口径方案

### 方案 A：轻量口碑状态机（销量/退款/质量派生，需新增内核产出）

- **数据来源**：`Product.finalQualityScore`、`defectLevel`、`salesByPeriod`（`grossUnits`、`netSalesRevenueCents`、`actualRefundUnits`）、`refundRate`（`tuning.ts:243-244`）。全部为已存在的真实内核数据。
- **新增内核产出**：**需要**。新增纯函数（建议落 `src/domain/value-objects/` 或 `src/simulation/services/`）按输入派生 `reviewScore`，再映射三档；需在 `Product` 增 `reputationBand` 字段或提供只读查询（避免改存档结构则可纯派生、不持久化）。
- **计算口径草案【C·待拍板】**：`reviewScore = clamp(finalQualityScore − k_defect×defectLevel + k_sales×归一化销量 − k_refund×实际退款率, 0, 100)`；`poor < 50 ≤ mixed < 75 ≤ positive`（阈值全部待拍板）。
- **DP 符合度**：DP-1 ✅（玩家可见）｜DP-2 ✅（点击/推进后有真实档位变化）｜DP-3 ✅（输入均为真实内核量）｜DP-4 ✅（偿还空态）。
- **实现成本**：中（L2：内核纯函数 + 单测 + UI 接线 + i18n；无存档迁移若纯派生）。
- **风险**：① 阈值是新一组 `NUMERIC_PENDING_P2` 风险，拍板不当会重演 C3；② "销量→口碑"映射是**设计约定**而非现实因果，须在 UI 明说"系统评估"而非"玩家评价"；③ 若直接改 `Product` 需处理老存档缺省。

### 方案 B：显式 DEFERRED + UI 改为"明确不支持"（最小成本诚实态）

- **数据来源**：无。
- **新增内核产出**：**不需要**。
- **计算口径**：无计算；把 `p10.reputation.none` / `p12.media.*` 从"暂无评价，上市后积累"改为"本作不支持玩家/媒体评价（P5 规划）"，按钮点击给出可读原因（DP-2）。
- **DP 符合度**：DP-1 ✅｜DP-2 ✅（前提：补点击反馈与原因）｜DP-3 ✅（不造假）｜DP-4 ⚠️（从"过渡态空态"改成"永久不支持声明"，必须有 Owner 书面 DEFERRED 裁定与 P5 计划，否则视为把 fail-closed 长期化）。
- **实现成本**：低（L1：文案 + i18n + 少量交互）。
- **风险**：**不满足 SUP-03 验收②"玩家看到真实评价反馈"**，披露 4 无法撤销；只是把欠账从"空态"改写成"明示欠账"。适合作为 Owner 不愿为新口径拍板时的**兜底诚实态**，不是推荐解。

### 方案 C：复用既有 `effectiveReviewScore` / `reviewLift`，只读暴露 + 三档映射（推荐）

- **数据来源**：现成的 `computeReviewLift()` 结果 `effectiveReviewScore` 与 `reviewLift`（`sales-formulas.ts:214-226`）。当 `reviewScore === null`（当前生产恒为此态）时，`effectiveReviewScore = qualityScore`，而 `qualityScore` 来自真实质量画像（`market-simulation-service.ts:633`）。
- **新增内核产出**：**基本不需要**——只需把已在 `explainSalesPipeline` 中计算的 `reviewLift.effectiveReviewScore` 作为只读展示值暴露给 UI（或 UI 通过现有只读查询取得）；三档映射为纯展示函数。**不写回 `Product.reviewScore`、不建 BrandMemory、不新增存档字段**。
- **计算口径草案【C·待拍板】**：`band = poor if effectiveReviewScore < 50; mixed if 50 ≤ score < 75; positive if ≥ 75`（阈值待拍板）；UI 文案必须标注"基于产品质量的**媒体评价推算**，非玩家真实评价"，滑动窗口 N=10 可先作为展示位结构（与 `mediaWindowN=10` 对齐）而不伪造 10 条条目。
- **DP 符合度**：DP-1 ✅｜DP-2 ✅｜DP-3 ✅（复用真实在跑计算，零假数据）｜DP-4 ✅（空态被真实派生值取代）。
- **实现成本**：低~中（只读查询 + 三档映射 + i18n + 单测；无内核算法改造、无存档迁移）。
- **风险**：① 语义风险——把"质量代理"叫"口碑"须 Owner 明确同意口径命名；② 三档阈值仍需拍板；③ 与 S12-4"最近 N 条评价滑动窗口"不完全等价（没有真实条目），须在 UI 如实说明"聚合卡为档位摘要，非条目列表"，不能显示伪造的 10 条评价。

## B3. 推荐与理由

**推荐方案 C，兜底方案 B，暂不推荐方案 A。**

1. C 是唯一同时满足"真实计算""零新增内核产出""低成本"的选项：`effectiveReviewScore` 本就在每次销售计算中产生（`sales-formulas.ts:444`），只是被 UI 丢弃；不造假、不占位、不重演 C3。
2. C 与 S12-4 的"媒体评价聚合卡"语义天然贴合（媒体评价 ≠ 玩家逐条评价），且三档可严格复用 S10-1 的 `poor/mixed/positive` 枚举，满足 `ADJ-22-12 §65` 的"同枚举同序、禁止两套档位"。
3. C 不触碰 `BrandMemory` 永久约束（`ADJ-22-12:39`）。
4. A 的真实价值更高（销量/退款反馈闭环更完整），但它本质上要新定一组阈值并改内核，风险与 C3 同类；建议**等 C 上线并实测一轮后**再评估是否升级到 A。
5. B 不是"解决"，是"诚实挂账"；仅当 Owner 明确拒绝为口碑口径拍板时采用，且须附书面 DEFERRED 与 P5 计划，否则违反 DP-4。

> 三档阈值（50 / 75）是**本文草案**，规格从未给出（S10-1 标 `NUMERIC_PENDING_P2`，`ADJ-22-12:35`），必须 Owner 拍板后才可落地；不得把 50/75 写成"公式推导值"。
