## 结论

真实浏览器复验已经证明，当前问题不是单一的“预算帽太小”。项目能否完成取决于预算承诺、五学科团队、候选人技能、招聘时点、项目支出和公司工资支出的组合。现有自动化“默认成功上市”测试使用固定技能、固定薪资和直接招聘，不能代表真实招聘池路径。

同时发现一个可独立确认的展示问题：项目详情和项目列表的预计完成日调用旧项目的 `baseEffectiveWorkPerDay()` 与 `estimateDaysToFinish()`，而 REC-04 新执行项目实际由五学科 ExecutionProject 工作包推进。两条链路的技能系数、学科集合和可用状态不同，UI ETA 不能作为执行项目的完工承诺。

## 浏览器证据

### 路径 A：低技能程序员导致工期漂移

- Day 0 先按默认容量 `$136,000`、HRB 45% 立项，预算承诺 `$61,200`。
- 招聘顺序为美术 Lv.5、设计 Lv.2、测试 Lv.3、音频 Lv.5、程序 Lv.1。
- 配齐五学科后，UI 初始预计完成 Day 96，执行项目成本估算 `$52,758`，预算占用率 86.2%。
- Day 90：设计 24%、程序 14%、美术 22%、QA 37%，现金 `$76,695`，项目已花 `$9,085`，进入财务危机。
- Day 150：设计 71%、程序 43%、美术 67%、QA 100%，预计完成日已后移至 Day 176。
- Day 210：设计/美术/QA 完成，程序 72%。Day 240 仍未交付，程序 73%，现金 `-$2,976`，公司破产。

这条路径说明低技能瓶颈、招聘工资和长期推进会共同改变结果；它不是默认成功基准的充分复现，因为招聘池和招聘时点是玩家行为的一部分。

### 路径 B：后置立项与后置招聘

- 先等候并招聘高技能候选人，再在 Day 180 立项时，可用现金只有 `$57,365`。
- 为通过承诺额守卫，将容量改为 `$125,000`，HRB 45% 后承诺 `$56,250`。
- 立项后可用现金只剩 `$1,115`，工资跑道约 3.1 个月，不能形成稳定的自然推进路径。

这条路径验证了“招聘时点”是现金流决策，不能把 `$136,000` 默认容量与“先满配招聘后立项”同时视为无条件可行。

## 链路核对

1. ExecutionProject 的实际推进由 `advanceExecutionProjects()` → `advanceProjectDay()` → `computeCapacity()` 完成；`Cap_d` 读取 ExecutionProject 的五学科技能和在职状态，不读取疲劳或士气。
2. UI ETA 在 `project-detail.tsx` / `projects.tsx` 使用旧员工日产能和 `estimateDaysToFinish()`，只对当前速率做线性外推，不模拟执行工作包、五学科依赖或未来岗位状态。
3. 因此，浏览器中 ETA 从 Day 96 漂移到 Day 234 的直接证据是“展示 ETA 与执行链不一致”；不能把该漂移简单归因于执行引擎疲劳。
4. 项目成本估算在团队完整后可显示 `$52,758`，但公司现金还要承担招聘费、工资和其他日常支出；`Cost_est` 不等于上市前公司总现金需求。

## 现有自动化基准的修正

数值策划复跑 `src/simulation/__tests__/w5-c7-default-ipo.test.ts` 得到当前结果：路径 B 首次 READY 为 Day 2，Day 200 上市后现金为 `$36,056`。旧报告中“Day 97 READY”的数字已经过时，不能继续作为当前证据引用。

该测试只招聘 programmer / designer / artist / QA 四个岗位，观测的是 legacy `Project.phase`，不包含 `audio_designer`，也没有直接断言 ExecutionProject 的五学科 WP。它可以保留为旧链路回归测试，但不能作为 REC-04 五岗位自然推进或真实玩家上市闭环的数值证明。

项目执行成本公式的当前口径为：`Cap_d = Σ fSkill`，技能等级 1..5 的系数为 0.6 / 0.8 / 1.0 / 1.2 / 1.4；成本按各学科工作量、月薪/21/产能和风险缓冲计算。招聘费按一个月薪资计入，工资在月末结算；预算承诺是可用现金预留，不等于立刻从账面现金扣除。

## 冻结边界

本轮不改：起始现金 `$120,000`、默认薪资 `$1,300`、HRB 45%/60%、6 个月可用现金预留、默认上市周期 200 天、承诺额不超过可用现金的守卫、项目工作量和预算模型。任何锚点变更都需要新的数值裁定。

### 破产规则冲突

- seed `2404 / 2405 / 2422` 的 Day 0 高技能路径在 Day 180 记录破产；旧规格 DESIGN-M1.2-OI-21 §2.2 与 `test-bankruptcy-guard.test.ts` V20 明确允许破产公司上市，因此项目继续到 Day 200，销售回流后公司恢复为 `active`。
- seed `2413 / 2431` 的同一路径在 Day 211 左右进入 `CANCELLED`，没有上市收入；该分歧来自是否及时恢复/进入重整清算路径，需结合当前 M3 状态机复核。
- 这与更新且已冻结的 `DECISION-M3-P0-ENDGAME-002-AMEND.md` v2.2 §3.2 冲突：在研项目默认暂停并于 30 天内取消；唯一例外是破产当日已处于 `PRODUCTION`、完成度 ≥80%、剩余成本满足阈值的一个项目。现有 T-FIX-2/V20 则允许任何未解散公司的 READY 项目上市。
- 例外阈值原文为“剩余成本 ≤ 破产当日现金 10%”，但目前破产触发条件允许现金为负；对负现金如何计算 10% 缺少可执行定义。需要先按最新裁定补齐这个口径，再改旧测试/守卫并补应用层反证测试；本轮不擅自更改核心规则。

### 可复现性与限制

- 20 个组合第二次运行的序列化结果与第一次完全一致，说明本轮覆盖的 seed、城市和策略路径具有确定性。
- 城市差异目前只作为输入覆盖；本轮没有声称完成城市经济平衡，销售需求、工资系数和候选池分布仍需更宽的参数矩阵。
- 成功上市的控制变量路径销售收入仍集中为约 `$60.61M`，不能作为市场规模已平衡的证据；后续应拆分价格、营销、市场需求和产品质量的敏感性扫描。

## 下一步闸门

1. 已完成多 seed / 城市覆盖 / 四策略数值基准；下一闸门是按最新 M3 裁定统一破产项目处理规则，并明确“破产日现金 10%”在负现金下的计算口径。
2. 在破产边界裁定前不调整起始现金、工资、HRB、预算容量或承诺额守卫，也不把高销售值当作平衡通过。
3. 冲突规格对齐、守卫与反证测试完成后，再进行真实浏览器的自然 READY、交付、计划上市日、销量和收入真点击复验。
4. UI ETA 后续应改为执行链 forecast，或明确标注为“旧项目速率估算”，避免玩家把它当成 ExecutionProject 的完工承诺。
5. 完成基准后再决定是否需要新的 ADJ；若只需体验修复，应优先增加招聘池/现金跑道提示和“先立项后招聘”的顺序引导。

6. 本基准已完成固定条件的多 seed / 城市覆盖第一轮扫描；代码级路径能自然 READY、交付、上市并产生销售，但 REC-04 和 SUP-01 仍不能关闭，因为真实 UI 真点击、玩家理解和最新 M3 破产项目规则尚未落地。先完成规格冲突对齐、反证测试，再进入真实浏览器复验。
