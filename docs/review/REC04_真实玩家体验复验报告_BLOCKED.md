## 体验发现

1. **P1：移动视口布局不可用。** 在 390×844 视口中，侧栏占据固定宽度，项目表格被压缩到窄列，项目名称逐字竖排并出现横向滚动；需要移动端布局或表格改为卡片/可横向滚动容器。
2. **P1：默认预算与可完成工作量不匹配。** 本次 UI 创建项目的成本估算约 `$54,871`，默认预算上限为 `$18,000`；追加到 `$36,000` 后仍在第 210 天耗尽，玩家未能在一次正常流程中抵达交付。
3. **P2：危机横幅重复 key。** 浏览器控制台持续报告 `CompanyAlertBanner` 的 `projects` 子节点 key 重复。已在 `src/ui/components/company-alert-banner.tsx` 做最小修复，改为稳定唯一组合 key；类型检查和 lint 已通过，需下一轮完整危机路径确认控制台清零。
4. **P2：部分 UI 仍显示未接线降级文案。** 项目详情显示 `D-02 QualityAssessment 内核未产出`、`OPEN-D02-WIRING` 等内部状态，影响玩家理解和验收可读性。

HTTP 冒烟与 REC-04/SUP-01 定向自动化集成测试仍可作为代码级证据，但不能替代本次真实浏览器发现。上市、销量和收入已有临时参数下的浏览器证据；自然 READY 和交付闸门仍保持 `NOT_VERIFIED`。REC-04、SUP-01 仍未 CLOSED。

## 2026-11-26 探索性复验补记

本轮继续使用 Codex 模式的真实电脑端浏览器，从已有 `REC04 Default Studio` 会话继续检查招聘池和立项前置条件。Day 30 点击 `+30D` 后，候选池出现设计师、程序员、音频设计师，说明候选池不是永久缺岗阻塞；通过 UI 招聘后五学科均可获得候选。

本轮随后又招聘了额外候选，团队达到 10 / 15，账面现金为 `$90,638`，但可用现金为 `-$9,235`。填写项目名称和目标用户后，立项页将默认 `BudgetCapacity` 设为 `$136,000`，并显示需立即占用 `$61,200` 可用现金；因此“确认启动”被 AvailableCash 守卫挡住。该结果属于继续探索同一会话造成的资金污染，不能作为正式默认配置的数值结论，也没有修改代码参数或手写状态。

代码与 B-01c 基准已明确默认有效顺序是“先立项、后招聘”：新公司默认可用现金 `$120,000`，立项默认容量 `$136,000`、HRB 45%，承诺 `$61,200`；本轮从干净新档按该顺序立项成功，Day 0 账面/可用现金均为 `$120,000`，立项后可用现金 `$58,800`。

默认档继续走真实招聘时暴露新的前置阻塞：Day 0 候选池只有美术/测试；Day 30 仍为同一批未过期候选；Day 60 仍未刷新；Day 61 才生成音频/设计/程序候选。为组齐最小五学科团队，真实 UI 招聘至 9 人后，可用现金降至 `-$40,966`、现金跑道 `1.1` 个月并进入财务危机，项目尚未分配团队、研发尚未开始。该证据表明当前默认路径卡在“候选池覆盖与招聘现金安全线”，不应继续把后续破产结果当成交付闸门证据。
