### 3.4 ADJ-11 的数值论断（第 4 项，自己算）

**公式（FIN V0.2 `:404-411`）**

```
CumAvailable(0) = AvailableCash
CumAvailable(m) = AvailableCash − Σ_{i=1..m} NetBurn_i
NetBurn_i = max(0, CommittedBurn_i − ExpectedIn_i)
```

**§6.2（`:423-426`）**

```
AvailableCash = cashBalanceCents − Σ(未兑现承诺, horizon 内) − Σ(未结算应付) (+ 高应收)
```

**按算例代入**：现金 700,000；6 期承诺 100,000/月 → 承诺总额 600,000；无应收/应付、无流入。

- `AvailableCash = 700,000 − 600,000 = 100,000`
- `m=1`：`committed=100,000`，`expected=0`，`netBurn=100,000`，`cum = 100,000 − 100,000 = 0 ≤ 0`
- 插值：`k=0`，`runway = 0 + 100,000 / (100,000 − 0) = **1.0**`
- 真实跑道（从未扣承诺的现金起算）：`700,000 / 100,000 = **7.0**`

**代码核对**：`finance-formulas.ts:146-164` 的 `computeRunwayMonths` 起点是入参 `availableCashCents`，循环内又用 `committedBurnForMonthAny` 逐月扣 `netBurn`；调用方 `:262-286` 传入的正是 `computeAvailableCash(...)` 的结果 → 与 FIN 公式一致的双重扣减。**既有测试 `code04-legacy-defects.test.ts:136-159` 直接把 `toBe(1)` 锁死，并在注释里写明"真实 7 个月"**。所以"1 个月 vs 7 个月"**算对了**。

**但"危机后果"算错了。** 逐行读 `finance-crisis.ts`：

- `:130` `criticalByRunway = runway < runwayCriticalMonths(1)` → `1.0 < 1` 为 **false**；
- `:132` `warningByRunway = runway < runwayWarningMonths(3)` → true；
- `:168-175`：`const target = warningByCash ? 'warning' : 'watch'`。本例现金 700,000 > `cashWarningThresholdCents=400_000`（`finance-tuning.ts:104`），`warningByCash=false` → **进入 `watch`，不是 `warning`**；
- 破产唯一判定式 `:133-149`：`critical` 且 `deadline 到期` 且 `cashBalanceCents < 0`。现金 700,000 > 0，**永远不会破产**；若跑到 `critical`（需 runway < 1，例如 0.9），窗口到期但现金为正时，`:156-160` 是"沿用原 deadline 保持 critical"（OPEN-F6），**不是破产**。

**因此**：
- 数值论断：**成立**（1.0 vs 7.0，有公式、有代码、有既有测试）。
- "一个还有七个月现金的公司，会被系统在第一个月就宣布濒临破产"（ADJ-11 `:38`）：**不成立**。它会在第一个月进入 `watch`（带 `LOW_RUNWAY` 原因码），极端波动时进入 `critical`，但不会破产。ADJ-11 `:36` 的"窗口内未改善 ⇒ 走破产流程"也漏掉了 `现金<0` 这个 AND 条件。
- 阻断结论是否仍成立？**成立**，但理由应改为："S11 的跑道显示与危机等级错误，预警时点错误，玩家会基于错误信息做决策；且 `critical` 可被误触发、`watch` 被当成 `warning` 的语义会污染 UI 与试玩结论。" 这仍是 G1 阻断，但**不是"必然破产"**。

**判定：数值成立；因果链部分不成立。**（CRT-01）

### 3.5 ADJ-11 的 R-3（阈值同批重标定）是否自洽（第 5 项）

**算术层面**：旧算子下 `computed ≈ real/7`。真实 7 → 1 → `1 < 3` 进预警；旧 `warning=3` 对应真实约 21 个月。修好后 `computed=real`；真实 7 → 7 → `7 > 3` 不预警；真实 2.5 → 2.5 → `2.5 < 3` 预警。**"真实 3 个月才 warning"的描述在算术上成立。**

**但"不重标定就会漏报"不成立**：真实 2.5 个月时 `2.5 < 3`，`warningByRunway` 为 true，**不会漏报**；它只是进入 `watch` 而不是 `warning`（见 CRT-02）。真正需要重标定的理由是"3 个月预警是否太晚"这一**设计判断**，不是算术必然。

**更关键：R-4 的三条反例无法锁死 R-3。** 把阈值留在旧的 `3/1`、只修公式：

- `RV-1`：真实 7 → 7 > 3 → `healthy`，**通过**；
- `RV-3`：真实 0.8 → 0.8 < 1 → `critical`，**通过**；
- `RV-2`：真实 2.5 → 2.5 < 3 → `LOW_RUNWAY`，但状态是 `watch`（若现金 > 400k）或 `warning`（若现金 < 400k，任务卡取 250k 正是这种情况）——**它的 `warning` 来自 `LOW_CASH`，不是跑道阈值**。

也就是说：**三条 RV 没有一条能在"不重标定"时变红**。R-3 是"必须做"，但 R-4 证明不了它做了没有。这是典型的"要求写了、验收没写"。

**另外，ADJ-11 本身没有给新阈值数值**（只写"重标定"），而 `TASK-P1-CODE-FIN-RUNWAY` 给了 `warning 4.0 / critical 2.0 / window 60`。修订件 X-1 声称"已在 ADJ-11 R-3/R-4 固化"——**固化的是要求，不是数值**，追溯链断了。更麻烦的是 FIN §6.4 `:478-479` 仍写"默认候选值 3 / 1"，ADJ-11 R-6 的文档同步清单**只列了 §6.2 与 §20，漏了 §6.4**；按任务卡把代码改成 4/2 后，**FIN §6.4 会与代码直接矛盾**（CRT-03）。

**判定：部分成立。** 算术自洽；验收不自洽；文档同步不完整。
