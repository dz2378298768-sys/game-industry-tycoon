## 1. 目标

把已经建好的内核**接到玩家手上**，形成一条可完整走通的闭环：

> 立项（选蓝图 + 定学科内容）→ 组建团队 → 逐日推进（看产能/瓶颈/成本）→ 设计变更与返工 → 待交付 → 交付闸门 → 生成产品 → 上市

**一句话判据**：一个新玩家不看文档，能在 15 分钟内从开局走到第一个产品上市，且过程中每一个数字都能在 UI 上找到来源。

## 2. 范围（IN）

1. **主界面四区**：公司概览（现金/可用现金/跑道）、团队（成员/学科/士气/薪资承诺）、项目（七态 + 返工标签/进度/瓶颈学科/`Cost_est`）、产品（已上市，三质量**分开展示**）。
2. **关键交互**：
   - 立项向导：选类别/平台/内容 → 显示 `HRB` 可行性与 `Budget_cap` → 确认后建项目；
   - 追加预算 / 缩减范围（对应场景 A/B）→ 显示对承诺与跑道的影响；
   - 设计变更 → 返工预估（返工 unit、沉没成本、档位 δ、延长天数）；
   - 交付：显示 `blockingUnmet` 逐条 + 失败原因（`lastDeliveryFailure`）。
3. **必须直面的 UI 口径问题**（见 §4 与 ADJ-05）：跑道显示、三质量不合成、失败原因可见。
4. **存档/读档**：能存能读，读档后继续推进结果与不读档一致（同 seed 指纹相等）。
5. **性能**：L3 按需查看的分层——UI 不在每日循环里重算全量。

## 4. 硬性 UI 口径要求（**这几条会被审核逐条查**）

| # | 要求 | 来源 | 为什么 |
|---|---|---|---|
| U1 | **三质量永不合成**：产品页必须**分列** 设计质量 / 实现质量 / 完整度，禁止任何"综合评分""总评""星级" | D-02 IND-2 | 合成分数会把"好设计做砸"和"烂设计做精"抹平成同一个数字，玩家就看不出问题出在哪 |
| U2 | **跑道必须加口径说明**：展示"可支撑 X 个月"时，必须标明该值已扣除承诺，或改用"**承诺后可用现金**"表述 | ADJ-05 §2 / OPEN-F3′ | 该值当前存在已知双重扣减（实算 1 个月 vs 真实 7 个月），不加说明就是**误导玩家** |
| U3 | **交付失败原因必须可见**：显示 `lastDeliveryFailure.reasonCodes` 与逐条 `blockingUnmet`，不得只显示"交付失败" | ADJ-08 §1 | 失败不可解释 = 玩家不知道下一步做什么，等于强迫试错 |
| U4 | **返工成本必须前置展示**：玩家确认设计变更**之前**给出返工预估（unit/沉没/档位/延期），确认后才执行 | Project §6.5 | 事后才知道要花多少钱 = 不可决策 |
| U5 | **`qualityCeilingBand` 不得展示**：P1 该值恒 `ABSENT_P1`，UI 不显示任何"质量上限" | D-02 §6.5 | 展示一个恒为"缺失"的字段会让玩家以为系统坏了 |
| U6 | **瓶颈学科必须高亮**：项目页标出当前 `Cap_d` 最小（`burden_d` 最高）的学科 | Project §5.3-2 | 这是玩家唯一能做出有效决策的信号（该招谁） |

## 5. 验收标准
- [ ] `npx vitest run` 全绿；既有用例零回归；**UI 层新增用例**（组件测试 + 一条端到端闭环测试）。
- [ ] `npm run typecheck` 通过。
- [ ] **端到端闭环测试**：立项 → 招人 → 推进 N 天 → 变更 → 返工 → 待交付 → 交付 PASS → 产品上市，全链可跑通且断言关键数值。
- [ ] **U1–U6 六条逐条有测试或可截图证据**（U1/U2/U5 可用 DOM 断言"不存在合成分数字段/上限字段"）。
- [ ] **读档一致性**：存 → 读 → 续跑 30 天，指纹与不读档路径相等。
- [ ] 独立编码审核通过。
- [ ] **主 AI 亲自走一遍闭环**（这是 P1 验收的核心动作）。

## 7. 风险提示
- 最容易犯的错是"UI 层补内核的洞"：比如跑道数值难看就在 UI 里乘个系数、三质量不好展示就加个平均分。**一律禁止**，发现问题退回内核任务。
- CODE-07 是唯一碰 `src/ui/` 与 `src/app/` 的任务，前面所有任务都不碰；若发现前面任务已经污染了 UI 层，先在报告里指出。
