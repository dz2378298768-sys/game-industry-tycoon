## 七、问题证据与推导

### C-01（CRITICAL）E04 码未入闸门，E 级校验可绕过

**证据**：
- D-04 §5.2 L242 明确：「返工完成 / 交付时引用已失效 → 复用上列全部 E 码 → `RevalidationGate` FAIL → 不切快照/阻断交付」；§7.3 L351：「返工完成切快照 / `EXECUTING→COMPLETED` 交付（D-01 §7.2.1 `RevalidationGate`）：重跑 `resolveRefs`；任一 E 级违规 → FAIL」。
- D-01 §7.2.1 L865–872 的 `RevalidationGate` 定义为 `violations = RunHardRules(S)`，枚举仅 `E-EMPTY / E-USP / E-CONFLICT / E-DEP / E-CYCLE / E-TECH / E-ERA / E-EMPTY-CONTENT / E-OPT / E-INCOMPAT`——**全部来自 §11，无任何 `E04-*` 码**。§7.2 L858、§15.3 L1262 亦仅「复用 §11 全部 E 级硬规则及 §5.3/§5.4 硬规则」。D-04 §5.4 的 `E04-DEPRECATED-TAG` / `E04-UNKNOWN-TAG` / `E04-DEPRECATED-PLATFORM` / `E04-UNKNOWN-PLATFORM` / `E04-UNKNOWN-ARCHETYPE` 不在其中。

**推导（反证成立）**：玩家锁定蓝图时引用 `tag A`。研发期间 `tag A` 在新词表版本被 `deprecated`，或 API/旧档带入全版本未知的 `tagId`。返工完成时，D-01 的 `RevalidationGate` 按 §7.2.1 只跑上述 §11 码，**不会命中任何 E04 码**，判定 PASS → 新快照切换、`Project.snapshotId` 更新、可能进入 `COMPLETED`。但 D-04 §5.3 明定「新蓝图引用 deprecated/未知 → E 级阻断」。结果：D-04 自称「复用全部 E 码」在闸门处落空，一条已声明的硬规则被绕过。D-04 §0.2 自设「与 D-01 冲突时以 D-01 为准」，故实际实现将服从 D-01 的枚举，E04 码被静默忽略。

**修改要求**：① 由主 AI 裁定并补充 D-01 §7.2.1 `RevalidationGate`，在 `RunHardRules` 中显式纳入词表引用校验（`E04-DEPRECATED-TAG`/`E04-UNKNOWN-TAG`/`E04-DEPRECATED-PLATFORM`/`E04-UNKNOWN-PLATFORM`/`E04-UNKNOWN-ARCHETYPE`），或明确声明 `resolveRefs` 为闸门的独立强制前置且结果并入 FAIL；② D-04 §5.2/§7.3 同步改为准确表述（区分「D-01 §11 E 码」与「本包 E04 码」，不得笼统写「复用上列全部 E 码」）；③ 补 TC 覆盖「返工完成/交付时引用已 deprecated 或未知词条 → 闸门 FAIL、不切快照」（比照 D-01 TC-08a/08b）。

### C-02（CRITICAL）同一 tagId 语义可变更 vs G4 不成立

**证据**：
- D-04 §4.1 规则 1 L182：「已发布版本 `sealed=true`，不得修改词条取值；变更（增/改状态）必须发新版本」——只允许「增/改状态」，不允许改取值。
- D-04 §8.1 X-9 L374：「多版本共存时**同一 `tagId` 语义变更** | ID 稳定；语义变更须发新版本，旧版本 `sealed` 只读」——明示同一 ID 语义可跨版本变更。
- D-04 §8.2 A2 L381：蓝图「只存 `tagId`/`archetypeId`/`platformId` 引用，**不存词表快照**」；A1 L380「存档只记录『使用的词表版本』字符串」；A3 L382「若需按词表版本重放，版本字符串外置记录，**具体机制 OPEN**」；§4.1 规则 5 L186「P1 全局单版本；玩家/存档绑定特定词表版本 → OPEN」。
- D-01 §12 S2 L1154 的快照自包含仅覆盖 `ModuleTemplate.templateRevision` / `ContentPack.templateRevision`，**不含词表词条**；§6.6 L749 将「市场档案词表/群体」列为外部输入变化（估算会变）。

**推导**：「ID 稳定 + 不物理删除」只能保证旧引用的**可解析性**，不能保证**语义不变**。若按 X-9 允许同一 `tagId` 在新版本改变 `displayName`/`dimension`/`granularity`/`eraRange` 或其模块 affinity 语义，则旧蓝图只存 `tagId`、不存词条快照，打开时在 P1 全局单版本下必然解析到**新语义**——旧设计的 `positioningFit`、`affinity`、展示名称随词表改版漂移，且 D-01 只会提示「估算变了」而无法归因到词表语义变化。G4（§1 L40）「词表可版本化且不破坏旧存档」与 X3「可下钻到具体标签」同时落空。§4.1 规则 1 与 X-9 对「同一 tagId 语义能否变更」给出互斥答案，编码者无法判定应禁止还是允许。

**修改要求**：二选一并全篇统一——① **推荐**：禁止同一 `tagId` 语义变更，声明「已发布 `tagId` 的任何取值（含 `displayName`/`dimension`/`granularity`/`eraRange` 及语义）永久不可变；跨版本只允许新增 `tagId` 或改 `state`（active→deprecated），新语义必须用新 `tagId`」，删除 X-9 的语义变更许可并改写；② 保留语义变更，则必须在存档/快照中按 D-01 §12 S2 范式快照词表词条或绑定词表版本（落地 OPEN-6），并给出重放规则——此项超出本包「不向快照增字段」边界，须主 AI 裁定 D-01 变更。无论何者，补 TC 覆盖「旧版本 tagId 在新版本打开后语义/画像不漂移」（现有 TC-14/15 仅测新增与可解析）。

### M-01（MAJOR）主类型非 active 硬阻断无错误码

**证据**：D-04 §5.2 L238 将「主类型引用非 active」列为「硬 / 锁定阻断」，但注明「§4.13 约束（非独立 E 码）」；§5.4 L264–275 的 9 个新增码中 `E04-UNKNOWN-ARCHETYPE` 仅覆盖「类型 ID 不存在」，**无「存在但非 active（provisional/deprecated）」对应码**；§7.1 L338 的 `resolveRefs` 违规对象必含 `code` 字段；§5.2 通用错误格式 `code` 必填。D-01 §4.13 L443 有「primaryTypeId 必须引用 state=active」约束，但 §11 L1122–1142 无对应 E 码。

**推导**：一条「锁定硬阻断」规则没有可输出的 `code`，违反自身通用错误格式；编码者只能自造新码（违背 §5.2「不新增同义码」）或误用 `E04-UNKNOWN-ARCHETYPE`（语义错误，provisional 类型并非「不存在」）。同样问题波及 `secondaryTypeIds` 引用 deprecated 类型（§5.2 未列、§5.4 无码）。

**修改要求**：在 §5.4 增补 `E04-NONACTIVE-ARCHETYPE`（主类型非 active）/ `E04-DEPRECATED-ARCHETYPE`（次类型引用 deprecated），或明确映射到既有码并写明语义；§5.2 表格填入具体 `code`，去掉「非独立 E 码」表述；TC-06 期望写明具体码。

### M-02（MAJOR）读档未知 ID 行为未定义

**证据**：D-04 §7.3 L352：「读档：`resolveRefs` 恢复引用；deprecated 旧引用只读保留、不报 E；完全未知 ID 按 `E04-*` 处理」。§5.3 L249–259 的判定表仅有「草稿期」「锁定/闸门」两栏，**无「读档」栏**；§8.2 A3 L382 将版本绑定外置机制标 OPEN。

**推导**：「按 E04-* 处理」含糊——`E04-UNKNOWN-TAG` 是 E（硬），若读档套用「硬=阻断」则存档无法打开（整个存档被一条脏引用卡死）；若只标记则未说明是否入只读态、是否可继续。团队明确要求反证「未知标签与历史存档重放」，当前规格无法给出确定、可验收的读档行为，存在存档兼容风险。

**修改要求**：在 §5.3 增「读档」栏并明确：完全未知 ID 时是「拒绝该引用但保留存档可打开（标记只读 + `suggestedAction` 改选）」还是「整体拒绝读档」，二者择一且与 §5.2 级别语义区分；补 TC 覆盖「旧存档含未知 tagId → 读档行为符合定义」。

### M-03（MAJOR）平台输入能力字段与种子缺失

**证据**：任务卡工作范围第 3 项与 D-04 §2.1 I3 L65 均要求「平台**输入能力**」；D-04 §3.3 L136–144 的 Platform 字段表仅有 `platformId/code/displayName/existence/techStandards/state/source`，**无任何输入能力字段**（如手柄/键鼠/触屏支持）；§6.3 L315–321 三平台种子表亦无该列。D-01 §5.2 L483 明定硬规则「平台 ↔ 输入方式：视角+结构与平台输入能力（手柄/键鼠/触屏）兼容检查，硬（技术门）」。

**推导**：D-04 声称提供「输入能力」并作为 D-01 前置，但数据契约与种子均无该字段；D-01 §5.2 的硬兼容规则无输入可消费，编码时要么无法落地该硬规则，要么自造字段——与「本包不新增 D-01 字段」边界冲突，且任务卡验收「平台只提供存在性与输入能力」不成立。

**修改要求**：在 §3.3 Platform 增加 `inputCapabilities: list<enum{gamepad, keyboard_mouse, touch}>`（或等价结构，标 CONFIRMED 结构 / P1 种子取值），并在 §6.3 三平台种子填入 P1 取值（1978 北美：街机/主机=gamepad，家用电脑=keyboard_mouse，touch 留空/DEFERRED）；§7.1 的 `getPlatforms` 输出包含该字段；补 TC 验证 D-01 §5.2 兼容检查可消费该字段。

### M-04（MAJOR）平台种子无差异，G3/X2 承诺未落地

**证据**：D-04 §1 G3 L39 称「不同标签/类型/**平台**经 D-01 §6.4 TechGate 集合与 §6.5 `affinity`/`genreFit` 产生可解释差异」；§1.2 X2 L47 把「平台进入 `techStandards`」列为取舍抓手。但 §6.3 L319–321：三平台 `techStandards=[]`（全空）、`available=true`、`regions=[north_america]`、`era` 起点 1970/1977/1977——在 P0-B §4.0「1978 北美」世界下三者**全部可及且门槛贡献均为空**。

**推导**：在 P1，选择街机 / Atari 2600 类主机 / Apple II 类电脑，对 D-01 的 `T` 集合、`affinity`、`genreFit` 均无任何差异，「平台可及性有代价」的取舍感不存在，G3/X2 把预期体验写成已达成。门槛为空是 D-06 未就绪的客观结果（本包诚实占位，不属伪装），故问题不在「空门槛」而在**过度承诺**。

**修改要求**：二选一——① 软化 G3/X2 表述为「P1 平台仅提供候选与存在性；门槛差异待 D-06 就绪后体现」，并把平台取舍感登记为 DEFERRED→D-06；② 若需在 P1 体现差异，给出平台最小可观察差异字段（不碰具体门槛），如 `eraRange` 使某平台在 1978 不可及从而触发 `E-ERA` 软提示，并在 §6.3 落实。验收 TC 相应调整。

### m-01（MINOR）affinity 缺键缺省未显式定义

D-04 §4.1 规则 3 L184 / §5.3 / §8.1 X-5 L370 / TC-14 L417 多次声明「新标签无模块 affinity → 按缺省 0（D-01 §6.5 公式对未列标签自然为 0）」。但 D-01 §6.5 L729 的 `affinity[tag] = Σ i.template.audienceAffinity[tag] × … + Σ o.audienceAffinityDelta[tag]` **未显式声明缺键取 0**（对比 §6.5 L740 对 `typeAffinityVector` 明确「缺省为 0」）。建议在 §5.1 或接口契约显式声明「`audienceAffinity`/`audienceAffinityDelta` 的 map 缺键一律按 0 处理」，使确定性可验收。

### m-02（MINOR）「四类来源表」实为五行

D-04 §3.3 L162 称「§4.8 四类来源表」；D-01 §4.8 L315 标题写「四类取值来源」，但 L317–323 表内实为五行（模块模板/视角/平台/结构/选项），§6.4 L657–663 的 `T` 并集亦为五路。根因在 D-01 计数笔误，D-04 忠实复述。建议改为「取值来源表（§4.8）」不带数量，避免误导编码漏接选项/结构来源。

### s-01（SUGGESTION）补语义变更测试与 OPEN 责任登记

TC-14（新增标签缺省 0）/TC-15（旧 tagId 可解析）未覆盖 C-02 的语义变更场景；TC-20 要求「显示为什么变了」，但 OPEN-6（版本绑定/重放）与 §10 清单未登记责任人/时限。建议按 D-01 R-15 先例为 OPEN-6 登记责任人与时限（建议 P2 验收前），并在 C-02 裁定后补对应 TC。
