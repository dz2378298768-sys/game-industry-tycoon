# 核心服务接口契约

> 补充原因：V2.0/04_技术架构/05_数据结构与服务接口.md 只列了 9 个 Service 名字和一句话职责，没有接口签名、命令清单、查询清单、领域事件输出、幂等规则、状态守卫。Agent 不知道该怎么写每个 Service 的 API。

## 0. 通用设计规则（所有 Service 共同遵守）

### 0.1 命令执行模式

所有命令通过 Application 层的 Command Handler 调用，不直接由 UI 触发。每个命令执行：
1. 校验前置条件（状态守卫、权限、参数类型）
2. 调用 Service 内部逻辑
3. 写入持久化（仅 Service 自己的实体）
4. 产出领域事件
5. 返回 CommandResult

### 0.2 CommandResult 标准结构

```typescript
interface CommandResult<T = void> {
  success: boolean;
  result?: T;                    // 成功时返回的数据
  errorCode?: string;            // 失败时的稳定错误码（如 'PROJECT_ALREADY_LAUNCHED'）
  errorMessage?: string;         // 用户可读的错误说明
  idempotent?: boolean;          // true = 本次是幂等去重命中，未实际执行
  entityVersions?: Record<string, number>;  // 涉及实体的版本号（用于乐观锁校验）
  events?: DomainEvent[];        // 产出的领域事件列表
}
```

### 0.3 幂等规则

- 所有可能重复触发的写操作必须接受 `idempotencyKey: string` 参数
- 幂等 key 由调用方（Application 层）生成，格式 `{commandName}:{entityId}:{operationId}`
- Service 内部维护 `idempotencyKey → { result, timestamp }` 映射表（可裁剪，保留最近 30 天）
- 命中幂等 key 时直接返回缓存结果，不重复执行
- **例外**：只读查询不需要幂等

## 1. GameCalendar

### 职责
唯一日期管理入口。所有日期推进必须经过此 Service。禁止任何其他代码路径修改日期。

### 命令

| 方法 | 参数 | 说明 | 守卫 |
|---|---|---|---|
| `advanceDay()` | `seed?: number` | 推进 1 天 | 无（可以随时推进） |
| `advanceDays(n: number)` | n ≥ 1 | 推进 n 天 | n 必须为正整数 |
| `setSpeed(speed: CalendarSpeed)` | 见下 `CalendarSpeed` 定义 | 设置模拟速度 | 无 |

**CalendarSpeed 枚举（DECIDED，V2.1.1 最终）**：

| 值 | 人类可读 | 含义 | 实际推进速率 |
|---|---|---|---|
| `'paused'` | 暂停 | 完全停止日期推进 | 0 天/秒 |
| `'slow'` | 慢速 | 较慢模拟 | 0.25 天/秒 |
| `'normal'` | 正常 | 标准模拟速度 | 1 天/秒 |
| `'fast'` | 快速 | 加速模拟 | 3 天/秒 |
| `'ultra'` | 极速 | 最快连续推进 | 7 天/秒 |
| `'step'` | 单步 | 手动单次推进 | 暂停状态下按一下进 1 天 |

**说明**：
- 这是 TypeScript 字符串枚举，`CalendarSpeed = 'paused' \| 'slow' \| 'normal' \| 'fast' \| 'ultra' \| 'step'`
- `'step'` 是特殊操作，调用后执行一次 `advanceDay()` 并自动回到 `'paused'` 状态
- 连续推进期间（非 `'paused'`），Simulation 层按速度速率调度每日阶段
- 这是 V2.1.1 最终决策，取代之前遗留的 `'1x' \| '5x' \| '30x'` 写法
| `reset(newSeed: number)` | | 重置到 day 0 | 会清空所有世界状态（必须通过 Application 层协调） |

### 职责

### 查询

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `int(min: number, max: number, ctx: RngContext)` | min/max 整数 | number | 含头含尾 |
| `float(ctx: RngContext)` | | number | [0, 1) |
| `floatRange(min: number, max: number, ctx: RngContext)` | | number | [min, max) |
| `choice<T>(items: T[], ctx: RngContext)` | | T | 等概率选一个 |
| `gauss(mean: number, stddev: number, ctx: RngContext)` | | number | 正态分布 |
| `chance(probability: number, ctx: RngContext)` | 0-1 | boolean | |
| `state()` | | `{ saveSeed: number, algorithmVersion: string, currentDayIndex: number }` | V2.1.5 最终：只返回这三项。**没有 prngState** |
| `restoreState(state: { saveSeed: number, algorithmVersion: string, currentDayIndex: number })` | | void | 从存档恢复。不恢复全局推进状态（上下文派生已不需要） |

**RngContext 结构（**V2.1.4 统一为完整 6 字段**）**：
```typescript
interface RngContext {
  // —— 6 个字段全部参与子流 seed 派生，缺一不可 ——
  subsystemId: string;     // 必需。'sales' | 'project_progress' | 'employee_morale' | 'event_trigger' | 'ai_decision' | 'hire_candidate' | ...
  entityId: string | null; // 必需。关联实体 id（productId / projectId / employeeId / companyId）；全局随机时传 null
  dayIndex: number;        // 必需。模拟日期
  purposeId: string;       // 必需。区分同一实体同一天内不同用途（'sales_perturbation' / 'refund_check' / 'morale_fluctuation'）
  scopeId?: string;        // 可选但强烈建议。区分同一产品在不同市场/平台/人群的随机调用（marketId + platformId + segmentId 合成）
  sampleIndex?: number;    // 可选。同一 purpose 下多次调用时递增，保证每次结果独立；默认 0
}

// 完整派生（每次调用必须传入完整 ctx）
deriveSubStreamSeed(
  saveSeed: number,
  algorithmVersion: string,  // e.g. 'mulberry32-v2'
  ctx: RngContext
): number {
  const scope = ctx.scopeId ?? 'default';
  const sample = ctx.sampleIndex ?? 0;
  const raw = [algorithmVersion, ctx.subsystemId, ctx.entityId ?? 'null', ctx.dayIndex, ctx.purposeId, scope, sample].join(':');
  return fnv1a(raw) ^ mixBits(saveSeed ^ 0x9e3779b9);
}

// ⚠️ 为什么需要 scopeId？
// 同一个 productId 在 日本home_console_g3 和 美国home_console_g3 两个市场分别调用销售随机，
// 没有 scopeId 就会因为 productId + dayIndex + purposeId 相同而得到相同的随机扰动
// → 两个市场销量会被同样放大/缩小，这显然不是我们想要的
// scopeId 推荐格式：`${marketId}:${platformId}:${segmentId}`
```

### 领域事件

不产出独立领域事件。

### AI 决策评分框架（DESIGN，权重 TUNING）

```typescript
interface CandidateAction {
  actionType: ActionType;   // 'hire' | 'start_project' | 'adjust_scope' | 'launch' | 'set_price' | 'sign_contract' | 'marketing' | 'fire' | ...
  targetId?: string;
  params: Record<string, unknown>;
}

function scoreCandidate(company: Company, candidate: CandidateAction, context: AIDecisionContext): number {
  // 硬约束先过滤
  if (!passesHardConstraints(company, candidate, context)) return -Infinity;

  // 四维评分（权重 TUNING）
  const strategicValue = computeStrategicValue(company, candidate, context);  // 公司 persona + 长期目标匹配
  const expectedROI = computeExpectedROI(candidate, context);                  // 投入产出预期
  const risk = computeRisk(candidate, context);                                // 下行风险
  const opportunityCost = computeOpportunityCost(candidate, context);           // 放弃其他选项的代价

  return w1 * strategicValue + w2 * expectedROI - w3 * risk - w4 * opportunityCost;
}
```

## 12. 每日调度顺序（DECIDED V2.1.1，唯一权威版本）

### 12.1 设计原则

1. **严格固定顺序**，任何调整会影响确定性复现，因此必须更新 `simulationAlgorithmVersion`
2. **每日先结算、后推进**：前一天产生的收入/退款/合同在今日结算，新一天的模拟在后半段执行
3. **先世界后公司**：AI 公司和历史事件在玩家公司动作之前推进，保证公平的信息时序
4. **先查询后写入**：各模块的"检查阶段"不写入状态；"执行阶段"才写入
5. **所有写入通过 Service 命令**，Simulation 层不直接修改实体字段

### 12.2 顺序定义

```
[Day N，非月末]
═══════════════════════════════════════════════════════════════════
PHASE 0 — 锚定
───────────────────────────────────────────────────────────────────
  0.1 GameCalendar.advanceDay()
      → DayAdvanced{day: N} 领域事件
      → GameCalendar.currentDay() = N

// ⚠️ V2.1.4 修正：删除 advanceAllSubStreamsForDay
// 旧机制需要每日预分配所有子流位置，新机制每次完整 ctx 重新派生种子，
// 不再需要预分配步骤。存档恢复也不需要保存子流推进位置——只需 saveSeed + dayIndex。

PHASE 1 — 历史事件触发
───────────────────────────────────────────────────────────────────
  1.1 检查 historical_events.json，所有 triggerYear == calendarYear(day) 且尚未触发的事件
  1.2 对每个事件：调用 Simulation 层 applyHistoricalEvent(event, context)
      → 修改世界状态（需求/成本/行业趋势等），不直接修改公司实体
      → 产出 HistoricalEventTriggered 事件

PHASE 2 — 世界市场模拟（所有公司共用规则）
───────────────────────────────────────────────────────────────────
  2.1 MarketSimulationService.simulateDemandForDay(day)
      → 更新各区域/类型/平台的 eligibleAudience 和 categoryDemand
      → 此步骤无随机，是历史趋势 + 事件影响的确定性推算
  2.2 MarketSimulationService.simulateCompetitorLandscape(day)
      → 更新竞品列表、竞品上市、竞品退市

PHASE 3 — 营销效果执行（**销售之前先完成营销**，修正 V2.1.3 中营销在销售之后的错误）
───────────────────────────────────────────────────────────────────
  3.1 MarketingService.executeDailyCampaigns(day, all_active_campaigns)
      → 消耗今日预算、更新 Product.awarenessByMarket（**今日营销预算影响今日认知度**）
      → 更新 Product.awarenessByMarket 后，Phase 4 销售计算会读取最新 awareness
  3.2 对每个 Campaign，计算今日实际消耗 = min(dailyBudgetCap, campaignDailyRemain)
  3.3 产出 MarketingSpent 事件（含 campaignId, companyId, day, amount）

PHASE 4 — 收入确认与退款处理（先有营销效果 → 再算销售 → 入账 → 最后处理到期退款）
───────────────────────────────────────────────────────────────────
  4.1 ProductService 对所有 LAUNCHED Product：检查是否有新补丁/折扣/更新生效
  4.2 MarketSimulationService.simulateDailySales(day, all_products_of_all_companies)
      → 对每个公司的每个 Product × MarketRegion × Platform × ConsumerSegment：
          按 05_TUNING 规格中的销售管线计算今日预期销量
          **注意**：这里读取的 awareness 是 Phase 3 刚更新过的（今日营销影响今日销售）
          加入确定性随机扰动（每次调用都用完整 RngContext 派生 seed，见 RandomService）
      → 写入 Product.salesByPeriod += SalesRecord（**唯一写入 Product 的记录**，含 estimatedRefundUnits 预测值）
  4.3 FinanceService 批量入账所有今日销售收入（sales_revenue category，含 AI 公司收入）
      幂等键：sales:${productId}:${marketId}:${platformId}:${dayIndex}
      **注意**：零金额交易（grossUnits=0）**不得入账**，跳过
  4.4 FinanceService 批量入账所有今日平台抽成（platform_fee category）
      幂等键：platform-fee:${productId}:${marketId}:${platformId}:${dayIndex}
  4.5 检查到期退款批次（**V2.1.7 新增：正式纳入 Phase 4 调度**）
      → 查找所有 RefundBatch 中 refundDayIndex == currentDayIndex 且 status == 'pending' 的批次
      → 批次来源自动窗口到期（source='auto_window'）或 Phase 4.2 生成时同时创建
      → 校验：同一 salesRecordId 下累计 refundedUnits ≤ SalesRecord.grossUnits
  4.6 处理退款批次入账
      → 对每个通过校验的 RefundBatch：
          FinanceService.postTransaction（category='customer_refund'，金额=-refundBatch.refundAmountCents）
          幂等键：customer-refund:${refundBatch.id}
          退款不返还 platform_fee 抽成（首发简化规则）
          RefundBatch.status = 'posted'
          关联 SalesRecord.actualRefundUnits += refundBatch.refundedUnits（累加，不覆盖 estimatedRefundUnits）
  4.7 产出领域事件
      → SalesRecorded（每个 Product × Market × Platform 一条）
      → RefundBatchPosted（每个 posted 的 RefundBatch 一条）


PHASE 5 — 研发进度推进
───────────────────────────────────────────────────────────────────
  5.1 对每家公司（玩家 + AI）的所有未取消、未 LAUNCHED、isPaused=false 的 Project：
      计算每个学科的 effectiveWork（调用 EmployeeService.getEffectiveWorkPerDay 汇总）
      按学科推进 workRemainingByDiscipline
      更新 Project.progressByPhase
  5.2 ProjectService 检查每个项目的阶段转换条件：
      CONCEPT → PRE_PRODUCTION（立项批准守卫）
      PRE_PRODUCTION → PRODUCTION（预制作完成守卫）
      PRODUCTION → QA（**制作学科 ≥ 90%**，不含 QA 学科；或玩家主动提前）
      QA → READY_TO_LAUNCH（上市决策守卫）
      READY_TO_LAUNCH → LAUNCHED（plannedLaunchDay ≤ 当前 day）
      → LAUNCHED 时生成 Product 实体 + 触发 ProjectLaunched 事件
  5.3 ProjectService 检查 isPaused 自动取消条件（连续 60 天暂停）

PHASE 6 — 员工更新
───────────────────────────────────────────────────────────────────
  6.1 EmployeeService 对所有公司所有员工：
      计算 morale 自然衰减 / 恢复
      计算 fatigue 恢复（非加班日）/ 累积（加班日）
      员工离职检查（morale < 阈值 + 持续 N 天）
      → 产出 EmployeeMoraleChanged / EmployeeFatigueChanged 事件

PHASE 7 — 合同与发行结算
───────────────────────────────────────────────────────────────────
  7.1 ContractService 检查所有 active 合同：
      里程碑到期检查 → 自动完成 → 预付款入账
      每日自动分成计提（具体结算见 Phase 10 月末结算）
      合同到期检查 → 自动终止
      违约检查（质量门槛未满足 + 宽限期过期）

PHASE 8 — 产品生命周期更新
───────────────────────────────────────────────────────────────────
  8.1 ProductService 对所有 active Product：
      检查 lifecycleStage 切换条件（launch → growth → mature → decline → long_tail）
      生成 ProductLifecycleChanged 事件
      检查是否达到退休条件（长周期亏损 + 无补丁 + 折扣无效）

PHASE 9 — 月度边界预警（**仅每月最后一天执行**）
───────────────────────────────────────────────────────────────────
  9.1 FinanceService 检查连续负数现金天数 → 触发破产预警
  9.2 标记 isLastDayOfMonth = true（Phase 10 月末结算据此判断）
  9.3 产出 MonthEnded{day: N} 领域事件（月末触发）
      ⚠️ V2.1.4 新增 MonthEnded 事件——区分于 Phase 11 的 MonthStarted

PHASE 10 — 月末结算（**仅每月最后一天执行**，Phase 9 之后立即执行）
───────────────────────────────────────────────────────────────────
  // ⚠️ Phase 9 和 Phase 10 发生在**同一天**（某月最后一天）的先后顺序：
  // 先预警（9）→ 再结算（10）。都在 Day N（last day of month）。
  10.1 FinanceService 结算所有固定支出（工资 / 租金 / 福利）
       先 AI 公司后玩家公司（保证公平的破产判断顺序）
  10.2 FinanceService 结算所有发行合同分成（前月收入）
  10.3 FinanceService 计提税费（季度汇总实际扣税）
  10.4 FinanceService 处理所有项目已承诺但尚未支付的支出
  10.5 EmployeeService 处理合同到期 / 自动续聘 / 遣散
  10.6 FinanceService 检查最终现金 → 触发 CompanyCashWarning / CompanyCashCritical / 破产
       破产时调用 Company.dissolve()，员工进入失业状态，合同终止

PHASE 11 — 月份/季度/年度边界事件（**仅每月第一天执行**，Phase 10 的次日）
───────────────────────────────────────────────────────────────────
  // ⚠️ 明确：Phase 10 在某月最后一天；Phase 11 在**次月第一天**。
  // Day N（last day）：Phase 0 → 1 → ... → 9 → 10 → 13 → done
  // Day N+1（first day）：Phase 0 → 1 → ... → 9（跳过，非月末） → 11 → 12 → 13 → done
  11.1 GameCalendar 检查 MonthStarted
       → 触发 MonthStarted{day: N+1, newMonth: X} 领域事件
  11.2 GameCalendar 检查 QuarterStarted / YearStarted
       → 触发相应领域事件
  11.3 年度边界：AI 公司自动重新评估产品组合和战略

PHASE 12 — AI 月度战略决策（**仅每月第一天执行**，Phase 11 之后）
───────────────────────────────────────────────────────────────────
  // ⚠️ 顺序：Phase 11（MonthStarted 等事件）→ Phase 12（AI 决策）
  // AI 决策**已经读取到 Phase 11 新更新的月份/季度/年度状态**
  12.1 CompanyAIService.runMonthlyDecisionForAllActiveCompanies(day)
       对每家 AI 公司：
           硬约束检查（资金/技术/人员/准入/合同——Phase 10 刚结算完的新现金余额）
           候选动作评分
           执行决策（调用与玩家完全相同的 Service 命令）
  12.2 CompanyAIService 检查 AI 公司破产（Phase 10 已处理，这里做最终确认）

PHASE 13 — 事件日志与存档更新（每天）
───────────────────────────────────────────────────────────────────
  13.1 EventLogService 聚合今日所有领域事件，追加到公司事件日志
  13.2 检查自动存档条件（每 30 天 或 玩家手动保存）

PHASE 14 — UI 层通知（每天，只读）
───────────────────────────────────────────────────────────────────
  14.1 Simulation 层完成所有写入后，产出 SimulationResult（世界快照 + 领域事件列表）
  14.2 Application 层把结果推送给 UI 层（Zustand store 更新）
  14.3 UI 层渲染新的日期、事件时间线、风险预警、项目进度条
```

### 12.3 关键边界条件

| 条件 | 处理 |
|---|---|
| 公司现金在 Phase 9 结算前已经 ≤ 0 | Phase 8.1 会触发预警；Phase 9.6 会在结算后判断连续负数天数 |
| 项目在 Phase 3 销售阶段还未 LAUNCHED | 不在 MarketSimulationService 输入范围内，自然跳过 |
| AI 公司在 Phase 9 中破产 | 该公司 Phase 10 不再执行月度决策；Phase 2 市场模拟移除其产品 |
| 玩家暂停游戏（setSpeed 'paused'） | Phase 0-13 全部不执行；`advanceDay()` 手动调用时正常执行 |
| 存档加载后恢复 | SaveMeta 中 saveSeed / simulationAlgorithmVersion / currentDayIndex 原样加载；之后所有 RandomService 调用每次从完整 RngContext 重新派生种子（**V2.1.6：无 randomState / prngState，也不需要"子流位置恢复"**） |

### 12.4 确定性复现断言

如果给定：
- 相同 `saveSeed`
- 相同的模拟操作序列（玩家命令 + 速度设置）
- 相同的 `simulationAlgorithmVersion`

则 Phase 0-13 **每一步**都必须产生完全相同的领域事件序列和世界状态哈希。升级调度顺序中的任何一步，都必须递增 `simulationAlgorithmVersion`。
