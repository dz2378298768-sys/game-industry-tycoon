# 销售管线公式与计算口径最终定义（DECIDED V2.1.1）

> 本文档统一销售管线中所有变量的**计算口径、取值范围、计算顺序、上下限和正负号约定**。
> 读取顺序：先读本文档，再读 05_TUNING 参数默认值候选.md（数值候选）。

## 0. 总体设计原则

- 销售管线是**确定性函数 + 确定性扰动**，不是黑盒随机
- 所有变量有明确的 TypeScript 类型、取值范围和上下限
- 所有计算公式**只算一次**，结果存入 Product 实体的 salesByPeriod 数组
- 财务正负号约定统一在本文末尾"附录 A"节

## 1. 销售管线全链路变量定义

### 1.1 输入变量（每次模拟时已知）

| 变量 | 类型 | 取值范围 | 含义 | 来源 |
|---|---|---|---|---|
| `eligibleAudience` | number | ≥ 0 | 理论上能接触到的消费者总数 | MarketSimulationService（平台用户规模 × 区域覆盖 × 可用年代） |
| `awareness` | number | [0, 1] | 产品在目标市场的认知度（0 = 完全没人知道，1 = 所有人都知道） | Product.awarenessByMarket 每天更新 |
| `categoryInterest` | number | [0, 1] | 目标群体对该游戏类型的基础兴趣度 | genres.json × consumer_segments.json |
| `baseConsideration` | number | [0, 1] | 产品自然进入消费者考虑集的概率（无营销无口碑加成） | TUNING 基准 0.5 |
| `qualityScore` | QualityProfile weighted | [0, 100] | 质量加权分（按 consumer_segment.qualityPrefWeight 加权） | Product.qualityProfile |
| `price` | Money (cents) | > 0 | 当前日目标市场价 | Product.priceByMarket[region] |
| `elasticityFactor` | number | > 0 | 价格弹性系数（>1 = 价格敏感，<1 = 不敏感） | TUNING 基准 0.12 每 +10% |
| `priceRelative` | number | > 0 | 当前价格相对基准价的比值 | price / originalPrice |
| `reviewLift` | number | > 0 | 评价带来的购买意愿倍率 | reviewScore / 60（reviewScore 为 0-100 实际收集值，初始用质量评分代替） |
| `competitionFactor` | number | [0, 1] | 竞品分流系数（0 = 完全不分流，1 = 全被分流） | MarketSimulationService 计算 |
| `platformFeeRate` | number | [0, 1] | 平台抽成比例 | platforms.json 30% 行业默认 |

|---|---|---|
| `consideration` | number [0, 1] | 进入考虑集的消费者比例 |

#### SalesRecord 新字段定义（**V2.1.6 最终统一**）

```typescript
interface SalesRecord {
  dayIndex: number;                                    // ✅ 销售发生日（不是退款日）
  marketId: string;
  platformId: string;
  grossUnits: number;                                  // 今日毛销量
  estimatedRefundUnits: number;                        // 预测退款量（TUNING refundRate 计算结果，UI 展示用）
  actualRefundUnits: number;                           // 实际已退款量（退款发生时累加）
  grossRevenueCents: number;                           // grossUnits × price.cents（正数）
  platformFeeCents: number;                            // round(grossRevenueCents × platformFeeRate)（正数表示金额，正负号由 Transaction 层控制）
  netSalesRevenueCents: number;                        // = grossRevenueCents - platformFeeCents
  // ⚠️ 不包含 actualRefundUnits × price.cents——实际退款在独立 Transaction，不回写 SalesRecord
}
// ✅ 明确：销售日期（dayIndex）和实际退款日期分别保存；
//   退款是独立 Transaction，不回写/覆盖原 SalesRecord
```

## 2. 计算公式（唯一权威版本）

### 2.1 Step 1：基础考虑集概率（**修正：去除 awareness 重复乘**）

> **V2.1.3 修正说明**：原公式在 consideration 和 consideringConsumers 两处都乘了 awareness，导致 awareness²。
> 认知度是"知道有这款产品的人数比例"，应该**只乘一次**。
> 修复：考虑集概率（considerationRate）只算"对这款产品感兴趣的人占知道它的人的比例"，awareness 留给 Step 4 的人数计算。

```
considerationLift = clamp(1 + (qualityScore - 60) / 100 * 0.5, 0.5, 2.0)
// qualityScore 相对于行业基准 60，±20 = ±50% 考虑集加成
// clamp 保证不低于 0.5（极差产品不会完全没人考虑），不高于 2.0

reviewLift = clamp(reviewScore / 60, 0.5, 1.8)
// 评价分相对于 60 基准，每 +10 评价 → reviewLift +0.167
// 无评价时用质量评分代替（reviewScore = qualityScore 初值）

// ⚠️ 注意：这里**不乘 awareness**，避免后续重复
considerationRate = clamp(baseConsideration
                     × categoryInterest                    // 目标群体对类型的兴趣
                     × considerationLift                  // 质量加成
                     × reviewLift                         // 评价加成
                     × (1 - competitionFactor),            // 竞品分流（减法关系）
                   0, 1)
```

**边界**：如果 `competitionFactor ≥ 1`，considerationRate = 0 合理表达"完全被竞品抢走"。

### 2.2 Step 2：购买转化率（**修正：补全所有缺定义的变量**）

> **V2.1.3 修正说明**：原公式中 qualityScoreBonus 和 marketingResponseLift 有使用但无完整定义，
> 价格弹性文字说明（涨 10% 降 12%，跌 10% 提 8%）和实际对数公式结果不同。
> 本节统一给出完整定义，价格弹性用**非线性对数公式**保证文字和数学一致。

```
// ===== 完整定义 =====

// qualityScoreBonus：质量每超过 60 基准 10 点 → 购买转化率 +0.05
qualityScoreBonus = (qualityScore - 60) / 100 * 0.5
// qualityScore 60 → +0
// qualityScore 80 → +0.10
// qualityScore 50 → -0.05

// priceElasticityUp：涨价弹性（TUNING 基准 0.12 = 涨 10% → 降 12% 购买转化）
// priceElasticityDown：降价弹性（TUNING 基准 0.08 = 跌 10% → 提 8% 购买转化）
priceElasticityUp = 0.12
priceElasticityDown = 0.08

// 对数价格偏移（以 10% 为一个档位单位）
// 涨价时用 up 弹性，降价时用 down 弹性
if priceRelative > 1.0:
  priceDeltaEffect = log(priceRelative) / log(1.1) * priceElasticityUp
else:
  priceDeltaEffect = -log(1/priceRelative) / log(1.1) * priceElasticityDown

// 营销响应：基于当日营销预算和产品生命周期阶段
// formula: marketingResponseLift = 1 - exp(-marketingSpend / responseScale)
// responseScale 随生命周期变化：launch 阶段 $500, growth $1000, mature $2000, decline $3000
// 即 $500 花费在 launch 阶段 → lift ≈ 0.63；$1000 在 growth → lift ≈ 0.63
marketingResponseLift = 1 - exp(-dailyMarketingSpend / marketingResponseScale)
// 示例：dailyMarketingSpend = $1000, responseScale = $1000 → lift = 0.632 → 转化 ×1.63
// 示例中的 1.05 旧值是错误的估算，正确值按上面公式计算

purchaseConversionLift = clamp(
  1 - priceDeltaEffect + qualityScoreBonus,
  0.2,  // 极限制下限：即使质量极差 + 价格极高，仍有最低转化
  2.0   // 极限制上限：即使完美质量 + 价格极低，不会超过此倍数
)

// ===== V2.1.6 P1-3 新增：marketingResponseLift clamp 与预算示例 =====
// 营销响应 clamp：防止极低预算仍有可观 lift、或极高预算收益溢出
marketingResponseLift = clamp(marketingResponseLift, 0.0, 2.0)
// 即 purchaseConversion 最终被 (1 + marketingResponseLift) 放大约 1x ~ 3x 倍
// 注：maxLift = 2.0 是 TUNING 候选值，需要 1000 组模拟校准

// 低/中/高预算计算示例（growth 阶段，responseScale = $1000）：
//  低预算 $100 → lift = 1 - exp(-100/1000) = 0.0952 → 转化 ×1.10（约 +10%）
//  中预算 $1K  → lift = 1 - exp(-1000/1000) = 0.6321 → 转化 ×1.63（约 +63%）
//  高预算 $10K → lift = 1 - exp(-10000/1000) = 0.99995 → 转化 ×2.00（被 clamp 封顶）
//  → 高预算几乎顶到 maxLift=2.0；低预算效果微弱但不为零；中预算是性价比拐点
//  → TUNING 标记：当前 responseScale 是 estimate，未经过场景模拟校准。
//    不得在没有校准数据的情况下宣布营销系统已平衡。

purchaseConversion = clamp(basePurchaseConversion
                          × purchaseConversionLift
                          × (1 + marketingResponseLift)
                          × randomPerturbation,             // 确定性扰动，见 Step 3
                        0.01, 0.5)
// purchaseConversion 不能太低（防止极端长尾产品 0 销量）也不能太高（防爆款异常溢出）
```

### 2.3 Step 3：确定性随机扰动（**V2.1.4 加 clamp 上下限**）

> **V2.1.4 修正**：原公式只写了 `1 + gauss(0, 0.05)`，没说如果随机结果超出 ±20% 怎么办。
> 必须 clamp 保证极端随机不会让销量变成 0 或异常翻倍。

```
// clamp 范围 [0.8, 1.2]——正态扰动 ±4σ 以外的值被截断
randomPerturbation = clamp(1 + RandomService.gauss(0, 0.05, ctx), 0.8, 1.2)

// RngContext 完整 6 字段（见接口契约 + 附录 B）
ctx = { subsystemId: 'sales_perturbation', entityId: productId, dayIndex: day,
        purposeId: 'purchase_conversion', scopeId: market:platform:segment, sampleIndex: 0 }
```

**为什么 clamp 到 [0.8, 1.2]**：stddev=0.05 时，4σ=0.20。99.994% 的随机结果已经在 [0.8, 1.2] 内。截断只影响极个别极端值，防止异常销量。

### 2.4 Step 4：销量计算（**修正：awareness 只乘一次；退款独立计算**）

> **V2.1.3 修正说明**：(a) awareness 应该在这里**只乘一次**，得到"知道这款产品且在考虑集中的消费者数"；
> (b) 退款必须独立于毛收入计算，不能在毛收入里先扣净销量再单独记退款交易（那样会双重扣减）。

```
// ✅ awareness 只在这里乘一次
consideringConsumers = eligibleAudience
                     × awareness                       // 知道这款产品的人数比例
                     × considerationRate                // 这些人中对产品感兴趣的比例

grossUnits = floor(consideringConsumers * purchaseConversion)
// ⚠️ P2-1 取整规则（V2.1.4 明确）：
//   主运算用 floor（向下取整），保证 grossUnits ≥ 0 且不会因为四舍五入突然产生额外销量。
//   如果 consideringConsumers * purchaseConversion = 0.6 且 purposeId 属于
//   'sales_small_market_floor' 且 概率 chance(RngContext) → 给 1（最小保底销量），
//   否则 grossUnits = 0 跳过财务入账。
//   grossUnits = 0 时**不得提交零金额 Transaction**（见 Phase 4.3 守卫）。

// ========== V2.1.5 统一退款财务模型（消除 V2.1.4 L173-179 vs L216-237 矛盾）==========
// ⚠️ 最终权威：采用"实际退款制"，消除"预期退款提前扣现金"的风险。
// 每日 Phase 4 计算退款率 **只用于预测、质量评价和 UI 展示**，**不得提前影响现金**。
// 真实退款发生时才由 FinanceService 记录负数 Transaction。

refundRate = clamp(baseRefundRate + (defectLevel - 30) / 100 * 0.2, 0.02, 0.35)
estimatedRefundUnits = floor(grossUnits * refundRate)
// estimatedRefundUnits 是**预测值**，写入 Product.salesByPeriod.estimatedRefundUnits（UI 展示用）
// ⚠️ 不影响财务入账。财务入账用的是 grossUnits × price.cents（毛收入全额）。

// 每日只记录毛收入全额（退款还没发生，不得提前扣）
grossRevenue = floor(grossUnits * price.cents)

// Product 实体记录（**V2.1.7 唯一正确写入字段**——与上方 SalesRecord interface 完全一致）
Product.salesByPeriod += SalesRecord{
  dayIndex: dayIndex,
  marketId: marketId,
  platformId: platformId,
  grossUnits: grossUnits,
  estimatedRefundUnits: estimatedRefundUnits,   // 预测，不影响现金
  actualRefundUnits: 0,                        // 初始 0，真实退款发生时累加
  grossRevenueCents: grossRevenue,             // grossUnits × price.cents（正数）
  platformFeeCents: round(grossRevenue * platformFeeRate),
  netSalesRevenueCents: grossRevenue - round(grossRevenue * platformFeeRate)
  // ⚠️ 不含 actualRefundUnits 相关金额——实际退款在独立 Transaction，不回写 SalesRecord
}

// ========== RefundBatch 接口定义（**V2.1.7 引入**）==========
// 每个退款批次 = 一次实际退款操作的完整身份。
// 用于：
//   (a) 幂等键统一：customer-refund:${refundBatch.id}
//   (b) 关联原始销售记录，区分同一天不同退款批次
//   (c) 存档恢复后重新执行退款检查时能判断批次是否已入账
interface RefundBatch {
  id: string;                       // 唯一 ID，格式：RB-${productId}-${saleDayIndex}-${refundDayIndex}-${seq}
  productId: string;
  salesRecordId: string;            // 关联原始 SalesRecord（唯一回指入口）
  marketId: string;
  platformId: string;

  saleDayIndex: number;             // 原销售发生日
  refundDayIndex: number;           // 退款发生日（= saleDayIndex + refundWindowDays 或玩家请求日）

  refundedUnits: number;            // 本次退款单位数
  refundAmountCents: number;        // = refundedUnits × pricePerUnit.cents

  source: 'auto_window' | 'player_request';  // 自动窗口到期 或 玩家请求
  firstRefundRequestId?: string;    // 玩家多次操作同一批次时的首请求 ID（去重）

  status: 'pending' | 'posted' | 'rejected';
  // pending = 批次已生成，尚未入账
  // posted  = customer_refund Transaction 已入账
  // rejected = 超过 grossUnits 上限 / 批次重复 / 窗口未到
}
// ✅ 每一份购买最多退款一次：同一 salesRecordId 下累计 refundedUnits ≤ SalesRecord.grossUnits
// ✅ 幂等键统一：`customer-refund:${refundBatch.id}` —— 只用批次 ID，不再用 productId/dayIndex 组合

// ========== 真实退款发生时 ==========
// 触发条件（Phase 4 4.5-4.7 正式调度步骤）：
//   - 自动退款：Phase 4 4.5 遍历 refundDayIndex == currentDayIndex 的 pending RefundBatch
//   - 玩家请求：任何时间点玩家操作 → Simulation 层生成 RefundBatch → 幂等检查 → 入账
//
// 幂等键：customer-refund:${refundBatch.id}
//   ✅ 唯一身份，同一天同一产品可有多批次（若拆批）
//   ✅ 存档恢复后重建批次时 id 相同，不会重复入账
refundBatch = RefundBatch{ ... }  // 由 Simulation 层按 Phase 4 4.5-4.7 流程生成并校验
Transaction {
  category: 'customer_refund',
  amount: Money({ cents: -refundBatch.refundAmountCents }),
  referenceId: refundBatch.productId,
  idempotencyKey: `customer-refund:${refundBatch.id}`,   // ✅ V2.1.7 统一幂等键
  description: `Refund batch ${refundBatch.id}: ${refundBatch.refundedUnits} units`
}
// 入账后：
//   refundBatch.status = 'posted'
//   SalesRecord (salesRecordId 指向的那条).actualRefundUnits += refundBatch.refundedUnits （累加）

// ⚠️ 最终公司真实收入 = Σ sales_revenue - Σ platform_fee - Σ customer_refund
// UI 层"净收入"展示 = grossRevenueCents - platformFeeCents（不含尚未发生的退款）
// Product.salesByPeriod 字段（**V2.1.7 正式字段，旧字段全部废弃**）：
//   dayIndex            = 销售发生日
//   marketId / platformId = 销售发生的市场/平台
//   grossUnits          = 销售毛量
//   estimatedRefundUnits = 预测退款量（TUNING refundRate × grossUnits，UI 展示用）
//   actualRefundUnits    = 实际退款量（RefundBatch posted 时累加，不覆盖 estimatedRefundUnits）
//   grossRevenueCents    = grossUnits × pricePerUnit.cents（正数）
//   platformFeeCents     = round(grossRevenueCents × platformFeeRate)（正数金额）
//   netSalesRevenueCents = grossRevenueCents - platformFeeCents（UI 每日展示用，不含退款）
// ❌ 旧字段废弃：day / grossRevenue / platformFee / finalCompanyRevenue / refundsByPeriod
```

## 3. 计算示例（完整数值，**V2.1.3 修正后**）

### P1-4 价格弹性公式验证示例（**V2.1.4 新增，确保文字说明与数学一致**）

> 文字承诺：涨价 10% → 购买转化降 12%；降价 10% → 提 8%。
> 参数：priceElasticityUp=0.12, priceElasticityDown=0.08。
> 公式：涨价用 up 弹性，降价用 down 弹性。

**假设 qualityScoreBonus=0（基准质量 60），只看价格对 lift 的影响**：

```
示例 A：保持原价（priceRelative = 1.0）
priceDeltaEffect = 0
purchaseConversionLift = 1 - 0 + 0 = 1.00    → 转化 = base × 1.00 ✅

示例 B：涨价 10%（priceRelative = 1.10）
priceDeltaEffect = log(1.10)/log(1.10) × 0.12 = 1.000 × 0.12 = +0.12
purchaseConversionLift = 1 - 0.12 + 0 = 0.88  → 转化 = base × 0.88 ✅（降 12%）

示例 C：降价 10%（priceRelative = 0.90）
priceDeltaEffect = -log(1/0.90)/log(1.10) × 0.08
                 = -log(1.1111)/log(1.10) × 0.08
                 = -0.10536 / 0.09531 × 0.08
                 = -1.1054 × 0.08 = -0.0884
purchaseConversionLift = 1 - (-0.0884) + 0 = 1.0884
→ 转化 = base × 1.0884 ≈ 提 8.8% ✅（接近目标 8%）
```

**如果 qualityScoreBonus ≠ 0（如质量 75.25 → +0.07625）**：
- 涨价 10% → lift = 1 - 0.12 + 0.076 = 0.956（质量好的产品对涨价不那么敏感）
- 降价 10% → lift = 1 + 0.0884 + 0.076 = 1.164（质量好+降价双重加成）

### 完整计算

           = clamp(0.02, 0.02, 0.35) = 0.02

## 4. 研发工作量与员工产能的数学关系

### 4.1 员工每日有效产出（单人）

```
baseCapacity = {
  programmer: 5,
  designer: 5,
  artist: 5,
  qa: 4,
  producer: 0,    // 制作人不产出学科 WorkPoint，而是项目管理系数
  manager: 0      // 同上
}   // 单位：WorkPoint / 人 / 天（DECIDED）

skillFactor = 0.6 + skillLevel × 0.2         // skillLevel 1 → 0.8, 5 → 1.6
roleFit = primarySkill ∈ requiredPrimarySkill ? 1.0 : 0.7
focusFactor = allocationRatio                // 0-1（被分配到其他项目则下降）
moraleFactor = clamp(0.7 + morale / 100 × 0.5, 0.5, 1.2)   // morale 30 → 0.85, morale 100 → 1.2
fatigueFactor = clamp(1.0 - fatigue / 200, 0.6, 1.0)        // fatigue 70 → 0.65, fatigue 100 → 0.5（封顶 0.6）
teamCoordinationFactor = clamp(
  companyManagementCapacity
    ? 1.0 - 0.05 * Math.max(0, headcount - managementCapacity)
    : 0.7,
  0.5,    // 最低值：即使超容量很多，团队效率不会低于 50%
  1.0     // 最高值
)
// ⚠️ 修正：原公式只写了注释"封顶 0.5"但没写 clamp。
// clamp 是必须的——超容量 20 人 → 1.0 - 1.0 = 0，这显然不合理。

effectiveWorkPerDay = baseCapacity[role]
                     × skillFactor
                     × roleFit
                     × focusFactor
                     × moraleFactor
                     × fatigueFactor
                     × teamCoordinationFactor
```

### 4.2 项目整体学科工作量推进

```
totalDisciplineWorkPerDay[discipline] = Σ(employee.effectiveWorkPerDay for employee in Project.teamAssignments where employee.role maps to discipline)

fundingFactor = project.budget.available / project.budget.requested
// ≥ 1.0 → full output
// 0.8 - 0.99 → ×0.95
// 0.6 - 0.79 → ×0.85
// 0.4 - 0.59 → ×0.65
// < 0.4 → project isPaused = true, effectiveWork = 0

projectDisciplineWorkPerDay[discipline] = floor(totalDisciplineWorkPerDay[discipline] × fundingFactor)

remainingWork[discipline] = max(0, previousRemainingWork[discipline] - projectDisciplineWorkPerDay[discipline])
```

### 4.3 工期估算公式

```
totalProjectWork = Σ(disciplineTotalWork[discipline] for discipline in all)
averageProjectWorkPerDay = average(projectDisciplineWorkPerDay across all days of estimate)

estimatedDays = ceil(totalProjectWork / averageProjectWorkPerDay)
// 保守估算 = estimatedDays × 1.3
// 乐观估算 = estimatedDays × 0.8
```

延续 1978"像素赛车"场景：

## 5. 附录 A：Money / 财务交易 正负号约定（DECIDED）

### A.1 交易金额正负号

| 场景 | amount.cents | 含义 |
|---|---|---|
| 员工工资 | **负数** | 公司支出 |
| 办公室租金 | **负数** | 公司支出 |
| 项目直接支出（外包、素材购买） | **负数** | 公司支出 |
| 营销预算消耗 | **负数** | 公司支出 |
| 裁员遣散费 | **负数** | 公司支出 |
| 发行商给公司的预付款 | **正数** | 公司收入 |
| 发行合同分成收入 | **正数** | 公司收入 |
| 产品销售收入 | **正数** | 公司收入 |
| 退款（从公司退款给玩家） | **负数** | 公司支出（冲减收入） |
| 税费 | **负数** | 公司支出 |
| 保险赔偿 / 意外收入 | **正数** | 公司收入 |

### A.2 ProjectBudget 字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `totalCap` | Money | 公司批准给项目的预算上限（正数，代表可花的总金额） |
| `committed` | Money | 已承诺但尚未支付的固定成本（合同定金、固定支出；正数代表已预留的额度） |
| `spent` | Money | 已经实际发生的支出总和（正数代表已花的钱，**不是负数**） |
| `remainingCap` | Money | = `totalCap - committed - spent` |

**注意**：`spent` 是正数，表示"已花的钱"，在界面上直接显示"已花 $X / 上限 $Y"，不做符号翻转。

### A.3 FinanceService 现金余额

`getCashBalance().cents` 含义：
- **正数** = 公司有可用现金
- **0** = 无现金但也无负债
- **负数** = 透支/连续负数（触发破产预警）

交易入账后 `balanceAfter.cents = balanceBefore.cents + transaction.amount.cents`。

### A.4 禁止混淆的场景

- 不要用 Transaction 的 `category` 来推断正负——必须信任 `amount` 的符号
- FinanceService 内部**永远不翻转符号**——写入时是什么，查出来就是什么
- UI 层显示"支出 $3,500"时，从 `amount.cents = -350000` 取绝对值并显示标签
- BDD 测试用例中，财务断言统一用 Money 绝对值比较并检查 category，避免符号混乱

## 6. 附录 B：RandomService 子随机流最终定义

### B.1 设计原则

- 所有随机值必须**可复现**：相同 saveSeed + 相同操作序列 → 相同结果
- 随机调用越多，子流派生越明确；**禁止隐式共享**
- 子流派生是**确定性纯函数**，不依赖任何外部状态（除了 saveSeed）
- 存档恢复时从 `saveSeed + algorithmVersion + currentDayIndex` 恢复，保证从断点继续也能复现（**V2.1.6：不再有 randomState / prngState**）

### B.2 子流 ID 命名规则

```
subsystemId: {
  'sales',           // 产品销售管线扰动
  'project_progress', // 项目学科产出随机（如"某天产出刚好在 floor 边界"）
  'employee_morale', // 员工 morale 自然波动
  'event_trigger',    // 历史事件是否实际触发（避免 100% 触发所有事件）
  'ai_decision',      // AI 决策评分中的随机扰动
  'hire_candidate',   // 招聘候选池生成
  'platform_adoption' // 平台用户规模年度增长
}
entityId: {productId, projectId, employeeId, companyId, eventId}
```

### B.3 派生子流公式（**V2.1.4 最终版：统一 6 字段 RngContext**）

> **V2.1.4 修正**：RngContext 从 4 字段扩展为 **6 字段**（subsystemId / entityId / dayIndex / purposeId / scopeId / sampleIndex）。
> 每一个字段都参与 seed 派生，保证不同产品 × 市场 × 平台 × 人群不会意外得到相同随机。
> 删除 advanceAllSubStreamsForDay 旧机制（每次完整 ctx 派生已足够，不需要预分配）。

```typescript
// ✅ 完整 6 字段（接口契约 04 同步定义）
interface RngContext {
  subsystemId: string;
  entityId: string | null;
  dayIndex: number;
  purposeId: string;
  scopeId?: string;   // "${marketId}:${platformId}:${segmentId}"
  sampleIndex?: number;
}

// 统一派生（纯函数，确定性）
function deriveSubStreamSeed(saveSeed: number, algorithmVersion: string, ctx: RngContext): number {
  const scope = ctx.scopeId ?? 'default';
  const sample = ctx.sampleIndex ?? 0;
  const raw = [algorithmVersion, ctx.subsystemId, ctx.entityId ?? 'null', ctx.dayIndex, ctx.purposeId, scope, sample].join(':');
  return fnv1a(raw) ^ mixBits(saveSeed ^ 0x9e3779b9);
}

// ⚠️ advanceAllSubStreamsForDay 已废弃（V2.1.4 删除）
// 旧机制需要每日预分配所有子流位置，新机制每次完整 ctx 重新派生种子，不再需要预分配步骤。
```

**实际调用示例（销售管线 2020-06-15 日本市场 8-bit 主机 核心玩家 场景）**：

```typescript
const perturbation = randomService.gauss(0, 0.05, {
  subsystemId: 'sales',
  entityId: productId,           // 'PROJ-001'
  dayIndex: 10950,               // 2000-01-01 = day 10950 (1970-01-01 起算)
  purposeId: 'purchase_conversion_perturbation',
  scopeId: 'JP:home_console_g2:core_gamer',   // ✅ 没有这个会导致同一产品在不同市场随机相同
  sampleIndex: 0
});
```

### B.4 存档恢复（**V2.1.5 彻底统一，消除 B.4 vs B.6 矛盾**）

> **V2.1.4 遗留 bug**：B.4 说"不保存 subStreamPositions"，但 B.6 反模式表把"只存 saveSeed 不存子流位置"列为反模式——**自己骂自己的方案**。
> **V2.1.5 最终裁定**：采用"每次完整上下文派生"方案，**不需要保存子流推进位置**。
> B.6 反模式表中那条（L656）是**旧方案的残留**，V2.1.5 已删除（见下方 B.6 修正版）。

```typescript
SaveMeta = {
  schemaVersion: number,
  simulationAlgorithmVersion: 'mulberry32-v2',
  saveSeed: number,
  currentDayIndex: number
  // ✅ V2.1.6 最终：只有这 4 个字段
  // ❌ 不保存 subStreamPositions —— 每次完整 ctx 派生已足够
  // ❌ 不保存 prngState —— 上下文派生是纯函数，不依赖全局推进状态
  // ❌ 不保存 randomState —— 旧方案残留已彻底删除
}

// 恢复流程（确定性）：
// 1. 从存档加载 saveSeed + algorithmVersion + currentDayIndex
// 2. 之后所有 RandomService.gauss/int/chance 调用都从这个 saveSeed + 完整 ctx 派生
// 3. 两个独立存档从 Day 1 分别推进到 Day 200，WorldState.hash + eventLog 必须完全一致
```

### B.5 确定性断言（V2.1.5 补充恢复测试）

给定相同 saveSeed + 相同操作序列，以下场景必须产生**完全一致**的结果：
- 存档从 Day 100 → 恢复 → 推进到 Day 200 → WorldState.hash
- 直接从 Day 1 → 推进到 Day 200（跳过 Day 100 存档点）→ WorldState.hash
- 存档从 Day 100 → 恢复 → **另一个独立存档** → 再恢复 → 推进到 Day 200 → WorldState.hash
- 所有 Product.salesByPeriod 数值
- eventLog 序列的哈希（含事件顺序）

### B.6 禁止的反模式（**V2.1.5 修正**）

| 反模式 | 为什么坏 |
|---|---|
| 在业务逻辑中直接调用 `Math.random()` | 无法复现；lint 规则禁止 |
| 用同一个子流做两个不同子系统的随机 | 新增随机调用会偏移后一个子系统的结果 |
| 存档时保存全局 prngState（旧方案残留） | 导致存档间的随机偏移；上下文派生已不需要全局状态 |
| 升级 PRNG 算法后不加 algorithmVersion | 旧存档加载结果和历史不一致 |
| RngContext 缺 scopeId（同一产品多市场随机重复）| 不同市场/平台/人群得到相同扰动，销量异常同步 |

⚠️ **V2.1.5 删除的旧反模式条目**（原 L656）：
> "存档时只存 saveSeed 不存子流位置 → 恢复后无法复现中间状态"
> 这条是 V2.1.3 的上下文派生方案**之前**的旧方案描述——当时用的是"全局推进 + 各子流记录位置"机制，后来改成了"每次完整 ctx 派生"。旧反模式条目在新方案下**不再适用**，已删除。

## 8. 附录 D：工程配置 lint 命令修正

原 `2_工程配置规格.md` 中混用了 `npm run lint`（自动修复）和 `npm run typecheck`（检查）两个命令。**统一分离**：

| 命令 | 用途 | 是否修改文件 | 执行时机 |
|---|---|---|---|
| `npm run lint:check` | ESLint 仅检查，输出报告 | ❌ 只读 | CI 前置、PR 检查、开发前确认 |
| `npm run lint:fix` | ESLint 自动修复可修复问题 | ✅ 修改文件 | 本地开发时手动执行；**禁止**在 CI 中自动执行 |
| `npm run typecheck` | TypeScript 仅类型检查 | ❌ 只读 | CI 前置、每次提交前 |
| `npm run format:check` | Prettier 仅检查格式 | ❌ 只读 | CI 可选 |
| `npm run format:write` | Prettier 自动修正格式 | ✅ 修改文件 | 本地手动执行 |
| `npm run test:all` | 运行所有单元+集成+类型检查 | ❌ 只读 | CI 主流程 |

**禁止**：在 `npm test` 或 `npm run build` 中包含 `lint:fix` 或 `format:write`，因为自动修改文件会导致 CI 不可预测的 diff。
