## 1. 逐项详细审计

### 问题 1：ProjectPhase 与 isPaused 的关系

| 项 | 详情 |
|---|---|
| **发现** | README 提 10 状态（含 DRAFT/EVALUATING/APPROVED）；V2.1 规格 6+2（CONCEPT...READY_TO_LAUNCH + PAUSED/CANCELLED）；01_项目状态机.md 自己就矛盾——枚举表列 PAUSED，转换图画 PAUSED，又说 PAUSED 不作为枚举值；03_领域实体注释写"与 PAUSED 状态互斥"；04_接口契约 ProjectService.resume 守卫用 isPaused=true；07_P0页面项目列表筛选项列 PAUSED；BDD 测试写"自动进入 PAUSED 状态" |
| **修改位置** | 01_项目状态机统一方案.md **整个文件重写**；07_P0页面.md 状态筛选；08_BDD测试用例.md TC-PRJ-003；04_接口契约.md resume 守卫（已在重写的状态机文件中明确） |
| **最终决策** | ProjectPhase 7 个值：CONCEPT / PRE_PRODUCTION / PRODUCTION / QA / READY_TO_LAUNCH / LAUNCHED / CANCELLED。PAUSED **永远不是枚举值**。暂停 = isPaused: true（phase 不变）。暂停守卫由 `phase !== 'LAUNCHED' \|\| phase !== 'CANCELLED' \|\| !isPaused` 统一执行 |
| **风险** | 原始 V2.1 规格文档（01-12 分档的）中"PAUSED 作为 phase"的旧描述还存在，但明确说明以 08_设计补齐/01_ 为准。Agent 实现时只读补齐档，不会混淆 |

### 问题 3：每日调度顺序

| 项 | 详情 |
|---|---|
| **发现** | 原 13 步顺序：日历 → 预分配 → 销售 → 研发 → 上市 → 产品生命周期 → 营销 → 员工 → 合同 → 月末结算 → AI 决策 → 日历检查 → UI。问题：(a) 没有历史事件 Phase；(b) 市场需求更新缺失；(c) 销售和研发顺序颠倒（应该先收入确认再推进研发）；(d) 员工更新在合同之前（逻辑应该先合同再员工）；(e) AI 决策在月末结算**之前**（AI 没看到当月结果就决策）；(f) 没有明确"先查询后写入"原则 |
| **修改位置** | 04_接口契约.md **整个 12 节重写** |
| **最终决策** | 13 个 PHASE 严格固定：锚定预分配 → 历史事件 → 世界市场模拟 → 收入确认 → 研发推进 → 员工更新 → 合同结算 → 产品生命周期 → 月度边界检查 → 月末结算 → AI 月度决策 → 季度/年度触发 → 事件日志/存档 → UI 通知。每个 Phase 有明确的查询/写入边界和关键边界条件表 |

| 项 | 详情 |

| **最终决策** | 4 步主管线：(1) considerationLift 质量加成 → consideration 最终考虑集比例；(2) purchaseConversionLift 价格/质量/营销/评价 → purchaseConversion 购买率；(3) 确定性正态扰动；(4) grossUnits → refundUnits → netUnits → grossRevenue → platformFee → netRevenue。所有变量有明确 TypeScript 类型和 [min, max] 约束 |
| **风险** | TUNING 参数值（basePurchaseConversion=0.05、priceElasticity=0.12 等）未校准，这是设计声明的 TUNING 状态，预期行为 |

### 问题 5：研发/产能/工期/预算数学关系

| 项 | 详情 |
|---|---|
| **发现** | 原 05_TUNING 给了乘数（skillFactor / roleFit / moraleFactor / fatigueFactor / coordinationFactor），但没给**完整的公式链**——乘数之间是加法还是乘法？是串联还是并联？预算耗尽是 isPaused 还是自动取消？workRemainingByDiscipline 是整数还是浮点？所有系数乘起来如何得到"每天推进多少 WorkPoint"？ |
| **修改位置** | 09_销售管线.md **Section 4** 完整公式链 + **完整计算示例**（4 员工项目 → 61 天 art 瓶颈 → 131 天总工期估算 → 保守 171 / 乐观 105） |
| **最终决策** | effectiveWorkPerDay = baseCapacity × skillFactor × roleFit × focusFactor × moraleFactor × fatigueFactor × coordinationFactor（全乘法链）；fundingFactor 阶梯表（≥1.0 满额 → <0.4 自动 isPaused）；每日推进 = floor(effectiveWork × fundingFactor)；瓶颈学科决定工期；工期 = ceil(totalWork / 每日瓶颈推进) |
| **风险** | fundingFactor 阶梯阈值（0.8/0.6/0.4）是 TUNING 候选 |

### 问题 6：Money/FinanceService 正负号约定

| 项 | 详情 |
|---|---|
| **发现** | Money.amount 到底是"花出去是负数还是正数"？Transaction.amount 呢？ProjectBudget.spent 存的是已花的钱——是正数还是负数？原 03_领域实体 ProjectBudget 字段注释只写"已花"没写符号。FinanceService.getCashBalance() 负数表示什么？UI 显示"支出 $3,500"是直接取 Transaction.amount.cents 还是翻转符号？ |
| **修改位置** | 09_销售管线.md **附录 A** 完整正负号约定表（12 种场景 × amount 正负号 + 含义）；ProjectBudget 三个字段 totalCap/committed/spent 都是正数代表"预留额度"或"已花额度"；CashBalance 正数 = 有现金，负数 = 透支；UI 层负责翻转符号显示（FinanceService 内部永远信任 amount 的符号） |

| **风险** | 无。BDD 测试明确要求"用 Money 绝对值比较 + 检查 category" |

### 问题 7：1970 历史数据年代错误

| 项 | 详情 |
|---|---|
| **发现** | (a) V1.0 起始现金 $100K（2026 不变美元）→ 用于 1970 严重失真，已在 05_TUNING 中修正为保守 $30K / 基准 $50K / 乐观 $80K；(b) 平台没区分 街机 / 实体家用机 / 电脑软件 / 数字下载 四类——原只笼统叫"平台"；(c) 准入年份不准确：原 V2.0 platforms.json 只有 1 条样例数据 |

### 问题 8：RandomService 子随机流/确定性/存档恢复

| 项 | 详情 |
|---|---|
| **发现** | 02_工程配置规格选了 mulberry32，04_接口契约定义了 RngContext（subsystemId + entityId + dayIndex + eventId），但：(a) 没有**子流派生公式**；(b) 没有存档恢复的**完整状态清单**；(c) 没有**确定性断言**（给定什么输入保证什么输出）；(d) 没有**禁止反模式**清单 |
| **修改位置** | 09_销售管线.md **附录 B** 完整补充 |
| **最终决策** | (a) 派生子流公式：`mixBits(saveSeed ^ 0x9e3779b9 ^ fnv1a(ctx))`；(b) 存档必须保存 saveSeed + mulberry32State + subStreamPositions（每个子流已推进次数）+ algorithmVersion；(c) 确定性断言链：saveSeed + 完整操作序列 → WorldState.hash 必须一致；(d) 禁止 Math.random() / 隐式共享子流 / 存档只存 seed 不存位置 |
| **风险** | 无。mulberry32-v1 是 DECIDED；子流算法是确定性纯函数；存档恢复契约明确 |

### 问题 9：lint 命令自动修复混用

| 项 | 详情 |
|---|---|
| **发现** | 原 02_工程配置规格命令表：`npm run lint # 运行 eslint --fix`；`npm run format # 运行 prettier --write`；`npm run test:all # test:unit + test:ui + typecheck`。问题：(a) `npm run lint` 自动修复（--fix）与 `npm run typecheck`（只读）放在一起，命名暗示同一语义；(b) CI 如果跑 `test:all` 会不会隐式 lint:fix 并自动修改文件？(c) 没有明确区分"检查命令（只读）"和"修复命令（会改文件）" |
| **修改位置** | 02_工程配置规格.md **Section 7 完整命令表重写**；09_销售管线.md **附录 D 单独章节** |
| **最终决策** | 命令明确分两类：只读（lint:check / format:check / typecheck）+ 会改文件（lint:fix / format:write）。CI 主流程 test:all 只跑只读命令。**禁止在 CI 中运行 lint:fix 或 format:write**。 |
| **风险** | 无。命名语义化后 Agent 不会混淆 |
